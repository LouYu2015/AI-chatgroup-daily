## GPT-5.6 实测第四日

### 版本演进论：从把屎把尿到真的懂你

接着前几天 [「打工人 Sol：踏实但不聪明」]({{ '/daily/2026/07/10/daily/#打工人-sol踏实但不聪明' | relative_url }}) 的定位讨论，<span class="mention">@三只纳垢灵</span> 今天给出了一份完整的世代总结：

> <span class="mention">@三只纳垢灵</span>：openai 进步还是很快的，5.2/5.3 的时候要把屎把尿，5.4 终于能在 rich instruction 下干活，5.5 是一个耐心多了一点的 5.4，5.6 总算是有了点 intelligence。我觉得这次的飞跃就是他能理解我在项目里写的 high level 的哲学观点，而不是做做表面样子。

他的例子很具体：告诉模型「OOP 时 follow DRY、LSP 和 open-close」，5.5 明显不懂这些原则之间的张力——「你 dry 了之后不得已加了个 friend 关键字算违反 open close 吗，做 combinator 的特殊胶水算违反 lsp 吗」，不写清 exception 出来的就是「地铁老头手机.jpg」；而 5.6「在分清主次上有进步」，第一次「给了我一种他真的知道我在干什么的感觉，以前的模型都像带弱智实习生」。<span class="mention">@机智的水獭</span> 提出不同坐标系：他用 5.5 加上 <span class="mention">@今天群内信息量极大</span> 那套 infra 和 context 引导，早就能理解项目的 high level 原则了——「每个人有自己的『ai 可用』时刻，过了这个点就可以享受超线性进化」，顺带补刀「gemini 还差得远」。他把这一代的换代动力比作 iPhone4：单位 intelligence 在变便宜，「但是有新的谁愿意用老的呢」——现在也能玩当年的小游戏，可大家都想玩原神。

### 收敛难题：让它少干点

<span class="mention">@随和的企鹅</span> 报告了一个 5.5 没有的烦恼：小项目让 5.5 迭代修问题，最终能修到它自己认为没问题；换 5.6「似乎它就永远能找到啥可修的」，中间还 break 过程序，不人工干预需求判断的话很难收敛——「通过一个模糊的初始状态，确实是干不完，总是可以编出一些需求来」。<span class="mention">@洒脱的猫头鹰</span> 一句话完成建模：

> <span class="mention">@洒脱的猫头鹰</span>：5.5 你得想办法让它多干点。5.6 你得想办法让它少干点。

他甚至第一次考虑把思考等级降到 medium/high，「有点儿不耐烦了」；<span class="mention">@三只纳垢灵</span> 倒觉得正好。治法来自 <span class="mention">@开朗的企鹅</span>：

> <span class="mention">@开朗的企鹅</span>：处理这个问题最简单的方式就是再开一个 session，然后把之前那个 session ID 给他，让他好好分析一下这个问题到底怎么解决。一般来讲，是因为目标设定得不够具体，或者写得不够清晰

长跑数据同样惊人：<span class="mention">@开朗的企鹅</span> 周末一个需求没开 goal 模式跑了 19 个小时，「碰到五小时线了，要不然还能继续跑」；<span class="mention">@飘逸的猎豹</span> 一个任务从周五晚跑到现在，「究极猛干」。<span class="mention">@豁达的灰熊</span> 由此点出商业逻辑闭环：「可能这就是取消 5hr limit 的原因，agency 大幅度提高」，以及方法论结论——「先 plan 弄清边界的重要性增加了」。

### Ultra 的呆调度与自建 harness

<span class="mention">@热情的狮子</span> 贴出官方对 max 和 Ultra 的正式区分：max 只加推理深度（单 agent 更多探索、检查、修订），Ultra 则是「orchestration + reasoning」——root agent 默认并行调度四个 agent，代价是总消耗更高外加分解与合成风险。他用 Ultra 猛干 3 个 repo 的 refactor（前一天单日 6.3B token，gpt-5.6-sol 占 86.5%），但对调度评价不高：「这个 ultra 的调度还是有点呆，他什么 task subagent 都用 sol max，很多简单任务用个 sol med、terra xh 差不多得了」——而且没法 customize，<span class="mention">@开朗的企鹅</span> 确认这一代 codex 的 subagent 不能指定 model。对照组是 Fable：给它写明「具体执行用 sonnet5+opus4.8，你做 plan 和最终 aggregate 验收」，它会老实 follow。<span class="mention">@飘逸的猎豹</span> 的结论指向自力更生：「coding agent sdk 上的 harness 还是要自己做，自己做才能保证编排层可控、自由，不会被哪一家绑定锁死。」

大局观之争维持原判：<span class="mention">@热情的狮子</span> 的官方姿势仍是「fable 做 plan 和 goal prompt，5.6u 执行」，<span class="mention">@豁达的灰熊</span> 测了自己的 repo 也「咋觉得还是 fable 好用」。<span class="mention">@热情的狮子</span> 给出一个（未证实的）体量解释：听说 GPT-5.6 还是 4-5T 参数的 base，Fable 是十几 T——「planning scoping 什么的大局理解还是 fable 好，体量还是大很多」。

### 省 token 姿势：Terra 日常、Luna 更便宜

<span class="mention">@淡定的剑鱼</span> 提出灵魂问题：不限 5h 敞开蹬，两三天就把周额度用完，各位是再开一个 200 刀号交替吗？<span class="mention">@神秘的企鹅</span> 的答案是分层——日常任务 Terra、复杂任务 Sol，还有一条元建议：「让你的 codex 教你怎么省 token，OK 的。」<span class="mention">@直率的鹦鹉</span> 补充网络实测口碑：「要聪明就 sol，要便宜就 luna。」

<span class="mention">@开朗的企鹅</span> 晒出自己的配置（`model_auto_compact_token_limit = 220000`、scope 设 total，配 high/xhigh）和一份让 AI 做的用量调查，结论有点反直觉：不是 5.6 普遍更耗，异常主要来自新增的 max 档、长上下文被每次工具调用反复计入、多 agent 循环，以及面板把缓存输入也计入毛 token——同为 high 档时 5.6 Sol 平均毛输入反而比 5.5 低约 12%。真实的成本变化有两条：cache write 从 5.6 开始按未缓存输入价的 1.25 倍计费（呼应前天 [「Cache writes 收费：额度不耐用的真相」]({{ '/daily/2026/07/11/daily/#cache-writes-收费额度不耐用的真相' | relative_url }})）；单次输入超过 272K 会进入 2 倍输入、1.5 倍输出的长上下文价格阶梯。官方建议日常保持 high、长任务到 15-20 万上下文就新开线程、谨慎组合 max + 多 agent。

## 方法论

### 任务合同当立：给强模型写责任

<span class="mention">@风趣的企鹅</span> 分享[《Prompt Engineering 已死，任务合同当立》](https://mp.weixin.qq.com/s?__biz=MzcwNDE5NzI3Ng==&mid=2247484155&idx=1&sn=55c775e8e0df8f0467840119680be0e4&chksm=f56f936aa8bdd625e38c83277bfeb39b20c5500e944982ed846744184a86a50ea1a77752d51f&mpshare=1&scene=1&srcid=0713V1XsZgu1zvsJ4atS9tPL&sharer_shareinfo=a8c081d0f89c7ff5ffd108c68a8fdd54&sharer_shareinfo_first=a8c081d0f89c7ff5ffd108c68a8fdd54#rd)，核心论断一句话：「给弱模型写步骤，给强模型写责任。」写死的每一条步骤都在替模型关掉一扇决策的门，用户写下的其实是自己的认知盲区；该写清的是目标、验收标准、证据规则和失败出口——判断型任务放开路线，批处理任务锁死流程保一致性，审计型任务写死失败出口，共同底线是允许模型说「不知道」，「不给 AI 一个体面的失败方式，它就会编造一个漂亮的成功」。他自己摘的结语也很有传播相：Prompt Engineering 作为岗位死了，但作为能力成了必修课，「课程内容从『怎么写咒语』变成了『怎么管理一个比你聪明的下属』」。

实战派立刻给出修正案。<span class="mention">@三只纳垢灵</span> 的经验是不能全放手：「事实证明完全不要步骤的话，5.6 每一次自己推理出来还是不可靠的」——得有专门一个 request 让它做这个推理然后存下来，不能合并进其他步骤。<span class="mention">@稳重的海豚</span> 则贡献了反面素材：用 Fable 做调研，「一旦报告复杂了之后错误率就飙升」——中途重定了几个 option，它只加新的不清理旧的；也可能是 context 的锅，检索把上下文撑爆过一次（大于 1M 没法 compact），「还得我手动进去替换掉 tool result 然后再让它 compact——by 手动 i mean codex」。
