## K3 实测次日

### 冲了 699：全面耐干，就是慢

接昨天 [「群友实测：惊艳与烧光 token 并存」]({{ '/daily/2026/07/16/daily/#群友实测惊艳与烧光-token-并存' | relative_url }})，<span class="mention">@开朗的企鹅</span> 今天直接冲了 699 一个月：让 K3 修复一个做到一半的 repo，没提任何指标，「就说自己看看还差啥给做完，自己框框就做好了」。他给出的画像克制而正面：

> <span class="mention">@开朗的企鹅</span>：我觉得就是比较全面，能一直干活，能做一整个项目，有多模态，有充足的subagent，可能没有GPT-5.6/Fable在处理最难的问题时那么聪明（还没有push到边界），但是也不需要我具体的给他指示他应该怎么干活。他自己就可以根据我相对模糊的需求开始干一整个工作

他的组合拳是 K3 + K2.7-highspeed 覆盖大部分需求，另外发现「/」菜单按常用性排序这个小细节很舒服。代价同样明显：今天开始速度明显变慢（他猜是算力不够），<span class="mention">@淡定的喜鹊</span> 的账本一致——「K3 coding plan 烧得好快 不划算」。<span class="mention">@活泼的树懒</span> 的疑问代表观望派：GPT 已经这么强了，还要冲 K3 吗。

### 一句话游戏横评：5 轮烧光 199

<span class="mention">@务实的长颈鹿</span> 交出一句话游戏 vibe coding 的 K3 卷：起手依然是「结合 POE2 核心要素的恶魔城式横版像素游戏」，结果 5 轮交互就把 199 的月额度全部耗完（其中一轮还是修素材绝对路径的 bug），整个耗时一整天。惊喜有二：一上来就做了审美很好的标题画面（虽然游戏内画面惨不忍睹）、和 Fable 一样找到了同源的开源素材库——Sol 和 hy3 都没做到；不足是太慢太费 token、技能宝石参考到 POE1、没有多职业，progression 设计极度 hardcore——高装等捡了装不上、技能全耗蓝血瓶不补、BOSS 打不过，「kimi 的品味很硬核」。

<span class="mention">@开朗的企鹅</span> 随即贴出自家三连对比：[K3 版](https://exile-k3.ifix.xin/)、[K2.7-highspeed 版](http://poe2vania-k27-highspeed.ifix.xin/)和 [5.6 版](https://cinderbound.ifix.xin)（中途切到 Luna 效果太差正在重做），结论是 K3 明显强很多；K2.7-Highspeed 的优势在快，「别人做一轮，我这边都交互优化三四轮了」。开源素材的威力得到双向确认——<span class="mention">@开朗的企鹅</span> 贴出月夜城堡的恶魔城场景图惊叹「原来开源素材这么厉害」，<span class="mention">@务实的长颈鹿</span> 补充 Kimi 找到素材库之后的处理速度比 Fable 5 慢很多很多。<span class="mention">@风趣的企鹅</span> 也交了作业：[一句话 K3 做的 3D 塔防](https://ket2u5bejmwbq.ok.kimi.link)。

### 主动但跑偏：先把态度端正

<span class="mention">@搞仁义毛义仁</span> 观察到 X 上开始出现和 <span class="mention">@沉稳的仓鼠</span> 昨天同款的体验：K3 主动是很主动，但总在做无关的事；他自己还撞见 K3 weekly 0% 之后居然还在蹬。<span class="mention">@天真的浣熊</span> 的诊断是「996，首先态度要端正」，并给出管理方案：让 K3 写时报、日报、周报，有效监督进度。<span class="mention">@沉稳的仓鼠</span> 则宣布到现在除了生成过一个 txt 还没用 K3 跑出过东西，已经回头去 harness Gemini 了——顺带发现一个妙招：让 GPT-5.6 Sol xhigh 扮演「非常严厉的父亲」，可以写出非常严厉的 harness。

### 图解与路线之辩：多模态还是 agentic

<span class="mention">@冷静的麋鹿</span> 凌晨贴出一张自制图解，给 K3 的热度降温定调：优势在长程执行、短板在推理（官方自承差一档），「比肩 Fable」只在特定 benchmark 成立；真正的争议不在能力在价格——输出 $15/M 约是 GLM-5.2 的三倍多、DeepSeek 的十五倍，能力没拉开代差、价格先拉开了；权重目前仍是「承诺开源」状态，结论是好工具而非全能王，用对场景很能打。

路线判断上，<span class="mention">@沉稳的仓鼠</span> 认为 K3 可能是一个更好的多模态模型，跟 GLM 5.2 走的 agentic 方向不是一回事；<span class="mention">@豁达的灰熊</span> 认领这条线——K2.5 时期他的多模态方案就选的 Kimi，只是一直在 coding 能力和多模态之间争 tradeoff。<span class="mention">@细心的熊猫</span> 从训练数据角度解释「总做无关的事」：都用长程任务数据训练，「ai就喜欢max effort」——就像某一版没发布的 FSD 全拿边缘数据训练，能当秋名山车神应对极端路况，普通高速巡航的体验反而非常差；他的乐观在飞轮：用户越多数据越多，模型越来越强，「虽然没用户也没关系，可以花钱蒸馏别人」。

### 安全松绑红利

<span class="mention">@开朗的企鹅</span> 转发推主 enzo 用了 16 小时 K3 后的观察：这个模型很强（尤其前端），但人们喜欢它的一个不明显的理由，是它显然在安全措施和版权方面不遵循同样的规则——Kimi 会很乐意克隆 MacOSX，让它帮你改进另一个 AI 模型，它会带着微笑去做；让 Fable 做同样的事，「它会开始把你视为犯下战争罪的罪犯」。推文的引申判断是：连用 Fable、GPT-5.6 和 Kimi 三个新版本之后，很明显顶级模型的潜力正在被安全限制严重压制。

### 为 LLM 时代而生的履历

## 工具

### base64 之罪：2.1G session 与每天 10GB 上传

凌晨一场集体诊断把 Codex 桌面版的老毛病钉上了墙。<span class="mention">@开朗的企鹅</span> 先报案：单独给 Codex 配的 VPN 每天要上传 10+GB、很快就干废，<span class="mention">@坚定的貂</span> 附议最近 VPN 消耗异常。<span class="mention">@直率的鸵鸟</span> 给出第一块拼图：Codex 会很积极地截图，每轮交互带着上下文中全套图片上传，他的解法是补一条规则——图片分析必须新开子 agent。<span class="mention">@洒脱的狐狸</span> 补上第二块：他明明在远程开发、本地只跑 desktop 却几天就卡死，原因是 imagegen 生成的图以 base64 存在会话历史里——他的 sessions 目录已有 5.6G，最大的单个 session jsonl 文件 2.1G；正确姿势是生成图片用 sub agent、存本地后只把路径交给主 agent。<span class="mention">@洒脱的猫头鹰</span> 当场对上号：昨晚让它逐个表单截图给 imagegen 调 UI，「卡到关机都没反应，只能按电源键」——几张图干掉了 48G 内存的 MBP。

> <span class="mention">@坚定的貂</span>：万亿级别公司为什么做这么傻的事情

> <span class="mention">@直率的鸵鸟</span>：我感觉做codex桌面版的程序员应该和我一样，是用ai开发的，一点代码都没看

### CodeFuse：monorepo 的虚拟文件系统

大 monorepo 检索的痛点今天收获一个开源答案。<span class="mention">@稳重的海豚</span> 抱怨在超大 mono repo 上 agent 一用 grep 基本就废了，还得手动告诉它 workspace；<span class="mention">@搞仁义毛义仁</span> 的血泪教训是在 office 代码库 grep 一次两小时起步，「grep完把自己弄死了」，他的方案是干脆禁掉 grep、逼模型想好关键词后走 indexed search。<span class="mention">@冷静的白鹭</span> 顺势亮出自己新开源的 [CodeFuse](https://github.com/zzszmyf/codefuse)：面向 AI agent 的代码虚拟文件系统，先把代码库预索引成符号关系图，再暴露成 agent 能用 ls、cat、find、glob 原生浏览的视图，支持通配符查询、调用链追踪和 vfs 增量索引，绕开脆弱的文本 grep。土法派也有各自的轮子：<span class="mention">@天真的浣熊</span> 做了个 skill 定期自己更新索引，<span class="mention">@稳重的海豚</span> 用 lancedb 加 cron。<span class="mention">@沉稳的兔子</span> 给这场争论画了条判断线：grep 这事儿主要看同义异名的问题是否严重。

### <span class="mention">@今天群内信息量极大</span>的 skills 军火库

<span class="mention">@今天群内信息量极大</span> 自曝统计了一下手头有一两百个 skill，日常检索基本都靠自己的 [semantic-search-skill](https://github.com/grapeot/semantic-search-skill)（本地嵌入 + 磁盘缓存 + JSON 输出），完整清单在 [skills 目录页](https://grapeot.github.io/skills/)，覆盖从会话归档、PDF 解析到多 agent 交叉验证、E-Ink 视觉日记；他还在整体重写 AI Builder course，「现在完全agentic了，不讲传统chat了」。<span class="mention">@冷静的大象</span> 求分享 AGENTS.md，<span class="mention">@神秘的麋鹿</span> 直接指路他 GitHub 仓库里的上下文基础设施。<span class="mention">@专注的剑鱼</span> 问到多人协作——<span class="mention">@今天群内信息量极大</span> 坦承这个 skill 为个人设计，多人场景建议用专门的 service；<span class="mention">@专注的剑鱼</span> 的经验是即便自己的 know-how 库，索引前那一步也得投入很重的人工，才能保证后面 agent 好检索。

## 方法论

### 不同频之痛：monorepo 布道与 KB 政治

<span class="mention">@80-HD</span> 给 manager 解释了半个小时为什么 AI 时代要用 monorepo、为什么要用老鸭汤，「不同频的交流就好累」。<span class="mention">@开朗的海豚</span> 共情这种信息差——这在本群至少是几个月前的知识；<span class="mention">@淡定的喜鹊</span> 补充同事间对 AI 理解的深度和新鲜度差异太大，「不像 ai agent team 可以一秒同步 context」。<span class="mention">@搞仁义毛义仁</span> 从历史角度撑腰：前 AI 时代也该用 monorepo，office 之前太激进就在这里吃过亏。职场政治线也很真实：manager 追问这和隔壁组的 knowledge base 有啥区别（<span class="mention">@80-HD</span> 猜是想挖 scope），搞 KB 的受到器重，而他自己被拉进 KB 项目做 RAG，索性用「老油条打工方式」应付——你说啥我做啥，不多做也不多想。

### RAG 的位置：隔离、retrieval tool 与鸭哥考据

<span class="mention">@稳重的海豚</span> 抛出正经问题：现在还有人做 RAG 吗？很多企业一说 agent 就要做 RAG，可他平时用的老鸭汤本质上不也是一个 agentic RAG。<span class="mention">@淡定的喜鹊</span> 转述 Claude 的意见：doc 数量不够大，做 KB 用 RAG 是 overkill；<span class="mention">@沉稳的兔子</span> 给出更工程的定位——广义 RAG 主要是做 KB 隔离，别让 agent 不小心干爆 context，这样 KB 随便增长、context 需求维持在 sublinear。<span class="mention">@80-HD</span> 则复述了 <span class="mention">@今天群内信息量极大</span> 的老观点：不要做 one shot 的，把控制权给 model、只提供 retrieval tool。

好玩的是溯源过程：<span class="mention">@稳重的海豚</span> 让 AI 去查这句话的出处，AI 的结论是「大概率不是某篇文章的逐字原文，而是几篇文章合在一起的口语化总结」，并列出最贴近的四篇——[《Agent 文件系统：从"喂给模型记忆"到"让模型自己翻文件"》](https://yage.ai/share/agent-filesystem-survey-20260507.html)（push 转 pull）、[《AI 脚手架正在商品化》](https://yage.ai/share/ai-scaffolding-commodity-runtime-20260505.html)（控制权交给 runtime，人定义目标与验收）、Thin Harness Fat Skills 拆解和 grep 主干考。<span class="mention">@80-HD</span> 恍然：「所以说我已经内化了鸭哥？」<span class="mention">@稳重的海豚</span> 授予称号：「鸭bot」。

### Memory 该测 precision：全群关机实录

<span class="mention">@今天群内信息量极大</span> 预告了一篇排期 7 月 19 日的檄文，先放出[预览版](https://yage.ai/share/ai-memory-benchmark-precision-20260719.html)：

> <span class="mention">@今天群内信息量极大</span>：现在memory benchmark和厂商宣传全在测recall（AI记的有多全）。但产品痛点完全是反的，记错了对用户的困扰比漏记了大多了。benchmark和产品不匹配，能做好就怪了。

文章的论据颇有冲击力：对 ChatGPT 用户的调查显示 96% 的记忆条目由系统主动创建、52% 包含对心理状态的推断；Mem0 的一个部署案例里用户 32 天积累一万多条记忆，人工清理后只留 224 条。结论是写入端要偏向 precision——AI 可以发现候选、建议范围，但长期状态应经用户确认才生效。群友的实践早已投票：<span class="mention">@80-HD</span> 把 cc 的 memory 关了以后体验好多了，吐槽它老记不重要的、触发机制奇怪，「很容易记偏，然后偷偷藏在你的context里面」；<span class="mention">@搞仁义毛义仁</span> 把 codex/chatgpt 的 memory 都关了，<span class="mention">@今天群内信息量极大</span> 本人也全关；坚持开着的 <span class="mention">@稳重的海豚</span> 需要定期手动检查，总有莫名其妙的 leftover。

### 教师产品各做一半与平均人论

<span class="mention">@今天群内信息量极大</span> 今天连发的另两篇：[《vLLM x TileRT：两个目标相反的推理引擎，为什么开始共用一套服务》](https://yage.ai/share/vllm-tilert-specialized-inference-paths-20260717.html)（推理引擎从单引擎最优转向专用路径编排），以及[《ChatGPT 与 Claude 都开始服务教师，但只各做完了一半》](https://yage.ai/share/chatgpt-claude-teachers-two-halves-20260717.html)——OpenAI 先做学区治理、把「什么算好教案」留白，Anthropic 先把课程标准写进 skill、治理功能欠奉，两家都没打通学生学习结果的反馈闭环。

### Coding Plan 排名：一线只认 O 和 A

<span class="mention">@沉稳的仓鼠</span> 发布新文章[《2026 年 Coding Plan 对比与排名》](https://ranchen.org/content/20260716-ranchen-article-2026-coding-plan-ranking)，基于每月 500-1000 亿 token 的消耗实践：排名逻辑是模型能力 × 编程外壳 × 官方补贴的乘积，一线只认 OpenAI 和 Anthropic 的 200 刀档（有时 200 刀套餐能吃出近 2 万刀的 API 账面量）；第二梯队是 GLM-5.2 和 Grok 4.5；Gemini 3.5 Flash 不适合做主编程代理，但写文章、改写和翻译极强——他的写作流程正是 Codex 整理上下文、Gemini 写初稿。文中明确劝退多开账号和中转站：把代码安全和长期稳定性换出去不值。

### LangGraph 连更：状态机而非 Agent 框架

<span class="mention">@淡定的大象</span> 的科普系列（前情见昨天 「<span class="mention">@淡定的大象</span>连更：数据炼金与灾难性遗忘」）今天更新[《95% 的 LangGraph 教程，都没告诉你它真正解决了什么》](https://mp.weixin.qq.com/s?__biz=MzY4NTM1MDc1NQ==&mid=2247485744&idx=1&sn=32379d720decaa2fe7b5a7a5c3ebb754&chksm=f2c061c800aa056ef7e873d714bec5399f47e1ed05c3149a0bcdf0ef92d7ab1a592ccb363ed0#rd)：LangGraph 本质是 LLM 应用的状态机执行引擎，用同一个数据排障 agent 对比两条极端路线——全交给模型的 ReAct 路线 token 消耗准平方级增长，焊死在代码里的 StateGraph 路线零成本但只会查预设的 bug；生产落地是混合态，原则一句话：能用代码算清的，就别变成 token 被反复重发进上下文。

### 先搞懂还是先放手

<span class="mention">@稳重的海豚</span> 自我检讨了一个习惯：做大任务前喜欢先问 AI 应该怎么干、能不能干，自己搞清楚了再让 AI 去干——但自己搞清楚花的时间太长，「有我搞清楚这个问题的时间，AI可能已经自己把活儿给干透了」。<span class="mention">@风趣的企鹅</span> 只回了四个字：「不太可能呢。」放手与掌控的边界，仍是各人各解。
