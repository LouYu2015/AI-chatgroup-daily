## GPT-5.6 实测第六日

### 多任务与 DRY：5.6 终于像个人了

接上 7 月 12 日 [「版本演进论：从把屎把尿到真的懂你」]({{ '/daily/2026/07/12/daily/#版本演进论从把屎把尿到真的懂你' | relative_url }})，<span class="mention">@三只纳垢灵</span> 今天补充了新证据：一次塞好几个任务时，sol ultra 的表现明显好于 5.5 xhigh，verification 写太多 5.5 会偷懒、sol ultra 目前没发现，结论是「5.6 终于像个人了，这是一次历史性的突破」，而且「随着模型的升级，prompt 和 context 的写作也能越来越 DRY，是好事」。<span class="mention">@淡定的剑鱼</span> 同感：「模糊的描述了几件事，他能自己理清楚。」定位也从「打工人」上调了一级：

> <span class="mention">@三只纳垢灵</span>：sol ultra 看起来差不多稳定有我大一的水平了，就是不断在学习 best practice 但是还不太会主动用的时候，只要稍微指导一下就可以写出不错的东西来。比以前要把屎把尿的感觉要好太多了

成本侧他也给了个参照：就算猛蹬 sol ultra，编译测试的部分依然超过推理的两倍；网传 5.6 过度设计过度验收，但「给 C++ 做测试还没超过必要限度」。

### 收敛续辩：xhigh 把需求打磨到怀疑人生

> <span class="mention">@洒脱的猫头鹰</span>：sol xhigh 在把一个不太成熟的想法往八九十分的状态去不断的叠加优化，检查边缘场景，搞得我都有点怀疑提的那个需求值不值这么细致的实现了。

<span class="mention">@三只纳垢灵</span> 的立场毫不动摇：「我永远都想他做到 100。」<span class="mention">@聪明的灰熊</span> 则报告疑似 bug：sol ultra 经常陷入长考，哪怕是不太复杂的任务——<span class="mention">@洒脱的猫头鹰</span> 表示深有同感，但「判断不了这个深度而又全面的思考的必要性」，只能等它跑完整个 goal 再跑复盘。

### 需求当 hero：auto research 还得 Opus 收尾

<span class="mention">@灵巧的树懒</span> 指出 5.6 的一个抽象毛病：开发网站时会把用户需求本身（「要一个好看的网站」）作为 hero 放在首页，搞不清什么是任务需求、什么是任务目标——「人类感觉不会干这样的事情」。<span class="mention">@开朗的企鹅</span> 给出了精准类比：「就有一种『买五个苹果，如果看到西瓜买一个』」。<span class="mention">@三只纳垢灵</span> 认为这个 scope 的问题解决还不到时候，「等 5.8 吧」。<span class="mention">@灵巧的树懒</span> 正在折腾 auto research：实验设计还可以搞，但初始 proposal 和最后端到端的成文「反而不如 opus 4.5/4.6」，他的方案是加上一大堆和 pipeline 差不多长的 skills 去迭代表达方式，目标是「一句话 idea 就出成品论文」——「感觉基本上接近那个形态了」。

### Subagent 分层配置表

针对前几天 [「Ultra 的呆调度与自建 harness」]({{ '/daily/2026/07/12/daily/#ultra-的呆调度与自建-harness' | relative_url }}) 和 [「Runtime skill 替代 spawn_agent」]({{ '/daily/2026/07/13/daily/#runtime-skill-替代-spawn_agent' | relative_url }}) 的痛点，<span class="mention">@热情的狮子</span> 宣布搞明白了 codex 0.144.4 调用不同 level subagent 的姿势：自己定义几个不同的 agent，分别指定 model + reasoning effort。他晒出的分工表值得抄作业：Luna/xhigh 只做精确查找和文件/符号/调用点 inventory；Terra/high 负责机械、确定性、低风险修改；Terra/xhigh 处理边界明确、验收清楚的常规实现；Sol/medium 做宽研究、跨文件集成和非平凡 debugging；Sol/high 上 messy repo、长链路实现和架构/API/数据模型决策；Sol/max 只留给极少数高影响的独立 review。最终配置是 Sol xhigh 做 main orchestrator、Terra medium/high 做 routine worker、Sol max 做 hard specialist、独立 critic 用 Sol xhigh（高风险 merge 升 max），外加一组 escalation triggers（重复失败 ≥2、agent 意见分歧、不可逆变更、安全/并发/迁移、缺确定性 verifier）。至于 ultra 本 ultra——「很好，但太 jb 慢了，我在 tweak」。

## 工具

### herdr：现代版 tmux

### Token 政治学：部门第三被谈话

某群友分享了一手风向标：他所在公司此前不限 token，他 7×24 小时猛蹬，蹬累了还请假休息了一周——结果公司突然开始统计 token 消耗，他在三千多人的技术部门排到第三，被领导谈话，「还好请了假，不然得冠军」。他上个月用掉约 1.5 万刀，<span class="mention">@冷静的麋鹿</span> 换算：相当于两个 20x 跑满，「在为资本家工作的领域，肯定算努力的了」。值不值的问题他倒不慌——老板已经拿出去吹了几波。但 <span class="mention">@谨慎的灰熊</span> 点出更深一层：「老板呢，也有老板」「怎么评判值不值，我觉得在座各位都可能会被挑战」，他自己的解法是干脆不用公司额度、自费 codex。<span class="mention">@冷静的麋鹿</span> 以管理者身份给出了分配原则——只有一类人他闭着眼加额度：

> <span class="mention">@冷静的麋鹿</span>：我这边有一个做广告投放的团队，他一阵猛蹬，搞了个ai托管的投放agent，让投放量在满足roi要求的情况下直接翻倍了，那我觉得，这种，你爱怎么花怎么花

> <span class="mention">@冷静的麋鹿</span>：我们公司是看了一下，大部分人都在瞎搞，要么是不会用乱来，要么是会用但都在忙自己的事情乱来

另一位群友则贡献了硬币的反面——摸鱼经济学：他刻意把 PR 数量控制在组里 top 30%，一天最多干 5 小时，「枪打出头鸟」「就跟打魔兽虐菜一样，要控温」；想刷公司 token 榜也有攻略，「做个 knowledge base 项目，然后跑数据烧 token 就行了」（还有群友自曝曾这么刷了两天、烧掉 1B 后「觉得有点太过分了就停了」）；如果自己当老板，会砍掉公司里绝大部分瞎搞的 knowledge base 和 oncall bot 项目——<span class="mention">@冷静的麋鹿</span> 苦笑「那你会砍掉公司 99% 的项目了」。他还遭遇了模型配给：在公司用 Opus 都会收到提醒让换便宜的模型，<span class="mention">@冷静的白鹭</span> 的安慰堪称金句——「仅仅是让你换便宜模型，而不是让你换便宜人」；他的对策是钻空子换 Sol，「我看了看他那个 spend optimizer 是写死在 cc 上的」。最后借 <span class="mention">@沉稳的仓鼠</span> 的文章完成自我和解：「不要给公司提效，自己摸鱼最重要」——「哎，我最后还是变成了自己不喜欢的职场老油条。」

### 古法 agent 体力学

<span class="mention">@神秘的企鹅</span> 提出一个量化问题：一天要干多久，才能把两个 20x 跑满？<span class="mention">@80-HD</span> 算了笔账：按 cc 一小时花费 20 刀左右，一天 500 刀需要 25 个满载小时，「相当于 10 个小时满载工作三个 session」，前提还是「古法 agent」——这个词被 <span class="mention">@冷静的麋鹿</span> 当场认证「用的精髓」；纯 coding 而言这已经是天花板，跑数据不算，「像 <span class="mention">@稳重的海豚</span> 这种就属于作弊」。<span class="mention">@神秘的企鹅</span> 认领古法流派：「古法掌控力最强」，goal 模式跑废过几次、一跑十几个小时。他还有一段上瘾者自白——有了 AI 以后明显累多了，「现在能够写代码从上午九点干到凌晨两点」，vibe coding 乐此不疲，「真的是有 M 的倾向」；<span class="mention">@神秘的麋鹿</span> 一语中的：「高浓度决策，高浓度反馈。」

### 先发者的 3% 与后来者的 97%

<span class="mention">@80-HD</span> 推荐 <span class="mention">@沉稳的仓鼠</span> 的新文章[《AI 对每个人都是公平的》](https://ranchen.org/content/20260713-rancheng-article-ai-equal-for-everyone)，自述「减轻了一些 ai 焦虑」。核心模型：看到别人把 AI 用得熟练，那 3% 的领先只对应当下的能力截面，拉长到三年、上千次真实使用之后会被大幅稀释；真正锁死差距的不是起点而是信心——把模型犯错当成一次调试还是当成「我果然不适合」；界面和提示词技巧折旧极快，耐用的是拆解问题的能力和最内层的专业判断。文中还引 NBER 对 5179 名客服的研究：生成式 AI 让新手生产率提升约 34%，高经验员工增益很小——反馈提前才是关键。作者本人在群里的补注也算文章的活案例：「本群客观上遥遥领先，不过遥遥领先就会看到更遥遥领先的人。」

### 温度旋钮与极限

<span class="mention">@淡定的大象</span> 的科普系列（前情见昨天 [「内燃机式学习：先现象后公式」]({{ '/daily/2026/07/13/daily/#内燃机式学习先现象后公式' | relative_url }})）今天更新[《高中觉得最玄乎的"极限"，其实是大模型"从犹豫到笃定"的那个旋钮》](https://mp.weixin.qq.com/s?__biz=MzY4NTM1MDc1NQ==&mid=2247485632&idx=1&sn=8c955a3177664b5b6ba102dc308ac695&chksm=f2baaa40ae50a03a5eb578d14bc3dc563aad249934571fa1baded8cf95c6f67d319e17ed2bc3#rd)：temperature 就是在两个极限之间滑动的旋钮——T 趋近 0 时 softmax 逼近 argmax（贪心解码的底层），T 趋向无穷时逼近均匀分布；loss 的收敛下界、导数定义里的 h→0，都是「无限逼近但不一定抵达」这一母题在大模型里的具象。
