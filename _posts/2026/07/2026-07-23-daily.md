> <span class="mention">@随和的企鹅</span>：当认知的壁垒在竞争中没有那么重要之后，弱增长的公司就追不上强增长的公司，就会发现做什么都力不从心，从而在这个自强化的成长过程中落后

## 工具

### prewalk：交接轨迹，而不是童话

<span class="mention">@80-HD</span> 分享了 [stencil 的 prewalk 实验](https://stencil.so/blog/prewalk)：SWE-Bench Pro 实测里，传统 /plan 模式（Opus 只读代码写计划、交给 Gemini Flash 实现）反而比 Opus 单干贵 14%，因为 agent 的开销大头在读代码、编辑只占约 9% token——贵模型读完便宜模型还要再读一遍，等于重复购买最贵的那部分。/prewalk 的做法是让前沿模型带隐藏规划指令开工，在第一次落地编辑的瞬间透明切换到便宜模型，后者拿到已探索的轨迹和勾选中的 TODO，只当是自己走出来的。

数据相当能打：GPT-5.6 Sol 用 prewalk 达到单干 97% 的通过率、成本降到 61%；Opus 4.8 通过率 92%、成本仅 53%、速度还是 solo 的 1.5 倍，顺带大幅减少了模型陷入困境后上 GitHub 搜答案的作弊行为。<span class="mention">@80-HD</span> 自嘲这对群里只用 fable/sol 的人没啥用，但盛赞博客金句「Hand off a trajectory, not a fairytale」好文艺；<span class="mention">@洒脱的猫头鹰</span> 例行提醒不知真伪。

### WorkBuddy：连接器市场当 CLI hub

昨天 [「Computer use 扒会议纪要」]({{ '/daily/2026/07/22/daily/#computer-use-扒会议纪要' | relative_url }}) 的续集。<span class="mention">@神秘的麋鹿</span> 指出批量下载会议转写明明有 CLI 可以做，<span class="mention">@冷静的麋鹿</span> 随即交出完整姿势：下一个腾讯 WorkBuddy，连接器市场里通达信、QQ 邮箱、腾讯文档、飞书、钉钉一大排，他把连接器摘出来放进老鸭汤，WorkBuddy 在他那里就是个可视化寻找插件和 CLI 的 hub——用被检验过的现成货，省得自己封装还要运维。

<span class="mention">@开朗的企鹅</span> 顺藤摸瓜找到[腾讯会议官方开源的 tencentmeeting-cli](https://ulink.meeting.tencent.com/news/hya20260625.html)：OAuth 设备码授权后 agent 就能创建会议、拉录制和转写、按关键词检索发言，官方还给出一条给 agent 装 skill 的现成命令。<span class="mention">@冷静的麋鹿</span> 的忠告是别装 codebuddy、没用；<span class="mention">@开朗的企鹅</span> 总结套路——WorkBuddy 有的连接器，找到对应 CLI/skill 喂给自己的 agent 就好，所有 agent 都能共用。

### 瞪出来的 TUI 绘图 API

<span class="mention">@搞仁义毛义仁</span> 瞪了 8 个小时把 TUI 的绘图 API 做出来了，回头 GacUI 就可以上 TUI 渲染器。顺手蹬出的测试绘图程序能画重叠长方形、交叉处自动换成合适的字符，底部像 codex cli 一样打字，拖动 CLI 窗口不丢画布，鼠标键盘全支持，最终体验就跟普通 UI 一样；他打算把 feature 补齐后当成手工测试的一部分长期维护。

## 方法论

### 认知过载：自己发的 doc 自己要能讲清

接 20 日的 [「AI 文档洪水与以读攻读」]({{ '/daily/2026/07/20/daily/#ai-文档洪水与以读攻读' | relative_url }})，<span class="mention">@稳重的海豚</span> 交出一线复盘：做 post training 的数据评估时 AI 会产出海量文档和代码，负责的工程师却讲不清里面的问题，跨团队交流成本无形暴涨、信任滑坡。

> <span class="mention">@稳重的海豚</span>：我觉得主要的核心问题在于内容生产方对自己产出内容的理解不到位，也就是他个人的认知过载 间接引发了其他团队人员的认知过载

他的解法是降低频率、先深入理解，保证 AI 产出的东西自己能讲清楚，还把文档从 Markdown 转成 HTML——前者的首要读者是 agent，后者是人。数据佐证：26 年至今 13000 个 commit/PR，进七月后 token 消耗更高但 PR 反而少了很多，大部分时间花在调研上；他还把 manage up 的 trick 教给了自己的 agent，所有文章最长不超过两页。配套阅读是他转的[《亲历 AI 提效的真实混乱：一个 PR 改了 50 万行代码、产研关系差点崩了》](https://mp.weixin.qq.com/s?__biz=MzkzMDY1NDgyOQ==&mid=2247833498&idx=1&sn=2c84f48313c19730fcc7643b31d2c9b2&chksm=c31f14e04bb222e489f1198b769408d04061312e3d7283026a962a3f67048ac16905a9401535#rd)：50 万行的 PR 没人能 review 直接合入，最后靠强制手写 TL;DR 和核心模块 Code Owners 把人的交流拉回来。

响应者众。<span class="mention">@80-HD</span> 一句话总结：自己发出去的 doc 自己要能看懂，看不懂就别发——AI 浓度高的典型症状是明明两句话说完的、前后铺垫几百字（他认证 <span class="mention">@今天群内信息量极大</span> 的 AI 报告这个问题不严重，读起来压力不大）；<span class="mention">@认真的灰熊</span> 表示现在经常古法手写或强加工；<span class="mention">@洒脱的猫头鹰</span> 先打趣 <span class="mention">@稳重的海豚</span> 这段发言本身 AI 浓度就好高，再交出自己的流程——让 agent 根据源码梳理用户旅程、用 computer use 验证、验证完自己再看。<span class="mention">@80-HD</span> 还点出恶性循环的终点：辛辛苦苦写一篇，结果没有真人看，全是别人用 AI 给你的点评；<span class="mention">@飘逸的狮子</span> 的脑洞更黑——碳奸可能已经在思考，为什么要人来拖后腿放慢节奏。
