## Fable 5 降智风波

<span class="mention">@今天群内信息量极大</span> 报告最近十几个小时自己对 Opus 和 Fable 的「粗口率直线上升」，感觉又降智了。<span class="mention">@稳重的海豚</span> 的遭遇更惨：睡前布置了二十几个任务让 Fable 一气写完，结果每个 issue 的 investigation 从此前的详尽变成半吊子，「质量大概是之前的 30% 左右」；他一度怀疑后台被偷换成 Opus 或 Sonnet，让 codex 分析 transcript 却没发现模型替换——「确实就是他在后台做出降智，不知道是不是给 route 到别的模型上了」。他随后贴出量化对照表：#1838 之后 issue 深度下降约 9%、issue 正文长度暴跌 54%，linked PR 平均分从 6.98 跌到 1.78。他把这体验比作「去店里买金条，商家给你金包钨说是纯金」，并痛斥所谓 model routing 组干的 balance cost/performance「完全就是 bullshit」——<span class="mention">@80-HD</span> 冷冷补刀：这是个「多好 quantify 的 impacc」的 scope，而且估计 80–90% 的用户根本感觉不到。

## 随身 Vibe Coding 装备

### Herdr 装进手机与墨水屏畅想

<span class="mention">@坚定的貂</span> 晒出手机上跑 Herdr 的实况——一屏管着 cosheaf、ogc-clean、unimodal-k-median 等多个 space，agent 混跑 codex / claude / agy，蹲在院子里就能 review 一个「Brewed for 1h 4m 37s」的合并任务并让它 git push。这是 7 月 2 日 [「Herdr 与多主机 Agent 调度」]({{ '/daily/2026/07/02/daily/#herdr-与多主机-agent-调度' | relative_url }}) 的移动端续集。但他嫌手机「屏幕太小」，开始物色随身 vibe coding 设备：看中了 Go 10.3 (Gen II) 墨水屏平板，计划配蓝牙键盘走 ssh + herdr，还贴出 LinkedIn 上 870 赞的帖子佐证——有人在纯手写墨水屏上跑通了 Claude Code，模型逐词流式输出意外完美匹配慢刷新节奏，零背光无通知续航数天，「旁边看模型沉思一小时，感觉像在读一本书」。<span class="mention">@坦荡的灰熊</span> 的终极愿望是「有个大屏的眼镜就好了，绿色的也行，不需要全彩」，<span class="mention">@神秘的企鹅</span> 则站三折叠。

### AgentHub：PTY 拦截的 Agent 收件箱

<span class="mention">@开朗的企鹅</span> 顺势晒出自己开源的 AgentHub：浏览器端是一个 933 个会话的「会话收件箱」，支持 Codex / Claude / Kimi 等 provider，手机端能看重点消息流、批审批、语音输入。架构上是本机 worker + server 同步：worker 用 tmux（Windows 上是 psmux）把 Codex/Claude 跑在持久终端里做 PTY 拦截；理解会话不靠脆弱的 regex 解析 stdout，而是 Transcript Sync——直接监控 `~/.claude/sessions/` 等目录里 agent 自己写的结构化日志，渲染出语义 100% 准确的 chat UI；遇到「Do you want to run npm run build? (y/n)」就挂起 PTY 流生成 Pending Approval，用户在手机上点 Approve，服务端再把 `y\n` 用 tmux send-keys 注回 stdin。<span class="mention">@坚定的貂</span> 连呼「果然暴力」「高级，有了这个就能创建任意 UI 了」，<span class="mention">@坦荡的灰熊</span> 表示「学到了，psmux」。

### ACP 替代 TUI 套壳？fork 是硬伤

<span class="mention">@洒脱的猫头鹰</span> 提出用 ACP 做协议应该比 TUI 套壳更通用，<span class="mention">@坦荡的灰熊</span> 泼冷水：ACP 不能 fork（最新版 Zed 实测不行），而且「还有很多隐性的东西没有，比如那个 fable5 的路由」。<span class="mention">@洒脱的猫头鹰</span> 去问了 GPT 后回来汇报：fork 属于客户端能力、协议不管；再更新——session fork 目前是 ACP v2 协议的草稿状态，部分场景可用。结论：想要任意 UI 和完整状态，暴力 PTY 方案暂时仍是刚需。

## 方法论

### 煤老板追问：AI-native 的需求与价值捕获

<span class="mention">@敏锐的雪豹</span> 转发了自己对 <span class="mention">@沉稳的仓鼠</span> 新文章[《企业的 AI 转型都会失败，就像煤老板做不了互联网》](https://ranchen.org/content/20260704-rancheng-article-ai-transformation-will-fail-like-coal-boss-internet)的长评：文章「非常佩服，但写了个表面」——第一，AI 到底使成本结构如何改变、什么样的需求适合 AI-native 承接？第二，就算承接了，参照 <span class="mention">@今天群内信息量极大</span> 的短剧研究，供给侧省下的成本价值捕获不一定归你，「利润归你还是归别人」？他透露自己公司正是按「稳住旧现金流、开辟 AI-native 新战场」在做，「但开辟的新战场都不怎么达预期哈哈，我们内部也在讨论反思」。<span class="mention">@沉稳的仓鼠</span> 的原文核心判断是：转型失败的根因不是技术，而是旧组织的生产关系本身就是阻力——约 95% 的企业 GenAI 项目没有可衡量的财务影响，创始人该做的是把旧业务推入 maintenance mode、自己下场从零做 AI-native 新业务。他对追问的回应很坦诚：

> <span class="mention">@沉稳的仓鼠</span>：说啥不 work 容易 但是说啥能 work 预测未来还是难啊 都是摸着石头过河 我的石头都发出来 大家来摸着我过河也蛮好的呢

<span class="mention">@温暖的斑马</span> 补充了一个组织侧的反面教材：亚马逊内部员工自建的 token 使用排行榜后来被关闭——「排行榜一旦出现，人就会优化排行榜」，本想鼓励用 AI 解决客户问题，最后鼓励出一堆刷 token 的动作，「我每次看到那个 token maxxing 就想到眼镜蛇效应」。<span class="mention">@三只纳垢灵</span> 总结：「只要 KPI 不是直接作用在项目上的，那就别想员工关心项目。」<span class="mention">@直率的海豚</span> 归因为 Data/Telemetry Driven 公司的路径依赖。

### Agentic 之道：养 Context、蒸馏知识、编排智能

<span class="mention">@风趣的企鹅</span> 发布了 GTLC 杭州站演讲整理版[《Agentic之道》](https://mp.weixin.qq.com/s?__biz=MzcwNDE5NzI3Ng==&mid=2247484074&idx=1&sn=6dd6e8b6471b51ee5c3b35b61484ab86&chksm=f52655918d55b65b51d1be0dd253c79cfc6cf365f51ec9be0ce6267a9717c4fef5899b5a6877&mpshare=1&scene=1&srcid=0706HfAEUXwfaTLkdYGRngUx&sharer_shareinfo=2405440555dc49ab97350e1b5931f17c&sharer_shareinfo_first=2405440555dc49ab97350e1b5931f17c#rd)：核心论断是「Prompt 不是资产，Context 才是资产」——Prompt 只解决一次怎么问，Context 沉淀你的业务、规则、边界与品味；个人工作流是 1 个 Lead 加多个 Execute Agent，人从执行者变成系统设计者，最终导向 OPC——「一个人，拥有一家 AI 公司」。他自己总结的道就八个字：「养 Context，蒸馏知识，编排智能」。<span class="mention">@冷静的麋鹿</span> 掐指一算：「12 个字[旺柴]」。
