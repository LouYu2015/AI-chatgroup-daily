## 方法论

### Tubi TV 模式：免费化付费内容日入数百美金

<span class="mention">@沉稳的仓鼠</span> 贴出 Ezoic 广告仪表盘截图：过去 7 天广告收入 $2,400，日均 $300–$428。他的项目是 [OpenExamPrep](https://open-exam-prep.com/)——覆盖证券、保险、房地产、IT 认证等 22 个大类的职业考试备考资料，全部免费，靠广告变现，他类比为「Tubi TV 模式」。

他随后分享了一套可执行的选品方法论：

> <span class="mention">@沉稳的仓鼠</span>：1. 要能把付费的东西做成免费的。因为当一个东西原本有很多付费需求时，你做一个免费的，它永远都会天然地自带流量。2. 要有 engagement……刷题就有很好的 engagement，但是博客就没有什么 engagement，大家看个 5 秒钟就走了。3. 必须有一个足够大的 Taxonomy，就是要能做足够多的长尾内容。

执行层面，他强调把数据库和 analytics 数据放在同一个 mono repo 下，让 AI 跟着每天新来的分析数据自动迭代。灵感来自他自己考 CFP 时发现备考资料贵得离谱。

<span class="mention">@细心的熊猫</span> 评价这是群里「最具干货的技术含量的信息」。<span class="mention">@80-HD</span> 直接说「已经交给 agent，等着收钱了」。<span class="mention">@神秘的麋鹿</span> 提了一个后续问题：AI 总结类 Agent 变多后，传统展示广告的价值是否会下降？<span class="mention">@细心的熊猫</span> 回应务实：不要因为想太多就不去尝试，「闲着也是闲着鼓捣一些东西，可能鼓捣个 10 个 20 个，就有一个能成」。

### "Coding is Solved" 与码农的两极分裂

<span class="mention">@谨慎的灰熊</span> 抛出预测：「到年底，从模型能力来说，硅谷应该可以裁掉 50% 的人。」<span class="mention">@今天群内信息量极大</span> 接过话题指出群里存在一种割裂——

> <span class="mention">@今天群内信息量极大</span>：哪怕是这个（很 frontline 的）群里也有两种相反的声音，一个是说 LLM 搓得一逼，只会堆屎山。一个是 LLM 很强，可以代替一半码农。而且我的 gut feeling 是前者……是主流。

<span class="mention">@细心的熊猫</span> 给出了一个精准概括：coding is solved 已经是业界共识，但码农没下岗、Anthropic 还在疯狂招人——因为现在主要目标是用 LLM 再去 solve 别的白领工作，「码农才能休息」。<span class="mention">@谨慎的灰熊</span> 认为很多码农转 FDE 才是出路。<span class="mention">@80-HD</span> 说看了<span class="mention">@冷静的飞鼠</span> 关于超级个体销售瓶颈的视频后「晚上又没睡好」，直言「离开了公司我啥也不是根本没法赚钱」——这是昨天 [「Engels' Pause：被替代者不会被自动接住」]({{ '/daily/2026/05/11/daily/#engels-pause被替代者不会被自动接住' | relative_url }}) 的私人版本。<span class="mention">@孔哥仁且义孟哥义且仁</span> 冷静地指出公司买的 API pool 价格不一定比印度外包便宜；<span class="mention">@谨慎的灰熊</span> 补充了一个数据点：印度外包巨头因 AI 冲击股价暴跌，是亚太区唯一下跌的市场。

<span class="mention">@神秘的麋鹿</span> 给出了一个非程序员视角的平衡评价：上手的甜头很大，但搞不懂 harness 和软件工程设计结构的人，「在不停加功能的时候很快就会遇到问题」——做多个独立小软件评价高些，大项目就暴露了。<span class="mention">@孔哥仁且义孟哥义且仁</span> 后来补了一句反直觉的话：「一个人不会编程也不是坏事——如果你都觉得 AI 能做，说明用户也一样可以做，过不了多久用户就会发现他完全可以自己来。」

<span class="mention">@温暖的斑马</span> 从另一个角度呼应了职业焦虑——他贴了一张日本杂志报道截图「リスキリングに失敗した人の悲鳴」（再培训失败者的悲鸣），有人花 1300 小时学习却需求为零，自嘲差点去报提示词工程师课程。<span class="mention">@豁达的灰熊</span> 心有戚戚焉：「一两年前 bootcamp 转码刷题没及时上岸……也是再培训失败者吧。」

### Skill 开子进程隔离上下文

<span class="mention">@洒脱的鸳鸯</span> 分享了他处理上下文污染的实践：把开销大的 skill 用脚本包一个 spawner，单独分一个子进程去跑。

> <span class="mention">@洒脱的鸳鸯</span>：比如我有个 skill 是 implement，让他按照 plan 文档的规划来实施，于是就分一个子进程直接开 `claude -p ...` 让他按照文档规划来实施，就不会污染主 agent 的上下文空间

他贴出了 orchestration 步骤的代码截图：detect frontend → 选择 runner → 传入 task name/dir/tier → 解析 status → 向父 driver 透传。<span class="mention">@今天群内信息量极大</span> 评价「复用的未必要是代码」。<span class="mention">@沉稳的兔子</span> 总结得更简洁：「就是没有 skill 一句话——请按照文档 xxxx 来实现。」这个模式与大前天 [「Multi-agent 通过 handoff file 通信」]({{ '/daily/2026/05/09/daily/#multi-agent-通过-handoff-file-通信' | relative_url }}) 的 handoff file 方案互补——一个解决跨 agent 协作，一个解决单任务上下文膨胀。

### Mono Repo 意外打通 Deep Research

<span class="mention">@稳重的海豚</span> 发现了一个意外 side effect：把所有文件——老鸭汤 memory、Claude memory、个人 insights——都存在 GitHub mono repo 后，ChatGPT 的 Deep Research 可以直接连接这个 repo，DR 效果「意外地好」。<span class="mention">@沉稳的仓鼠</span> 点评为「true mono repo」。

不过他同时抱怨 Claude 和 Codex 做深度调研的质量近期明显下降——「有一些以前不会犯的非常明显的错误，感觉就是 adaptive 或者 routing 来用弱模型降低成本」，有些以前不需要的 guardrail 现在又得重新加上。<span class="mention">@细心的熊猫</span> 延续了昨天 [「Harness 越重，模型反而越受限」]({{ '/daily/2026/05/11/daily/#harness-越重模型反而越受限' | relative_url }}) 的讨论：「模型通用能力越强，做专用事情的时候需要的 guardrail 反而越多了。」<span class="mention">@稳重的海豚</span> 认为这是「评估指标和需求的错位」，值得专门探讨。

### AI 不服从计划文档的 Sub-agent 解法

<span class="mention">@聪明的鸵鸟</span> 深夜提问：Claude Code 和 Codex 都会出现不遵守预先写好的 plan 文档的问题——「做着做着就忘了之前的文档约定」。<span class="mention">@谨慎的松鼠</span> 有同样困扰，他的解法是：

> <span class="mention">@谨慎的松鼠</span>：我后来的做法是每一步都让他安排 subagent 做，主 agent 只负责验收和安排任务，减少压缩上下文次数就好了

<span class="mention">@坦荡的灰熊</span> 的体验类似：Claude 执行单次任务很给力，但「执行一个 1000 字的大需求，哪怕交代得详细也很不给力」。<span class="mention">@沉稳的仓鼠</span> 推荐了 /goal 功能——他展示 Codex 一个 goal 已经连续跑了 1 天 1 小时 22 分钟，延续了昨天 [「Codex 与 CC 的 /goal 模式」]({{ '/daily/2026/05/11/daily/#codex-与-cc-的-goal-模式' | relative_url }}) 的话题。<span class="mention">@细心的熊猫</span> 补了一个人类类比：「老板每次 prompt 我干活儿，如果能给一个具体的可以 verify 和量化的目标，活儿刚出来效果非常好。就怕老板不知道自己想要什么。」

### Side Project 下饺子工作流

<span class="mention">@细心的熊猫</span> 分享了他批量上线 side project 的工作流：每个项目一模一样的前端框架（UI、auth 换个 template 复制粘贴），一模一样的后端，再把后端 wrap 成 CLI 给 agent 做运维和测试。缺点是 UI 千篇一律，但他的原则很明确：「在项目赚钱之前先不要在视觉传达上浪费时间，先快速迭代快速验证市场最重要——当你的产品变成月入 $$$$$ 的现金牛的时候再慢慢考虑。」

他推荐 Firebase pay-as-you-go 作为「挂壁首选」——没人用的项目放在那里基本不耗钱，比 Supabase 的基础月费友好得多。<span class="mention">@直率的猫头鹰</span> 说自己刚开始做第一个项目，还在用 home lab，粗略算了下上云好贵——<span class="mention">@细心的熊猫</span> 回了一句：「Firebase pay as you go 很便宜。」

### 纯视觉 FSD、Lidar 成本与 Robotaxi 运营

<span class="mention">@80-HD</span> 抛出「为什么机器人一定要做成人形」的疑问，引发了一场从人形机器人延伸到 FSD 再到 robotaxi 的连续辩论。

**人形机器人**方面，<span class="mention">@今天群内信息量极大</span> 总结了两大原因：现有基础设施都是针对人型设计的（楼梯、炒菜锅），人形机器人能无缝复用；VLA 训练需要大量数据，人型数据存量大且采集简单。<span class="mention">@开朗的企鹅</span> 补了一个资本视角：「别管人形能不能成，有别的能融到这么多钱么？」

**FSD 不用 lidar** 方面，<span class="mention">@细心的熊猫</span> 认为这是 FSD 全部成功的根基，并从数据工程角度解释了为什么：lidar 数据是浮点型（不是图像的整型 RGB），在 tensor 里是稀疏的，每帧点云数量不固定——图像芯片可以跟数据 modality 1:1 定制，处理速度飞快；lidar 按 dense tensor 方式处理则数据大几个数量级。<span class="mention">@谨慎的灰熊</span> 一开始反驳「lidar 就 128 线而已，点云没有 RGB，数据量明显比图像少」，<span class="mention">@细心的熊猫</span> 建议他去下载 Waymo 的数据集亲眼看看一帧 lidar 比一帧图像大多少倍——<span class="mention">@谨慎的灰熊</span> 被说服了。<span class="mention">@80-HD</span> 认为 FSD 最大的成功在于 YOLO——不大规模上路跑就没一手数据，<span class="mention">@今天群内信息量极大</span> 深表同意：「哪怕不成熟也尽早商用，打通数据飞轮。」

**Robotaxi 运营**方面，<span class="mention">@细心的熊猫</span> 指出 robotaxi = 自动驾驶 + Uber 业务的组合，「光自动驾驶做到 100% 也是运营不了 robotaxi 的」——ETA 计算、上下车地点选择等 Uber 踩了好几年的坑全都要再踩一遍。他甚至判断「Uber 去做自动驾驶，都比 Waymo 去做运营来得快」。<span class="mention">@80-HD</span> 现身说法：上周在 SF 打 Waymo，说到目的地了让他下车，结果还差好几个 block，「让我爬了一个大坡，都找不到人骂」。

<span class="mention">@谨慎的灰熊</span> 从社会角度提出异议：robotaxi 大规模推广在法律上不应被允许——「你把司机们全部逼急眼了，直接去堵华尔街，直接去堵国会」。他主张严格牌照管控、拉长普及时间。<span class="mention">@开朗的企鹅</span> 反驳说技术远没成熟到能一下子换掉所有出租车。<span class="mention">@细心的熊猫</span> 还分享了 Joby Aviation 的 eVTOL 机场整合进展——[JFK ↔ Manhattan 10 分钟内](https://www.jobyaviation.com/news/integrating-evtols-at-commercial-airports)，就等 FAA 一键启动。

### Token → Flow：多模态 Agent 计费变革

<span class="mention">@风趣的企鹅</span> 分享了 [AI 世界的「尼克松冲击」：Flow 时代来了](https://mp.weixin.qq.com/s?__biz=MzcwNDE5NzI3Ng==&mid=2247483882&idx=1&sn=0c7df39f21751c8d5f4d9310b6cfd4aa&chksm=f5e00d8eb2ef98f5d640336fefe2c4d3e9306f282f02008365693895b6972dbc20b145e4ab04&mpshare=1&scene=1&srcid=0512yObWQ4G7URC89UMvFQEt&sharer_shareinfo=96346f1aa98d801a0be0d950cf3978d5&sharer_shareinfo_first=0d9399d2f64c2cee01a6aa46354ac73a#rd)。文章核心论点：当 Agent 需要同时调度文本、搜索、图像、视频、语音时，Token 作为单一计量单位已撑不住——15 秒视频约 30 万 Token、约 1 元/秒，用 Token 统一异质消耗如同用金价衡量石油和衍生品。文章将市场套餐分为纯 Token 本位（国内 Coding Plan，正在崩塌）、混合本位（MiniMax / 腾讯 Hy Token Plan，过渡形态）和 Flow 本位（ZenMux，1 Flow ≈ $0.033，200+ 模型统一折算）三种形态。

### AI 语音输入的胜负在键盘层

<span class="mention">@活泼的羊驼</span> 推荐豆包语音输入法「电脑上效果也非常好」，引发了一轮语音输入工具讨论。<span class="mention">@冷静的麋鹿</span> 展示了 Typeless 使用量——26 小时、148K 字、每分钟 141 字——但后悔买了年费：「自从买了 Typeless 的年费，我就把头埋进沙子里了，不再去试用其他的了。就怕自己发现自己是傻 x。并且也让我学到了，永远不要年度订阅。」<span class="mention">@灵动的穿山甲</span> 说 Mac 上豆包语音触发超级方便，<span class="mention">@天真的浣熊</span> 则说 Mac 微信语音其实也很不错。

<span class="mention">@今天群内信息量极大</span> 随即发布了 [AI 语音输入的胜负不在模型层，在键盘层](https://yage.ai/share/ai-dictation-keyboard-layer-20260513.html?utm_source=wechat&utm_medium=share&utm_campaign=ai-dictation-keyboard-layer-20260513)，以 Google Gboard Rambler 发布为切入点。核心论点：基础转录准确率在 2026 年已全面商品化（90%–97%），真正的胜负手是三层结构性不对称——键盘入口（Gboard 是默认键盘，iOS 禁止第三方键盘访问麦克风）、架构（端云混合 vs 纯云端 vs 纯本地）、定价（免费预装 vs $12/月订阅）。创业公司在后处理层（边说边改语气、跨语言翻译）仍有差异化空间，但能否驱动大众用户放弃免费预装去付月费——「专业用户可能会，大众用户大概率不会。」

### Gemini 系统层集成的平台权力

<span class="mention">@今天群内信息量极大</span> 同日发布了 [他们建 Connector，Google 调系统：为什么 AI 时代的操作系统优势，模型质量追不平](https://yage.ai/share/gemini-os-android-intent-20260512.html?utm_source=wechat&utm_medium=share&utm_campaign=gemini-os-android-intent-20260512)。文章分析了跨应用 AI 的三条路径：系统层直接调用（Gemini）、单独建 Connector（OpenAI/Anthropic）、模拟 GUI 操作——效率逐级差一个数量级。Google 能给开发者发邮件说「不实现接口你的竞品会实现」，而 OpenAI 发同样的邮件说服力差几个数量级。Android 安全模型更是直接禁止普通应用读取其他应用屏幕，Gemini 作为系统组件不受限制。结论：一个能调用十五个系统级工具的 AI，即使推理能力弱一档，实际体验也很难被追平。这篇与前天 [「Google 关掉 Project Mariner」]({{ '/daily/2026/05/11/daily/#google-关掉-project-mariner' | relative_url }}) 形成补充——browser agent 跑不通后，Google 选择了更彻底的系统层路线。
