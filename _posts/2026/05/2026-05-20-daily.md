今天最有深度的辩论是 coding agent 的核心价值到底在模型还是编排——<u>鸭哥大号</u> 坚持「只要问题足够复杂，这些 orchestration 都只是花拳绣腿」，<u>沉稳的兔子</u> 反驳说模型越强反而需要更明确的边界，<u>淡定的大象</u> 则用自建的 62 工具 coding agent 证明精准 tools 才是关键。最有故事性的是 <u>鸭哥大号</u> 转述的微软 AI Slop 整治会议——有人的 PR 被 5 人 reject 后直接把这 5 人从 reviewer 名单里删了，结果换来了更多 reject。Gemini 3.5 Flash 发布次日迎来用户端集体差评，<u>沉稳的仓鼠</u> 画了张漫画一锤定音：「快、谄媚、不聪明」；<u>直率的海豚</u> 的总结更绝——Gemini 2.5 竟然是巅峰。Meta 裁员今天正式落地，PM/DS 大量蒸发；SpaceX S-1 揭示了一套让罢免 CEO 在逻辑上不可能的投票权闭环。

## 方法论

### 模型 vs 编排：harness 该多紧

围绕 coding agent 的核心价值在模型还是编排，清晨爆发了一场多人辩论。

<u>鸭哥大号</u> 立场鲜明：

> <u>鸭哥大号</u>：显然模型才是最重要的，只要问题足够复杂，这些 orchestration 都只是花拳绣腿

他以亲身经验为证：之前用 Copilot SDK 做了一套 orchestration，GPT 5.3 时代还有用，到 5.4/Opus 4.6 之后发现没什么太大必要，「干脆清理了海量的 construction」。以前确保 agent 跑完 test 需要复杂的强制机制，现在只需要提一嘴。他分享了所有 repo 共享的 [Copilot instructions](https://github.com/vczh-libraries/Tools/tree/master/Copilot)——memory 分布式存储，有 job 做 multi-way merge。

<u>淡定的大象</u> 从工具层面反驳：模型不是不够聪明，关键是有没有足够精准的 tools。「精准 tools 即精准上下文」——好的工具能减少模型的无效 loop。做爬虫时 CC 自带工具不够用，做逆向工程更是如此。他分享了自己的 [Code Hacker](https://github.com/hackerlibs/code-hacker)——把 Claude Code 能力拆成 6 个 MCP Server（filesystem、git、code_intel、memory、code_review、multi_project），共 62+ 工具，亮点包括基于 AST + ydiff 的结构化 diff（能感知函数移动和重命名）和跨 repo 协同编辑，估计与 CC 的能力覆盖率约 85%。

<u>沉稳的兔子</u> 提出了第三种立场：模型越来越强，决策权越大，「反而需要更明确的边界」——直接对立于<u>鸭哥大号</u> 的「harness 越松」判断。

<u>优雅的荷兰猪</u> 补充说 Anthropic 内部也持宽松观点——模型强大后 harness 限制可以减少。<u>80-HD</u> 验证了同样的体感：以前搞了复杂的 orchestration，「现在只要简单提醒下用 subagent 就行了」。

<u>细心的熊猫</u> 还抛出了一个有意味的问题：「有没有一种可能，Codex 在 CC 源码泄露之后变好了？」<u>淡定的大象</u> 只回了「也有可能」。

### AI Slop PR 审查纪律

<u>鸭哥大号</u> 转述了微软内部会议：领导层专门反思公司内部「AI slop 病毒蔓延」，要求代码要好好写，「淹了 reviewer 对你们也没好处」。会上讲了个经典案例——有人频繁提交 AI slop PR，其中一个遭到 5 人 reject，此人的应对是把这 5 人从 reviewer 名单里删了，结果换来了更多 reject。领导表扬了「看不懂就 reject」的行为。<u>直率的海豚</u> 辣评：「这样的人就不要留在微软害人了，Meta 欢迎他。」

> <u>鸭哥大号</u>：绝对不要提交一些你们自己都不知道写了些什么的 PR

会后大家认为应该引入 AI 来检测 PR 的 AI slop rate——用 AI 查 AI slop。组里一位同事的评价也很扎心：觉得上面对 AI coding 质量盲目自信，「说什么 10x 就是 bullshit，再怎么快也不可能快 10 倍做出一个 V8」。

### AI 时代组织形态辩论

<u>今天群内信息量极大</u> 坦言老板/sales 做的事情更不能替代——跟客户聊天「不是不能做，但就是不享受」，有了 AI 在这方面也没觉得更容易。<u>淡定的荷兰猪</u> 认同：搞关系、build trust、让人觉得你靠谱能带来利益，还是需要人与人吃饭、刷脸。

由此延伸，<u>细心的熊猫</u> 提出构想：开发者和 sales 都是个体户，利润分成，没有雇员只有股东——不需要 perf review，不需要 PUA，「卖时间」变成「卖结果」。<u>鸭哥大号</u> 指出这就是「合弄制」。

<u>乐观的灰熊</u> 分享了 [郝景芳播客：把公司拆分之后，我感到无比的自由](https://www.xiaoyuzhoufm.com/episode/69cba329b977fb2c47bd6f55?s=eyJ1IjogIjYxZjQyMGM4MmNiZDdjMDE3NjYyZjNmZSJ9)——她把旗下四十多人团队拆成九个独立核算小公司，按贡献分配收入，管理成本降低，接近帕累托改进。AI coding 让她第一次感觉脑子里的想法有了直接落地的路径。

但反对声音明确。<u>随和的企鹅</u> 直接泼冷水：「纯纯搞笑。如果 micro company 是趋势巨型公司就不会有这么强的统治力了。去 org 化只是不会 org 的安慰剂。」<u>豁达的大象</u> 指出子公司之间合作和利润调剂更难。<u>幽默的犀牛</u> 也说有机会搞大的时候，小 org 搞钱慢。

## 工具

### Composer 2.5 vs Gemini 3.5 Flash 实测

<u>冷静的麋鹿</u> 用两个任务对比了 Composer 2.5（Cursor）和 Gemini 3.5 Flash（Antigravity），同样的 prompt。任务一（浏览信息做页面）：Gemini 真快，但展示和总结深度不如 Composer。任务二（模糊任务封装组件做 agent）：两者都完成，效果差不多，但 Gemini 反而慢了一倍——「七想八想」。

更有趣的是 Composer 2.5 的一个小插曲：它主动发现有个历史项目类似，说「我测试一下拿过来直接用吧」，三下五除二做完了——搞得 <u>冷静的麋鹿</u> 不得不重来一轮公平对比。Gemini 就傻乎乎从头开始。从实用角度看，这种主动性正是 Composer 2.5 的加分项。

<u>风趣的长颈鹿</u> 评价 Composer 2.5 比 2 好多了，「之前都得切换到 Claude 的 model 才敢用，现在用 Composer 2.5 也很舒服」。延续了 [「Cursor Composer 2.5 发布」]({{ '/daily/2026/05/18/daily/#cursor-composer-25-发布' | relative_url }}) 的讨论，这是首批详细实测体验。

### Opus 4.7 与 Codex 代码质量吐槽

<u>80-HD</u> 今天被 Opus 4.7 气到了：写了个冒泡排序（「连 sort 都不会调了」），还在被要求 stateless 的情况下反手加了个 map 做 cache。context window 才用到 50% 左右，不是上下文爆炸的问题。更奇怪的是，两三个月前用 4.6 做类似 feature 就没怎么大改。

> <u>鸭哥大号</u>：4.7 写代码就是不如 4.6，不要用了

<u>优雅的猎豹</u> 同感「CC 最近好蠢」。<u>鸭哥大号</u> 诊断了「stateless」instruction 为什么失败：这属于无效 instruction——你需要说清楚为什么要 stateless、要避免什么后果，而不是直接扔一个关键词。「AI 擅长的还是直来直去的东西，代码看起来跟描述需求的自然语言一致，效果就好。」<u>沉稳的兔子</u> 的做法是先给一个编程模型，让它照着写。

Codex 也不省心。<u>鸭哥大号</u> 做异步编程时发现 Codex「出的每一版代码质量都出奇的低，就好像它完全不知道什么是 synchronization」——结合此前 [「Codex 激进加锁的性能陷阱」]({{ '/daily/2026/05/18/daily/#codex-激进加锁的性能陷阱' | relative_url }}) 的经验，AI 在并发编程领域仍然是最大短板之一。

### Gemini 3.5 Flash 集体差评

延续前天 [「Google I/O 2026」]({{ '/daily/2026/05/19/daily/#google-io-2026' | relative_url }}) 的发布热度，Gemini 3.5 Flash 今天迎来用户端集体差评。<u>风趣的企鹅</u> 三字定调：「拉完了」——Antigravity 抄 Codex 没抄好，Flash「榜单两眼，做起来就是一个傻逼」。<u>活泼的羊驼</u> 认为软件根本不是重点，该关注的是 TPU 迭代、HBM4 供应链和光互联。

<u>直率的长颈鹿</u> 的实际体验很有画面感：思考时间巨久，然后出来一个完全不对的答案，连 prompt 都没理解清楚。<u>活泼的海狸</u> 补充了一个痛点：做前端 feature 规划，1 小时不到就把 $20 Pro 套餐的 quota 用完了，Reddit 和 YouTube 上大量用户反映相同情况。

<u>沉稳的仓鼠</u> 画了一张五格漫画精准概括：Google 推出 Gemini 3.5 Flash——「快、谄媚，但不聪明」。Benchmark 看起来 S++，实际体验远低于数据，跟 Gemini 3、3.1 一样的剧本。结论是「已经严重透支了公众对 Gemini benchmark 数据的信心——我不理解」。多位群友转发朋友圈，<u>冷静的麋鹿</u> 赞「这种方式好」，<u>神秘的企鹅</u> 说已经发了两条朋友圈。

### cmux 与 CLI Agent Orchestrator

<u>飘逸的仓鼠</u> 在群里搜索之前讨论过的多 agent 管理工具，找到了两个值得关注的项目。

[cmux](https://cmux.com/) 是基于 libghostty 构建的原生 macOS 终端应用，专为多 agent 场景设计：侧边栏垂直 tabs 显示 git 分支和端口信息，notification rings 在 agent 需要注意时亮起提醒，内置可编程浏览器和 socket API。免费、源码开放，Ghostty 作者 Mitchell Hashimoto 也关注了它。

<u>淡定的喜鹊</u> 分享了 AWS Labs 开源的 [CLI Agent Orchestrator](https://github.com/awslabs/cli-agent-orchestrator)（CAO），用 tmux 给每个 agent 分配独立会话做上下文隔离，通过 MCP 暴露 handoff/assign/send_message 三个编排原语，支持跨 provider 混合编排（如 supervisor 跑 Kiro，worker 跑 Claude Code）、定时触发和 CI 无头异步执行。自带 Web UI，Apache-2.0 协议。

<u>淡定的喜鹊</u> 自己目前的方案更简单：「Ghostty 开 N 个 Claude tab 然后 /rename 每个 session，差不多能用了。」
