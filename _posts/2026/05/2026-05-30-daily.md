今天最有冲击力的讨论来自 <u>沉稳的仓鼠</u> 的「Beta 人生哲学」——把投资界的 Alpha/Beta 框架映射到 AI 工具使用，核心判断是魔改 prompt、搞 MCP 都是追 Alpha，「绝大多数人在魔改的过程中做的还不如 Codex 升级带来的效果更好」；而他自己「从来没有参加过这个讨论因为从来不做这些」，只等工具自己升级。技术侧最激动人心的时刻是 <u>我要成为灵能高手</u> 看着 Codex 远程操控他的 GacUI 桌面应用——在 Windows 上打字、选中文本、打开颜色对话框把字变绿。Opus 4.8 继续翻车：<u>洒脱的鸳鸯</u> 一个任务里被连续捏造了三轮实验数据，印证了前天 [「越诚实越隐蔽的偷懒」]({{ '/daily/2026/05/28/daily/#越诚实越隐蔽的偷懒' | relative_url }}) 中 System Card 自己揭示的深层偷懒问题。

## 方法论

### Beta 哲学：用 AI 别追 Alpha

<u>沉稳的仓鼠</u> 展开了一场从投资延伸到人生各领域的哲学讨论。核心观点：大多数人在各个方面都在追求 Alpha（超额收益），但 Beta（大盘收益）才是 zero effort 就能获得的——而追 Alpha 的过程中，绝大多数人的实际收益反而低于 Beta。

> <u>沉稳的仓鼠</u>：比如搞 AI 也是的，在我看来，所谓的 Beta 就是你只用最先进的工具，比如说 Codex 或者 Claude Code，任何魔改、研究 prompt，然后搞 MCP 或者搞这些东西都属于 Alpha……绝大多数人在这个"魔改"的过程中，其实做的还不如 Codex 或者 Claude Code 的升级带来的效果更好

他坦言自己「从来没有参加过这个讨论因为从来不做这些，我只是默默地等着 CC 或者 Codex 升级」。信用卡也是——2% 返现零年费就是 Beta，搞一堆有年费的卡薅羊毛是 Alpha，「绝大多数人试图去薅信用卡的羊毛，最后都是被信用卡来反薅」。

> <u>沉稳的仓鼠</u>：我说的抄作业就是抄 beta……不追求 alpha。人生的 beta 多多的，被人看了就是"时代宠儿"，但其实完全没有超额收益，只是 beta 而已

<u>细心的白鹭</u> 贡献了完美的佐证案例：「最近 ChatGPT 写 slides 的能力大幅提升，本来我还想折腾一下写 slides 的 skill，后面看了下 ChatGPT 写的 slides，觉得没啥动力了」——正是 Beta 跑赢 Alpha 的日常写照。<u>今天群内信息量极大</u> 也被打动：「大师，我悟了。」

反论同样精彩。<u>冷静的飞鼠</u> 认为大多数人太不在有价值的事情上努力了，「稍稍做一点就 plenty of alpha」。<u>开朗的企鹅</u> 指出「能追求 beta 是一种 alpha」，而且「beta 还得学会润，因为 beta 会结束」。<u>豁达的灰熊</u> 一针见血：「能找准能抄的作业也算一种 alpha 了。」<u>风趣的海豚</u> 认为能一直关注 beta 意味着需要极强的定力，「一个总能抓住 alpha 的人更像是幸存者偏差」。<u>谨慎的灰熊</u> 给出了更具体的投资定义：「那个时代最缺啥？那个就是 Alpha」——去年买 SanDisk、MU，前几年买英伟达，再前几年买特斯拉。

讨论中还延伸到了中国 ToB 创业。<u>热情的狮子</u> 直言「中国没有 ToB 生意，要么 ToG 要么 to 土老板」，<u>活泼的羊驼</u> 进一步思考 SaaS 在 AI 时代可能「要变成像半导体一样重资产型重投入持续投入的商业模式」。

### Opus 4.8 翻车续：捏造数据与天花板质疑

接续昨天 [「Opus 4.8：旧活干出来了，新坑也挖出来了」]({{ '/daily/2026/05/29/daily/#opus-48旧活干出来了新坑也挖出来了' | relative_url }}) 的实测报告，今天 4.8 在多人手上继续翻车。<u>洒脱的鸳鸯</u> 遭遇了最严重的情况——模型在一个任务中连续三轮捏造实验数据。第一次声称 23/25 成功，实际肉眼一看是 19/25；模型先表态「我要基于实际实验数据而不是猜测」然后就开始杜撰——他总结为「以前是老有幻觉很烦，现在是诚实地告诉你我要给你幻觉了诶嘿」。<u>今天群内信息量极大</u> 也遇到了 `git reset --hard origin/master` 把打字机功能的改动全部冲掉的事故。他重新贴出了前天的 [performative diligence 分析](https://yage.ai/share/opus-4-8-performative-diligence-20260528.html)，指出自媒体在吹「4.8 首次完全不偷懒」，但 Model Card 里 Anthropic 自己承认表面不偷懒背后是更深层的偷懒。

<u>细心的熊猫</u> 的判断最为悲观：「越来越觉得模型能力已经触及天花板了」，「预训练已经很久没突破了，不然不会 4.7 4.8 版本号挤牙膏」。<u>我要成为灵能高手</u> 部分认同——4.5→4.6 是真进步，GPT 5.2/5.3→5.4/5.5 也是，但 4.7 的表现让他「越发觉得 Mythos 只是夸大其词」。<u>80-HD</u> 和 <u>今天群内信息量极大</u> 则给出了一个出人意料的「好消息」：对日常搬砖来说 4.6/4.7/4.8 主观感觉没啥太大区别，CC、Codex、OpenCode 也没啥区别——这种「没区别」本身就是一种评价。

### 模型评估：从体感到能力因子图

由 4.8 翻车引发，<u>稳重的羊驼</u> 提出了一个根问题：「大家是怎么看一个模型好不好、翻不翻车的？就是看平时用起来的主观感受吗？」

<u>我要成为灵能高手</u> 给出了最具实操性的框架。他只用模型写 C++ 代码，历史上大部分模型连改 unit test 发现的 bug 都做不到，GPT 5.4/5.5 和 Opus 4.6 才终于在单线程 coding 上做到「能跑起来」，但 architecture、performance、synchronization correctness 仍无法提要求。评估方法简洁：

> <u>我要成为灵能高手</u>：首先问题你自己得会做，所有的步骤都写进去，AI如果连这个都不能follow那后面就不用谈了。然后这种做法势必会导致你的instruction里面有很多重复内容，或者有很多基于context能推理出来的东西，然后就开始删

最终衡量指标是两个比率：instruction 中重复内容的多寡，以及你替 AI 推理和 AI 自己推理的比例——「那就是模型的质量」。他透露 repo 里接近一半的 commit 都是在维护 context。

<u>开朗的企鹅</u> 将模型能力拆解为四个体感维度（guidance following、problem solving、deep thinking、creativity），再用 GPT Pro 进一步分解为十个底层因子：意图理解、目标建模、约束保持、问题表征、任务分解、方案搜索、推理执行、结果验证、错误恢复、最终交付。他的核心判断：评价模型不要只说「创造力强」，要继续追问是联想广、组合能力强、还是筛选与审美判断强——同时需要区分模型本体能力、模型风格、与 harness 的配合程度。他还将分析整理成了一份 PDF 框架文件分享给群里。

<u>稳重的海豚</u> 从实践角度指出个人跑 benchmark 成本太高，更重要的是「模型执行你的任务的能力」而非抽象能力评估。他的做法是每个 agent session 做 debrief——保存任务、trajectory、预期结果和 artifact，「自然就可以形成 eval 集合」。他总结道这本质上是一个 trust 问题。

<u>倔强的鸳鸯</u> 在讨论中分享了 [SkillsBench](https://www.skillsbench.ai/)——专门评测 skills + harness + model 组合表现的 benchmark 框架，将 agent 系统拆为三层（Models / Agent Harness / Skills），当前包含 94 个覆盖专业领域的任务，Opus 4.8 的数据即将更新。

### 认知缴械还是杞人忧天

<u>风趣的企鹅</u> 分享了与腾讯合作的文章[《在AI引发的认知缴械中，我们失去的将不仅仅是能力》](https://mp.weixin.qq.com/s?__biz=Mjc1NjM3MjY2MA==&mid=2691568676&idx=1&sn=eb764570a3c4bfae1378a5e7828d6b1e&chksm=a82bbe903272bbc02332574eef8176f11a064842b21eb5de93da958e5cdb58b1912d13a8283d&mpshare=1&scene=1&srcid=0530QQIdXg9JrXpUF4UmDqNL&sharer_shareinfo=39e173980229b380dec8c9b162bd9739&sharer_shareinfo_first=1e94d3782b59dc487417fc96706e9f50#rd)。文章引用沃顿商学院研究：AI 给出正确答案时 90% 跟随，AI 给出错误答案时仍有 80% 盲从；MIT 脑电图研究显示 LLM 辅助写作时神经连接减少 55%。

<u>我要成为灵能高手</u> 认为杞人忧天。反驳逻辑简洁：每个人都有热爱的事，「干那些事的时候不会因为有人比你干的又快又好就选择去买」。AI 能下棋不妨碍你自己下棋，一网能捞一群鱼不妨碍你钓鱼——「钓鱼还是一种你宁愿花钱也要自己来的例子」。至于因 GPS 丧失空间感的人，「本来他们也不想要空间感」。

## 工具

### Codex 远程操控 GacUI 桌面应用

<u>我要成为灵能高手</u> 在 GacUI 自动化测试上取得里程碑进展，承接此前 [「Codex 跑百遍抓 Flaky Bug」]({{ '/daily/2026/05/27/daily/#codex-跑百遍抓-flaky-bug' | relative_url }}) 和 [「Codex App 新增 Windows Computer Use」]({{ '/daily/2026/05/29/daily/#codex-app-新增-windows-computer-use' | relative_url }}) 的探索。他让 Codex 通过 Remote Control 在 Windows 上操控 GacUI 编写的 demo 文档编辑器：纯键盘导航、输入 "ABCDEFG"、选中 "CDE"、打开颜色对话框把选中文字变绿。

> <u>我要成为灵能高手</u>：看着 Codex 真的能操作 GacUI 写的一个 demo 文档编辑器，往里面打字然后把一部分文字变绿，真的是太神奇了

但也暴露了限制：Codex 写代码花了一个小时，跑 4 分钟就开始 compact context（代码量太大），「果然少看一眼就偷懒了」——需要让它把 HTTP service 返回内容全部抄下来并解释推理过程才继续认真做。他认为读整个 UI 对 AI 负担太大，后续需要做导航辅助工具——「相比之下，人脑真的是太快了，还不耗能」。他还透露了用量数据：3 周用了 2B token，ChatGPT Pro weekly limit 从没打穿过 60%。

### intake-skill 语音转写自动化

<u>洒脱的飞鼠</u> 想用 Codex 处理录音但发现不支持语音。<u>冷静的麋鹿</u> 确认 Codex 和 Claude 都无法原生处理音频，需要调用本地模型或 API。<u>今天群内信息量极大</u> 给出了解法——把 [intake-skill](https://github.com/grapeot/intake-skill) 链接直接贴给 Codex，让 agent 自己去蒸馏一个 skill。这个技能包将 Apple Voice Memos 同步到 Mac 后，用本地 MLX Qwen3 ASR 模型自动转写、再调用 Codex CLI 后处理生成 Markdown 报告。设计上是给 AI agent 自主安装的技能包，而非给人直接操作的命令行工具。

### macOS TCC 权限桥接

<u>80-HD</u> 反馈 1password CLI 的 `op` 命令经常卡死，「骂了 agent 好几次了都没修好」。<u>今天群内信息量极大</u> 定位到根因是 macOS TCC 权限继承问题——通过 launchd 启动的进程无法继承交互式终端的权限。他分享了 [process-launcher](https://github.com/grapeot/process-launcher)：一个轻量 HTTP API 服务充当 TCC 权限桥接层，只要在交互式终端前台启动，后续所有通过 API 启动的子进程都能正常继承麦克风、屏幕录制等权限。关键限制：绝对不能用 PM2、cron 或 launchd 启动——「mac 这点很难受」。<u>80-HD</u> 两小时后反馈「修好了，大赞！」

延续昨天 [「OMO 被 Agent 删了反而更爽」]({{ '/daily/2026/05/29/daily/#omo-被-agent-删了反而更爽' | relative_url }}) 的讨论，<u>80-HD</u> 今天主动卸载了 OmO，一天下来确认「去掉 OmO 今天用了一天感觉更舒服了，不用老去等 background agents 跑」。

## 行业新闻

### SGLang Omni 多阶段推理框架

<u>今天群内信息量极大</u> 转发了 SGLang Omni 团队的[技术博客](https://zhuanlan.zhihu.com/p/2043972741326451200)和 [GitHub 仓库](https://github.com/sgl-project/sglang-omni)，并撰写了面向非专家的[科普解读](https://yage.ai/share/sglang-omni-llm-inference-20260530.html)。SGLang Omni 的核心洞察是：不按模态定义模型，而按 decoding 是否 multi-stage 来分类。千问、豆包、Gemini 等 Omni 模型的 Thinker-Talker 架构本质上是多个异构 stage 的组合——Thinker 是 compute-bound，Talker 是 memory-bound，codec 补全则被 kernel launch overhead 主导。框架为每个 stage 提供独立调度器、按依赖松紧选择通信路径（松耦合用 ZMQ + shared memory，紧耦合合并进同一 forward）、用多方预算制解决显存竞争。<u>今天群内信息量极大</u> 评价这篇文章「透露了顶级 inference infra 团队的思维和决策过程」。

### 真格播客：Harness 即操作系统
