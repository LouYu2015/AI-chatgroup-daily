## Claude 配额政策双变

### Agent SDK 独立计费

<u>80-HD</u> 收到 Anthropic 邮件通知，<u>沉稳的白鹭</u> 随后贴出邮件截图：自 6 月 15 日起，Max 5x 用户每月获 $100 Agent SDK credit，覆盖 `claude -p` 及所有基于 Agent SDK 的第三方工具。用完后转入 extra usage（可手动开关），subscription limits 仅保留给 Claude Code、Claude Cowork 和 chat 的交互式使用。

### AI 行业在找新指标：Token 之后是什么

<u>今天群内信息量极大</u> 发布 [AI 行业在找一个新指标](https://yage.ai/share/ai-metric-proxy-search-20260513.html?utm_source=wechat&utm_medium=share&utm_campaign=ai-metric-proxy-search-20260513)。核心论点：Token 是输入指标，衡量消耗而非产出，天然倾向被刷高——亚马逊和 Meta 内部已出现员工让 agent 跑无效任务以抬高使用量。两个候选替代方案：Salesforce 的 AWU（Agentic Work Unit，数计件：完成一个可验证任务算一件，失败不收费）和百度的 DAA（日活智能体数，数人头）。计件更接近真实产出但面临粒度问题——客服 agent 回答问题和代码 agent 修 bug 算同一「件」，价值密度差十倍；数人头更简洁但「活跃」不等于「产出」。这与之前 [「Tokenmaxxing：Token 消耗量成为新 KPI？」]({{ '/daily/2026/05/09/daily/#tokenmaxxingtoken-消耗量成为新-kpi' | relative_url }}) 讨论的 metric 被 game 化问题一脉相承。

<u>敏锐的兔子</u> 提出了一个反向用法：token 消耗量可以用来量化部门墙和沟通摩擦成本。<u>温暖的飞鼠</u> 遗憾道「要是提前一周看到这个就好了」——他们的 roadmap 已经定了数计件，但文章的框架更能抓到要害。

## 方法论

### Plan Drift 解法：文档锚点与心跳检测

昨天 [「AI 不服从计划文档的 Sub-agent 解法」]({{ '/daily/2026/05/12/daily/#ai-不服从计划文档的-sub-agent-解法' | relative_url }}) 中 <u>聪明的鸵鸟</u> 提出的 plan drift 问题今天引来多个新解法。他补充了具体场景：通过 CC 控制仿真软件 A 和 B 做迭代——每步 A 出结果喂给 B，B 做多变量 sweep 后返回分析，20 次迭代后进入下一轮，B 的设置需要修改。CC 忘掉的正是两轮之间 B 的设置修改——尽管 plan.md 里写得明明白白。

**<u>孔哥仁且义孟哥义且仁</u>** 分享了他在 Copilot 上的实战方案：让 AI 一边执行一边维护一份调查文档，instruction 写在最开头，每个假设的验证结果也追加在最开头——AI 每次读文件都会重新吃一遍 instruction。他开源了完整的 [investigate.prompt.md](https://github.com/vczh-libraries/GacUI/blob/master/.github/prompts/investigate.prompt.md)，定义了六步自主调查工作流（构建测试 → 复现确认 → 分析源码 → 逐一尝试修复方案 → 代码审查），全程 DO NOT ASK ANY QUESTION。格式设计的关键技巧是留 anchor——描述插入点时同时说明上下各是什么，「永远不会格式错乱」。

> <u>孔哥仁且义孟哥义且仁</u>：没有被 CC/Codex 惯坏的 Copilot 用户实用小技巧

**<u>稳重的海豚</u>** 在他的 gehirn.ai 中实现了「plan drift detection」：预先写好 plan 和 outcome，执行时让 agent 在 heartbeat 节点自动检查是否偏离。他截图展示了 pmai-assistant 的 commander 界面，强调「这个东西在于你必须要最开始定好你的 outcome 是什么」。

**<u>认真的荷兰猪</u>** 从 context infra 角度切入：agents.md / claude.md 在 compact 时会被重新注入，只要在里面指引 AI 读对应的 checklist 文件即可。他也发现 skill 命中率和个人适配度有关——别人的老鸭汤 skill 拿来用「有些地方不能直接用，也开始理解为什么应该蒸馏自己」。

**<u>直率的鹦鹉</u>** 从模型层面泼冷水：所谓 1M 上下文的模型真正有效的就 200K 左右，「都是塞进模型之前给你筛一遍，丢的概率还是不小的」。<u>飘逸的狮子</u> 体感类似：CC 超过 85% context 就不太稳定。

**<u>80-HD</u>** 的经验是装了 oh my OpenCode 后体验明显改善——「omo 经常会自动触发 subagent」。他还总结了一条心法：「就是要多当反思怪，没事就问问为啥没按照想法来，然后改进下。」

### DeepSeek 深度写作与模型分工

<u>今天群内信息量极大</u> 展示了他用 DeepSeek 驱动的两个内容项目：[GuideMe.city](https://guideme.city/)（用建筑和工程讲城市历史，覆盖 62 座中国城市、超三千个地点的深度文章）和 [Guide Me Brand](https://yage.ai/share/brands/)（品牌策略与商业史，已完成万宝龙、徕卡、哈苏、爱马仕等十余品牌的机制节点分析）。他指出这本质上是「真·deep research 工作流」，DS 写文章「有深度有文笔」。<u>乐观的灰熊</u> 证实 DS 3.2 在 OpenRouter 创意写作排行榜上「超级断档领先」。

<u>冷静的麋鹿</u> 截图展示了批量工作流的规模——Opus 1M context 正在处理 449 条任务，进度 335/449，5 分钟约 43 条。他感慨文字类任务比执行类「烧 token 猛得多」，「很容易开多 subagent 并且跑起来没边，就很爽」，没事就找点陈年老文档来整理归类，「虽然感觉也不见得用的上，但是这种任务就让人很过瘾」。

<u>今天群内信息量极大</u> 随后梳理了自己的模型分工策略：执行类任务交给 Codex，brainstorm / 写文章 / 做分析用 DS Pro，Claude 的强项在写作和分析。他特别吐槽 Claude 执行时「老向上管理——做了两步停下来问，你看看我做的怎么样？要不要调整？」——不是权限卡住而是主动请示，「烦死了」。Codex 则「开箱即用，特别努力」。不过<u>80-HD</u> 现身说法了「特别努力」的副作用：让 Codex 清理一个旧工具，它搜到 `.openclaw` 文件夹后顺手删了——还好有备份。

<u>今天群内信息量极大</u> 也分享了 [DeepSeek 官方的 Claude Code 对接配置指南](https://api-docs.deepseek.com/guides/agent_integrations/claude_code)——三步即可把 Claude Code 的后端替换为 DeepSeek API，是目前配置成本最低的入门路径。<u>务实的灰熊</u> 反馈「V4 Flash 跑 CC 真是比 Pro 丝滑很多」，<u>天真的大象</u> 也试了 DS 接入 CC，「感觉速度还可以」。

### AI 用多了简单事反而变慢

<u>务实的灰熊</u> 坦言一个反直觉的变化：改一个简单参数明明手调很快，现在却倾向于让 AI 来做，「然后效率低了好几倍」。<u>稳重的海豚</u> 深有同感。<u>80-HD</u> 则表态更决绝：「手写是不可能的，这辈子都不能手写了。」<u>孔哥仁且义孟哥义且仁</u> 的建议是「需要找点别的事干」——不能让大脑频繁切换 focus。这与前天 [「AI 导致失眠：最大变量是晚上最后一次用 AI 的时间」]({{ '/daily/2026/05/11/daily/#ai-导致失眠最大变量是晚上最后一次用-ai-的时间' | relative_url }}) 揭示的 AI 使用习惯改变异曲同工。

## 工具

### HAPI：手机远程操控 coding agent

<u>冷静的麋鹿</u> 分享了 [HAPI](https://github.com/tiann/hapi)——一个开源项目，支持从手机或浏览器远程控制本地运行的 Claude Code、Codex、Gemini CLI、OpenCode 等会话。核心设计是「包裹而非替代」：在原有 terminal 会话外加一层远程访问层，保留快捷键和肌肉记忆，切换到远程模式不丢 context。实用功能包括 AFK 审批（离开电脑时手机一键同意 agent 操作确认）、语音控制和 Workspace Browser。连接通过 WireGuard + TLS 端对端加密，也支持 Cloudflare Tunnel 和 Tailscale 自托管。

### 豆包输入法 Mac 版正式上线

<u>严谨的长颈鹿</u> 分享了 [豆包输入法 Mac 版上线的详细评测](https://mp.weixin.qq.com/s?__biz=MzIyMzA5NjEyMA==&mid=2647682201&idx=1&sn=57321ea63b1ad5839bb682670c764d2a&chksm=f12599bd5d8cd40d30eb2db87776a9fee9f4793342ebae512454bcbe1a5d925f70239aea1a6d&mpshare=1&scene=1&srcid=0514KRyw2z3WUjAVpZnIAJH4&sharer_shareinfo=f649d35d94bdbeeff20e103b3e3fbc6a&sharer_shareinfo_first=06d0f07c4293f5700e8ef82eb2e355f4#rd)，免费使用，AI 语音流式实时输出、延迟极低。文章强调语音 200–350 字/分钟 vs 打字 40–90 字/分钟的速度差距，更关键的是语音来不及自我审查反而能给 AI 输出更充分的上下文——作者第一次用语音给 Claude 描述项目需求，三分钟说了约 800 字，是打字永远写不出的长度。<u>活泼的羊驼</u> 同时提到「Typeless 有键盘了」——延续了昨天 [「AI 语音输入的胜负在键盘层」]({{ '/daily/2026/05/12/daily/#ai-语音输入的胜负在键盘层' | relative_url }}) 的话题。

## 闲聊花絮

### GPT Image 2 vs 迪士尼法务

<u>今天群内信息量极大</u> 尝试用 GPT Image 2 为小孩生成 Elsa 的黑白刻章图。GPT 的 reasoning 暴露了一条内部规则：「we can transform user-provided copyrighted content if edited and requested by them」——理论上可以处理用户上传的版权内容，但实际上仍然不生成任何 Elsa 相关图像。让它「弄个类似的原创角色也行」，直接被以「similarity to third-party content」拦下。

转战 Gemini 更惨：先是输出一大段文字分析然后试图调用 `dalle.text2im`（连自己的工具名都搞错了），<u>今天群内信息量极大</u> 怒骂「不要嘴炮，你他妈倒是生成图片啊」后终于触发了图片生成——Prohibited content。

> <u>今天群内信息量极大</u>：迪士尼法务真牛逼

<u>孔哥仁且义孟哥义且仁</u> 说 GPT Image 2 最近整体变得过于敏感，经常需要安慰它：「我就是做来自己玩的，差一点没关系」，或者干脆不说角色名——「问就是我画的」。<u>今天群内信息量极大</u> 最后感叹，生成出来的「也不像 Elsa，看着像 AI 主动规避、根据特征二创出来的原创角色」——不过「糊弄，啊不是，满足小孩，好像也是一条路」。

<u>天真的浣熊</u> 贴了一张「优秀校友 20 亿 Token 捐赠仪式」的截图。群友迅速算账：<u>今天群内信息量极大</u> 算出全校师生共享每人约 20 万 token；<u>稳重的海豚</u> 嫌少——「什么玩意，两天就造没了」「至少也得两千亿才拿得出手」。<u>沉稳的仓鼠</u> 用实际数据补刀：CC 的 coding plan 开 Opus 大概 7 亿/月，20 亿「一天 1B 刚好用两天」。<u>天真的浣熊</u> 指出「20 亿正好是 2B」——用 Qwen 3.5 0.7B 那确实是个数。<u>随和的飞鼠</u> 的比喻最到位：「颇有点信用卡积分的感觉，瞧着巨多，一算才一点点。」
