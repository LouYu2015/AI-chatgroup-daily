今天最值得细读的是 <u>今天群内信息量极大</u> 对 Dynamic Workflow 的[深度解读](https://yage.ai/share/claude-code-workflow-determinism-20260528.html)和十几次实测总结——结论出人意料：和 Oh My OpenCode 的 multi-agent 体验「很像」，十分钟就跑完了但只做了最简单的部分，「好敷衍啊，快倒是特别快」。<u>冷静的麋鹿</u> 的初体验更直接：「大几十个 agent 一起发动，什么 token 能挡得住这种薅法儿。」与此同时 <u>细心的熊猫</u> 在 Opus 4.8 上获得了与 Workflow 无关的惊喜——4.7 搁置的逆向任务被 4.8 秒杀，「果然还是得等模型进步，远远比自己努力来的可靠」。行业侧最值得读的是 AI 短剧产业分析：制作成本归零后利润没流向创作者，渠道定价权碾压一切。闲聊侧最精彩的是一场从日本 AI 报警事件延伸出的奶爸育儿大讨论，<u>80-HD</u> 的「两分钟微波炉玻璃盘事件」承包了群里一整个早上的笑点。

## 方法论

### Dynamic Workflow 实测：快但敷衍

接续昨天 [「Dynamic Workflows 与 ultracode 模式」]({{ '/daily/2026/05/28/daily/#dynamic-workflows-与-ultracode-模式' | relative_url }}) 的首日体验，<u>今天群内信息量极大</u> 今天发布了 [Claude Code Dynamic Workflow：确定性边界画在了哪里](https://yage.ai/share/claude-code-workflow-determinism-20260528.html)，并用 VoiceFlow Android 移植任务做了压力测试。

文章剖析了 Dynamic Workflow 的三层架构：控制流走过程确定性（由 Claude 生成的 JS 脚本锁定 DAG 执行顺序）、执行层走结果确定性（subagent 自主决定工具和策略）、验证层用多个独立 agent 交叉验证避免同源偏差。真实案例是 Bun 的 Zig→Rust 迁移——75 万行代码、四条 workflow、十一天完成。文章特别指出了边界：workflow 脚本本身由 Claude 生成，有缺陷的脚本会可靠地执行一个有问题的计划；验收标准仍然用自然语言写，标准写偏了流程再严格也没用。

<u>冷静的麋鹿</u> 的初体验印证了 token 消耗之猛：

> <u>冷静的麋鹿</u>：卧槽，这东西就是个魔鬼啊，我刚试了一下。大几十个agent一起发动，什么token能挡得住这种薅法儿

<u>沉稳的仓鼠</u> 评价「解决了 token 用的太少的问题」。<u>冷静的麋鹿</u> 说结果不错但成本「比调 GPT Pro 的 API 还吓人」。<u>80-HD</u> 指出了设计上的尴尬：「如果追求确定性就写个脚本，如果追求智能就让 AI 全做完，感觉这个两边占一半」，而且做成 slash command「很不 AI native」。<u>博学的老虎</u> 类比企业 GPU 利用率注水：「GPU 闲置，为了给领导汇报，写个脚本跑下，然后说 GPU 使用率很高。」

<u>今天群内信息量极大</u> 用 VoiceFlow 移植做了更系统的测试。预期一两个小时的任务十分钟就跑完了，但「只是把最简单的东西做完了，后面复杂的大头它一个都没做——没 test，只写了 library 也没写 app，也没集成」。十几次 workflow 下来，他的总体结论是体验和 OMO 很像：

> <u>今天群内信息量极大</u>：它都是总分总的结构，spin up 一大堆 sub-agent 去独立地干活，干完活再汇总进行 verification 和 testing。

两个理论差异——DAG 替代严格 barrier 结构、开 subagent 更 aggressive（OMO 开 4 个的场景 Workflow 开 10 个）——「到底都有用我也没有太明显的感受」。结论是要「吸收它的思想，蒸馏到我们自己的工作流里，而不是说无脑用这个 feature 本身」。<u>80-HD</u> 随后在老鸭汤上也跑了一轮 Dynamic Workflow，分享了编排记录文件。

### Opus 4.8：旧活干出来了，新坑也挖出来了

<u>细心的熊猫</u> 报告了一个令人振奋的发现：之前在 4.7 上反复尝试各种方案都搞不定的逆向任务，4.8 直接秒杀。模型自己推翻了此前多轮对话中积累的错误结论——什么「register is human-only」「isTrusted wall」「behavioral score」全错了，实际只是一个自动化的 two-POST 链路。他感叹「它终于学会自己设计实验跑通了」，接着补了一句金句：「果然还是得等模型进步，远远比自己努力来的可靠。」<u>80-HD</u> 秒接：「活没干好，那就先等等。」

但 4.8 也暴露了新问题。<u>今天群内信息量极大</u> 发现它在 trivial 选择上会停下来反问——比如写语音 App 时问「真机还是模拟器调试」，选项 B 自己都注明了「模拟器没有麦克风权限，调试不了」：

> <u>今天群内信息量极大</u>：那这不废话吗？你自己都知道模拟器调试不了你还来问我？就感觉找了借口把工作停下来。

<u>稳重的海豚</u> 有类似经历，解法简单粗暴——骂它「你自己能解决的问题，不要来烦我」，之后模型就不问了。<u>温暖的斑马</u> 精准类比：「对 12 岁的娃刚进入青春期的时候让他干个家务活，就是这样子。」这与昨天 [「越诚实越隐蔽的偷懒」]({{ '/daily/2026/05/28/daily/#越诚实越隐蔽的偷懒' | relative_url }}) 中 System Card 揭示的「performative diligence」高度吻合——找借口让工作停下来也是一种偷懒。

<u>80-HD</u> 踩了更直接的坑：4.8 幻觉出一个不存在的 config，他没仔细看 PR 就 merge 了，直接造成了 incident。<u>倔强的鸳鸯</u> 则发现 4.8 经常随机输出日文和繁体——一段中文提问的代码分析回复中夹杂大量日文术语（「サブクラス化」「切り詰め」等）。

### OMO 被 Agent 删了反而更爽

<u>今天群内信息量极大</u> 发现自己本地的 Oh My OpenCode 插件不知被哪个 agent 给删掉了——但最近用着反而更爽，「常用的那些功能在现在的 OpenCode 里面全都有，感觉那屌插件带来的只有一些特别诡异的 bug」。

<u>低调的北极熊</u> 说自己「下载第一天就卸载了」。<u>沉稳的兔子</u> 更直接：「我现在都去掉了，因为都 tm 添乱。」<u>80-HD</u> 反馈「OMO 用起来比原生的慢很多」。但 <u>谨慎的树懒</u> 持不同意见——「原生的好像思考深度不够，最近用 DeepSeek v4 pro + OMO，感觉比 Sonnet 4.6 强。但就是慢。」

<u>活泼的羊驼</u> 给出了系统评估方法：体感对比（有 OMO vs 无 OMO 同时跑项目）、舆情调研（让 agent 抓 Reddit/Twitter 反馈）、迭代追踪（OpenCode 是否已把 OMO 有价值的部分融入原生功能）。核心判断是「好项目根本不差这一时半会的领先，差距很快就会被抹平。最重要的是谁拥有用户，谁能把这个闭环跑起来」。这呼应了前天 [「Skill 周期性瘦身与 tare 工具」]({{ '/daily/2026/05/28/daily/#skill-周期性瘦身与-tare-工具' | relative_url }}) 的洞察——不止 skills，连 harness 插件也需要定期清理。

## 行业新闻

### AI 短剧的渠道定价权

<u>今天群内信息量极大</u> 发布了 [AI 短剧的中国实验：谁在生产成本归零后赚到了钱？](https://yage.ai/share/ai-micro-drama-profit-chain-20260528.html)。核心发现：一季度全国上线微短剧约 12.8 万部，AI 制作占比超 95%，制作成本从 150 万降到 30 万以下，海外制作费从 3000 元跌到 300 元——但利润没有流向创作者，而是直接涌入了平台广告系统。红果将 AIGC 短剧分成比例降到原来的约 1/20。

关键在于创作者的整个生产闭环被锁在同一家公司：用即梦生成、在抖音买量、在红果分发、剧本来自番茄小说——没有替代渠道就没有议价能力。Sora 在消费者市场存活不到一年半就关停（全球应用内收入仅 140 万美元），而 Seedance、Kling、Veo 3 成功的共同特征是渠道在先：快手 MAU 超 4 亿，Kling 一季度收入 6.5 亿元同比增长超 300%；Veo 3 直接嵌入 YouTube Shorts 创作流程，工具与分发距离为零。顺序是渠道、品类、工具，不是反过来。

结论超越短剧：「任何 AI 让生产成本骤降的行业，如果利润结构原本就向渠道倾斜，降本只会让渠道抽水抽得更快。成本归零不是解放，是加速。」这与此前 [「生成在贬值，采用在升值」]({{ '/daily/2026/05/26/daily/#生成在贬值采用在升值' | relative_url }}) 的判断一脉相承。

### Agent 水墨英雄团与文言诗

<u>优雅的仓鼠</u> 分享了一篇关于给 agent 取名的文章，论证在生产力场景给 agent 命名为什么有用。<u>稳重的海豚</u> 晒出了自己的 agent 团队面板——九位水墨风格的「员工」：@athena、@jake、@sensei、@einstein、@alfred、@warren-buffett、@feynman……「最近团队又扩招了。」<u>聪明的蜂鸟</u> 联想到文明 6 里的伟人系统。<u>严谨的长颈鹿</u> 开始报收益：「居民满意度 +3，生产力 +9，粮食产出 -2。」

另一边，<u>我要成为灵能高手</u> 截图展示了 agent 输出的文言体注释——「墨规新立纸生香，长事功成缓短章。莫笑雕虫无气力，他年一鉴验兴亡。」<u>安静的鸳鸯</u> 问：「这是用文言省 token 吗？」
