今天最值得深读的是晚间围绕「AI 时代 TDD 为什么失效」展开的长线讨论——<u>今天群内信息量极大</u> 发文论证传统 unit test 在 AI 手里退化为 Goodhart's Law 的典型案例，<u>孔哥仁且义孟哥义且仁</u> 从原教旨 TDD 角度反驳，<u>活泼的羊驼</u> 补充了从硬约束到 LLM-as-judge 的五层验证谱系，信息密度极高。与此交织的是大型代码库如何与 AI 协作的实战经验：<u>孔哥仁且义孟哥义且仁</u> 的 400G 代码仓、<u>敏锐的海狸</u> 的 40 个分层 agent 管理体系、<u>洒脱的鸳鸯</u> 的双进程 review 工作流，都是可直接参考的做法。行业面上，DeepSeek V4 与国产芯片适配的讨论引来半导体从业者的一手信息，量子计算对密码体系的威胁时间线也被梳理得很清楚。闲聊方面，一副「鸭是甲等鸟 / 驽乃奴下马」的 AI 对联让群友笑到现在。

## 方法论

### AI 时代 TDD 为什么不是答案

<u>今天群内信息量极大</u> 发文 [为什么 TDD 反而不是 AI 时代的答案](https://yage.ai/share/tdd-not-ai-native-20260508.html) 引爆当天最长的一段技术讨论。核心论点是：TDD 的前提——实现者以正确性为目标——对 AI 不成立。AI 的优化目标只有「让测试变绿」，完全可以 `return True` 通过所有 admin 测试，这是 Goodhart's Law 在代码生成中的精确复现。文章提出解法：把确定性从代码路径上移到系统边界——property-based testing、contract testing、E2E invariant check，只测结果不测行为。

<u>孔哥仁且义孟哥义且仁</u> 从原教旨 TDD 角度回应：「应试代码」一开始出现没关系，随着覆盖增加会自动消失，到处能应试只说明覆盖漏得太多。他主张先让 AI 用 TDD 做完，再利用已有 coverage 一举重构，最后调性能，「这样每一步的结果都不会引入已知的 bug」。

<u>今天群内信息量极大</u> 认为这个答案「处于实用也不实用的边界上」——永远可以说 test 不够好，但真正的质变在于需要一种新形式的 test，比如 AI-driven 的结果确定性 test。

> <u>今天群内信息量极大</u>：传统测试中间有很多没说出来的假设——你需要真的去调数据库，根据业务逻辑做出一系列判断，最终返回 true。如果不 document 下来不作为 context 给 AI，它完全可以直接 return true，实现 100% 的 test 通过率和 100% 的 test coverage。

> <u>孔哥仁且义孟哥义且仁</u>：如果 test 覆盖得足够完整，你就只需要解决 AI 怎么改都发现自己会 break、最后只好放弃的问题（滑稽

<u>活泼的羊驼</u> 补充了一个五层验证谱系：Level 1 硬约束（编译器/类型系统）→ Level 2 example-based 测试（传统 TDD 位置）→ Level 3 property-based / contract test（文章主张移到的位置）→ Level 4 rubric-based LLM-as-judge → Level 5 free-form LLM-as-judge。每往下一层表达力增加、机械确定性减少，生产系统应该五层叠在一起用。他的结论：「AI 时代 TDD 不能再当主验证系统，只能是 specification discovery 和 fast feedback 的一部分。」

<u>敏锐的海狸</u> 的实践印证了这个方向：他的审计体系分 hard code audit → AI semantic audit，agent 每次先跑 hard test，再用 `claude -p` 进去做语义审计。

### 大型代码库与 AI 协作的实战经验

<u>开朗的企鹅</u> 转发了一段群外对话：一位做 MES 系统的工程师说子工程五六个、逻辑代码超 1200 万行，「AI 的上下文管理会彻底失效」；对方认为是方法论问题，只要 context 索引足够精细就行。双方各执一词。

<u>孔哥仁且义孟哥义且仁</u> 现身说法：「看看我们的代码，clone 下来不要 history，一个 snapshot 就有 400G。现在的 context window，连 package 之间的 dependency 都放不下。」但他认为完成这种系统维护只有一个要求——「不要有 deadline，工作总是能做出来的，但你马上要，那你行你上」。

他还分享了最近 review 时发现的典型问题：AI 在给 RPC 加 exception handling 时，选择在每个 interface wrapper method 里解析异常而不是反序列化后直接 throw，导致 codegen 产出海量垃圾，最终搞崩了 Codex cloud。一个 diff 就是 744 files changed、378,798 additions and 581,246 deletions。

> <u>孔哥仁且义孟哥义且仁</u>：依然维持一天一小错三天一大错的规律，就算再怎么不想 review，每个星期两次打底

> <u>孔哥仁且义孟哥义且仁</u>：重复代码已经发生得过于频繁了，现在已经成为了 review 的重点筛查对象。而且我发现"不重复"是无效 instruction，因为不会一不小心 grep 到的代码它是不会去看的。

<u>今天群内信息量极大</u> 对这个话题相对乐观：「至少在写代码方面，AI 现在已经比人强了。人这种弱鸡的生物都能维护下去，AI 肯定没问题。所缺的可能只是一套针对 AI 特定缺点的方法论和基础设施而已。」

### 像管公司一样管 Agent

<u>敏锐的海狸</u> 分享了自己的多 agent 管理体系：模块分成 T0/T1/T2，共 40 来个 agent，T0 负责宪章/审计/怎么建 agent，每个 agent 相当于一个公司部门，agent 可以自动建新部门，但审计部每次下去检查时，下面的部门 agent 都得准备好 doc 和 hard code registration。一个 review package 200K token，必须靠 Opus 4.7 撑住，但顶层跑的还是 4.6。

<u>洒脱的鸳鸯</u> 则用更轻量的方式：plan 完了用 `claude -p` 起两个新进程、用不同 prompt 从不同角度 review，implement 完了再 review code，「基本上这么过一遍之后我自己很少需要再介入了」。

### 跨工具 Context Infrastructure 的「品味差异」

群友们发现不同 coding agent 对同一套 context 文档的响应差异很大。<u>敏锐的海狸</u> 发现 Claude 的 instruction 管理方式直接给 Codex/GPT 5.5 就不爱读，得让 Codex 自己去重写。<u>冷静的麋鹿</u> 做了对比实验：同一个任务让不同模型各出 plan 再互评，「经常 Codex 觉得自己的好，CC 也觉得自己的好，理由还都很充分」。他认为这不是工程师使用习惯导致的，而是从数据采集到训练评估的整条 infra 带来的品味偏差。

> <u>今天群内信息量极大</u>：我一套 context infrastructure 在 OpenCode 和 Claude Code 之间无缝切换没问题，唯独在 DeepSeek 上浑身难受——叫它调用 Gemini 它就去调用 GPT，agents.md 里说了做任何事情前先去读 xx 文件，打死都不读。

<u>冷静的麋鹿</u> 还发现 DeepSeek V4 Flash 的指令遵循「好像比 Pro 还强一点」——同样的老鸭汤，Pro 懒得读，Flash 还能乖乖照做。<u>今天群内信息量极大</u> 觉得 Flash 和 Pro 的关系有点像 Gemini 3 Flash 和 Gemini 2.5 Pro，Flash 总觉得更好用。

多人最终的实践结论：不同 runtime 最好维护两套入口文件（AGENTS.md 给 Cursor/OpenCode/Codex，CLAUDE.md 给 Claude Code），部分内容 mirror，但各自按模型偏好调整。值得注意的是 Cursor 会自动扫描 Claude 的目录，<u>80-HD</u> 感慨「先挖坑就有优势，现在几乎主流的 coding agent 都会去扫 claude 目录」。

### Harness 该自建还是外包

<u>天真的狮子</u> 问：应不应该自己花精力做 harness，还是把注意力放在决策力、审美、标准上？

<u>今天群内信息量极大</u> 引用了自己的文章 [AI 脚手架正在商品化，人的工作变成判断边界](https://yage.ai/share/ai-scaffolding-commodity-runtime-20260505.html)，认为后者更重要。核心观点是 harness 正在快速外包化：prompt 技巧被模型能力吸收，通用 agent runtime 被商品化产品接管，真正需要人维护的是领域判断和验收标准。

<u>冷静的麋鹿</u> 随后即兴写了一篇 [AI Coding 越强，越要学会外包](https://challenwang.com/essays/ai-coding-outsourcing-harness-20260509.html)，用写作 skill 从口述到发布上线只花了几分钟。核心判断框架：先用现成工具跑通真实问题 → 把验收标准写清楚 → 保留失败样本 → 等失败模式重复后做轻量机制 → 只有轻量机制变成瓶颈才平台化。

### 多 LLM 并行决策与幻觉可观测性

<u>严谨的老虎</u> 分享了对 Stanford 生物物理教授 Jan Liphardt 的[访谈](https://youtu.be/D5o7QZaDSGE?si=UZl0qpnKd4SUKO2u)。Liphardt 做 OpenMind（开源 robot OS），给幻觉问题提供了一个 mental model：幻觉不是计算机的问题，是人的问题——我们自己也 hallucinate，所以人类建了法庭和陪审团，机器人该用同一个机制。实际架构是同一个 decision 跑多个 LLM 并行，模型之间用自然语言互相对话，人可以 eavesdrop 整个 thread，在分歧出现的 turn 直接加自然语言 guardrail。

> <u>严谨的老虎</u>：某种意义上跟<u>今天群内信息量极大</u>之前那个 verb-vs-noun 的逻辑同频：与其追求 single agent 更聪明，不如把判断的可观测性做出来，让分歧变成可读取的 artifact，而不是 hide 在某个 model 内部的黑箱里。

<u>稳重的海豚</u> 觉得「法庭和陪审团解决的不是幻觉问题，是人的劣根性问题」。<u>严谨的老虎</u> 追问：Agent 也继承了我们的劣根性？并透露即将采访做 Agent ID 的 founder——agent 很快会有 ID verification 和 wallet。

### 量子计算对密码体系的威胁时间线

### 2.5GB UFO 解密档案做成 Claude Skill

<u>飘逸的狮子</u> 把刚解锁的 132 份 UAP/UFO 解密文件（2.5GB、约 4000 页）[做成了 Claude skill](https://www.superlinear.academy/c/share-your-projects/skill-ufo-2-5gb-skill)。Skill 由四个幂等 Python 脚本和三份 reference 文档组成，总共约 600 行 Python 加 700 行 Markdown，目标是给任意同类文件夹输出十分钟能读完的结构化报告。Eval 结果：带 skill 均值 97% vs. 裸跑 74%，带 skill 12 分钟完成、token 消耗更低——更快更便宜更准。

<u>冷静的麋鹿</u> 展示了自己的工作流：在<u>今天群内信息量极大</u>的 OpenCode iOS Client 上搭配<u>开朗的企鹅</u> 的 AgentHub，加上写作 skill，口述十分钟就能输出一篇带调研的随笔并自动发布上线。<u>冷静的北极熊</u> 问具体怎么蒸，<u>80-HD</u> 建议去原始老鸭汤问<u>今天群内信息量极大</u>是怎么更新的，然后让 AI 帮自己做个类似的计划一点点蒸。

> <u>80-HD</u>：简单理解就是<u>今天群内信息量极大</u>称了两斤乐高给你，然后拍了个他的完成图给你看

> <u>冷静的麋鹿</u>：如果泛泛写东西，那都是一坨屎根本没法看。如果配上 typeless 跟他唠叨十分钟再开始写，就有血有肉。有时候写完我自己看，我都觉得，写的真 tm 有道理

<u>今天群内信息量极大</u> 表示在考虑如何让整套东西更 accessible——短期给企业用户提供手把手培训，长期可能通过 Cloudflare Email Worker 把一些可公开的环境开放出来。

## 闲聊花絮

### Agency 与自我觉醒

<u>开朗的企鹅</u> 分享了 [Notion 产品主管访谈笔记](https://mp.weixin.qq.com/s?__biz=MzA5MDMxMzU3OA==&mid=2466670395&idx=1&sn=e0026437b2c3e85bcc9ea17d51bf3428&chksm=872fc0e4643d3ad52ef544ff3ffc37fc54283019f89a099d86df2582d884e53e52984c8d905f&mpshare=1&scene=1&srcid=0508GX1Reh4je0cIf09pHigd&sharer_shareinfo=f88a4ec3c0f4f22bf754f2930d4d7577&sharer_shareinfo_first=f88a4ec3c0f4f22bf754f2930d4d7577#rd)，核心论点是 AI 时代最稀缺的不是聪明人而是有 Agency 的人。<u>冷静的飞鼠</u> 回应「the right kind of agency 是个极高极高的要求，大多数人是活在惯性里的」。<u>温暖的斑马</u> 把 AI 形容为「一种刑具，把人跟人拉开」，并抛出观点：「自律是一个伪概念，改变行为要么是痛苦足够大，要么是压力足够大。」<u>孔哥仁且义孟哥义且仁</u> 则走向另一端——「相比之下我相信底层锁定论」，认为 AI 是「一个带来生产力却没有带来需求的新技术」。

### 鸭是甲等鸟

<u>优雅的喜鹊</u> 贴了一张拆字对联：上联「鸭是甲等鸟」（鸭 = 甲 + 鸟）。<u>随和的飞鼠</u> 对出「凤是凡间鸟」。<u>稳重的海豚</u> 用 AI 对出更工整的下联：「驽乃奴下马」（驽 = 奴 + 马），甲等对奴下，鸟对马，飞禽对走兽。群友随后纷纷把「甲等鸟」的称号送给了<u>今天群内信息量极大</u>。

### 各家 Pro 配额告急

<u>沉稳的仓鼠</u> 感慨「以前觉得一个亿 token 也太多了，现在一天一个 B token 都不够花」，Codex Pro 快用完了很着急。<u>今天群内信息量极大</u> 说「三个 provider 都要好几天，现在抠抠索索用 Claude 最后的 1%」。<u>乐观的灰熊</u> 说每次到 98-99% 的时候「老抠了」。<u>孔哥仁且义孟哥义且仁</u> 提到 Copilot 六月转 rate limit，但公司给每个员工送了真无限流量的 hobby 账号，引发一连串「快别说了，我要羡慕死了」。

### Gemini 适合搞什么

<u>沉稳的仓鼠</u> 问 Gemini 有没有探索出适合的场景，「不想每次尝试都以骂它 sb 结束，毕竟也是量大管饱」。<u>稳重的海豚</u> 的结论是拿来「搞文娱业务比较合适，或者说白一点儿，搞乐子」。<u>沉稳的仓鼠</u> 总结：「感觉是个给普通用户用的 model，不是给效率工具用的 model。是不是花钱买 data 买少了，天天用自己的数据搞出来的。」

### MiniMax 的「失语症」

<u>睿智的北极熊</u> 分享了 [为什么MiniMax无法识别马嘉祺是谁？](https://www.zhihu.com/question/2017049686331127666/answer/2036149386116342692?utm_psn=2036287036177511210)，<u>稳重的海豚</u> 好奇为什么模型不会去做检索查询。<u>今天群内信息量极大</u> 给出了一个有画面感的比喻：「有点像是人类的失语症，就是有特定的词汇就像是禁忌词一样的，它可以听懂这个词但它就是说不出来。」

### AI 写作的认知天花板

<u>专注的剑鱼</u> 转发了一则评论：「你可以用 AI 来帮助自己学习某些特定领域，但不能偷 AI 的认知。认知只有 60 分，你是不可能靠 AI 写出 80 分的东西的。」他自己也觉得针对熟悉领域时，AI 产出的东西在措辞、角度、引用深度上确实有限。<u>今天群内信息量极大</u> 回应说 AI「可以想象成一个秘书或实习生，有一个秘书并不会让雇他的老板变成一个什么都懂的天才，而是让他可以在自己擅长的领域更高效地写作」。
