今天最热闹的是一场由 Claude Code 团队成员推文引发的「Markdown vs HTML」格式大战——十几人参战后共识是这更像稻草人论证甚至「Token 阳谋」，<u>冷静的麋鹿</u> 说「我又多读了几遍……然后还是没感受到他观点的精髓」。技术含金量最高的是两篇外部文章：一篇复盘 DeepSeek V4 Pro 工具调用，揭示同一模型在不同平台成功率从 4% 到 35% 的巨大差距，不是模型不行而是 harness 没接好；另一篇关于一次性软件的长文值得收藏。凌晨 <u>孔哥仁且义孟哥义且仁</u> 从原教旨 TDD 视角续上了昨天的讨论，并与 <u>随和的企鹅</u> 展开了关于编程语言未来的辩论。此外 <u>风趣的海豚</u> 发现 DeepSeek V4 Flash 自动补全会泄露训练数据中的陌生用户 ID，值得警惕。

## 方法论

### MD vs HTML："格式战争"还是 Token 阳谋？

<u>幽默的犀牛</u> 分享了 [Claude Code 团队成员 Thariq 关于从 Markdown 转向 HTML 的推文](https://x.com/trq212/status/2052809885763747935)，引发当天最长的一轮讨论。Thariq 的观点是 HTML 在表达维度和阅读体验上全面优于 Markdown，甚至在回复中声称「I think HTML is strictly better for all of that too」——包括 plan、skill.md 等给 agent 读的文件。

群友普遍持怀疑态度。<u>直率的猫头鹰</u> 最为犀利，指出 Thariq 立了个稻草人——「现在大家做汇报、总结、分享的时候也不会直接上 md 啊」，渲染后的 md 本身就是 html，想做到 fancy 的交互式体验 token 成本远不止多几个 tag，直呼其为「snake oil salesman」。<u>开朗的企鹅</u> 抛出最简洁的反驳：「markdown → html 也不需要 token 啊」。

> <u>冷静的麋鹿</u>：这个热点看得我一头雾水，第一次有了一种，我的认知领先 cc 原厂专家的错觉。上个时代 deep research 的产品，哪个没有 html 预览啊。

<u>谨慎的灰熊</u> 和 <u>冷静的麋鹿</u> 不约而同嗅到商业动机——前者称「这是 CC 团队的阳谋，又可以把 ARR 往上拉个 40%」，后者认为是「有组织有预谋的，从全员 coding 向第二增长曲线引导全员 design 的一次营销事件」。

<u>活泼的树懒</u> 是少数为 HTML 辩护的人，他认为 Markdown 一长就没人看，HTML 的交互形式让人留在 review loop 中，「现在很多人根本就不 review，因为改得太多了都没有人看」。但 <u>直率的猫头鹰</u> 回应说核心问题是信息压缩，不是格式——该不想读的换了 HTML 还是不想读。

<u>神秘的麋鹿</u> 贡献了当天最有结构的分析，从功能性（不同信息有其合适的模态）和受众（弥补背景知识差异、审美与潜意识信任）两个维度拆解，结论是场景和对象的组合决定格式选择。<u>灵巧的飞鼠</u> 整理了一张实用决策表：「你会反复改的用 MD，写完只读的用 HTML」。<u>淡定的雪豹</u> 另辟蹊径推荐飞书文档——可分享性比 html 好、还能插入好看的流程图，他已日常用飞书 CLI 生成文档。<u>优雅的荷兰猪</u> 指出 feed 给 LLM 时无意义的格式 tag 会降质，「本来就是两个并行不悖的东西，非要搞对立」。

多人最终收敛到一个实操共识：**MD 是 source of truth，HTML 是展示层**。<u>稳重的海豚</u> 先写好 markdown 再转成网页；<u>淡定的喜鹊</u> 两版并行——需要 publish 走 HTML/PDF，本地存档保持 md，「md 是 source of truth」；<u>低调的北极熊</u> 用 hooks 自动生成但加了白名单，给 agent 读的 md 不转，人读的才转（这条与昨天 [「Agent 输出从 Markdown 转 HTML」](/daily/2026/05/08/daily/#agent-输出从-markdown-转-html) 衔接）。<u>孔哥仁且义孟哥义且仁</u> 最后提了一句反讽：「为了更强的文档表现力，不如一步到位用 OpenXML」。

### TDD 讨论续：原教旨 TDD 的反击与编码的未来

昨天 [「AI 时代 TDD 为什么不是答案」](/daily/2026/05/08/daily/#ai-时代-tdd-为什么不是答案) 的讨论今天凌晨由 <u>孔哥仁且义孟哥义且仁</u> 续上。他从原教旨 TDD 视角做了系统回应：「return true」不是 AI 偷懒的证据，而恰恰是覆盖率不够的证据。随着覆盖增加，AI 最终会被迫把 return true 改成真正可运行的实现。

> <u>孔哥仁且义孟哥义且仁</u>：至于"return true"的这个问题，原教旨主义 TDD 本来就是让你能 return true 就 return true 的。如果你 return 了一堆复杂的东西，结果你的 test case 只需要他 return true 就能过，说明这个 code coverage 就是一坨屎。显然你需要做的是接着覆盖而不是马上就指责 AI 说她写的太应试。

他还指出 vibe coding 比人类的真正进步，应该体现在 xUnit Test Patterns 中一部分「缺点」不再是缺点——比如 test 覆盖太多导致重构工作量太大的问题，机器就应该孜孜不倦地做完。最终把对 AI 的要求缩减为「能在 context window 足够远的前提下稳定运行越久越好」。

<u>活泼的羊驼</u> 回应说「如果一个工程师可以把它的 AI 调教到运行 1-2 小时、端到端完整把一个需求做完，说明这个人驾驭 AI 的功底确实很可以」。<u>孔哥仁且义孟哥义且仁</u> 感慨「我觉得这就是刚需，不然天天跟 AI 聊天难道不累吗，有空说那么多话的话我自己做了得了」。<u>坦荡的灰熊</u> 则对 <u>今天群内信息量极大</u> 文章中「为什么人不会这样」的段落（人类有维护负担、CR 审查、on-call 恐惧等隐式代价结构）发出感叹：「有一些隐性的上下文，注入进去是很费劲的。」

### Harness 决定模型表现：DeepSeek V4 Pro 6/10 胜 Opus 4.7

<u>风趣的海豚</u> 分享了一篇 [DeepSeek V4 Pro 工具调用复盘](https://mp.weixin.qq.com/s?__biz=Mzk0NjY1ODk0MQ==&mid=2247488084&idx=1&sn=9d1fb4b927d43ffd366d5a2a9d4c80ef&chksm=c2d055c97b0be18956418000cfddacda14717d4f16d12f9a99e8ed6b698ae9bd6eafa3429030&mpshare=1&scene=1&srcid=0509mMdBMVecGQ6eJ5qwELL2&sharer_shareinfo=602e17dbe3f3fe52a3e6f1933239d348&sharer_shareinfo_first=602e17dbe3f3fe52a3e6f1933239d348#rd)，核心结论：开源模型工具调用差「几乎每次都是 harness 的问题」。开发者盯了两天、看了数十亿 token 的调用日志，归纳出四类高频 shape-level 错误（optional 字段传 null、数组 vs 字符串混淆等）合计占约 90%，每类修复不过 30–100 行代码，最终让 V4 Pro 在内部评测里 6/10 胜过 Claude Opus 4.7。

SambaNova 的数据最震撼：同一模型权重在不同平台上多轮调用成功率分别为 35% 和 4%，相差近 9 倍。你以为看到的是「模型 A 比模型 B 聪明」，实际看到的是「平台 A 的 harness 比平台 B 接得好」。这与前天 [「跨工具 Context Infrastructure 的「品味差异」」](/daily/2026/05/08/daily/#跨工具-context-infrastructure-的品味差异) 的讨论一脉相承。<u>风趣的海豚</u> 由此追问了一个元问题：「如果到这一步的话，那么模型的进步究竟体现在什么地方？」

### GPT Pro 深度调研 vs Claude：实战对比与混合工作流

<u>稳重的海豚</u> 发现最近 Claude 做深度调研的结果不如 GPT Pro + Deep Research，即使用了 adaptive + max effort，「感觉深度还是不够」。<u>冷静的麋鹿</u> 有同感——GPT Pro 写出来的东西「有观点有深度」。

<u>冷静的麋鹿</u> 的解法是双模型融合工作流：先用鸭汤 skill + Pro 写完保存 md，再看鸭汤 skill 写出来的有哪些跟自己经历相关的内容，最后融合一份——「毕竟 GPT Pro 没有鸭汤对我那么了解」。<u>稳重的海豚</u> 表示要把 Pro + DR 搞成 API 调用（<u>冷静的麋鹿</u> 提醒「游走在封号的边缘」），考虑用 Browsebase 或 Stagehand 之类的浏览器自动化工具来实现。

### 为 AI 设计编程语言：从 Rust 到机器证明

<u>随和的企鹅</u> 透露自己五一期间「用 GPT 5.5 做了个程序语言，编译到 LLVM 可以输出 native binary，实现一个单一 owner 内存管理的范式」。<u>孔哥仁且义孟哥义且仁</u> 认为换语言不解决根本问题：「模型并不是不能写 C++，只是他有自己的错误的哲学。」

两人随后展开了一场凌晨辩论。<u>孔哥仁且义孟哥义且仁</u> 认为「未来是属于机器证明的」——Haskell / Lean4 / Idris2 / C++ TMP / TS 类型体操才是正确道路；C++ 的独特优势在于「需要证明的时候可以尽情发挥，需要做 dirty work 的时候也不阻止你，两个抽象层次间的丝滑过渡不可避免」。<u>随和的企鹅</u> 指出纯 FP 的老问题不是本身有缺陷，而是「industry 普遍学不会，而且纯 FP 在真没办法的 stateful 场景也有点蛋疼」——不过「现在第一个问题应该算是 noop 了」，AI 可以替人跨过学习门槛。<u>沉稳的兔子</u> 务实地补充：「语言简单，周边设施太麻烦了。」

### 一次性软件与 AI Native 的本质

<u>冷静的飞鼠</u> 分享了 [一次性软件与被压缩的现实：AI Native 的本质是策略重构](https://www.superlinear.academy/c/ai-resources/ai-native-cost-structure-4e4d27)。文章核心洞察：DRY 原则和可复用代码不是技术真理，而是特定成本结构下的妥协——代码昂贵时，人被迫「压缩现实」靠直觉和抽样猜测全貌。AI 打破了这张价格表后，真正理性的选择是为每个十分钟的临时决策现场构建一个专用工具，用完即弃。真正的 AI Native 不是用 Copilot 更快写函数，而是「遇到不确定时的第一反应不是调用经验去猜，而是现场构建工具去看」。

## 行业新闻

### Tokenmaxxing：Token 消耗量成为新 KPI？

<u>风趣的企鹅</u> 分享了 [争夺 Token "榜一大哥"](https://m.mp.oeeee.com/a/BAAFRD0000202605091586851.html?&layer=3&share=chat&isndappinstalled=0) 的报道。硅谷和国内正在兴起「Tokenmaxxing」风潮——迪士尼内网上线全员 Token 消耗看板，有员工 9 个工作日调用 Claude 约 46 万次；Meta 30 天全员消耗 60 万亿 Token，排行榜走红后因刷榜迅速下线。黄仁勋公开表示「年薪 50 万的工程师如果没有烧掉 25 万的 Token，我会深感不安」。报道也指出成本端 DeepSeek V4 系列的连续降价正在重塑讨论底层逻辑——同等编码效果的成本差距可达 100-200 倍。<u>风趣的企鹅</u> 评价「记者努力了但还是没讲好故事」。

### DeepSeek V4 Pro 加"无用"工具后回答突然变长

<u>开朗的企鹅</u> 分享了一篇 [知乎文章](https://zhuanlan.zhihu.com/p/2036449001084565006)：为什么给 DeepSeek V4 Pro 的 tool 列表里加一个「几乎没用」的工具后，模型回答反而突然变长了？这个现象暗示 tool definition 的存在本身会改变模型的输出行为——与前面 harness 文章中「训练分布副作用」的判断相呼应。

### DeepSeek V4 Flash 自动补全泄露陌生用户 ID

<u>风趣的海豚</u> 在文本编辑器中开启了 DeepSeek V4 Flash 的自动补全后，发现它突然补出了一个自己从未见过的用户 ID `@articuno`，指向一个 [Discord Bot 项目](https://github.com/B1ue-Dev/Articuno)。他强调「在我的个人生活里这是我第一次见到这个 id」，这意味着自动补全模型的训练数据或推理上下文中混入了其他场景的信息。所有使用 FIM 模型做代码/文本补全的用户值得留意。

## 工具

### 停止使用聊天窗口：10 倍生产力差距的起点

<u>今天群内信息量极大</u> 分享了 [用好 AI 的第一步：停止使用聊天窗口](https://www.superlinear.academy/c/ai-resources/stop-using-chatgpt)，核心论点是聊天窗口与 coding agent 之间的生产力差距不是 30% 而是 10 倍量级，差距来自反馈闭环、上下文供给、资产积累三个维度。

这篇文章恰好呼应当天的一个具体案例：<u>倔强的飞鼠</u> 一直在 DeepSeek 网页上生成 LaTeX 再手动复制进 Overleaf，编译错误一堆。<u>今天群内信息量极大</u> 看到后直言：「网页/app 这种聊天窗的和能自己写 code 读文件的 AI 完全是两种东西，效果不是差一点点是很多倍。」<u>淡定的喜鹊</u> 给出了具体方案：用 VS Code + AI 插件 + LaTeX Workshop 插件开 yolo mode，让 AI 自己写 → 编译 → 看 PDF 效果 → 改到满意为止。<u>今天群内信息量极大</u> 还提到「Claude 非常神奇地用 TikZ 画图很牛逼，不知道什么原理」。

### Slidev：AI 友好的 Markdown 幻灯片工具

<u>谨慎的狮子</u> 推荐了 [Slidev](https://github.com/slidevjs/slidev)，用 Markdown 写幻灯片，内置 KaTeX 公式、Mermaid 图表、Monaco Editor 实时编码，支持导出 PDF/PNG/PPTX。由于整个幻灯片就是纯文本，非常适合让 AI coding agent 直接生成或修改。

### 本地模型 SDK 自动路由

<u>细心的熊猫</u> 提到 Google 的一些 SDK 已支持自动检查本地有没有小模型可以直接调用，将简单 request 自动短路到本地模型——判断用户输入是否合法、简单生成式 UI、翻译等小活儿能显著降低延迟，评价「很好用」。

### Multi-agent 通过 handoff file 通信

<u>开朗的飞鼠</u> 问多个 agent（一个看邮箱回邮件、一个搜网做研究）之间怎么交流。<u>淡定的喜鹊</u> 的做法是「一般不直接交流，写到同一个 handoff file、写到同一个 KB，这样彼此有 visibility 就行」。

## 闲聊花絮

### 给女儿的幻想生物百科

<u>稳重的海豚</u> 用 AI 生成了精美的幻想生物图鉴卡片——先是一只「Elephant Owl」（大象身体配小猫头鹰脑袋，在洞穴中害羞地发出低沉叫声），然后是「Space Dinosaur」（穿越小行星带的星际探险恐龙），均有详细的栖息地、体型标注和精美插画。他感叹「感觉可以搞个 fantasy wikipedia」给女儿出版。<u>孔哥仁且义孟哥义且仁</u> 提醒如果做战锤系的就别想出版了——「法务猛的一逼」。

### Codex 限额漏洞：最后一个任务永不停止

<u>沉稳的仓鼠</u> 分享了一个让人哭笑不得的发现：Codex 每周限额跑满时最后一个任务不会被停掉而是会跑到完成，于是有人提出在额度耗尽前塞一个能跑几十小时的任务，让它一直跑到下一个 Reset。<u>直率的猫头鹰</u> 感慨「This is why we can't have good things」，<u>稳重的海豚</u> 表示「懂了，跑个 SWE-bench Pro」。

### 飞机上用手机 vibe coding 比电脑还爽

<u>80-HD</u> 人在纽约刚下飞机，报告说飞机上用手机干活「感觉比旁边用电脑的都爽，因为网太差老掉线」——手机端异步 agent 反而更稳定。更惨的是落地后因为路程太近被三个 Uber 司机拒载。
