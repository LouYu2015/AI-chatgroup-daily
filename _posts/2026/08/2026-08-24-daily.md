## 驯服 Codex 过度工程

### 三家 Agent 周末横评

<span class="mention">@灵动的考拉</span> 这个周末让 Codex、Claude Code 和 Grok Bot 跑类似的 goal 任务——把一批明确的 issue 逐个 close，提交 PR、交叉 review（两个 review bot）、fix 到无新意见，中间发现问题自提新 issue。三家表现差距悬殊。

Claude 和 Grok 都在不到十小时内完工。Codex 则连续跑了 48 小时，不但没清完，反而把 10 个 issue 膨胀成了 80 个——干活慢且不用 subagent 并行、动不动大惊小怪开新 issue、连 worktree 清理都磨磨唧唧。让 Claude 分析后发现新开 issue 七成有意义、三成是臆想，但 Codex 谨小慎微到屁大的事也要开 issue、几行代码就能 fix。

> <span class="mention">@灵动的考拉</span>：codex 这是人类软件工程上也出现的那种 bug 越修越多的困境😂 估计 token 够它会永远循环下去

<span class="mention">@沉稳的兔子</span> 同感：Codex over-design 严重，喜欢自己发明新概念，写出的东西特别 verbose。<span class="mention">@灵动的考拉</span> 当天退订了 Codex $200、降级为 $20。

### Follow instruction 与品味对齐

<span class="mention">@沉稳的仓鼠</span> 给出了相反视角。他承认 Codex 开 5.6 xHigh 有明显的 over-engineering 倾向，但它在 follow instruction 上是所有模型里最强的——前提是边界设好。他有一个 daily pipeline 包含七八个方向的 multi-step 任务、跑一遍要七八个小时，目前只有 Codex 能完整执行；其他模型中途总会偷懒或糊弄。

<span class="mention">@搞仁义毛义仁</span> 从更深层切入。他认为现在告诉 Sol 不做什么比告诉它做什么更重要，Sol 有一种「大学生写代码的中二气质」，顺着这个气质去 instruct 效果不错。但 over-engineering 没有指标可看，归根结底需要人做 code review。

他主张在执行前做 plan review：把目标和预期做法都写下来让 Sol 出 plan，提前发现想法与代码现实的冲突。冲突越多，Sol 跑偏和 over-engineering 就越离谱。/goal 则有点许愿的意味——你得自己看 Sol 哪里做得不好，然后改 instruction。

> <span class="mention">@搞仁义毛义仁</span>：人类的 reasoning 还是太稳定了，事情做到一半发现此路不通，能耐住性子重新思考，不会偷懒打补丁。打补丁就会丑，这种价值判断只有亲自 code review 才能有感觉

> <span class="mention">@搞仁义毛义仁</span>：保持项目设计干净，已经不是有没有必要的问题了，这是实打实的省钱

<span class="mention">@敏锐的海狸</span> 调教后也认同：给 Sol 设好边界后基本能照着来，关键是把设计和 scope 定严、让它慢慢做。<span class="mention">@稳重的海豚</span> 更直接——不做自动 review，只检查是否按 spec 做了，没按 spike 写的全删。<span class="mention">@80-HD</span> 则认为古法 agent 用 Codex 也挺好，发现 over-engineering 及时制止就行。

### 长任务 Checklist 实战

<span class="mention">@搞仁义毛义仁</span> 分享了他在 [GacUI 项目](https://github.com/vczh-libraries/GacUI/tree/master/.github/Jobs)上驯服 5.6 Sol 做超长手工测试的方法：让模型维持一个 checklist，每次状态更新就立刻保存，再适当 PUA。检验偷懒的方法是看 checklist 文件的 tool call 频率——两个 tool call 之间做了什么一目了然。不想看可以把 session dump 出来让另一个 AI 读。

他还写了一份 [Coding Convention](https://github.com/vczh-libraries/GacUI/blob/master/.github/Guidelines/Coding.md)，明确定义 DRY 原则边界（重复信息才要提取、重复代码不一定要）、何时允许 breaking change、不得发明代码生成器、创建新抽象层须有实际收益等。这些规则一部分是他写的，一部分是 Sol 从 review comment 中自行总结积累的。核心思路是 align AI 的价值观——Sol 能写出复杂代码后，如何 follow 长期积累的品味成了真正的难题。

<span class="mention">@沉稳的兔子</span> 补充品味最好分段，增加一些 check。<span class="mention">@灵动的考拉</span> 则坚持用 evaluate 脚本做刚性验收，不依赖模型自觉性。

这场讨论延续了近日的主线（[「Agent 约束先行」]({{ '/daily/2026/08/22/daily/#agent-约束先行' | relative_url }})、[「Sol 健忘症持续」]({{ '/daily/2026/08/23/daily/#sol-健忘症持续' | relative_url }})），群内共识逐渐明确：模型能力不再是瓶颈，约束工程和品味对齐才是当前主要挑战。

## 工具

### 2×5090 自托管全景分析

<span class="mention">@今天群内信息量极大</span> 发布了 [2×5090 跑 Qwen 3.8-27B 的完整实测](https://yage.ai/share/2x5090-27b-sweet-spot-20260824.html)，这是连日本地部署实验的集大成之作（前情 [「单卡超越官方基准」]({{ '/daily/2026/08/22/daily/#单卡超越官方基准' | relative_url }})、[「Qwen 3.8-27B：SGLang 负优化与含妈量」]({{ '/daily/2026/08/23/daily/#qwen-38-27bsglang-负优化与含妈量' | relative_url }})）。

核心吞吐数据：8 路并发每路仍有 141 tok/s，整机总吞吐 962 tok/s，1→8 路扩展倍率 3.59×，PCIe 互联未成瓶颈。DFlash2 投机解码 215–256 tok/s，长文本思考模式 156 tok/s。文章横评了 4090（带宽只有 56%、不支持 NVFP4、停产溢价反超 5090）、PRO 6000（带宽相同但溢价 8 倍且有固件崩溃隐患）、以及各类云端方案（月账单比自建电费高 6–50 倍）。

经济账令人清醒：一天处理 2.24 亿 prefill token、生成 225 万 decode token，真正高负载约 3.8 小时，月电费约 $11——但同等负载用 Luna API 只要约 $1/天。靠省钱回本需 25–33 年。

> <span class="mention">@今天群内信息量极大</span>：有点类似在家里优化汽油发电机，和发电厂比效率和成本

他坦言自托管的价值在于数据留本地、无审查、可微调、断网可用。<span class="mention">@细心的熊猫</span> 则指出硬件本身在升值：5090 从 MSRP $2,000 涨到全新 $4,300–5,000、国内回收价 3.4 万人民币，Qwen 3.8 发布后又涨了 20%。<span class="mention">@今天群内信息量极大</span> 吓了一跳——他 $2,000 入手的卡如今溢价翻倍。

### claude-devtools Context 可视化

昨晚 <span class="mention">@飘逸的浣熊</span> 分享了他为 [claude-devtools](https://github.com/LouYu2015/claude-devtools/releases/tag/v0.5.0-exp.1) 新增的 context 可视化功能。他发现 agent 开始隐藏思考过程后，用户对 context 占用的直觉就不准了——屏幕没怎么变化，但 agent 可能悄悄读了一大段 skill，比满屏滚动的输出还占 token。

新增功能包括按 token 或运行时间可视化每个 tool call 的资源占用、智能分组分类、本地 LLM 对分组自动总结、以及 subagent 可视化。实用发现：他以前总让 agent 不要用 heartbeat，可视化后才知道 heartbeat 几乎不占 context，真正的大头是冗长的 skill 和代码文件读取。工具支持 macOS 和 Windows，可与官方版并排安装。

### Qwen 3.8-27B 实战收尾

昨晚 <span class="mention">@今天群内信息量极大</span> 做了一笔直白的经济计算：一天用了 1.2 亿 token，如果用 Luna 换算成 Codex $200 plan 只相当于约 $1 的额度。GLM coding plan 最高档月付 $60、实际用量相当于 API $1,200，也是 20 倍量级。他判断目前最划算的是 Grok Heavy，但 <span class="mention">@热情的大象</span> 提醒 Grok 早期送 Cursor Ultra 的福利已结束，<span class="mention">@活泼的火烈鸟</span> 补充当前版本 Grok 是最差的——划算的是之前的 Grok Heavy。

实战踩坑方面，<span class="mention">@今天群内信息量极大</span> 发现 Qwen 3.8 在做小更改时把他的密码明文提交到了 GitHub PR 上。他总评 27B 非常 impressive、可用，但有不少 regression，需要定制 review 流程和 prompt。部署用双卡 5090 NVFP4 量化，吞吐约 1000 tok/s，但多任务并发时 SGLang 容易卡死。<span class="mention">@细心的熊猫</span> 建议低精度快速度优于高精度慢速度，one shot 偶尔写错改一下就好。

另一个亮点：Qwen 3.8-27B 在 Code Arena WebDev 排到第 9（1,595 分），超过 Gemini 3.7 Flash、GLM-5.2 Max 和 DeepSeek V4 Pro 等商用模型——一个 27B 开源模型打进前十。
