## 工具

### Cursor 工具面 KV cache 优化

<span class="mention">@活泼的羊驼</span> 分享了 <span class="mention">@今天群内信息量极大</span> 对 Grok Bot 0.18.0 逆向代码的深入分析（前情 [「Grok Bot 0.18 源码重建」]({{ '/daily/2026/08/24/daily/#grok-bot-018-源码重建' | relative_url }})）。他发现 Cursor 的桌面 agent 在工具面设计上有一个反直觉做法：30 多个工具中，模型每轮只看到 9 个动态工具的完整 schema，其余 18 个静态工具给全量定义、动态的只给一行 hint。要调用动态工具，模型得先调 GetMcpTools 拉完整 schema，再调 CallMcpTool 执行。

根本原因是 KV cache——工具定义序列化在 context 最前面，改一次 tools 数组会导致整段前缀缓存失效，每轮都按原价重算。Manus 走了完全相反的路（工具全量常驻、解码时 mask），但两者收敛到同一条约束：序列化的工具面必须稳定，把动态性推到别处。两个团队独立设计却殊途同归，说明这是底层逼出来的架构约束。

## 方法论

### TQ 与 Model Overhang

<span class="mention">@活泼的羊驼</span> 将此前一期演讲对话整理为[微信公众号文章](https://mp.weixin.qq.com/s?__biz=MzU4MTgxOTE2OQ==&mid=2247484738&idx=1&sn=9dcf7d783e485ca84c537526d8c8f795&chksm=fcfa9f71c854bd926f3caa56f6c04ac3e9ed8d7c5360a3362b1010719c8265122ebd50ea3cde#rd)，配有选择题和问答题供读后自测。核心概念是 TQ（Token Quotient）和 Model Overhang——模型实际能力远超用户感知，弥合这个差距不只是 Prompt Engineering 能解决的，需要通过真实任务、持续练习把模型潜能转化为工作成果。

文章还收录了 FDE（驻场工程师）将快速普及、AI 原生一代应先让 AI 做再想办法让 AI 做好、适应窗口从 PC 时代的十五年压缩到三至七年等判断。<span class="mention">@活泼的羊驼</span> 特别推荐读后自测环节，认为选择题和问答题有助于内化 mindset。

### 迁移老代码的感知缺失

<span class="mention">@坦荡的灰熊</span> 凌晨分享了一个观察：模型自主做新程序完成得很好，但迁移老代码一塌糊涂——它无法从人的角度感知「app」本身，只能看到「app 的代码」。这种感知缺失不是截图能解决的，模型看完代码后没能产生应有的信号。他补充了更直白的判断：让模型幂等地处理老程序，就完犊子。

这与近日关于 agent 约束工程的讨论一脉相承（[「Follow instruction 与品味对齐」]({{ '/daily/2026/08/24/daily/#follow-instruction-与品味对齐' | relative_url }})）——模型的瓶颈不只在生成能力，更在理解既有系统意图的能力。
