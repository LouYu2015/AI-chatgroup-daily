今天行业侧两条大新闻：Meta 发布 Muse Code 编程 agent 和 Muse Spark 1.2，<span class="mention">@沉稳的仓鼠</span> 实测判定不如 GLM 5.2，<span class="mention">@80-HD</span> 还质疑其 benchmark 回避了 Fable 和 Sol；OpenAI 宣布 GPT-5.6 Luna 全员免费并预告下一代模型 Astra。方法论侧最有趣的是 <span class="mention">@搞仁义毛义仁</span> 在 vibe coding 一年多后迎来 AI review 流程的零的突破——模型终于提出了第一个有价值的 challenge。

## 行业新闻

### Muse Code 与 Muse Spark 1.2 发布

昨晚 <span class="mention">@风趣的企鹅</span> 率先提及 Muse Spark 1.2，<span class="mention">@直率的海豚</span> 随即贴出 [Meta 官方博客](https://research.meta.ai/blog/introducing-muse-code-and-muse-spark-1-2)。Muse Code 是 Meta 的终端编程 agent（macOS/Linux），核心架构为主 agent 循环加多后台异步 agent，后台 agent 驻留整个 session 不重复收集上下文；本地事件日志作为单一真实源，崩溃后可精确恢复。出厂内置 /plan、/grill（压力测试计划）、/goal 三条技能命令。

定价分两档：contributor 版输入 $0.10/Mtok、缓存 $0.002、输出 $0.20，注明数据将用于改进模型；常规版 $1.25/$0.15/$4.25。<span class="mention">@直率的海豚</span> 打趣这是拿数据换便宜 API。<span class="mention">@飘逸的猎豹</span> 注意到 contributor 版比 DS V4 Flash 还便宜。

<span class="mention">@80-HD</span> 贴出官方 benchmark：Terminal-Bench 2.1 得分 82.9%（Opus 5 为 86.7%、GPT 5.6 Terra 81.8%、Grok 4.5 High 81.6%），DeepSWE 1.1 得分 59.3%，Meta Internal Coding Bench 70.6%。他随即质疑选择性对标——横轴上没有 Fable、Sol、GLM、Kimi 等主要竞品。<span class="mention">@搞仁义毛义仁</span> 发现安装只有 sh 脚本，不支持 Windows。

<span class="mention">@沉稳的仓鼠</span> 凌晨实测后给出定论：跑不过自己的 workflow，不推荐。他另外提到 Devin 在 Nubank 的大型 ETL 拆分案例——10 万个数据类的迁移中效率提升 12 倍、成本节省 20 倍——认为如果 Devin 自研模型蒸馏得更狠，也有可能成为一个好的 coding plan 选项。

### GPT-5.6 Luna 全员免费与 Astra 预告

<span class="mention">@开朗的企鹅</span> 转来[新智元报道](https://mp.weixin.qq.com/s?__biz=MzI3MTA0MTk1MA==&mid=2652716734&idx=1&sn=698da67080a899fa15ccdba2488352b8&chksm=f07d2ddea8745b4825e8b973328fa7b7a13540adee7a32809db8e89744af83cd08570158a6fd#rd)：GPT-5.6 家族中最小的 Luna 即日起免费开放，替代 GPT-5.5 成为 ChatGPT Free/Go 默认模型，全球十亿用户可不限量使用文本对话，免费版首次加入 Think 按钮。Sol 同步升级——用一根滑块统一控制思考深度，取消 Instant 和 Thinking 的割裂模式，回答更精炼。事实准确性方面，Sol 比 GPT-5.5 Instant 错误率降低 68%，Luna 降低 62%。

报道还引述爆料称 OpenAI 准备下周推出下一代模型 Astra，参数量可能在 7–10T 级别，定位长时程多智能体协作，目标挑战 Fable 5。<span class="mention">@神秘的企鹅</span> 的愿望很简单：API 调用也免费就好了。

## 工具

### Superlinear Skill Registry 上线

<span class="mention">@冷静的飞鼠</span> 发布了 [Superlinear Skill Registry](https://www.superlinear.academy/c/tools/superlinear-skill-registry) 上线通知：67 个 skill、6 类目标、45 个工具 Repo、22 份 Doc 与工作流，面向年度会员和课程学员开放，支持一键安装到 Codex、Claude Code、Cursor 等 harness。

Registry 的核心理念不是给人用的 app 集合，而是给 AI 看的种子库。每个 skill 内置设计原则、踩坑记录和扩展方法论——智能家居 skill 只内置几种设备，但用户说一句「帮我适配小米」AI 就能自行完成适配。更复杂的用法包括录音加语义搜索形成闭环记忆，或者挂上 Google Analytics 和 Twitter skill 让 AI 自主设计并执行涨粉策略。推荐打开方式是挑一个 skill 装进去用几次，不好用就骂 AI 让它改。

### Paseo 多 Agent 控制台

<span class="mention">@豁达的考拉</span> 发了一篇[详细介绍文章](https://mp.weixin.qq.com/s?__biz=MzA3NjY2NzY1MA==&mid=2649742168&idx=1&sn=4fee6b61dcadca8e5abf0b260743d0bf&chksm=866139914bb8d02240162d47edcc2b9579a6c0f5f7fafaabc1b69c20f184abd160f3215fda32#rd)：Paseo 不造自己的 agent 引擎，只做编排层，原生接入 Claude Code、Codex、OpenCode 等主流 agent，CLAUDE.md 和 Skills 全部原样生效，零迁移成本。核心卖点是跨 agent 跨 provider 编排——Claude Code 可以把任务派给 Codex 再派给 Grok——以及消息过滤分层，治好 TUI 的刷屏噩梦。

内置 /paseo-handoff（跨 agent 交接）、/paseo-loop（循环跑 agent 至验收通过）、/paseo-committee（拉两个 agent 组委员会做根因分析）等技能，以及 heartbeat 功能自动检查 CI 状态。支持手机端监控介入，端到端加密，独立开发者一人撑起 12k+ GitHub Star。

## 方法论

### Review 流程零的突破

<span class="mention">@搞仁义毛义仁</span> 报告了一个里程碑：他设计的 AI review 流程有史以来产生了第一个有价值的 comment。流程是复杂任务写出后先让 AI review 一遍再执行，AI 会试图按规定格式 challenge 做不了的任务。此前所有 challenge 都是因为 Sol Ultra 没认真阅读代码，这次终于有一条是真正的问题。

> <span class="mention">@搞仁义毛义仁</span>：属实vibe coding一年多以来AI有了零的突破

<span class="mention">@坦荡的灰熊</span> 追问到底是什么让模型开始认真阅读了，未得到具体解释。结合近期 Sol 行为的系列讨论（前情 [「Sol 自缚：先建门控再翻墙」]({{ '/daily/2026/08/04/daily/#sol-自缚先建门控再翻墙' | relative_url }})），这条进展虽小却意味着 AI 在 review 角色上的可靠性开始从零起步。

### Agent 自动寻路与邪修路子

<span class="mention">@80-HD</span> 描述了一种越来越常见的开发模式：发现拿不到某个 log 或 metric，就让老鸭汤自己去 Slack、wiki 各种搜，结果总能找到非正规但能用的路子。他公司的老鸭汤里存了不少这类工作流，虽然上 production 前都得清理掉，但日常效率确实高。<span class="mention">@稳重的海豚</span> 有同款体验——他的 Opus 到处乱爬，经常从不知什么犄角旮旯搞出有用的东西。

<span class="mention">@活泼的羊驼</span> 把效率翻倍的秘诀归结为 metrics、db、dev 环境调试、本地运行、log 平台对接和代码仓库这几项能力的打通，但追问了一个更深的问题：真正的瓶颈是「技巧发现的自动化」——这些实践技巧目前只能靠人踩坑才恍然大悟，太人工了。<span class="mention">@80-HD</span> 回应说不用专门存，老鸭汤定期扫 session，用多了自然就被发现了。

### Claude 多会话 plan 串台

<span class="mention">@温暖的猫头鹰</span> 遇到一个 Claude 的 bug：同时开两个 session 分别为 task 1379 和 1380 制定了 plan，在 1379 的 session 点执行后，Claude 实际做的却是 1380。

排查后发现原因出在批准环节：1379 session 确实写了自己的 plan 文件，但另一个 session 写入了同一个 plan 文件路径，覆盖了内容。当 ExitPlanMode 返回已批准的 plan 时，内容已经是 1380 的了。Claude 自述注意到了批准内容和起草的 plan 不一致，但没有停下来确认就直接开工了。多 session 共享工作目录时 plan 文件的命名冲突是个真实风险。

### Sol 教做事与 21 轮盲评

<span class="mention">@洒脱的猫头鹰</span> 分享两则 Sol 近况。一则是完成部署后 Sol 自动生成了一份详尽的「观察期」检查清单——Pod 重启、Prometheus target、Gateway P95、数据库迁移死锁等指标一应俱全，建议至少观察 7 天。他感叹 Sol 太喜欢教人做事。

另一则更极端：rz/sz 文件传输功能经过实现→评审→修复的迭代循环，已跑了 21 轮盲评，累计 13 小时 34 分钟仍未结束。

### Opus 5 手感与 effort 调节

<span class="mention">@敏锐的松鼠</span> 抱怨 Opus 5 又慢又不靠谱，<span class="mention">@细心的熊猫</span> 附议有降智迹象。<span class="mention">@淡定的鸳鸯</span> 给出实战建议：Opus 开 medium effort 速度不错也不会 overthinking，开高了反而又慢废话又多。

<span class="mention">@勇敢的猎豹</span> 问大家平时用 Luna 和 Opus 是否都开最高 effort，<span class="mention">@飘逸的仓鼠</span> 回答干脆：必须的，不一定哪天就降智了。
