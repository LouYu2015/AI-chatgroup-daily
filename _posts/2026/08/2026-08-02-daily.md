## ESP32 车库门实战

### 10 小时攻关，30 分钟 dev time

<span class="mention">@今天群内信息量极大</span> 凌晨交出一个完整的机器视觉项目：从搜集图像、标注、训练、量化，到 ESP32 上的系统构建、固件烧录、性能与耗能调优、最终部署。他的经验是一个很好的 senior scientist 从头做要一个月，而这次他的纯 dev time 只有 30 分钟，GPT-5.6 Sol 干了 10 个小时——吃中饭时只有一个想法，现在手上已经拿着一个能拍照、能跑神经网络识别车库门的单片机。心得写成了[《10小时攻关，半小时Dev Time：在指甲盖大小的单片机上跑神经网络识别车库门》](https://yage.ai/esp32-garage-door-ai.html)。

文章里的工程细节很密：AI 自己用本地视觉模型做初轮标注、用初始模型反挖开门样本迭代数据集；90 万参数的 MobileNet V4 直接 int8 量化后超 30% 结果反转，在他建议下改用 QAT 重训才压住损失；关键一步是让 AI 写一个仅供自己用的测试固件，HTTP POST 收图、串口回传温度延时和结果，打通烧录-指令-回传的全自动闭环。人的角色只剩两件事：强烈要求 AI 打通自主闭环，以及提前梳理技术坑给方向性建议。<span class="mention">@神秘的企鹅</span> 表示最喜欢看他的硬件分享。

### overfit 就完了：长尾视觉的直球生意

<span class="mention">@神秘的企鹅</span> 由此发问：很多看上去简单的硬件加上 AI 大脑是不是就有新场景和商业机会。<span class="mention">@直率的鸵鸟</span> 指出这些东西和开源项目以前就在，只是 AI 加持后非专业人士也能快速上手，就像现在人人都能写软件。<span class="mention">@今天群内信息量极大</span> 的回答把商业逻辑讲透了：

> <span class="mention">@今天群内信息量极大</span>：以前机器视觉为什么难，因为你一个模型要处理无数种可能的情况……现在为什么我这个算法效果这么好？因为只要管这一个车库，这一个视角。overfit就完了。问题一下简单很多。比如超市监控识别有没有人抽烟，视角定死，抽烟的位置就那几个，识别不要太简单。那为什么以前大家不这么做？因为做不过来。换个场景做一个月，谁做的过来。现在AI能把这个做的自动化，等于算法一下能作弊了，质量一下可以做得巨好。非常直球的商业模式。

<span class="mention">@随和的飞鼠</span> 独爱「overfit就完了」这句，评价非常的工程师。<span class="mention">@细心的飞鼠</span> 给出系统视角的类比：低成本硬件加通用训练框架平台，很像大规模计算里 commodity server 加 whitebox switch 加通用管理平台的组合；他还惊讶 ESP32-CAM 成本不到 1 刀，准备也弄一些试试，并感叹 IoT 炒了那么多年、现在可能真是爆发的时候。<span class="mention">@飘逸的狮子</span> 一句长尾机会定调。

### 识书讲故事：娃用硬件许愿池

<span class="mention">@冷静的飞鼠</span> 当场许愿：求做一个能自动识别书、给娃讲故事的 camera 加 speaker，最好能挂娃脖子上。<span class="mention">@今天群内信息量极大</span> 的第一反应是 ChatGPT Live 就行，后来补充 iPad nano 或类似的小安卓机 form factor 很吻合、能装 ChatGPT app 即可；<span class="mention">@稳重的海豚</span> 提出异议——AI 发音不行，容易把孩子发音带跑偏。<span class="mention">@聪明的鸵鸟</span> 贴来现成产品[小方机的报道](https://m.36kr.com/p/3903419023083397?channel=moments)：100 克的挂胸前设备，主打 PBL 项目式学习和第一视角提问。

## 方法论

### Token maxxing for yourself：月烧 5.4 万刀

昨晚 <span class="mention">@沉稳的仓鼠</span> 给全群的烧钱行为定了性，<span class="mention">@优雅的鲸鱼</span> 与 <span class="mention">@热情的狮子</span> 齐声附议，后者补充老 O 老 A 都是 50 倍补贴、现在是时代红利：

> <span class="mention">@沉稳的仓鼠</span>：不过我真心觉得还是得 token maxxing for yourself 很多 hands on 的体验只有真的一天烧个 Billion 级别的 token 才有感悟

凌晨 <span class="mention">@热情的狮子</span> 晒出账单坐实：7 月 62.9B token、折合 5.47 万刀，平均每天 20 亿 token、1800 刀，8 月才 2 天已经烧了 9.89 亿；他连呼感谢 sam 感谢 tibo，<span class="mention">@豁达的灰熊</span> 则许愿 A 社也该出个 tibo 这样的角色。另一边 <span class="mention">@开朗的企鹅</span> 报告 K3 weekly 额度 100% 用完，这次做了几个比较大的修复、效果还是可以的。

### 先问可以抄谁：workflow 框架选型

昨晚 <span class="mention">@敏锐的海狸</span> 求教：他在设计一套支持循环回边（Writer→Reviewer→Writer）的 agent workflow 管理系统，要求每个节点能独立测试和 A/B、支持 checkpoint、断点续跑、人工审批和完整 tracing，看了 LangGraph 后想知道还有哪些成熟框架，尤其是循环状态管理和生产可观测性上的坑。他的 Codex 已经吭哧吭哧自己做了一天，他才意识到这玩意儿难搞。

<span class="mention">@谨慎的灰熊</span> 给出一套完整的方法论：这是典型的 graph engineering 问题，让 Codex 搜最新的文章和研究、跟你讨论出方案；更重要的是尽可能用人类已有的知识资产——第一时间先问可以参考哪些软件、哪些工作流引擎、哪些权限控制，选技术栈时再让它确认这个项目还活着吗、最近有没有更新、流不流行。他的血泪经验是没交代这些时，AI 自己写的效果就是没有开源好。<span class="mention">@敏锐的海狸</span> 表示已在实践这条路：pipeline 从 Codex 自写 taskd 换成了 dagster，但图管理这块适配 agent 的估计还得自己写；<span class="mention">@幽默的犀牛</span> 在旁调侃这波也没让 LangGraph 迎来第二春。

### 魔改上游与忍住不动

<span class="mention">@稳重的海豚</span> 昨天宣布 herd 收摊后，今天把候选看了一圈：从 <span class="mention">@今天群内信息量极大</span> 的 opencode client 到 happy、qm、agentcanvas、coder、herdr，结论是产品都不错但很多 quality of life feature 都没有，还是得拿过来自己魔改、在上面加定制化——好处是心理压力小、维护成本低，坐等上游大佬开工就行，「删自己的slop太爽了」。搞了半天他自己也乐了：这不就和 cowork 是一回事吗。

<span class="mention">@冷静的麋鹿</span> 是同款路线的老用户：用 <span class="mention">@今天群内信息量极大</span> 的 opencode client 稍微魔改，大功能等上游，这两天看到 <span class="mention">@今天群内信息量极大</span> 的截图变化太大又集中追了一波。他的反思很有代表性，还点赞了 <span class="mention">@冷静的飞鼠</span> 前两天那篇讲忍住不动的文章：

> <span class="mention">@冷静的麋鹿</span>：其实，用其他人的，很多小地方，忍忍都能过得去，之所以现在难忍，还是动一动的门槛太低了。过去那些难用到死的saas软件，也都慢慢习惯了。

魔改的具体形态相当接地气：<span class="mention">@冷静的麋鹿</span> 把话筒按钮从左上角移到右上角，因为右手九宫格单手打字摸不到左边，<span class="mention">@80-HD</span> 表示自己也移到了右边，<span class="mention">@稳重的海豚</span> 的话筒则放在最底下输入键旁。<span class="mention">@冷静的麋鹿</span> 由此总结：这么多 agent 客户端长得一样，可能都是各自思考过的——思考完发现 md 一样还是最好。

> <span class="mention">@沉稳的仓鼠</span>：我们上个月有一个泰国的专家，给我发邮件，说看到我写过一篇文章，讲一个问题该怎么解决，他想跟我探讨一下。我tm标题都没看懂🤷

### <span class="mention">@淡定的大象</span>连更：FIM 完形填空

<span class="mention">@淡定的大象</span> 今天的连更是[《英语考试的完形填空，就是大模型学会写代码的全部方法》](https://mp.weixin.qq.com/s?__biz=MzY4NTM1MDc1NQ==&mid=2247486285&idx=1&sn=f39473c63e0580c4de58b361f48b2ef4&chksm=f23dc42e3fa4a6e7ae61516f0a83f827b1c58774e3e75f5fc3af69414bc9ac547d42e84a6ce6#rd)：代码补全本质是完形填空，GPT 的因果掩码天生不会填空、BERT 会填空但不会续写，FIM 不动模型结构只重排数据（prefix+suffix→middle），损失只算 middle 段，混合 PSM/SPM 两种排序——StarCoder 到 Qwen-Coder 全靠这一套。群里没讨论，连更惯例照登。
