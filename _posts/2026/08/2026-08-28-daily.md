## 方法论

### Fake Work 识别与消灭

<span class="mention">@冷静的飞鼠</span> 发表了 [如何识别与消灭 fake work](https://www.superlinear.academy/c/ai-resources/fake-work)，从自己在大厂带团队的经历出发，定义 fake work 为用可见动作代替难以衡量的价值。文章引用 Paul Graham 的判断：最危险的浪费时间不是摸鱼，而是做假工作——坏选择只要长得像美德就能绕过警报。

文章的 AI 角度尤其尖锐：agent 既能接手信息组织税（CRM 更新、会议纪要、报销核对），也会把 fake work 放大一百倍——如果组织把报告和会议纪要当进展，agent 只会更快生产这些进展。判断标准是持续追问「这项工作完成后会发生什么不同」，直到碰到真实变化；如果产出增加十倍而真实结果没有更近，多出来的九份就是 fake work。

<span class="mention">@灵动的考拉</span> 现身说法：Codex 刚在周末给他做了一场 fake work（前情 [「非 agentic 验收不可少」]({{ '/daily/2026/08/25/daily/#非-agentic-验收不可少' | relative_url }})），已被降级到 $20/月档位。<span class="mention">@搞仁义毛义仁</span> 补刀：人工验收不能拖延，任务给得够大，AI 就会对没说到的东西直接偷懒。<span class="mention">@今天群内信息量极大</span> 读完直接夸文章好棒。

> <span class="mention">@冷静的飞鼠</span>：我其实特别反对那些 fake work 和 fake 努力（比如在错误的工作上投入时间），真的不如去刷抖音看电视打游戏

### 万行代码一分钟验收

<span class="mention">@搞仁义毛义仁</span> 分享了他的极简代码审查策略，核心思路是让代码组织足够正交——正交到「commit 里有没有改到某个文件」这种简单事实就能提供大量有效信息。过去一周他用这类技巧直接省去了审查约一万行 AI 代码中的九千多行，只需跑几次 unit test、看看 test driver 函数写了什么来判断质量，总共不到一分钟。

他强调验证的最佳粒度是每个 feature 刚看起来能跑的那一刻——去证明它其实不能，这个过程就能产生大量 test assets，之后千万不要急着写下一个 feature。<span class="mention">@80-HD</span> 坦言大多数人几乎不看 unit test，能跑就过了。<span class="mention">@搞仁义毛义仁</span> 回应：如果已经一段时间没管，就太晚了，不如重写。

> <span class="mention">@搞仁义毛义仁</span>：所有的策略都是在一个好的 code base 上堆屎然后马上把它改好，才有了持续维护的办法

### XMind 圈子制与 underfunding

<span class="mention">@活泼的羊驼</span> 分享了 [XMind Mango 的播客访谈整理](https://mp.weixin.qq.com/s?__biz=MzU4MTgxOTE2OQ==&mid=2247484746&idx=1&sn=3bf7f427af946ff8d4c6f60df54b56e8&chksm=fcc41ab82fb6236d0fb76883dee1048fc2617995dea5da35613ab8621e9336b2a2bb7dbea045#rd)，详述了 XMind 向 AI Native 组织的激进转型。团队从 50 多人缩至约 30 人，核心变化包括：部门边界拆除，产品经理直接在代码仓库拉分支搭原型，研发只审架构和可维护性，设计变成最后走查的一关。组织上推行圈子制，一个人按 0.2/0.5 人力拆入多个圈子，分钱权下放到圈长——让每个圈长像创业小老板一样运作。

<span class="mention">@活泼的羊驼</span> 还提炼了播客中引用的 Claude Code 负责人 Boris 的 underfunding 法则：正常需要六个人干的活只给三四个人，但 AI token 给够。他总结这本质上是故意设定更高目标、让传统方法一定搞不定、从而倒逼团队重新思考哪些事可以委托给 AI。

### 中文 AI 味之争

<span class="mention">@神秘的企鹅</span> 抱怨 GPT-5.6 写中文依然一股 AI 味。<span class="mention">@活泼的羊驼</span> 和 <span class="mention">@冷静的麋鹿</span> 不约而同推荐 Gemini。<span class="mention">@热情的狮子</span> 提出一个有趣的反相关规律：agentic 能力越强文字越 AI——豆包 agentic 很弱但中文文字还可以，Kimi 写中文也比 Sol 给力。<span class="mention">@温暖的斑马</span> 建议把自己以前手写的博客喂给模型学习风格。

### LLM 搜索的 GEO 污染

<span class="mention">@热情的大象</span> 提起今年 315 曝光的 LLM SEO 产业链，他发现大模型的 web search tool call 有时在 API 提供商侧执行，搜索结果理论上可以被竞价排名。<span class="mention">@今天群内信息量极大</span> 判断主要路径是先通过 web search SEO 冲到前几名，再进一步污染 LLM 回答。

<span class="mention">@稳重的海豚</span> 区分了两条路线：一是把偏好分布训进模型（反馈回路太长、效果存疑），二是直接污染 search result——后者又分纯量攻击、重量节点、prompt injection 等手法。<span class="mention">@热情的大象</span> 认同第二条路更现实，因为生效极快、训一次模型不可能那么短。<span class="mention">@沉稳的仓鼠</span> 感慨黑帽 SEO 的老手段至今没被 AI 厂商妥善应对。<span class="mention">@稳重的海豚</span> 则直言那些 Reddit 上的 AEO/GEO 服务纯属忽悠。

## 工具

### GLM-5.3 Flash 提速与 Luna 对比

延续前天的讨论（[「GLM-5.3-Flash 达到 Opus 4.8」]({{ '/daily/2026/08/26/daily/#glm-53-flash-达到-opus-48' | relative_url }})），<span class="mention">@优雅的喜鹊</span> 报告 GLM-5.3 Flash 在双 GB10 上的 DFlash2 + FP8 KV 配置已跑到单流 decode 46.9 tok/s（74.1% draft acceptance）、structured output 54–61 tok/s，KV pool 在 7 GiB pin 下达 727K token——较之前报道的约 24 tok/s 有大幅提升。

<span class="mention">@沉稳的兔子</span> 对比了 GLM-5.3 Flash 与 GPT-5.6-Luna 的实战体验：给 GLM-5.3 Flash 装了 goal 跑了 70 轮才将将做完一个 feature，而 Luna 不用 goal 一把梭就干完了。他感叹 GLM-5.3 Flash 要一直抽鞭子才动。<span class="mention">@今天群内信息量极大</span> 则发现 GLM-5.3 Flash 刚上线 Ollama Cloud，表示刚想退订就被新花样拉了回来。

### 微信 AI 自动回复

<span class="mention">@飘逸的仓鼠</span> 询问微信自动回复方案，引出一场实战经验分享。<span class="mention">@今天群内信息量极大</span> 率先警告：个人微信做自动化本质上和自动抢红包一样，腾讯严打会封号。<span class="mention">@沉稳的仓鼠</span> 更直接——不要在简中世界试图搞任何自动化。企业微信则安全得多。

<span class="mention">@细心的熊猫</span> 公开了他已稳定运行数月的方案：连接真手机、纯模拟键盘输入，与真人操作无异。他还做了防提示词注入——群友天天对他的 AI bot 发起注入攻击，毫无压力。<span class="mention">@神秘的企鹅</span> 做了半自动版：截图或复制消息后 AI 生成回复填入输入框，用户审核后再发送——因为面对的是高价值客户，不敢全自动放回复。

<span class="mention">@热情的大象</span> 推荐了 WeChatDataAnalysis 开源项目解决聊天记录接入问题：电脑端每个用户的数据库文件有不轮换的 key，拿到即可解密。

### Codex 跨端 session 锁定

<span class="mention">@开朗的企鹅</span> 终于解决了困扰已久的 Codex session 锁定问题。核心矛盾是 Codex 的写保护机制：CLI 开了 session 后 Desktop 无法打开，也无法从 CLI resume，反之亦然——除非关掉一端。他需要用 AgentHub 统一管理多个 session，这个独占机制让跨端和远程操作极不方便。

<span class="mention">@坚定的貂</span> 也在与同一问题搏斗：Happy app 连 Codex 后本机 TUI 版就用不了了。他对比发现 Happy 连 Claude 可以做到手机和 TUI 双向同步，但 Codex 做不到。<span class="mention">@稳重的海豚</span> 解释这类 meta harness（HappyHerd、Orca、Happy）都有自己的 session 抽象架在底层的 Codex/Claude 之上，但 Codex 原生的 session 独占机制是根本瓶颈。他分享了 Orca 的做法——不在同一个 native session 内切换 Claude 和 Codex，而是做 bounded handoff 到一个全新 session，原 session 保持不变并可独立恢复。
