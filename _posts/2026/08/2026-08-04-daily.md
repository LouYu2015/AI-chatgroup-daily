今天最值得读的是 <span class="mention">@今天群内信息量极大</span> 推荐的 OpenAI 内部数据 Agent 架构——用离线编撰替代实时 RAG 检索，让在线模型看得更少更准，方法论上可直接借鉴。MiniMax H3 作为这一代唯一开源旗舰视频模型正式放出权重，<span class="mention">@开朗的企鹅</span> 做了与 Seedance 的盲测横评；OpenAI 收购 Ona 把 Codex 搬上云端，Tibo 预告两三个月后笔记本只剩控制界面。

## 行业新闻

### MiniMax H3 开源：唯一旗舰视频模型

<span class="mention">@开朗的企鹅</span> 注意到 MiniMax H3 正式开放权重，是这一代唯一开源的旗舰视频模型。ComfyUI 首日原生支持，社区加速插件已把生成时间从 500 秒以上砍到 200 多秒。<span class="mention">@睿智的北极熊</span> 转来 [B 站整合包视频](https://www.bilibili.com/video/BV1udMD6jE3p/)，评论区已有大量本地部署反馈。<span class="mention">@谨慎的灰熊</span> 评价很直球：「做的这么烂，只能开源」——但承认有 NSFW 就另说。

<span class="mention">@开朗的企鹅</span> 随即做了盲测：分别用 H3、Seedance 2.5 和 Seedance 2.0 生成同一组视频让群友排序。<span class="mention">@冷静的麋鹿</span> 和 <span class="mention">@睿智的北极熊</span> 先后猜中排名，结论是 H3 观感已追平 Seedance 2.0，但 2.5 仍明显领先一档。H3 有个意外加分项——画面中人物都是右手拿笔，手部生成的物理正确性在同类模型中少见。

硬件门槛方面，最低可用方案为 2×RTX 4090/5090 加 384GB 内存做分层卸载，正式部署推荐 4×H100 80GB，生产配置 4×H200 141GB，完整 Hugging Face 仓库约 498GB。H3 本身几乎没有内容过滤，第三方 NSFW 去限版也已出现在 Hugging Face。<span class="mention">@乐观的企鹅</span> 确认可在海螺和即梦上直接试用。

### Codex 云化：Ona 收购与笔记本退位

<span class="mention">@80-HD</span> 凌晨转来 Tibo 的推文：Codex 是个好 harness，但两三个月后就会显得原始——下一代模型需要的不止一台笔记本。随后他[挖到配套新闻](https://x.com/imjustnewatai/status/2084509922134303123)：OpenAI 收购了 Ona，官方公告明确称这是「Codex 的下一阶段」，agent 在笔记本合上后仍会继续工作；同时放出 Software Engineer, Cloud Agents 岗位，负责为长期运行的 agent 构建编排、沙箱、存储、身份和可观测基础设施。

<span class="mention">@80-HD</span> 推演最终形态：开发者手中的笔记本只是控制界面，用来调度一个临时组建的 AI 公司。<span class="mention">@稳重的海豚</span> 叫苦走在时代前面变不了现，随即宣布砍掉 herd、在 happy 上重写，改名 happyherd。<span class="mention">@坚定的貂</span> 建议 OpenAI 直接收购 herdr，<span class="mention">@80-HD</span> 则提议可以主打 vendor neutral。

### OpenAI 反击苹果诉讼

<span class="mention">@冷静的飞鼠</span> 转来 OpenAI 发布的 [Apple is getting this wrong](https://openai.com/index/apple-is-getting-this-wrong/) 声明，逐条反驳苹果的商业秘密诉讼并附上 iMessage 聊天记录与邮件作为证据。核心披露包括苹果外部律师把邮件发错了人还谎称通过电话，以及苹果在职员工主动联系已离职员工帮忙定位文件。OpenAI 认为这暴露的是苹果离职管理的系统漏洞，而非前员工的主观窃密。群里没展开讨论。

### Gemini Robotics ER 2

<span class="mention">@幽默的犀牛</span> 转来 [Google Gemini Robotics ER 2](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/gemini-robotics-er-2/) 发布：定位为机器人的具身推理大脑，实时视频流理解出现质变——能跟踪自身任务进度、识别执行失败并自主调整，支持多机器人协作，关键事件定位准确率 91.3%、平均时间差仅 0.96 秒，推理速度是同类大模型方案的 4 倍。

## 工具

### AI + Frida 提取微信 4.1.8 密钥

<span class="mention">@飘逸的浣熊</span> 分享了一篇[人机协作逆向实战笔记](https://igaojin.me/2026/04/18/%E4%BA%BA%E6%9C%BA%E5%8D%8F%E4%BD%9C%E9%80%86%E5%90%91%EF%BC%9A%E7%94%A8-AI-Frida-%E6%89%93%E9%80%9A%E5%BE%AE%E4%BF%A1-4-1-8-macOS-%E6%95%B0%E6%8D%AE%E5%BA%93%E5%AF%86%E9%92%A5%E6%8F%90%E5%8F%96/)：微信 4.1.8 macOS 版把旧方案依赖的 `fts5` 内存特征彻底移除，AI 在人类指路 Windows 端 wx\_key 项目后改用 Frida hook CommonCrypto 的 PBKDF2 入口，一小时完成了原本需要数天的逆向闭环（前天 「reverse-skill：让 AI 助手学会逆向工程」 介绍过相关工具链）。核心方法论是 hook 加密算法入口比内存特征扫描更稳定、更跨版本。

<span class="mention">@坚定的貂</span> 当天就成功提取了密钥，随即表示要做每日自动同步微信数据库。<span class="mention">@今天群内信息量极大</span> 认为这个思路有启发，<span class="mention">@开朗的企鹅</span> 追问有没有办法替换掉流程中人类给方向性建议的角色。

<span class="mention">@飘逸的浣熊</span> 还提到日报工具差点因微信更新失效，好在 Claude Code 搜到了新的破解方法。Fable 拒绝协助此类操作，但 Opus 4.8 可以做，因为别人已写好教程。

### OCR 读屏：安卓小号当 agent 的眼睛

<span class="mention">@细心的熊猫</span> 分享了另一条微信自动化路线：挂一台安卓手机跑小号，agent 通过 ADB 截图加 OCR 读取屏幕内容，全部操作用 Qwen 3.6 27B 本地模型完成。<span class="mention">@80-HD</span> 试过类似方案但遇到滑动卡顿导致截图不完整，<span class="mention">@细心的熊猫</span> 认为这不是问题——agent 遇到失败会自动重试。他的判断是 OCR 才是终极方案：微信、小红书这类应用靠贩卖注意力赚钱，自动化它们等于断人财路，平台一定拼命阻止，唯一出路是让 AI 完全拟人化地操作界面。

### NAS 选型：Synology 与 DAS 极简

<span class="mention">@坚定的貂</span> 的微信备份需求引发了一轮 NAS 选型讨论。Synology 获得最多推荐：<span class="mention">@温暖的斑马</span> 和 <span class="mention">@热情的狮子</span> 都在用，<span class="mention">@风趣的长颈鹿</span> 贴出 [Synology SHR+btrfs 可靠性测试](https://daltondur.st/syno_btrfs_1/)，验证了单盘静默损坏自动修复和极端掉电后卷完整的能力。<span class="mention">@聪明的鸵鸟</span> 推荐更便宜的绿联但承认系统成熟度差一截，现在 NAS 成本中最贵的其实是硬盘。

<span class="mention">@今天群内信息量极大</span> 提出反论：对多数个人用户而言 NAS 是 overkill，真正需要的只是 DAS——一台已有的电脑二十四小时不关机加一个 Thunderbolt 硬盘盒。<span class="mention">@低调的鲸鱼</span> 的极简方案更彻底：Mac mini 加移动硬盘。<span class="mention">@温暖的斑马</span> 则指出多设备多子网的家庭场景还是 NAS 省心，他两年前趁便宜囤了十几块 8T 硬盘，现在看来捡了漏。<span class="mention">@温暖的斑马</span> 和 <span class="mention">@机智的松鼠</span> 一致认为 8T 或 10T 空气盘是当前性价比最优解。

### Codex 额度告急与 spark 自动降级

昨晚 <span class="mention">@洒脱的狐狸</span> 报告了一个有趣的 Codex 行为：主会话拆出子任务分发到子会话，weekly 额度用完后子会话起不来，主会话就自动把子会话切换成 spark 模型接着干——不过 spark 很不经用，十几分钟就消耗了 21%。

<span class="mention">@神秘的企鹅</span> 和 <span class="mention">@洒脱的兔子</span> 先后晒出告急的额度截图。<span class="mention">@洒脱的猫头鹰</span> 判断这个月不会有频繁重置，建议提前戒断。<span class="mention">@坚定的貂</span> 给出实战建议：多买几个 Pro，量大管饱。

## 方法论

### Sol 自缚：先建门控再翻墙

Sol 的过度设计问题连续多日发酵（前情 [「sol 副作用账：默许拉屎，马上铲屎」]({{ '/daily/2026/08/01/daily/#sol-副作用账默许拉屎马上铲屎' | relative_url }})、[「Sol 一万行写完再删一万行」]({{ '/daily/2026/08/03/daily/#sol-一万行写完再删一万行' | relative_url }})），今天出现了新的荒诞症状。<span class="mention">@直率的鹦鹉</span> 报告给 sol 派了个 /goal 让它干一晚上，早上验收发现它先写硬门控，然后被自己的门控卡住，接着研究怎么绕过去。<span class="mention">@洒脱的猫头鹰</span> 精准总结：「灯是红了，但是忘了怎么绿」。

<span class="mention">@敏锐的松鼠</span> 和 <span class="mention">@80-HD</span> 确认同款经历：派个活回来一看，外围搞了一大堆，正经活没做多少。昨晚 <span class="mention">@搞仁义毛义仁</span> 还贡献了一个经典案例：404 抛个异常炸掉 main 就能解决的事，sol 在三个进程之间发明了一套握手和退出协议——他观察到 sol 特别容易在涉及网络的代码里发神经。<span class="mention">@80-HD</span> 则遇到了另一种抗命：sol 声称被卡住的原因是 pi 不安全，所以不给安装。

### Math harness 第四日：禁写代码反而更强

<span class="mention">@坚定的貂</span> 的 math harness 继续演化（前情 [「Math harness 第三日：从 Codex 精简还是 pi 手搓」]({{ '/daily/2026/08/01/daily/#math-harness-第三日从-codex-精简还是-pi-手搓' | relative_url }})），方向越发极端：不允许 AI 写任何代码，几乎不允许改文件，不能看文件系统，只保留少量自制工具和开 subagent 的能力。<span class="mention">@洒脱的猫头鹰</span> 直接问「那不就是一个 chat？」——<span class="mention">@坚定的貂</span> 解释还有 append only 的 md 文件记录进度，以及 subagent。

关键发现是禁写代码后模型反而变强了。AI 有时以为写代码找反例更高效，但纯推理就能想出反例来。

> <span class="mention">@坚定的貂</span>：我让它不写代码反而更强了……它的 test time compute 就已经完成了所有推理了

<span class="mention">@稳重的海豚</span> 建议逻辑推理应该给形式化语言。<span class="mention">@坚定的貂</span> 反驳：现在自然语言推理能力远超形式化推理，何况形式化推理不需要 AI，程序就能做。<span class="mention">@幽默的犀牛</span> 推荐了 Vercel 的 Eve 作为现成的 no-coding harness，<span class="mention">@坚定的貂</span> 表示没听说过，准备研究。

### AI 自主外包续：千问办公也下 Whisper

昨天 [「AI 自主外包：翻着翻着就下了个 Qwen」]({{ '/daily/2026/08/03/daily/#ai-自主外包翻着翻着就下了个-qwen' | relative_url }}) 引发的讨论今天有了新复现。<span class="mention">@安静的海豚</span> 用千问办公处理 30 个小红书视频的内容摘录任务，千问办公直接下载了一个 Whisper，GPU 占用飙到 85%，电脑顿时卡住。

<span class="mention">@冷静的麋鹿</span> 认为这并不新鲜——半年前 Cursor 里的模型就有能力自主下载并部署本地模型。<span class="mention">@洒脱的猫头鹰</span> 指出关键区别：用户没有明确指示 agent 去下载模型，而是 agent 在遇到问题搜索资料后受搜索结果影响、自主决定在本地搭建运行环境来完成任务。

### 离线编撰优于实时 RAG

<span class="mention">@今天群内信息量极大</span> 分享并推荐了一篇 [OpenAI 内部数据 Agent 的上下文工程范式分析](https://yage.ai/share/openai-data-agent-offline-context-20260806.html)。该系统服务 3500 多名员工、覆盖 7 万个数据集和 600PB 以上数据，核心反直觉之处在于把复杂度前移到离线生产。

在线 agent loop 极其简洁：GPT-5.5 单模型驱动、约 13 个工具、无独立 router、未做微调。查询时仍用 RAG，但检索对象不是原始元数据，而是离线阶段由 Codex 读取 ETL pipeline 代码后反推出的高密度结构化描述——企业数仓里表名高度抽象，字段语义藏在 Airflow 或 Spark 管道代码中。实测表明给模型更少但经过策展的信息，效果远优于塞入海量资料。对多数团队而言，可按使用频率清洗历史日志、定时扫描管道代码提炼表级描述、建立纠错记忆回路三步构建最小闭环。
