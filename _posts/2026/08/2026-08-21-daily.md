今天最值得读的是 <span class="mention">@随和的企鹅</span> 用 Rust 手搓的 agent——graph executor 把 Qwen 3.8-max 推到 0.944，由此引发的讨论让文件管理加 grep 胜过 RAG 成为群内新共识。V4 Flash 多模态版上线，Codex 达到 2000 万活跃用户并预告 banked reset，OpenCode 的 Ox Alpha 被确认为 GLM。

## 手搓 Agent 与土方法

### Graph Executor 首秀

<span class="mention">@随和的企鹅</span> 展示了自己用 Rust + ratatui 纯手搓的 agent 中新增的 graph executor 功能。核心思路是先把目标拆成有向图，并行执行各节点，再合并结果。他在 TermBench 3 的一个灰度评分任务上做了对比：

| 配置 | 评分 |
|------|------|
| v4-pro plain | 0.556 / 0.750 |
| qwen3.8-max plain | 0.750 / 0.694 |
| flash plain (×3) | 0.750 (stable) |
| flash + --graph | 0.889 |
| qwen3.8-max + --graph | **0.944** (34/36) 🏆 |

Graph 模式下 Flash 和 Qwen 都有明显提升，token 用量约翻倍，整条 chain 用同一个模型，没有高模做 evaluator 或 planner。<span class="mention">@今天群内信息量极大</span> 评价这个思路「非常 Anthropic（dynamic workflow），但效率看起来比 dynamic workflow 高不少」。<span class="mention">@随和的企鹅</span> 之前也集成过 llm-as-a-verifier，确实有用但消耗和执行速度都受不了，graph executor 是更实用的替代。

Agent 还有几个亮眼设计：peers 之间通过文件系统互发消息或 queue 任务，方便同 repo 下一路做 research、一路做执行；context tab 分段显示实际 context 内容，debug cache 和确认模型看到了什么非常方便。模型组合以 K3 为主力，K3 额度耗尽后 Qwen 接力。

### 文件管理与朴素记忆

<span class="mention">@随和的企鹅</span> 的 peers messaging 实现极其朴素：~/.config/agent 下的 session 文件，其他 agent 通过文件系统触发更新。他本来想用 socket，被 K3 死谏劝回——文件天然保留消息 trail 方便 debug，反正也要周期性 purge。他坦言这条自己完全没想到。

<span class="mention">@开朗的企鹅</span> 确认所有 agent 本质上都是用 local file 管理，fork 就是复制一份。如果用文件管理根本不用考虑恢复现场——agent 自己在跑，状态都在文件里，牺牲的只是即时性。<span class="mention">@今天群内信息量极大</span> 也赞同文件最好，并顺势推荐了他的 [session export skill](https://skills.superlinear.academy/?skill=ai-session-export)：

> <span class="mention">@今天群内信息量极大</span>：我发现搞fancy的每日记忆归档不如就每日导出聊天记录。然后光grep就很有价值。

某群友分享了在公司搭建知识库的经历：上了 RAG 后系统极其复杂，效果却与直接用 markdown 没什么区别。更尴尬的是先走 RAG，怕漏了再走数据库全文搜索——两套成本全吃。<span class="mention">@今天群内信息量极大</span> 给出务实建议：公司里不搞 RAG 总有别人来搞，不如自己接了底下偷偷换成 md + grep，效果还更好。

> <span class="mention">@今天群内信息量极大</span>：技术的高地，你不去占领，煞笔就会去占领

这个朴素方法完胜的主题与前几天的讨论一脉相承（[「离线编撰胜过在线花哨」]({{ '/daily/2026/08/19/daily/#离线编撰胜过在线花哨' | relative_url }})），从 GraphRAG 进入 maintenance mode 到文件 + grep 取代花哨记忆系统，群内共识越来越清晰。

### Terminal 的结构化困境

昨天的 PTY vs ACP 路线之争（[「PTY vs ACP 路线之争」]({{ '/daily/2026/08/20/daily/#pty-vs-acp-路线之争' | relative_url }})）今天延伸到更根本的问题：terminal 作为 agent 交互界面是否有天生缺陷。

<span class="mention">@活泼的羊驼</span> 认为 herdr 这类纯终端工具不太适合提升人的并发度——他从 terminal 切到桌面版后并发度提升了 2–5 倍，侧边栏总结、右键 fork、视图管理都是终端做不到的。<span class="mention">@淡定的鸳鸯</span> 直指 terminal 最大的问题是依赖 keyboard input 的线性交互，UI 的多维度交互优势太大。

<span class="mention">@洒脱的猫头鹰</span> 从更底层解释：terminal 的输入和输出两个流本质上没有关系，无法稳定形成 request ↔ response 的对应。structured data 从 shell 传到 PTY 的过程中丢掉了——人是靠背景知识推断两个输出之间的关联，但程序做不到。

> <span class="mention">@洒脱的猫头鹰</span>：有点像古法爬虫，目标站点的 dom path 不能大改，改一次爬虫就得重写一次。

<span class="mention">@随和的企鹅</span> 感慨：那不如自己手搓个 agent。<span class="mention">@洒脱的猫头鹰</span> 回应：固定某一个 agent 用它自己的 SDK 就没有这些问题——问题都是因为 agent 太多太新导致的。ACP 的主要困难也不在协议设计，而在这些 agent 作者愿不愿意支持统一接口。

## 工具

### Qwen 3.8-27B 实战续报

<span class="mention">@细心的熊猫</span> 分享了一份 [Qwen 3.8-27B 与 V4 Flash 的对照评测](https://loktar00.github.io/qwen3-8-27b-vs-deepseek-v4-flash/)：8 个真实 bug 修复任务、48 次运行，结论是两者水平相当、排名随 harness 翻转。一个 27B 开源模型做到了与商用 Flash 模型持平。

邮件清理项目也迎来终章（前情 [「实战落地百态」]({{ '/daily/2026/08/19/daily/#实战落地百态' | relative_url }})）。INBOX 总计 696,103 封邮件，Qwen 3.8 分类后 568,066 封（81.6%）为广告，保留 128,037 封，零未分类。删除过程中 Qwen 自主发现了 iCloud 的限流规律——先给 2 个快 chunk（~50 msg/s）然后节流到 ~8 msg/s——于是提出将发送速率限制在稳态 ~30 msg/s 以避免触发重度节流。<span class="mention">@细心的熊猫</span> 吐槽 iCloud 基础设施极差，70 万封邮件要删十几个小时。

## 方法论

### AI 副业：别越做越不值钱

<span class="mention">@冷静的飞鼠</span> 分享了他准备的 [AI 副业演讲 deck](https://www.lizheng.ai/decks/ai-side-income-career-capital)，核心是打破大厂程序员的常见思维盲区：副业关键不是快速做产品而是快速验证付费意愿；技术先进不等于赚钱，多数项目输在需求理解和分发；第一笔收入不等于方向成立，复购和可重复获客才是判断标准；不能积累客户信任、数据和渠道的项目反而会稀释职业竞争力。

> <span class="mention">@冷静的飞鼠</span>：为啥总有程序员创业第一想法是我搞个fancy技术用户就会来，or比别人fancy的技术才敢收钱，这就是原因

<span class="mention">@活泼的羊驼</span> 现身说法——他把自己做的 MCP 服务以每月 10 元卖了出去，用收费来验证产品是否真有价值。<span class="mention">@洒脱的猫头鹰</span> 评价这也是从 0 到 1 打通了商业闭环。<span class="mention">@活泼的羊驼</span> 自嘲一天亏 20 万。

<span class="mention">@随和的企鹅</span> 指出 OpenCode 没什么独特技术，纯移动互联网买量逻辑。<span class="mention">@开朗的企鹅</span> 回应：会买量是互联网核心技术。<span class="mention">@飘逸的狮子</span> 则从另一个角度追问——如果目标是赚钱，是不是应该先学什么是钱、以及别人是怎么赚钱的。<span class="mention">@稳重的海豚</span> 同日分享了 [a16z 合伙人的访谈](https://mp.weixin.qq.com/s?__biz=Mzg3NDc2MjQxMg==&mid=2247495140&idx=1&sn=3655d38e9add4f311ddae6d9a69f020c&chksm=cfe4b9bdd6ba4fc399f36ed79b76c5a4591e4069d3519681c897cc086adc7ac9026e5aee0f46#rd)——做小、做深、卖贵，41,000 个用户每月 $200 就是一亿美金；<span class="mention">@沉稳的仓鼠</span> 则分享了他写的 [AI Native Distributor Playbook](https://ranchen.org/content/20260814-ranchen-article-ai-native-distributor-playbook)，认为 AI 不会让中间商消失，反而让小团队第一次能把分销能力做成软件和数据。两篇值得对照阅读。

## 闲聊花絮

### 番茄炒蛋加东坡肉

<span class="mention">@坚定的貂</span> 转发了一条出圈推文吐槽 GPT 5.6：让它做番茄炒蛋，它往里加了东坡肉；说没必要，它同意去掉；提 PR 后发现标题写着「番茄炒蛋（无东坡肉）」，注释里还写了一大堆为什么本道菜不需要加东坡肉。多位群友深有共感，<span class="mention">@随和的喜鹊</span> 说他刚 review 了一个 PR，两行代码改动配了上百行 comment。

<span class="mention">@搞仁义毛义仁</span> 由此延伸出一个观点：AI 写给 AI 看的文档如今没必要管它写什么了，反正最后都有 CI 做 fact check。真正该做的是把文档当成 API 的一部分 deliver，最好顺带给出测试方法——确保用户 one shot 成功率也是用户体验的一部分。

### 15 年写作 AI 复盘

<span class="mention">@沉稳的仓鼠</span> 让 AI 通读了他 2011–2026 年发表的全部 1114 篇文章，产出了一份[独立复盘报告](https://ranchen.org/content/20260821-rancheng-article-fifteen-years-independent-review)。AI 摘出约 1800 条带判断的句子，其中可核对的 19 条预测里命中 9 条、部分命中 7 条、落空 3 条，方向正确比例 84%。他总结说由于知行合一，看他在做什么就知道他怎么想的了。
