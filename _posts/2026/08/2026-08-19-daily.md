今天最值得读的是 <span class="mention">@今天群内信息量极大</span> 分享的离线上下文工程文章和由此引发的讨论——OpenAI 不用 finetune 不用 router，GraphRAG 已进入维护模式，fancy 技术为何总是先死。<span class="mention">@细心的熊猫</span> 把双 5060ti 上 Qwen 3.8-27B 推到四路并发新高度，从邮件清理到反爬逆向全靠本地跑。Ornith-1.5 开源系列声称多项指标逼近 Opus 4.8，闭源模型的护城河还能撑多久再度成为话题。

## Qwen 3.8-27B 实测第五日

### 双 5060ti 四路并发 367 tok/s

<span class="mention">@细心的熊猫</span> 继续在双 5060ti 上压榨 Qwen 3.8-27B 的并发极限（前情 [「5060ti flashinfer 加速与 DSH 亿 token 马拉松」]({{ '/daily/2026/08/18/daily/#5060ti-flashinfer-加速与-dsh-亿-token-马拉松' | relative_url }})）。通过提高 MRR 并发复制数和 MAMBA 块大小，以 16% 的上下文池缩减为代价换来翻倍聚合吞吐：

| 配置 | 池/ctx | 并发聚合 |
|------|--------|---------|
| MRR=2 + mamba20（现状）| 131,072 | 2 路 ~210 tok/s |
| MRR=3 + mamba24 | 118,784 (-9.4%) | 3 路 ~295 tok/s |
| MRR=4 + mamba28 | 110,592 (-16%) | 4 路 ~367 tok/s |

四路并发每路维持 84–95 tok/s，几乎无损。他还提到网上有人在双 3090 上跑到了 300 tok/s。<span class="mention">@随和的企鹅</span> 看到 AA 智能指数图表后震惊于 27B 竟能与 V4 Flash 持平，<span class="mention">@细心的熊猫</span> 直言 27B 的核心卖点就是本地部署，不想折腾本地的话 Luna 价格更香。

### 单卡 5090 部署全指南

<span class="mention">@冷静的白鹭</span> 分享了一篇[单卡 5090 全链路部署指南](https://mp.weixin.qq.com/s?__biz=MzIyNDgwNDg0MQ==&mid=2247483709&idx=1&sn=062c492881aac5bec65a749c3c478a0a&chksm=e98ca7d391ea3ec43dd553cb89fd304f190ff0b2156ee005d9b3ae323563be92c00104c00cdf#rd)，从量化选型到 agent 实战完整复现。四种投机解码方案中 DFLASH2 以 179.96 tok/s（2.62 倍加速）最快，MTP 次之 142.58 tok/s。两个硬坑值得注意：208 核容器 JIT 编译默认并行度打爆 90GB 内存（需设 MAX_JOBS=4），kill 父进程后 GPU 显存仍被子进程占用必须手动查杀。

32GB 显存下 KV 池上限约 33K token 是物理瓶颈——thinking 模式的无界输出可一次 decode 出超过 33K token 思维链直接打爆 KV 池。对策包括服务端关闭 thinking、每轮用文件传递状态、极简 system prompt 加工具白名单。agent 实测 6/9 轮编程任务高质量完成，甚至能主动构造反例推翻测试预期。

<span class="mention">@优雅的喜鹊</span> 补充实测 SGLang + NextN 跑 RadixArk NVFP4 达 183 tok/s、上下文 117K，但指出 RadixArk 有精度代价。

## 方法论

### 离线编撰胜过在线花哨

<span class="mention">@今天群内信息量极大</span> 分享了他写的[长文](https://yage.ai/share/openai-data-agent-offline-context-20260806.html)，拆解 OpenAI 内部 Data Agent 的架构。核心发现：服务 3500 名用户、70000 个 dataset、600PB 数据的系统，在线部分极简——单模型约 13 个工具，没有 finetune、没有 router、没有 graph、没有新 harness。复杂度全在离线：用 Codex 定期扫描数据管道代码，把藏在 ETL 脚本和老员工脑子里的业务语义提炼成结构化文档，在线端只需检索这些高密度材料。

讨论迅速延伸到 fancy 技术的生存率。<span class="mention">@今天群内信息量极大</span> 搜索后发现 GraphRAG 的 GitHub 仓库已进入 maintenance mode，几乎找不到成功案例，多数反馈是花了钱没改进。他提炼了两个值得学习的点：GraphRAG 用一两句话就让所有人觉得它很厉害，这种注意力获取本身值得研究；而从 AI 领域噪音中快速定位到真正 work 的技术，需要自己的 opinions 和实验。

> <span class="mention">@今天群内信息量极大</span>：fancy的东西主要是死得太快……理论上看起来很优美很厉害，但实践里不work

<span class="mention">@冷静的飞鼠</span> 认为 fancy 技术失败大多因为人性在追求 fancy 本身，并分享了一篇 [Superlinear 文章](https://www.superlinear.academy/c/ai-resources/verb)：市场只给「名词」（LangChain、RAG、fine-tune）定价，不给「动词」（分解、判断、路由、诊断）定价，结果大多数人零件堆了一地却什么也没造出来。<span class="mention">@坚定的貂</span> 附和：CS 出身的人天然觉得 graph 厉害，他那边做 math harness 的也一堆在搞 fact graph。

### 企业数据 Agent 落地之痛

<span class="mention">@冷静的麋鹿</span> 描述了传统企业做数据 Agent 的典型流程：用户问数 → agent 在老旧数仓找指标 → 写 SQL → 执行取数，他的团队用 V4 Flash 日常查询、复杂场景上 Pro。<span class="mention">@细心的熊猫</span> 建议用 agent 一次性重构数据资产做知识图谱，而非每次运行时堆算力。

<span class="mention">@80-HD</span> 从另一个角度补充：数据屎山比代码屎山难修得多——挪数据代价极高且没有 test 保证正确性，跑全量 QA 又贵得要命。但 <span class="mention">@冷静的麋鹿</span> 指出技术还不是最难的：

> <span class="mention">@冷静的麋鹿</span>：最难的是人心中的成见：比如，老板跟你说，修数据的屎山你让AI来搞就行；比如，老板跟你说，我要求这个agent的回答准确率100%

更扎心的是好不容易把指标做到 85% 并给老板讲明白了道理，隔壁一篇爽文就把老板带偏。<span class="mention">@沉稳的仓鼠</span> 总结得更犀利：AI 时代的黑暗森林法则就是互丢 AI Slop——文档、ticket、代码——只有让别人被 slop 淹没，自己才有生存空间。

> <span class="mention">@低调的鲸鱼</span>：天天听网上大v吵要不要开源，现在感觉开源确实很重要

亮点是 Sonnet 5 稳定性明显改善——<span class="mention">@低调的鲸鱼</span> 已将其作为 daily driver，此前的韩文日文乱飙现象基本消失。<span class="mention">@风趣的长颈鹿</span> 公司 Cursor 默认用 Grok，体感比 Opus 蠢一些；<span class="mention">@热情的大象</span> 反驳说蠢的好处是可控。
