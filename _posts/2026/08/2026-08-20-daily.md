今天最值得读的是 <span class="mention">@今天群内信息量极大</span> 对 Orca PTY 架构的逆向拆解——25 种 TUI 的就绪信号逐家摸索，脏活多到让他放弃了蒸馏念头，群友接着展开 PTY、ACP 与 SDK 三条路线之争。<span class="mention">@沉稳的仓鼠</span> 发布的 Happy AI Transformation 一文戳中企业 AI 转型痛点，群里顺势算了一笔 AI 军备竞赛的经济账。

## Orca 深度拆解

### Orca CEO 访谈

<span class="mention">@冷静的飞鼠</span> 分享了他对 Orca CEO 的[深度访谈](https://www.superlinear.academy/c/recording/orca)（昨天 [「Orca 与 Herdr」]({{ '/daily/2026/08/19/daily/#orca-与-herdr' | relative_url }}) 初步提及了这款工具）。Orca 定位为 Agent Development Environment（ADE），GitHub 近五万星，四人团队日更一版。它不重新实现 Claude Code、Codex 这些执行层 harness，而是处理上一层——多个任务并行推进、上下文跨模型切换、进展回写 Linear、人何时介入。

CEO 本人积累了 400 多个独立代码工作区，其中 200 多个已变成定时自动化流程。一位 Cloudflare 工程师每天让总控 agent 把所有 Linear ticket 拆成二十路并行 review。在模型选择上，CEO 不再总选最强模型——最强模型也没有强到可以在关键 design 上跑两天而完全不看，一个能力略低但速度快三倍的模型在需要反复讨论设计时可能更早交出可用方案。

Orca 解决了一个不起眼但很难做的点：应用更新后恢复正在运行的 session（聊天历史、进程和 dev server），用户因此敢每天更新。团队还做到 session 在某个 provider 额度用完后直接交给另一个模型接力，不必重新解释任务。

> <span class="mention">@冷静的飞鼠</span>：就比如我如果三分球命中率不高 我见到库里 不应该问他 你卷发对你三分命中率有没有帮助

<span class="mention">@冷静的飞鼠</span> 强调 Orca 团队从一开始就奔着 billion dollar business 去做——所有做法、基础建设和投入强度都按这个目标走。

### PTY 逆向：两层脏活

<span class="mention">@今天群内信息量极大</span> 深夜拆解 Orca 源码，先用 Grok 但觉得输出不说人话，换 GLM 重写后产出了一份极其详细的架构分析。Orca 所有 agent 都跑在 node-pty 伪终端里，核心是一张注册表，为 25 种 agent 分别声明检测命令、启动命令和六种不同的提词注入方式。

第一层是往 TUI 里安全注入指令。每种 agent 的就绪信号完全不同：OpenCode 在输入框创建前就开启了 bracketed paste 模式，粘贴早了文本直接消失，要等特定光标转义序列才敢动手；Codex 要监听 composer-ready 信号且有 20 秒超时防死等；首次启动弹出的信任对话框会无声吃掉注入的提词，所以必须预先写好信任文件让对话框根本不出现。

第二层是从字符流里掏出结构化状态。PTY 只给字符流，agent 是在等权限还是已跑完根本看不出来。Orca 的做法是往 agent 进程内部装探针：Claude 走 hooks 系统；OpenCode 写一个 JS 插件 POST 回本地 HTTP 服务；Codex spawn 官方 app-server 走 JSON-RPC。三个 agent 三套完全不同的机制，乘以 25 个 agent，就是维护成本的真实形状。

> <span class="mention">@今天群内信息量极大</span>：Orca 早期自己复刻 Codex 的 trusted_hash 算法，结果 Codex 每次发版算法漂移，坏了三次，最后改成让 Codex 本体当 hash 权威。不要逆向复刻外部 CLI 的私有算法，用它的官方 RPC。

<span class="mention">@今天群内信息量极大</span> 总结 Orca 的护城河不是算法，而是替整个生态垫付了这笔集成账——把一群天生不可编排的 TUI 逐个驯化成能被程序驱动的东西。他坦言看完连蒸馏的欲望都没了，因为这些全很脆弱、需要不停维护，背后满屏 issue 编号都是踩坑的尸检报告。<span class="mention">@稳重的海豚</span> 也感叹自己搞了半天 PTY 想吐。

### herdr vs Orca 实战翻转

<span class="mention">@坚定的貂</span> 当晚兴奋地全面转投 Orca，还发现了 Remote Server 等新功能。然而几小时后他就转回了 herdr——Orca 对远程场景太慢，herdr 原生调用速度差距明显。<span class="mention">@勇敢的猎豹</span> 也抱怨 Orca 不够 agent native，居然还要一堆手动点击操作。

<span class="mention">@灵动的考拉</span> 最初试用后总体肯定，尤其喜欢 git 集成度，但后来发现 Orca 安装时悄悄注入了 Claude Code hooks，评价其副作用约等于 virus，随即卸载。<span class="mention">@坦荡的灰熊</span> 则认为 Orca 的 computer use 确实好用。群友对 Orca 的评价明显分化——功能丰富但打磨和速度仍有差距。

<span class="mention">@坚定的貂</span> 的快速切换恰好印证了一个更深层的观点：harness 的粘性其实不强，真正有粘性的是背后累积的知识层。<span class="mention">@灵动的考拉</span> 更直白——模型完全没粘性，harness 也只剩一点习惯问题。<span class="mention">@热情的大象</span> 从 C 端视角反驳：大量普通用户连新开一个 session 都不愿意，harness 的设计正在绑定用户习惯。

### Cindy：二次元 ADE

<span class="mention">@灵动的考拉</span> 介绍了一位朋友开发的 [Cindy](https://cindy.app)——一款开源 ADE，出自一位上市游戏公司老板之手，二次元画风贯穿始终。与 Orca 的 PTY 逆向思路不同，Cindy 直接调用各家 CLI，支持 Claude Code、Codex 和 Pi 三种 harness 可跨模型中途切换，还集成了 Slack、Telegram、微信和灵动岛通知。

<span class="mention">@热情的狮子</span> 当即下载试用并贴出大量截图。mobile 联动顺畅，模型供应商管理界面清晰。不过初版 bug 不少——Codex 通道 502 报错完全不可用，Claude Code 倒是正常。他对 shell 进程和 subagent 的可视化管理表示认可，但对微信启动的 session 只能用固定 mid reasoning effort 感到困惑。

### PTY vs ACP 路线之争

Orca 的 PTY 逆向方案引发了一场技术路线辩论。<span class="mention">@优雅的仓鼠</span> 直言 PTY 是歪路，表示自己团队准备在 SDK 层做统一的 agent runtime 操作接口。<span class="mention">@洒脱的猫头鹰</span> 推荐 ACP（Agent Client Protocol）——本地 agent 通过 stdio JSON-RPC 通信，JetBrains 也已入伙。

> <span class="mention">@洒脱的猫头鹰</span>：拿 ACP 做这个干净清爽多了。PTY 属于 hack，太多脏活了，而且 agent 一升级还得适配，没钱干不了这个活

<span class="mention">@今天群内信息量极大</span> 提出折中方案：能用 OpenCode OAuth 的就用，嫖不了的（如 Claude）再用 [ai-agent-cli-skill](https://github.com/grapeot/ai-agent-cli-skill) 通过文件契约补足。<span class="mention">@淡定的鸳鸯</span> 在公司内部直接用官方 SDK 做了 agent management app，支持 Claude Code 和 Pi，比 ACP 灵活稳定得多，但也指出 Codex 的 SDK 不太行只能用 RPC mode。<span class="mention">@洒脱的猫头鹰</span> 补充说现在各家 CLI agent 都通过 OSC 发通知，只做通知的话其实用不上 PTY 这种 hack。

核心分歧在于：PTY 覆盖面广但脆弱，ACP 干净但生态未成熟，SDK 统一灵活但要逐家吃屎。目前没有哪条路线占据绝对优势。

### 做产品的「欲望纯度」

<span class="mention">@稳重的海豚</span> 发现自己做的 [HappyHerd](https://github.com/NickGuAI/HappyHerd) 功能与 Orca 高度重叠——PTY 管理、session 恢复、多 agent 编排都做了，但始终没做起来。<span class="mention">@冷静的飞鼠</span> 犀利指出问题不在产品功能或分发渠道。

> <span class="mention">@稳重的海豚</span>：说白了，就是欲望的纯度不够

他反思自己要创业赚几十个亿却每天做产品不分发、没系统性设计——和减肥每天配蛋糕本质上是一回事。<span class="mention">@冷静的飞鼠</span> 补充了分发数据：Product Hunt 日榜第一只能带来 80 个 signup，社区里几个 founder 反馈不如在 Superlinear 发个帖。

<span class="mention">@80-HD</span> 心疼 <span class="mention">@稳重的海豚</span> 领先了三个月却没吃到红利，还进一步预测 agent orchestrator 最终会被 agent harness 取代。<span class="mention">@冷静的飞鼠</span> 则认为被收购也是合理路径。<span class="mention">@稳重的海豚</span> 坦言自己 85% 的任务和 coding 无关，产品定位可能更适合需要高强度决策的个人助理场景，而非程序员群体——正好顺着访谈里的作业答案照着抄。

### Grok 4.6 跑分出炉

## 方法论

### Happy AI Transformation

<span class="mention">@沉稳的仓鼠</span> 发布[新文章](https://ranchen.org/content/20260819-rancheng-article-happy-ai-transformation)直指企业 AI 转型的普遍困境：台面上 AI-first、降本增效、全员用起来，关起门来高管心知肚明大概率没用。标准动作是挑不碰核心利益的项目——知识库、客服 bot、会议纪要、全员 Hackathon——好立项、有结项、没人丢岗位，核心业务纹丝不动。

文中引用 McKinsey 2025 数据：88% 的组织常规使用 AI，但仅 39% 认为影响了 EBIT，多数利润影响不到 5%。<span class="mention">@敏锐的雪豹</span> 深夜读完直呼牛逼，多位群友认同这篇精准命中了行业痛点。

### AI 军备竞赛经济账

<span class="mention">@细心的熊猫</span> 顺着文章冷静算了一笔账：AI 转型确实带来效率提升，但竞争对手效率也提升，行业总体利润瓜分维持不变。

> <span class="mention">@细心的熊猫</span>：一个求职者用AI自动化投比以往多100倍的简历，HR用AI自动化筛选了100倍数量简历，双方各烧$100 token得到了跟以前同样的结果。NVDA赚了$100，Anthropic赚了$100

<span class="mention">@活泼的羊驼</span> 修正了分配比例——NVIDIA 和供应链朋友们赚 $180（NV 先拿五成，剩下给 ASML、TSM、存储等分），Anthropic 只赚 $20。<span class="mention">@洒脱的猫头鹰</span> 补充说成本部门的效率提高并不会在短时间内影响收入。<span class="mention">@认真的灰熊</span> 认同还是要找到增量才行。

### 古法 agent 回归

多位群友不约而同从高度自动化回退到古法 agent。<span class="mention">@80-HD</span> 的工作流是在 Codex xhigh 里做 RFC，完了起个新 session 用 medium 去实现——公司屎山不能全自动铲屎。<span class="mention">@直率的鸵鸟</span> 也确认恢复了古法。

> <span class="mention">@敏锐的海狸</span>：我想要辆二脚蹬 他给我设计战地摩托

<span class="mention">@敏锐的海狸</span> 指出大设计还是得古法 agent，AI 互相 review 总是喜欢 over engineering。<span class="mention">@80-HD</span> 补充了一个典型踩坑场景：有人心血来潮取了个 codename 刚好与开源项目重名，模型就会写出奇怪的东西——公司屎山的 context 经常变，全自动扛不住。

### K3 主力体验

<span class="mention">@神秘的企鹅</span> 询问国内可用的快速编程模型。<span class="mention">@随和的企鹅</span> 力荐 Kimi K3 作为主力——他体感 K3 比 Sol xhigh 还略好一点，Sol 纯 coding 更强但分析需求容易过于简单。K3 的短板是速度偏慢且目前没有快速版本。V4 Flash 也被推荐为性价比之选。
