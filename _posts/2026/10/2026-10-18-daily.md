## Multi-agent 与 agent 工程

### 多 agent 买不到更强的智能，只能换几项工程指标

<span class="mention">@稳重的海豚</span> 在整理 multi-agent 讲义时问：这个方向前一阵声量很大，最近怎么没人提了？<span class="mention">@今天群内信息量极大</span> 的判断是，大家对 MAS 的好处和成本误解很深。有人觉得用了 MAS 模型就会更聪明、更快，或者配合路由更省钱，「但其实有很多定量研究证明这些全是错觉。它不是没有好处，而是好处在其他地方。」群里随后转来一篇长文[《多 agent 不是更聪明，是更贵：它到底买到了什么》](https://yage.ai/share/multi-agent-what-it-buys-20261021.html)，给出了具体数字。

**成本与收益**
- Anthropic 的生产复盘显示，单 agent 反复调工具的 token 消耗约为普通问答的 4 倍，多 agent 系统约 15 倍。在 BrowseComp 上，各家系统得分差异有八成能对应到 token 用量的差异。
- Vals AI 的 Vibe Code Bench 用 Sol 和 Opus 5.5 各跑 medium、max 两档。组队开销是单干的 1.8–5.1 倍，四组比较里只有 Sol medium 组队后提分显著（+7.3）。同样的钱把 Sol 单模型从 medium 提到 max，能涨 11.4 分。Opus max 团队拿了全场最高分，但花费是 medium 单干的 30 倍，只高 1.6 分，而且不显著。
- 成本的大头来自重复读取：每个子 agent 上场都要重读一遍规格和当前状态，缓存输入按次重复计费。
- 速度上，只有 Sol 团队真的变快了。Opus 团队串行分批派活，最慢时耗时是单干的 2.3 倍。

**能买到的四样东西，各有前提**
1. **端到端时间**：前提是子任务互相独立。写小说这类前后咬合的任务，加多少 agent 都不会提速。
2. **查漏补缺**：上面那组唯一显著的提分，几乎全来自高难度应用（难题 +15，简单题 +1）。起作用的是专门的核验角色，它补上了单 agent 自报完成、实际却漏掉的功能和测试。
3. **搜索多样性**：微软研究院的 Fork-and-Flush 在长程任务上得到 0.78，单次长跑是 0.47。分叉选路和清空父代历史两步必须一起做，只压缩摘要没用。
4. **上下文隔离**：拿干净窗口做审查的角色，常能发现写代码的 agent 自己没看出来的 bug。

**负面结论**
- 能力路由跨不过主控模型的天花板。弱主控带一群便宜 worker，分数不如强模型单干。
- Agentless 用「定位、修复、验证」三步固定流水线，在 SWE-bench Lite 上拿到 32%，每题 0.70 美元。
- MAST 分析了 1,600 多条轨迹，归纳出 14 种失效模式，其中步骤重复占 15.7%。
- 文章的建议是写入必须单线程，子 agent 只负责读、检索和审阅。

群友的看法：

- **为什么没人提了**：<span class="mention">@细心的飞鼠</span> 给了两种猜测。一是在固定工作流里 MAS 已经用上了，只是平平无奇地替代了原流程；二是模型的 agentic 能力上来了，原来要靠 MAS 解决的问题，单模型做得更好。<span class="mention">@随和的飞鼠</span> 的说法是：「能 scale up 就先不考虑 scale out？」
- **生产形态**：<span class="mention">@稳重的海豚</span> 认为实际生产中还是以 workflow-based 的 MAS 居多，只是大家不怎么说了。非硬性的 workflow，比如 skill，效果差别不大。
- **并行**：<span class="mention">@优雅的荷兰猪</span> 认为并行仍是最大优势，因为很多工作在某些阶段不需要互相沟通。<span class="mention">@稳重的海豚</span> 回应「并不只是并行处理这么简单」。
- **实用场景**：<span class="mention">@飘逸的浣熊</span> 会派多个 subagent 分别尝试不同算法、调研不同主题。让 agent 自己做 prompt engineering 时，用 subagent 代替 API 来测 prompt，可以省钱。

想补理论的话，<span class="mention">@稳重的海豚</span> 翻出了 Shoham 和 Leyton-Brown 2008 年的教材《Multiagent Systems: Algorithmic, Game-Theoretic, and Logical Foundations》，作者官网提供[全书 PDF](https://www.masfoundations.org/mas.pdf)。<span class="mention">@80-HD</span> 回忆，多智能体在十多年前就是一个挺火的方向。

### Memory 系统：人的 taste 放在哪一步

<span class="mention">@风趣的长颈鹿</span> 周末看了一圈 memory 系统，发现思路大同小异：从对话里提取精华，后台再有一个进程定期整理。难的是需要人或团队的 taste 来判断的地方，比如什么值得存、两条规则冲突时留哪条。两位群友给出了把 taste 注入进去的具体做法：

- **和 compact 合并**（<span class="mention">@聪明的蜂鸟</span>）：每到需要 compact 的时候，先跑一遍上下文提取，再新开 session 把提取结果 load 进去。好处是由正在干活的 session 自己做提取，麻烦是得自己记得走这套流程。他原本希望提取结果能变成人和 agent 都能用的 wiki，实际跑下来自己基本不看，「都是他自己存自己用」。<span class="mention">@风趣的长颈鹿</span> 也觉得市面上的这类 wiki 词条人没法看，给人用的和给 agent 用的毕竟不一样。
- **用修改前后的差异调 prompt**（<span class="mention">@飘逸的浣熊</span>）：他有一个生成周报的 agent。他把自己修改前、修改后的周报一起喂给 agent，让它自己判断提示词该怎么改。现在每周只需要改一些细节。

<span class="mention">@风趣的长颈鹿</span> 的结论是，这些领域很难自动验证，只能定期盯着。

### 个人 benchmark：记录模型更新后工作边界有没有移动

接着昨天关于私有 benchmark 的讨论（[「Bug Hunt：$1.01 修 38.7 个 bug，和体感对不上」]({{ '/daily/2026/10/17/daily/#bug-hunt101-修-387-个-bug和体感对不上' | relative_url }})），<span class="mention">@开朗的企鹅</span> 实际跑了一轮从 context infrastructure 里提取个人 benchmark，结论是可行，但核心价值不在打分，而在判断「模型更新之后，你的工作边界有没有移动」。

他的三点体会：

- 普通题很快就会饱和，再扩大模型和档位矩阵也增加不了多少信息。该测的是会改变实际决策和交付结果的地方。
- 好的 benchmark 能发现自身的遗漏。这次出现了「原测试全过，却丢了重启首帧」的情况，这类发现应该转成下一轮的验收条件。
- 最难的仍是找对任务。局部比较已经验证能做，但系统能否从完整 context 里持续找出最重要的卡点，还没有证明。

所以他打算把它做成一份持续维护的「能力边界记录」：过去卡在哪里、现在有什么新证据、值不值得重新投入、还有什么不知道。新模型发布时，只重测可能改变判断的部分。他还顺手调侃，<span class="mention">@今天群内信息量极大</span> 可以有一个专门的「删库 benchmark」。

## 本地推理

### M5 Ultra 对两台 DGX Spark：长上下文各有输赢

<span class="mention">@细心的熊猫</span> 贴出一组 200K 上下文上限下的输入长度扫描，对比 Mac Studio（M5 Ultra 80 核 GPU、256GB、oMLX）和两台 DGX Spark（2×GB10、vLLM TP2、200Gbps 互联）。结论是没有一边全胜：Qwen Flash 上 Mac 的 prefill 是 Spark 的两倍多；DeepSeek V4 Flash 0731 上 Spark 的 prefill 更快，长输入时 decode 也更稳；GLM Flash 在 Spark 上 decode 只有约 14 tok/s。这正好回答了昨天关于「两台 128G Spark 串联行不行」的问题。

下表是从图上读出的近似值，输入从约 30K 到约 190K token：

| 模型 | 指标 | Mac Studio | Spark ×2 |
|---|---|---:|---:|
| Qwen Flash | decode (tok/s) | 139 → 79 | 104 → 100 |
| | prefill (tok/s) | 5,500 → 4,700 | 2,600 → 2,000 |
| | TTFT (秒) | 5 → 41 | 11 → 94 |
| DeepSeek V4 Flash 0731 | decode | 60 → 27 | 约 51，基本持平 |
| | prefill | 1,380 → 880 | 1,980 → 1,710 |
| | TTFT | 22 → 217 | 15 → 111 |
| GLM Flash | decode | 67 → 54 | 约 14 |
| | prefill | 2,230 → 1,570 | 1,690 → 1,630 |
| | TTFT | 13 → 122 | 18 → 117 |

几点说明：

- Mac 的 decode 会随输入变长而下降，Spark 基本是平的。两条线的交叉点，Qwen 在约 100K，DeepSeek 在约 50K。
- 两边的测试条件并不一致。Mac 用 oQ4e 量化，Spark 上 Qwen 和 GLM 用的是 NVFP4。Spark 上有几项配置在启动失败后降低了 MTP，GLM 那组的 MTP 直接关掉了（MTP0），这可能是它 decode 只有 14 tok/s 的原因。图注也写明，主机、运行时、量化和 MTP 都不同，不构成纯硬件对比，也不涉及质量。
- 测的是 DeepSeek V4 Flash 0731，不是昨天刚发的 1017。

## Claude

### 深圳出差被封，地区政策按所在地判定

一段短视频在流传：一名美国开发者从香港到深圳参加 Rust 开发者大会，酒店网络波动、代理断线，大陆 IP 短暂暴露，一觉醒来 Claude 账号就被封了，视频的结论是「风控不认国籍，只认 IP 地理位置」。同一天 <span class="mention">@热情的狮子</span> 贴出 Anthropic《Supported Regions Policy》的截图，生效日期是 2026 年 11 月 12 日，条款写的正是按所在地判定。

截图里，政策覆盖 Claude.ai、Claude Code、Cowork、API，以及经云平台和授权经销商提供的 Claude 模型。不受支持的使用包括三类：

- 人在不受支持的地区时使用，即使其所属机构位于受支持地区；
- 注册地或总部在不受支持地区的实体，其用户和员工身在何处都不行；
- 被不受支持地区的个人或实体直接、间接多数控股或控制的实体，同样不论使用者身在何处。

<span class="mention">@博学的老虎</span> 的评论是：「Claude 现在的定价权，中国开发者、普通用户应该没有少贡献吧……虐恋至此。」<span class="mention">@幽默的火烈鸟</span> 半夜看到「For your security, sign in again to keep using Claude」的提示，判断「感觉号要完蛋了」。<span class="mention">@蓝色大肥虞</span> 转了一个 B 站整活视频[《IP, PLEASE》](https://b23.tv/M4bFiNb)：像素风复刻《Papers, Please》，玩家扮演的边检员是 Claude，专查「美国东八区」。作者称程序由 Claude Code 编写。
