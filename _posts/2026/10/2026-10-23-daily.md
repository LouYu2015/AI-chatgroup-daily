今天最值得读的是 **Kimi K3.1 Pro 发布**：官方跑分在 Terminal-Bench 4.0 上与 Opus 5.5 只差 0.7 分，单任务成本约为 Opus 的三分之一。但第一位上手的群友让它跑调研，一个多小时后发现它一直在执行 `true`，烧掉了 1.8 亿 token。第二件是 **测试与 review**：有群友让 Astra 把 CI 测试从 2800 个精简到 300 个，另一位转来 Anthropic 讲内部 code review 的长文，其中给出了回滚率、review 轮数等数字。第三件是一篇讲 **AI coding 落地失败根因**的文章：测试慢，是因为没人说得清正确答案长什么样。

## 模型

### Kimi K3.1 Pro：跑分贴着 Opus，上手先跑了 1.8 亿 token 的 `true`

Kimi 发布 [K3.1 Pro](https://mp.weixin.qq.com/s?__biz=MzcwMjM3ODEzOA==&mid=2247487748&idx=1&sn=ceec50327d6be7c1e07203c9306c9ebc&chksm=f5164bcb4b3c751185f98ec4f1fa0b03931826f76803d2b11d8de8d0bd3572a50a7f1c77cf18#rd)，这是 K3 的后训练版本。官方称它在多项基准上「达到或接近最强闭源模型」，完整权重会在 11 月 4 日前放出。群里的上手体验分成两种：有人做游戏 demo 觉得达到了 Astra 的水平，也有人让它跑长任务时空转了一个多小时。

### 测试从 2800 个砍到 300 个，以及 Anthropic 的 review 流水线

<span class="mention">@80-HD</span> 认为额度烧得快，部分原因是 Astra 验收时工具调用太多，还给他加了一堆没用的测试。<span class="mention">@蓝色大肥虞</span> 的态度是：验收和开发放在一起做已经没问题，效果反而更好，但没用的测试要及时删掉。<span class="mention">@80-HD</span> 随后让 Astra 精简 CI，测试从 **2800 个减到 300 个**。<span class="mention">@飘逸的浣熊</span> 现在每次提交前也让 agent 检查一遍，看有没有重复或可以优化的测试。他还转来 Anthropic 的 [Solving code review at Anthropic](https://claude.dev/blog/solving-code-review-at-anthropic/)，文中提到内部有一个 simplify diff skill。

文章里值得记下的：

- **判断标准**：读代码大部分交给机器，人类时间压到最少。判断这样做行不行，看的是回滚率和事故率有没有上升，而不是「有没有人读过代码」。目标是多数 PR 合并时最多只有一个人类在环，这个人可以就是作者本人。
- **数字**：Claude Code 自身约 90% 的代码由 Claude 写。6 月到 9 月，合并的 PR 数翻了一倍多，被回滚的比例下降 40% 以上。monorepo 每天合入的变更从 5 月约 2,500 个涨到 9 月 3 万个以上。研究预览上线后，内部 PR 收到实质性 review 评论的比例从 16% 升到 54%。
- **review 前移**：大部分 review 发生在 PR 创建之前。先给 Claude 能跑的验证手段，比如测试、构建、和设计稿对比的截图，并要求它展示输出，而不是只说一句完成；再让一个全新上下文的 subagent 审 diff。提交前跑三个内部 skill：找 bug、简化 diff、端到端行为检查。Boris Cherny 估计，给 Claude 验证自己工作的手段，能让结果好两到三倍。
- **降噪**：多个 agent 并行找 bug，再由另一组 agent 投票，票数够才发出。纯风格、诊断、清理类的意见直接丢弃。原因是噪音对 agent 作者的代价更高：人几秒就能忽略一个 nit，agent 会去改，于是多一个 commit、多一轮 review。有个 CLI PR 一夜跑了 50 多轮 review 和修复，最后被作者叫停。对反复被标记的代码做 git blame，约 59% 是 reviewer 第一轮看到时就已存在的旧代码。
- **硬规则**：风险等级由分类器根据变更内容判定，不看作者。敏感路径和 CI workflow 文件永远要人处理。agent 的批准不算人的批准，一次批准只对一个 commit 有效。
- **还没做到的**：回滚或事故数字上升时自动收紧审批的 circuit breaker 还没有；review 的另一项职能，即在团队里传播对代码的理解，也没有正式流程，目前的办法是让 Claude 给要看的代码写一份 explainer。

### MCP 加鉴权：难在中间层

某群友这两周在公司做一个统一 MCP，把所有第三方服务放进去，用户连一次就全都能用。他的结论是「MCP 这玩意就只适合裸奔，加 auth 就是折磨人」。难点不在 OAuth 本身，而在多套了一层：后面每个服务各有自己的鉴权，MCP 夹在中间要替用户再做一遍，还得同时支持 service-to-service 和 OAuth。他们缺一个 token exchange，有了的话「还是没那么难」。他认为做成 CLI 最好，可以直接复用已有的鉴权。

不同意见：

- <span class="mention">@细心的熊猫</span> 觉得 OAuth 很好用；<span class="mention">@稳重的海豚</span> 提醒 CLI 一样要走 OAuth。
- <span class="mention">@蓝色大肥虞</span> 认为关键在「全家桶够不够整齐」。他们也有大量东西建在 MCP 上，因为所有服务都走同一套账号体系，所以「特别丝滑」。

## AI 与组织

### AI coding 落地，先问「谁说了算」

群里转来一篇 [《什么重要，什么不重要：AI Coding 落地里的 Intellectual Honesty》](https://ranchen.org/content/20261022-rancheng-article-ai-coding-what-matters)。文章的判断是：AI coding 落地失败，工具和流程都是次要原因，排在最前面的是有没有人愿意诚实承认真正的问题是什么，并由一个人为结果负责。

文章的核心案例是一家企业用 AI 重写内部 CRM，几个人投入几个月，最终没有上线。报价模块的缺陷最多：开发用 AI 一晚上就写完，测试要 1–3 天，修完一个 bug 又在别处冒出新的。团队反复追问的是端到端测试怎么用 AI 提效、spec 写到什么粒度、要不要用追问需求的 skill。作者反问「这个报价到底谁说了算」，没人接得住，因为规则本身就没人能完整说清。

几个论点：

- **慢本身是纠错机制**：过去实现很贵，模糊的地方会在从文档到代码的几天到几周里被慢慢消化。现在 AI 一晚写完，遇到模糊处不会停下来问，而是挑一个看似合理的解释继续写，所有没想清楚的地方同时以 bug 的形式堆到测试环节。测试只是第一个必须回答「正确答案是什么」的环节。如果规则都清楚，一万条用例、一千台机器跑测试只是花钱的问题。
- **把口径写清楚**：作者自己的做法是，每个口径（指标定义）都有编号、理由和测试，和代码放在同一个库里，表和字段的 comment 没有歧义，这样弱模型也能做对。
- **更少的人、更大的权限**：谁说了算、谁对结果负责，就让谁去做，不必再分 PM、开发、QA。分工存在是因为过去每一段都贵；现在三段都便宜了，最贵的是交接，每重新理解一次，就多一个版本的「真相」。边界是：决定权可以集中，知识绝不能只存在某个人脑子里或某个 AI 会话的上下文里，否则账号被封、人一走就接不上。
- **不重要的清单**：spec 框架和文档粒度、Markdown 还是原型图、某个 skill 好不好用、端到端测试用什么工具、硅谷最佳实践。理由是这些答案便宜、随时会过期。工具便宜到可以同时试十个，贵的是能判断试完有没有用的人。作者还主张敢说「这东西本就不该存在」：那个报价系统的正解，可能是推倒重写成数据加固定公式。

<span class="mention">@坦荡的灰熊</span> 的读后感：「DDD 的价值越发高大起来。」
