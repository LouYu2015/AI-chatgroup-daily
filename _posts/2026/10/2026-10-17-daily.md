今天最值得读的是 **DeepSeek V4.1 Flash 1017**。它开源了权重，在第三方的 Bug Hunt 评测里修掉 38.7 个 bug（满分 105），真实账单只有 $1.01；Opus 5.5 max 修掉 41.7 个，按标价估算约 $58.5。不过群友的实测评价差距很大，有人说「比 Haiku 5.5 强多了」，也有人说「没法超过 5.6」，由此引出一个判断：私有 benchmark 才是刚需。第二件是对「用 iPhone 虚拟机做微信自动化」的一次拆解。一开始有人说「夯爆了」，逐条比较替代方案之后，只剩一点未经实测的成本优势；讨论顺带讲清了商用场景真正的约束是不能封号。另外，Codex 迎来 Day 13 重置；Astra 建的 3D 角色「没法看」，换成 Claude Code 加 Blender 后，群友评价「很强」。

## DeepSeek V4.1 Flash 1017

### 更新内容：跑分压过 K3，搜索 API 11 月起收费

DeepSeek 把 V4.1 Flash 更新到 V4.1-Flash-1017，网页、App 和 API 已同步切换，权重在 HuggingFace 和 ModelScope 开放下载。官方文章主打「许愿式编程」，即用较少的提示词和较少的交互轮次从零搭出完整项目。文章没有给出具体分数，群里流传的跑分表把它和上一版及几家竞品放在一起比较。

其他几点：

- **搜索 API**：新增 Search 和 Fetch 两个接口，都是 5 元/千次，底层是 DeepSeek 自研的搜索引擎。在 DeepSeek Harness、Claude Code、Codex 里调 DeepSeek API 时，服务端已经会自动调用搜索，目前不计费，北京时间 11 月 1 日起按次收费。
- **Harness**：官方针对 DeepSeek Harness、CodeBuddy、WorkBuddy 做了优化，DeepSeek Harness 要升级到 0.2.1-rc.1 以上。
- **参数量**：两处说法不一。Bug Hunt 作者的推文写 763B，下文的本地部署帖写的是 552B 总参数。
- **演示**：B 站有 UP 主把整本《斗破苍穹》丢给它，46 分钟后拿到一个叫「三年之约」的游戏方案：36 个月限时修仙，加上牌组构筑 roguelite，每月只能在修炼、历练、采药等六件事里选一件。<span class="mention">@今天群内信息量极大</span> 在 OpenCode 里用 DS4.1 跑了一个仙剑装备整理任务：先从视频口述里提取装备表，再和两个资料站交叉核对，最后单列出差异点，比如视频里念的「鬼针咒」其实是「鬼针胄」。

### Bug Hunt：$1.01 修 38.7 个 bug，和体感对不上

Pawel Huryn 维护的 [Bug Hunt Bench](https://bughunt.productcompass.pm/?preset=featured) 在两个真实生产代码库里埋了 105 个 bug，只按埋进去的 bug 计分，模型顺手修掉的其他问题单独统计、不计入总分。1017 的首批结果是 34，推文发出后榜单更新为三次平均 38.7。部分结果：

| 模型 · 档位 | 修复数 /105 | 用时（分钟） | 费用 |
|---|---:|---:|---:|
| Sonnet 5.5 · max | 51.3 | 287.1 | $154.03 |
| GPT-6 Astra · max | 45 | 89.8 | $33.03 |
| GPT-6.1 Sol · max | 44.3 | 139.3 | $5.88 |
| Fable 5.1 · max | 43 | 73.1 | $87.18 |
| Opus 5.5 · max | 41.7 | 66.9 | $58.53 |
| Gemini 4 Argon · high | 40.7 | 56.5 | $7.16 |
| DeepSeek V4.1 Flash 1017 · max | 38.7 | 54.1 | $1.01 |
| Opus 5.5 · xhigh | 36 | 42.5 | $34.98 |

费用口径不统一：DeepSeek 和 MiMo-V2.6-Pro 是真实账单，其余大多按标价估算，Grok 4.7 是反推出的下限。Qwen3.8-Max 25.7，Kimi K3 21，GLM-5.3 19。上一版 V4.1 Flash 在首批结果里是 21.7。

群友的实测评价：

- <span class="mention">@细心的熊猫</span> 没拿它写代码，而是换进了自己之前的 agent 应用，评价是比 Haiku 5.5 强多了，比 Sonnet 5.5 稍弱一点。
- <span class="mention">@幽默的火烈鸟</span> 觉得它和 Sonnet 差不多，「甚至 token 用量都大差不差，都跑的磕磕绊绊」。
- <span class="mention">@务实的灰熊</span> 测过之后的结论是没法超过 5.6。<span class="mention">@神秘的企鹅</span> 说国产模型都有这个毛病：跑分不错，实际用起来总差一点。
- <span class="mention">@冷静的麋鹿</span> 的猜测是蒸馏导致泛化不如打榜，「倒不是说在刻意打榜」。<span class="mention">@80-HD</span> 看到推上有人说它蒸的是 Astra，做出来的 UI 是「Astra 绿」。<span class="mention">@蓝色大肥虞</span> 的反问是：「这些人做 UI 是一点风格的提示都没有吗？」
- <span class="mention">@今天群内信息量极大</span> 的点评：「一个月前斩杀完 fable 5，现在又来斩杀 opus 5.5 了。」

公开榜单靠不住，自己的榜单怎么建？<span class="mention">@80-HD</span> 的看法是「私有的 benchmark 才是刚需，公开的早晚会被 overfit」。<span class="mention">@开朗的企鹅</span> 说自己大多数时候已经分不清模型之间的差距，但又能感觉到有的模型在某些任务上确实不行。他想从日常工作里自动提取 personal benchmark，并贴了一份第一版的方案：

1. 只接入一个常用的 AI 工作入口，比较当前主力模型和一个候选模型。
2. 从会话导出或工作记录里，识别纠错、修改、切换模型、任务完成这类事件。
3. 自动生成任务快照和验收标准草稿，挑出十几到几十条能可靠验收的案例，从同一起点重跑两个模型。
4. 客观结果自动检查，只把少数重要分歧交给人做匿名选择。

方案里提到，底层不必重造，Langfuse 已经支持把真实运行记录加进评测数据集。

### 本地部署：M5 Ultra 256G 跑到 97 tok/s

<span class="mention">@细心的熊猫</span> 转来一篇论坛实测。作者在 M5 Ultra 256G（64 核 GPU）的 Mac Studio 上用 oMLX 推理：

- DeepSeek V4.1 Flash：平均约 q3.5 量化，97 tok/s。engram 全部卸载到 SSD（读写 13GB/s）并做异步预读，作者称对性能的影响可以忽略。权重元数据无损压缩又省下 7.9GB，常驻内存 216GB，dspark 和视觉能力完整保留。
- Qwen3.8 Flash Next：oq6 量化，143 tok/s。

<span class="mention">@务实的长颈鹿</span> 觉得 97 tps 完全能接受，想弄一台 512G 的。他问两台 128G 的 RTX Spark 串联行不行，<span class="mention">@细心的熊猫</span> 说可以。

<span class="mention">@细心的熊猫</span> 自己在本地跑 8bit 量化的 Qwen3.8 Flash Next。一个任务连续跑了 36 小时，输入 13.8 亿 token、输出 1,110 万，平均功耗约 100W，电费约 $1。<span class="mention">@坦荡的灰熊</span> 说 170hx 在闲鱼上还在涨价，截图里近 7 日成交均价 ¥12,750，他后悔当初没拿下。<span class="mention">@细心的熊猫</span> 则说 M5 Ultra 是为数不多还能按原价买到的东西，只是要等。

## 微信自动化与逆向

### iPhone 虚拟机做微信自动化：拆到最后只剩边际优势

<span class="mention">@细心的熊猫</span> 分享了 vphone-cli。它用 Apple 的 Virtualization.framework 和 PCC 研究虚拟机，在 Apple Silicon Mac 上跑一台预先越狱的虚拟 iPhone。他认为这样做微信自动化就不再需要实体手机。追问下去，<span class="mention">@今天群内信息量极大</span> 的结论是，和 Mac 读 sqlite、开 Mac 虚拟机相比，它的优势只是一点没经过实测的成本差。

<span class="mention">@细心的熊猫</span> 的理由有三条：官方 iOS 很难读到微信数据库，越狱后可以读；收消息直接读库最快；Mac 方案不 scalable，成本更高，iOS 也比 macOS 轻量。<span class="mention">@今天群内信息量极大</span> 的反驳是，host 本来就是 Mac，Mac 自己也能开虚拟机：

> 可能 mac 一台机器能开 20 台 mac 虚拟机，你用 iphone 虚拟机能开 22 台。这个优势就很小了。而且是个需要实测的未经证明的东西。

他补充说，这不是针对谁，而是最近群里常有人分享没拆解过的 hype 项目，「带着大家拆一下」。这次讨论也接着 10 月 14 日虚拟机登录被风控的事（[「微信自动化：电脑端扫码登录被限一周」]({{ '/daily/2026/10/14/daily/#微信自动化电脑端扫码登录被限一周' | relative_url }})）。

做商用的人最怕的是封号。<span class="mention">@神秘的企鹅</span> 说，他的客户一个微信号背后可能是几十万到上百万的业务，所以他选的路线是：在 macOS 上截取 iPhone 模拟器的画面，交给大模型读图，再模拟点击，全程不 root、不破解。他还给出了两条行业经验：企业微信不支持自动回复；客服号的成交力度远不如人设号。另外有几条踩坑和分歧：

- **截图被拦**：<span class="mention">@神秘的企鹅</span> 在 Mac 上让 Codex 截图回复微信，截不到；有一次回完消息，微信直接掉线了。<span class="mention">@今天群内信息量极大</span> 解释说系统有禁止截图的功能，银行 app 和 Zoom 都用。<span class="mention">@细心的熊猫</span> 的建议是放弃电脑端，直接用手机。
- **root 还是不 root**：<span class="mention">@细心的熊猫</span> 手上有两台安卓，一台 root 了一台没有，做逆向时用起来差别很大，「root 了就是裸奔」。<span class="mention">@热情的大象</span> 说 root 后的手机就检测不了截图，还可以把 root 隐藏起来。<span class="mention">@今天群内信息量极大</span> 的意见是 root 对安全伤害很大，开发时用用就好，实际使用别用。
- **移动端红利**：<span class="mention">@细心的熊猫</span> 观察到，移动 app 一直被认为相对安全，所以很多 app 移动端的反爬和封号机制比网页端、桌面端宽松。同一个 app，移动端调用的 API 可能就没有 Akamai。他估计这个红利期只剩半年到一年。
- **视觉方案**：<span class="mention">@细心的熊猫</span> 和 <span class="mention">@神秘的企鹅</span> 都以视觉为主，理由是视觉「永远好用」，反爬反不了。<span class="mention">@热情的大象</span> 提醒视觉的成本和延迟更高。<span class="mention">@今天群内信息量极大</span> 认为独占式的视觉方案照样能 scale，点赞农场就是靠山寨机堆起来的，真正的限制是商业价值。

<span class="mention">@细心的熊猫</span> 还贴了一个真实在跑的例子：一家餐馆的团购群里，AI 客服回答堂食推荐和哪些菜要提前点，回复里有当天价格、几点到货这类细节。现在跑的是本地部署的 Qwen，这周末准备上云，打算用 DeepSeek 或 Haiku。<span class="mention">@神秘的企鹅</span> 问，「现在店里挤不挤」「到了要等多久」这类实时数据从哪来。<span class="mention">@开朗的企鹅</span> 的办法是：能接 API 的接 API，接不到的 @ 店员回复，也可以接摄像头分析，店里有点单系统就加一个 MCP。<span class="mention">@坦荡的灰熊</span> 的方案是「在店里藏个录音机悄悄蒸」。<span class="mention">@细心的熊猫</span> 的感想是：

> 其实我完全不能理解为什么有人喜欢在微信上点餐，如果不是真实进入这种业务场景，我根本不知道需求在这里。

### 逆向硬件：没有反馈信号，AI 只能猜

前一晚 Hackios 的讨论（[「Hackios：iOS 跑在安卓硬件上？」]({{ '/daily/2026/10/16/daily/#hackiosios-跑在安卓硬件上' | relative_url }})）延伸到了用 AI 逆向硬件。两个亲历者的结果相反，分歧在有没有可靠的反馈信号。

<span class="mention">@热情的大象</span> 的 ipKVM 用的是 H616 板子，原厂系统没加 GPU 硬件解码，远程画面延迟高。他用 Claude Code 去逆向原厂 GPU 驱动，参照网上泄漏的一份早期源码，最后还是失败了，最终靠一份签了 NDA 的源码才搞定。他的解释是这种开发得不到可靠的 feedback，结果只有 work 和不 work 两种状态，很多功能只能猜。他也认为把 iOS 移植到骁龙上，苹果自己可能都没做过，系统里找不到可以参照的蓝本，TEE 就更没辙了。

<span class="mention">@务实的灰熊</span> 在用 AI 抠相机固件：没有手册，就读二进制加实机调试来找入口函数，从 ISP 管线到 AF 驱动一点点抠出来；AI 还会自己插探针去看数据流。他认为入口和出口弄清楚之后，做一个转接层就能直接用原来的驱动。但人仍然不可少，要给 GPT 提供方向，还要处理物理接口：

> ai 的上下文太短了，没有办法全都尝试一遍，需要你自己理解并管理进度。

<span class="mention">@细心的熊猫</span> 的推论是，本地运行的东西基本都在裸奔，FSD 这类本地推理模型要想不被逆向，只能把权重焊死在芯片里，「虽然这样也可以被逆向」。他举了一个反例：Akamai 到现在都没人破解，「因为破解的方法就是重新造一个 chrome」。

同一天还有一个项目：[d2r-mobile](https://github.com/jhaizhou-ops/d2r-mobile)。它让 Switch 版《暗黑破坏神2：重制版》的原生 aarch64 程序直接跑在 iPhone、iPad 和 Mac 上：

- 不模拟 CPU，只重写少数在 Apple 内核下跑不了的指令；
- 图形 API 整个实现在 Metal 上，shader 离线翻译、预编译；
- iPhone 17 Pro Max 实测 60fps，最低要求 A14 或 M1；
- MIT 许可，仓库不含游戏文件，需要用自己的 Switch 游戏文件在本地生成。

作者说这不是模拟器，<span class="mention">@80-HD</span> 认为本质上就是模拟器，<span class="mention">@细心的熊猫</span> 则类比成 Rosetta 式的转译。<span class="mention">@今天群内信息量极大</span> 没看出它和五年前的同类东西相比有什么变化，唯一的不同是 AI 让复刻老游戏的门槛低了很多（[「Astra 复刻东方风神录：值得学的是验证方法」]({{ '/daily/2026/10/10/daily/#astra-复刻东方风神录值得学的是验证方法' | relative_url }})）。

## Agent 与企业

### Agent 这么强了，为什么还要 FDE

<span class="mention">@风趣的长颈鹿</span> 问：agent 已经这么强，A 社和 O 社为什么还在养 FDE（驻场工程师），市面上的 FDE agent 为什么也没跑通？几种回答都落在「人」上：<span class="mention">@今天群内信息量极大</span> 认为 FDE 不仅解决技术问题，更解决人的问题，最终还是看一把手。

<span class="mention">@今天群内信息量极大</span> 的解释是，tribal knowledge 这类东西要先把 infra 建好，人因为各种理由不想做，想用好 AI 却必须做。怎么劝说客户去做、怎么用 AI 降低构建成本，只能靠 FDE。<span class="mention">@神秘的火烈鸟</span> 补充：「都是人情世故」，一把手想推也不一定推得动。

一位做供应链的非技术岗群友讲了自己的视角。他认为完全不懂行业的 FDE 做出来的东西没法用，道理和传统咨询公司要驻场一样。FDE 要解决三件事：

- 对抗经验主义，很多人仍然不习惯用 AI；
- 协调外部一致性，比如做了一个工具，怎么让供应商也愿意用；
- 「蒸馏」领域专家（SME）。

他举的例子是蒸馏出一个「should cost model + 行业供需判断 + 个人沟通风格」的 agent，拿去和供应商谈价。问题在于供应商没人愿意跟 AI negotiate，所以文风要去 AI 化，还得设计 human-in-the-loop 的护栏，界定什么时候必须真人介入：

> 你也不想 AI 谈着谈着就帮你下了个 5M 的订单吧。

<span class="mention">@风趣的长颈鹿</span> 的猜测是，就算人的问题都解决了，给每个小流程写一个 skill，最后攒出几千个 skill 文件，agent 照样会出岔子。企业够复杂、codebase 够乱的时候，怎么执行还得靠人的 taste、knowledge 和 bias。

## 工具与实践

### Ambient Mode：语音秘书给 agent 派活

OpenCode iOS 客户端合并了 [PR #215](https://github.com/grapeot/opencode_ios_client/pull/215)：原来实验性的 Car Mode 换成了托管的全双工 GPT-Live，改名 Ambient Mode，并加入 native job tools。按 <span class="mention">@今天群内信息量极大</span> 的说法，它是一个常开的语音 agent，主要用途不是查资料，而是直接操作 OpenCode：提交新 job、查看老 job 的状态、继续操控老 job，可以同时管理多个任务。背后有 harness、skills 和 context，能做的事比 ChatGPT 多。底层能力来自 AI Builder Space。

这接上了 10 月 14 日他对 ChatGPT Voice 的评价（[「Gemini 4 Argon：配额薄，审查报告错一半」]({{ '/daily/2026/10/14/daily/#gemini-4-argon配额薄审查报告错一半' | relative_url }})所在那期的零碎）。实际用下来，他一口气聊了半小时，许的愿都被自动派给 OpenCode，「她当 PM，我问问进度」。<span class="mention">@80-HD</span> 的经验是，刚用 Codex voice mode 时也很上瘾，用一段时间就觉得「她说得太慢」。

### 去 AI 味：检测器、改写模型、逐段核对

<span class="mention">@认真的灰熊</span> 问有没有人真正做到了去 AI 化，他调教 agent 大半年还是不行。<span class="mention">@今天群内信息量极大</span> 推荐了 Superlinear Academy 上的一篇[项目分享](https://www.superlinear.academy/c/share-your-projects/ai-ai-7371bd)，可以直接扔给 AI 去配置。要点：

- **规则和提示词都压不住**：规则扫描只能抓排比、总结腔这类具体句式，管不了整体语气，提示词和 few-shot 也没用，最后只能微调。
- **数据怎么造**：作者让 AI 把自己的 185 篇博客改写成 AI 腔，再反过来配对，让模型学「把 AI 腔改回我的写法」。生成 AI 腔用了多个模型家族，避免只学到一种腔调。之后在一张 RTX 5090 上训练 Qwen3.5-9B 的 LoRA，整个流程由 Opus 5.5 执行。
- **单用改写模型会出错**：拿 7 篇文章逐段核查，发现约 70 处语义漂移。最危险的是两类：动作主体归错（「团队选了 4 卡」变成「我们选了 4 卡」）和方向反了（「会恶化延迟」变成「会降低延迟」）。
- **正确用法是三件套**：检测器定位需要重点检查的段落，改写模型只换措辞，再由逻辑强的模型逐段对照原文，抓事实漂移和新增的格式。

<span class="mention">@稳重的海豚</span> 的另一个方案：「实在不行买点国内年轻劳力给你改。」

### 内容站冷启动：先开 20 个

<span class="mention">@开朗的企鹅</span> 问，需求验证的冷启动阶段，即使建了 feedback loop，数据量也太小，怎么加速。<span class="mention">@沉稳的仓鼠</span> 的回答是多做：token 这么便宜，「起手开 20 个项目」。<span class="mention">@开朗的企鹅</span> 已经有 20 个，其中四五个买了域名，其余大多挂在 Vercel 上。<span class="mention">@沉稳的仓鼠</span> 的建议是继续迭代，保底可以挂 Adsterra 广告；没域名的「那肯定是假的咯」。

两个数字可以对照：<span class="mention">@神秘的企鹅</span> 的一位同事做了 100 个游戏攻略类内容站，两个月收入 20 美元；另一位群友则说自己一批没人关注的小站已经月入过千美元。<span class="mention">@神秘的企鹅</span> 的看法是，成功的站点难以复制，因为做的人自己有体感，知道痛点和路径，也耐得住。<span class="mention">@沉稳的仓鼠</span> 最近在研究长音频和长视频，已经做了几个 [radio 内容](https://open-exam-prep.com/radio)，比如一集 61 分钟、由两个角色对话讲解 Claude 认证考试的节目，打算这几天扩到上百个。
