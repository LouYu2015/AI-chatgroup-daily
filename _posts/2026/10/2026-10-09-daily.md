## 模型与研究

### Microsoft-Decision-1：Qwen 底座的快速决策模型

<span class="mention">@天真的浣熊</span> 贴出 Satya Nadella 的推文。微软发布了 Microsoft-Decision-1，定位是「快速决策」模型，在结构化决策任务上的延迟和质量都超过 LLM 和其他决策模型，内部已经用在事故响应、质量控制和科研发现上。技术说明里写得很直白：它是 **post-train Qwen3.5-9B** 得来的，做单次前向的决策打分，之后会换到 MAI 和 OpenAI 的底座上。给定一组固定选项，它为每个选项输出校准过的概率，支持 yes/no、多选、评分，以及按 rubric 给 AI 回复和 agent 行为打分，调用方式是一个结构化 API。

官方对比图转写如下。准确率是 36 个 benchmark（147,737 题）的平均值，延迟是 JevBench v1.6.1 的 p50：

| 模型 | 平均准确率 | 中位延迟 | 校准（100 为完美） |
|---|---:|---:|---:|
| Microsoft-Decision-1 | 83.5% | 85 ms（p95 125 ms） | 92.2 |
| Quyet-1.0-Large（JevBench #1） | 81.9% | 380 ms | 93.1 |
| Surogate Rune 26B-A4B | 79.7% | 380 ms | 91.8 |
| GPT-6 Luna Decisions | 79.4% | 300 ms | 89.9 |
| deck-31B | 77.8% | 400 ms | 83.5 |
| H2O-Lightning-4B v1.1 | 77.2% | 210 ms | 91.8 |
| Jev 1.13.0 | 未排名 | 240 ms | 未评分 |
| GPT-6 Sol（参考） | 未排名 | 3.01 s | 未评分 |
| Strands-Decider 2B | 54.8%（仅 23 项） | 未测 | 未评分 |

按官方说法，它比第二名 Quyet 快 4.5 倍，比 GPT-6 Sol 快 35 倍；校准分比 Quyet 低 0.9。这和前天公开课的结论方向一致：用小规模开源 LLM 平替高速决策模型就能打平 Jev（[「模型进化比折腾者快」]({{ '/daily/2026/10/07/daily/#模型进化比折腾者快' | relative_url }})）。

<span class="mention">@80-HD</span> 的反应是：「MAI 不是自己有模型么？」又补了一句：Dario 不出来喷一下 Satya 蒸馏别人模型么。

### Meta 两篇 agent 论文：把控制权还给模型

<span class="mention">@活泼的羊驼</span> 凌晨转来[机器之心的解读](https://mp.weixin.qq.com/s/prtvMyXdeKYGpLn5ViVbjg)。Meta 超级智能实验室一天发了两篇论文，共同的主张是：agent 的控制权不该写死在人设计的 harness 里，应该交给模型。

**Context Language Models（CLM）**，代码已开源。它把上下文镜像成一个文件，模型可以用 Bash 随意编辑，改完立即同步回上下文。上下文的更新方式由 cₜ₊₁ = cₜ ⊕ f(cₜ) 变成 cₜ₊₁ = f(cₜ)，从系统维护的日志变成了模型自己的作品。

- 配套的 ContextBench 在 32K 上下文、最高 24 倍压力下测试，没有任何现有方法拿到满分。总结压缩会丢信息、会幻觉；不能原地编辑的方法每改一格数独就得重写整个棋盘。
- 在零样本、没有人教的情况下，CLM 自己摸索出了一套管理办法：多 agent 编排时自建记分牌；163 次原地编辑后上下文仍稳定在 6–8K token；自写了一个 `compact_turns` 压缩函数，反复调用 37 次。
- 成绩：BrowseComp-Plus 59.4%，比最强基线（Codex 式总结）高 11.4%，FLOPs 还少了 21.5%。EdgeBench-10 上是 44.6 对 42.3，单次试验 179 对 437 PFLOPs。

**Thinking Before Thinking** 把控制和执行拆开：worker 只干活，controller 专门决策，每轮走 Assess → Propose（这一步不看预算）→ Evaluate（在剩余预算下择优）→ Dispatch 四步。

- ProgramBench 上，GPT-5.5 拿到 71.5%，同条件下 Codex 是 58.0%；Opus 4.8 拿到 67.2%，Claude Code 是 65.5%。worker 和预算完全相同，只换了控制方式。
- 预算 scaling 是最有分量的结果：调用额度从 400 提到 1200，元推理从 64.1% 涨到 71.5%，直接控制则停在 64% 附近。
- 边界也写清了：小预算下显式控制不划算。Opus 在 400 次额度时是 56.6%，反而落后直接控制的 62.7%。

## Agent 实战

### GPT 写的 skill，笔墨全花在 governance 上

傍晚 <span class="mention">@稳重的海豚</span> 开骂：Opus 5.5 又降智了，「skill 写了不读，读了不做」。他注意到出问题时 context 已经到了 500K，<span class="mention">@蓝色大肥虞</span> 建议直接开新 session。

真正的原因后来查出来了。分析结论原文如下：

> Most of the text goes to governance instead: ownership lists, fallback legality, an optional external "Einstein lens" file, and prohibitions. Putting the provider logic in a script made this worse. The agent never learned how to use Firecrawl, so when the script quietly ran keyless, no agent could tell anything was wrong.

这份 skill 是之前迁移时让 5.6 Sol 写的。它塞了一堆 governance、guardrail 和检测脚本，真正的调用逻辑反而藏在脚本里。结果是 agent 从来没学会怎么用 Firecrawl，脚本在没有 key 的情况下静默运行时，没有哪个 agent 察觉到出了问题。<span class="mention">@稳重的海豚</span> 的反省是「怪我太久没仔细看 skill 内容」。

关于怎么写指令，另有两条经验：

- <span class="mention">@敏锐的海狸</span>：重复性高的活，他都用独立 prompt 交给 LLM，而且一定要能一键生成，否则 agent 会「给你稀里糊涂」。
- <span class="mention">@稳重的海豚</span>：Gemini 这类较弱的模型，指令要写得更详细，让 agent 机械执行。

### 面试作弊，与一套自博弈 harness

<span class="mention">@80-HD</span> 说这周面了两个用 AI 作弊的候选人。屏幕共享虽然能隐藏窗口，但能看到对方的鼠标指针在跟着一个他看不见的地方移动。<span class="mention">@风趣的麋鹿</span> 认为，上班天天用 AI，面试却要求纯手搓并不合理。<span class="mention">@80-HD</span> 说他们有专门的 AI 轮，又补了一句：OpenAI 和 Anthropic 都还在「古法面试」。<span class="mention">@沉稳的兔子</span> 的看法是「都是被疫情带坏了，以前正常招人谁不 onsite」。<span class="mention">@80-HD</span> 还观察到，这些作弊工具为了省成本大多用较差的模型，答得不在点上。<span class="mention">@随和的老虎</span> 补充：AI 容易多说一堆话，反而会被追问 follow-up。<span class="mention">@稳重的海豚</span> 的建议是让它结论先行。

某群友借这个场景讲了一套做 agent 系统的思路，值得单独记下来。目标产品是一个「提词器」，做法是让三个 agent 自博弈：

1. 三个角色分别是面试官 AI、面试者 AI、提词器 AI，另设一个判官 AI 打分，互搏几百场。
2. harness 的关键设定：面试官和提词器能联网（Tavily API），面试者不能；面试官只出面试者模型知识截止日期之后的题。
3. 面试者用「笨 AI」扮演，比如关掉思考。挑出它单独答不对、看了提词器就能答对的题，证明提词器起了作用。同时记录从出题到答题全程的延迟，找出瓶颈在哪。
4. 来回迭代几轮后，把面试者换成真人跑一轮，再修改 harness，继续迭代。

他的总结：

> 你永远只做 harness，只做数据，只架构 agent 左右互搏的系统，永远不要手动写 prompt。

<span class="mention">@稳重的海豚</span> 不完全同意。他认为最大的瓶颈是真人能多快理解 AI 给的东西，其他部分不那么重要。

## Codex 与额度

### OAuth 503：Daybreak 校验误伤

上午 <span class="mention">@今天群内信息量极大</span> 发现 Codex 的 OAuth API 用不了了。他的 agent 调研结果是：token 没过期，scope 也没问题，任意模型（gpt-5.1-codex、gpt-6-astra 都试过）请求 `/codex/responses` 都返回 HTTP 503，报错 `Unable to verify Daybreak Blue access`。

Daybreak 是 OpenAI 面向防御性网络安全的批准访问模式。<span class="mention">@今天群内信息量极大</span> 的解释是，它类似 Anthropic 的 Glasswing，要用带安全功能的 GPT 得先进内测。他本来就没进，这道校验本不该打开，所以是 bug。搜索后发现这是一次比较大的 incident，不止他一个人。<span class="mention">@冷静的麋鹿</span> 那边一切正常，<span class="mention">@聪明的灰熊</span> 报过一次错后自己恢复，<span class="mention">@今天群内信息量极大</span> 的大约半小时后也好了。

顺带一个细节：他贴出的调研 session，顶部模型选的是 DS4.1。

大家的第一反应都是「这不得 reset」。<span class="mention">@直率的鹦鹉</span> 判断周末肯定会重置，因为低谷期算力充足，正好送个顺水人情。截至晚上，群里没人看到全员重置。

## 存储与构建

### C 盘为什么总是满

<span class="mention">@睿智的犀牛</span> 发现 Windows 上的 ChatGPT 客户端占了 4GB，于是让 ChatGPT 卸载 ChatGPT。随后群友开始晒 C 盘：<span class="mention">@蓝色大肥虞</span> 是 1.81TB，<span class="mention">@乐观的海豚</span> 是 2.48TB，<span class="mention">@热情的大象</span> 也是 2TB NVMe。<span class="mention">@幽默的火烈鸟</span> 的 1TB 快满了，清都清不动。<span class="mention">@热情的大象</span> 猜大头是各种 agent harness 的 runtime 和 session 会话历史。

<span class="mention">@蓝色大肥虞</span> 说，他的 C 盘除了项目、VS/VS Code 和 Chrome 什么都没有，空间都被 C++ 编译产物吃掉了：binary 是源码的两千倍，最大的是 pdb。更要命的是改共享的模板代码时，一次出错能吐出 1TB 的错误文本，限制 trace 深度也没用，因为问题不在嵌套层数，而在调用点太多。要把代码全拉下来编译，得准备 4TB 硬盘；只有 2TB 的话，就得先编 debug、提交 CI、删光，再编 release，x64 弄完再弄 arm。现在这些都交给 AI：「5 分钟写完 prompt 下班，明天再看。」

由此聊到构建系统：

- <span class="mention">@睿智的犀牛</span> 提议用 bazel 和远程缓存，别人编过的不用再编，代价是每个目录都得写 BUILD 文件，还要装 bazelisk 管版本。他所在团队用的是 cmake 加 ninja。
- <span class="mention">@蓝色大肥虞</span> 认为 bazel 要求在项目文件里写清每个文件的依赖，对 C# 这种只有项目级依赖的语言很不友好。他说 cmake 已经是事实标准，自己还写过一个 vmake，用来在 Linux 下 build vcxproj。
- <span class="mention">@飘逸的浣熊</span> 补充，bazel 也有文件大小和内存限制，输出太多会被 kill。还有 build_cleaner 可以自动补依赖。不过 Google 的东西是为超大 monorepo 设计的，所以没有 bazel 和 grpc 版本不一致的问题，搬到外部就有了。
