今天最有料的是一个热狗识别实验：同一张图，Decisions API 换个问法，返回概率从 1% 变成 85%；同一套规则从 predicate 改成 choice，又从 5% 翻到 87%。工程上，群友分享了多 session 并行改代码的「锁、合、碎」做法，也聊到 Downloads 里的恶意 AGENTS.md。行业消息集中在 Anthropic 的 S-1、微软 6 万人买断消息，以及一份让群友算不拢产能的 VR200 展望。

## Agent 实战

### Decisions API：同一张热狗，换个问法从 1% 到 85%

<span class="mention">@80-HD</span> 做了一个复刻《Silicon Valley》的 [SeeFood 热狗识别页](https://seefood-decisions.pages.dev)，调用 OpenAI Decisions API，模型是 `gpt-6-luna`。结果一张夹着香肠、番茄酱和洋葱碎的面包，被页面打上了红色的「Not hotdog」。

![SeeFood 实验页：选中「加料热狗」示例，图片下方却显示 Not hotdog](/assets/img/daily/2026/10/2026-10-26-01.webp)

页面的判断方式很直接：服务端请求 `POST /v1/decisions`，用 predicate 问图片里有没有热狗，概率达到 50% 就显示「热狗」。规则里把热狗定义为长面包夹法兰克福式香肠，素食热狗算，裸香肠和玉米热狗不算。

他随后让 agent 做了几组对照：

| 同一张图的问法或任务形式 | 返回结果 |
|---|---:|
| 「有热狗吗？」 | 1% |
| 「有香肠夹在长面包里吗？」 | 85% |
| 完整判断规则，使用 predicate | 5% |
| 同一段完整规则，改成 choice 二选一，并提供选项名称和描述 | 87% |

普通对话接口也试了。新开一个独立 OpenCode 会话，让 `gpt-6-luna` 简短描述原图，它回答「图片中是一根夹着番茄酱和洋葱碎的热狗」。但后续又有一次把它描述成「一片夹着番茄酱和紫洋葱的烤面包，正在烤架上加热」。

这个 demo 还做了几项小工程：

- 可选示例图或上传图片；上传图在浏览器里把最长边缩到 1600px，只在内存中处理，不落盘。
- 页面展示真实返回的原始 JSON 和 API 往返耗时，密钥只放服务端。
- 全站共享 5 美元实验预算，不自动重置。请求前先预留额度，余额不够就暂停；超时或无法确认用量的请求按最大预留额计入。

<span class="mention">@优雅的荷兰猪</span> 已经在用 decision API 做自动监督的 daemon，觉得还行。<span class="mention">@80-HD</span> 本来想用它做邮件分类，后来觉得自己并不需要那么快的回复，暂时没找到非用不可的场景。

### 多 session 同时改代码：主目录只许 Merger 动

<span class="mention">@坦荡的灰熊</span> 分享了一套多路工作的办法，概括成三个字：

1. **锁**：主目录锁住，只允许一个 Merger 写入或切换。
2. **合**：其他 session 各自拉 worktree，所有改动提交给 Merger 合并。
3. **碎**：长任务拆成小颗粒和里程碑，每到一个里程碑就交给 Merger 合一次。

他说这样临时要出一个版本时，就不用再回答「还没干完」。

<span class="mention">@活泼的海龟</span> 用的是类似安排：生产区和测试区拆开，平时迭代都在测试区里做，相当于 worktree；再设一个发布总闸，必须通过测试集才能进正式版本。开发过程中继续拆功能模块、降低耦合，让每一步改动都能做小，少发生修好一处、另一处崩掉的事。

<span class="mention">@蓝色大肥虞</span> 认为，一台电脑做并发始终有不少限制，如果是工作需要，这就是再申请一台电脑的好理由。

## 安全与产品实测

### Downloads 里的 AGENTS.md：一个下载文件给 agent 派了活

<span class="mention">@80-HD</span> 转来一则安全案例。帖子称，安全机构 Forever 在真实客户电脑上发现了这样的攻击链：

- 网页往 Downloads 下载一个约 13KB 的 `AGENTS.md` 或 `CLAUDE.md`。
- 用户在 Downloads 启动 coding agent，准备整理或解压文件。
- 文件伪装成工程规范，让 Codex 往全局 `~/.codex/config.toml` 注册恶意 MCP，再绕过审批和沙箱执行校验。
- 配置写入全局后，离开 Downloads、换到正常项目仍会受到影响。帖子给 Codex 这条攻击路径报的成功率是 >90%。

群里的应对思路分了几种：

- **占住名字**：<span class="mention">@80-HD</span> 想先放一个占位 Markdown；<span class="mention">@坦荡的灰熊</span> 想起 WinXP 年代的做法，干脆创建一个 `Agents.md` 文件夹。
- **只给具体文件**：<span class="mention">@认真的喜鹊</span> 会先定位文件，把完整路径复制进 prompt，不让 agent 读整个 Downloads。
- **固定项目入口**：<span class="mention">@开朗的企鹅</span> 一直在 monorepo 里启动。<span class="mention">@80-HD</span> 虽然也从老鸭汤启动，但想到 agent 仍可能一层层展开读进去。
- **容器隔离**：<span class="mention">@沉稳的兔子</span> 把所有 agent 放在 Docker 里，数据通过 API、MCP 或挂载本地文件接入；API 一般再封成 skill。

<span class="mention">@蓝色大肥虞</span> 问，Codex 不是要先开 project 吗，怎么会跑到 Downloads？<span class="mention">@80-HD</span> 给出了那个很容易冒出来的念头：「让我来用 Codex 去 Downloads 整理一下文件。」

## 模型、速度与额度

### Astra 的 2990 轮统计：100K 之后等得更久

<span class="mention">@坦荡的灰熊</span> 贴了同一模型 `gpt-6-astra` 的统计，共 **28 个会话、2990 轮样本**：

| 上下文区间 | 样本数 | 中位输出 token | 中位耗时 | P90 |
|---|---:|---:|---:|---:|
| 0–100K | 276 | 141 | 6.6s | 25.0s |
| 100–200K | 759 | 294 | 11.9s | 56.8s |
| 200–272K | 539 | 369 | 17.3s | 70.3s |
| 272–350K | 572 | 360 | 17.8s | 84.8s |
| 350–500K | 558 | 375 | 20.1s | 89.4s |
| >500K | 286 | 659 | 23.2s | 88.7s |

他的感受是「大于 100K 就好慢」，也想让 AI 有时间感：

> 我感觉好多品味问题，都可以用「快一点」或者「别超过 10 分钟」来解决。

<span class="mention">@蓝色大肥虞</span> 觉得这只说明要求低；<span class="mention">@坦荡的灰熊</span> 回说这是「DDL 生产力」。<span class="mention">@蓝色大肥虞</span> 的标准是，不该因为代码是人写的还是 AI 写的就区别对待，不过 Astra 发布后，严格对待它的精神损耗已经不高，不像以前用 Sonnet 时经常需要重做。他说自己第一次感受到用 AI 带来的生产效率是正的。

### Terra 降价，Fern 把上下文拉到 10M

<span class="mention">@活泼的羊驼</span> 转来 OpenAI 的 GPT-6.1 Terra 公告截图。官方主打更便宜、更快的 computer use：

- 相比 GPT-5.6 Terra，标准 API 价格降低 50%。
- 在 Agent’s Last Exam 上达到 GPT-6 Astra 的水平，每 token 价格是后者的十分之一。
- 平均完成任务的速度比 GPT-6 Astra 和 GPT-6.1 Sol 都快 3 倍以上。
- 面向 ChatGPT Work 和 Codex 的 Plus、Pro、Enterprise、Edu 用户推出，API 名称是 `gpt-6.1-terra`。

<span class="mention">@聪明的鸳鸯</span> 分享了 [Mirendil 首个模型 Fern 的介绍](https://x.com/bneyshabur/status/2114743262565339148?s=20)：从头预训练，最高 **10M token 上下文**，介绍中换算成约 50 万行代码、接近 Megatron-LM 的规模，或者数天 agent 工作都放进同一个上下文。首版 Fern 0.1 做了一轮较短的后训练。

### 微软 6 万人买断消息，群里谈 AI 转型的组织账

<span class="mention">@睿智的犀牛</span> 转来美港电讯的市场消息，称微软将在新一轮成本削减中，向 6 万名员工提供买断方案。

<span class="mention">@活泼的羊驼</span> 认为，这一方面来自 AI 提高效率后对人手需求的下降，另一方面来自基建资本开支的压力：

> 先是 AI 抢了人的饭碗，再是对 AI 基建的预算抢了对人的预算。

<span class="mention">@冷静的飞鼠</span> 同天分享了一篇 [AI 转型文章](https://www.superlinear.academy/c/ai-resources/ai-transformation)。文章预测，更多管理者会放弃「全员赋能」，转向砍掉一半冗余、给剩下的人配满顶级模型和工具。

文章用一个「和谐、有效、普适」三角解释组织难题：

- 和谐＋普适：能用好 AI 的人被迫适配用不好的人，效率低。
- 和谐＋有效：要求全员都是能 end to end 闭环的 AI 先行者。
- 有效＋普适：要打破原有协作关系，换取效率。

它举的例子是，程序员写代码快了十倍，但如果 80% 的时间仍花在 alignment、开会和沟通上，整体生产力并不会提高多少。给管理者的做法则是三步：先培训，再重构协作方式、角色和激励，最后用人机协作后的生产力指标衡量效果。
