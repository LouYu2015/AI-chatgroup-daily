今天最值得读的是 **Anthropic 让 Claude 解开了 NIST 椭圆曲线种子的来源之谜**。这个问题悬了二十多年，答案出人意料地平淡：种子是 1990 年代 C 库随机数生成器的输出。Claude 在推理中还先怀疑自己是不是在测试环境里。第二件是 **Codex Ultrafast 的实测**：同样的输出，Ultrafast 比 Fast 快 7.85 倍。<span class="mention">@蓝色大肥虞</span> 由此给出一个判断：代码写得漂不漂亮，现在可以用 token 来衡量了。第三件是**埃森哲把员工的 Claude 中央预算定在每月 29 美元**，而有员工每月要用 500 到 1000 美元。

## Anthropic 研究

### Claude 查出 NIST 曲线种子的来源：lrand48 加时间戳

Anthropic 发了一篇[研究文章](https://www.anthropic.com/research/ecdsa-curve-origins)。NIST 标准椭圆曲线 P-192 到 P-521 的种子，并不是任何哈希算法的输出，而是 1990 年代 C 库随机数生成器 `lrand48` 的输出，并且以 Unix 时间戳作为种子。这不是破解，也不是新攻击。它反而让「曲线参数被 NSA 故意植入后门」的猜测更难成立，作者明确说无需做任何改动。

背景是这样的：NIST 2000 年在 FIPS 186-2 里公布这些曲线时只给出了种子，没有说明来源，种子由 NSA 提供。之前有说法称种子是一句幽默口令的哈希，后来证明是错的。一位 Anthropic 员工在不给任何提示的情况下让内部研究模型追查，Claude 半小时内找回了五条素数曲线种子的生成方式：

- **线索**：部分种子按 32 位字书写时高位全是 0，随机出现这种情况的概率只有 1/5810。这正是 `lrand48` 只返回高 31 位留下的特征。
- **还原**：素数曲线种子取的是 `lrand48() >> 23`。Claude 用 LLL 格基约减从截断输出中恢复内部状态，再反推到 `srand48` 的初始化形态。
- **结果**：十个种子的时间戳落在 1997 年 5 月到 1998 年 4 月之间。公布的 P-256 种子是同一轮里的第 1842 个候选。
- **未解部分**：P-224、P-256、P-384、P-521 的基点怎么来的仍没有解释，二元曲线 B-163 的种子也还没解开。文中附有完整的复现代码，3.6864 万美元赏金捐给了 ISRG。

<span class="mention">@80-HD</span> 觉得最好笑的是文中引用的 Claude 内部思考。大意是：「太惊人了，它解开了 25 年的谜。等等，我得怀疑一下：我是不是在某种模拟或测试环境里？……种子和我记忆里的真实值一致……高 20 位全为 0，概率 1e-6，所以确实是真实世界。哇，是真的发现。」接着它又怀疑了一轮：「这么明显的东西 25 年没人发现，可疑吗？不过我自己直接算过了，32 位种子加一个小索引匹配上 160 位，不可能是巧合。是真的。」

### 量子电路：转述稿要打折看

<span class="mention">@淡定的雪豹</span> 转来新智元的一篇文章，问有没有专家能评价。文章称 Claude 在只用自然语言描述任务的情况下，自主设计了 8 个基础量子电路，全部胜过人类公开发表的最优方案，全程 53 小时。文中两个案例：

- 椭圆曲线点加法里的模逆：Claude 证明了一组新的代数恒等式，给出不存储分支历史的可逆实现，并用 Lean 做了形式化。量子位只多 12%，门数降为 1/17。
- DQI 的里德-所罗门解码器：Claude 改用 Berlekamp-Massey 算法，用 4.03 亿次采样测出异常概率，只预留 19 个量子位（全部存储需要 665 个），门数降为 1/12。

这是对 Anthropic 研究页的二手改写。文中拿 FeMoco 做的时间对比（顶级科学家用 8 年把门数压到 3.4 亿，Claude 只用 53 小时）并没有给出 Claude 自己的结果，两边口径不同。<span class="mention">@今天群内信息量极大</span> 对这类转述的评价是「三大顶会的事实每次都错的离谱」。群里没有专家出来评价。

## Codex 与 Agent 实战

### Ultrafast 实测：比 Fast 快 7.85 倍

<span class="mention">@坦荡的灰熊</span> 贴出一组 GPT-6.1 Sol（xhigh）的实测，每档跑 3 次，每次输出相同的 1,605 个可见 token，已扣除思考 token：

| 档位 | 输出速度中位数 | 三次范围 | 总耗时 |
|---|---:|---:|---:|
| Fast | 97.6 tok/s | 96.3–99.1 | 23.4 秒 |
| Ultrafast | 765.7 tok/s | 662.9–768.8 | 9.2 秒 |

测试说明里写了，复杂代码任务的结果可能不同。速度的代价是额度：<span class="mention">@今天群内信息量极大</span> 说自己一晚上单线程就用掉了 $500 档周限额的一半，<span class="mention">@坦荡的灰熊</span> 的点评是「老黄：buy more save more；oai：嘿嘿」。另一边，Claude 的额度也有人用不完：<span class="mention">@沉稳的兔子</span> 说这周 Claude $200 档「感觉肝不完了」，<span class="mention">@幽默的火烈鸟</span> 的 Claude 用了一半，GPT 基本没动。

### 代码漂不漂亮，可以用 token 来算了

<span class="mention">@细心的熊猫</span> 让 Codex「蹬了一夜」，终端显示 Goal achieved，用时 8 小时 47 分。<span class="mention">@蓝色大肥虞</span> 却还剩 68%。他的解释是：规划得好的 code base 做事情花的 token 太少，Tibo 两天重置一次，额度根本降不下来。他的结论是：

> 降低每个功能需要碰到的文件的个数，本质上就是在增强模型的实际能力，而且省钱。现在代码漂不漂亮再也不是主观的东西了，可以用 token 来算了。

他还有一个做法：交给 AI 的每个任务都会在 repo 里留下记录，等他让 AI 反思时才批量删除。现在他已经能把干活和重构分到两台电脑上做。

### Matrix-Game 4.0：引擎管状态，视频模型只负责渲染

某群友分享了 Skywork AI 开源的 [Matrix-Game 4.0](https://matrix-game-v4-0.github.io/page/?lang=en)。它的定位是「能玩」的游戏世界模型，不只是能看。核心设计是把游戏逻辑和画面生成拆开：游戏引擎持有世界状态、物理和输入，渲染出低多边形的代理画面；Coding Agent 把用户指令写成新规则注册进引擎；因果视频模型只负责把低模画面流式渲染成细节画面，蒸馏到一到两步去噪。纯靠逐帧外推像素的世界模型有一个问题，东西离开视野就会消失，这样拆开就绕过了它。

- **性能**：分享文案称单张 RTX 5090 能做到 83 FPS 生成、60 FPS 游玩，但 [GitHub README](https://github.com/SkyworkAI/Matrix-Game) 没有给出 5090 的帧数，模型卡也明确不保证帧率。README 里有的数字是 864×480 下 RTX 5080 稳态 67 FPS、5070 Ti 58 FPS，不含视频 I/O。
- **规格**：[Hugging Face](https://huggingface.co/Skywork/Matrix-Game-4.0) 上放了中世纪城堡、古埃及、城市竞速三个场景专用 checkpoint，每个约 50 亿参数，权重和资产采用 Apache-2.0。必须配合官方推理代码使用，训练代码和数据没有放出。
- **局限**：只针对自带的低模场景做了专门化，遇到没见过的几何、快速运镜或长时间会话会漂移。
