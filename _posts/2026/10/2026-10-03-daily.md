5090 双卡配什么推理引擎？<span class="mention">@优雅的喜鹊</span> 用同一台机器跑了 NInfer、ninfer-tp2、vLLM Swift 三套方案的完整基准，各场景胜负分明，想搭本地服务的读者直接翻表格。OpenAI 给 Pro 100 上线了按次购买的即时重置，不再需要为偶尔爆量去订高档套餐，订阅策略该重算了。<span class="mention">@冷静的飞鼠</span> 和 <span class="mention">@今天群内信息量极大</span> 在哥大做的 AI 学习讲座回放已公开，把当下热门技术名词逐一拆成时代包装与底层真问题，适合完整看一遍。

## 本地推理引擎横评

### Strata 多卡扩展

继昨天 <span class="mention">@今天群内信息量极大</span> 在单卡 5090 上用 Strata 跑通 Qwen3.8-Flash-Next（[「Strata 单卡跑 MoE」]({{ '/daily/2026/10/02/daily/#strata-单卡跑-moe' | relative_url }})），今天 <span class="mention">@细心的熊猫</span> 和 <span class="mention">@优雅的喜鹊</span> 分别测试了多卡方案。

<span class="mention">@细心的熊猫</span> 用 4×5060Ti 把 83% 的专家（20,347 / 24,576 个）装进 GPU，覆盖 99.5% 路由流量。短上下文 decode 代码 89–94 tok/s、散文 58.5 tok/s，大约是 README 所列单卡数字的两倍。<span class="mention">@今天群内信息量极大</span> 看到 83% 的命中率惊叹——自己单卡 5090 只装了不到一万个。<span class="mention">@细心的熊猫</span> 解释：四卡显存大的好处是能塞更多 KV cache，专家少一点问题不大。

<span class="mention">@优雅的喜鹊</span> 在双 5090 上测了同一个 MoE 模型（262K 上下文），双卡缓存 17,632 个专家，覆盖 99.1% 路由流量：

| 配置 | 解码 temp 0 | 首 token | prefill 119k | 119k 后解码 |
|---|---|---|---|---|
| Strata 单卡 | 137 tok/s | 450–660 ms | 6,124 tok/s | ~154 tok/s |
| Strata 双卡 | 168 (+22%) | ~240 ms | 8,307 (+36%) | ~198 (+28%) |

双卡在大多数场景提速 20–36%，首 token 延迟更是砍半。但他试完后还是切回了 Qwen3.8-27B dense 模型——Strata 只支持串行处理单个请求、不能并发，而且 cache 管理落后于 NInfer。

> <span class="mention">@优雅的喜鹊</span>：我 8 并发 2000 toks 不香吗

<span class="mention">@今天群内信息量极大</span> 也有类似体感：跑了一段 Flash-Next 后没觉得明显更聪明，加上 IQ3 量化下「粗口率直线上升」，他决定等 NVFP4 量化再试。<span class="mention">@细心的熊猫</span> 判断 Strata 的意义是让人尝到 MoE 的甜头，「可能发现 moe 好用后就去买 dgx 或者 m5 ultra 了」——但他自己在 4×5060Ti 上已经把 Strata 删了。

### 双 5090 全引擎对比

<span class="mention">@优雅的喜鹊</span> 在同一台机器（2× RTX 5090 32GB，PCIe 5.0 x8，Ryzen 9 9950X，186GB DDR5）上系统对比了四种部署配置跑 Qwen3.8-27B（QUASAR NVFP4 权重，全部启用 MTP 投机解码）：NInfer 单卡、NInfer 双卡双实例（每卡独立运行）、ninfer-tp2（张量并行）和 vLLM Swift 1.5 双卡。

解码与并发（tok/s）：

| 指标 | NInfer 单卡 | NInfer 双实例 | ninfer-tp2 | vLLM Swift |
|---|---|---|---|---|
| 散文单流 temp 0 | 169 | 同单卡 | **249** | 184 |
| 代码单流 | 220 | 同单卡 | **290** | 241 |
| 119k 后散文 | 168 | 同单卡 | **270** | 185 |
| 散文 8 并发总吞 | 874 | 1,221 | 1,053 | **1,213** |
| 代码 8 并发总吞 | 1,168 | 1,366 | 1,266 | **1,517** |
| 8 并发每路（散文）| 130 | 171 | 151 | **173** |

预填充与容量：

| 指标 | NInfer 单卡 | NInfer 双实例 | ninfer-tp2 | vLLM Swift |
|---|---|---|---|---|
| prefill 7.5k | **12,351** | 同单卡 | 10,112 | 7,598 |
| prefill 119k | **6,426** | 同单卡 | 5,396 | 5,147 |
| KV 池（万 token）| 31 | 63 | 115–**210** | 139 |

（加粗为该行最优；ninfer-tp2 KV 池 115 万为 int8 格式、210 万为 NVFP4 格式）

NInfer 双实例的独特优势在极高并发：16 路代码解码总吞吐达 2,080 tok/s，是唯一测了 16 并发的配置。代价是两个独立端口，需要自行做负载均衡。

<span class="mention">@优雅的喜鹊</span> 给出选型建议：追求单请求延迟选 ninfer-tp2（散文 249、代码 290 tok/s）；多 agent 并行选 NInfer 双实例（16 路代码 2,080 tok/s）；需要单端口、大 KV 池、高并发每路稳定性选 vLLM Swift 1.5（8 路每路 173 tok/s）。NInfer 单卡在预填充上遥遥领先（7.5k prompt 达 12,351 tok/s），适合需要快速读入长文档的场景。

### TensorFold 初探

<span class="mention">@优雅的喜鹊</span> 分享了新发现的推理引擎 [TensorFold](https://github.com/ashhart/TensorFold)，同时支持 Apple Silicon 和 NVIDIA GPU（compute capability ≥ 8.9），对外暴露 OpenAI 和 Anthropic 兼容接口。DGX Spark 社区已经「全都转到这个推理栈了」，引擎原本为 Mac 开发，双 DGX Spark 跑 GLM-5.3-Flash 可达散文 60、代码 110 tok/s。

但在 Mac 上表现不佳。<span class="mention">@细心的熊猫</span> 在 M5 Ultra 上对比了 TensorFold 和 mlx-serve 跑 Qwen3.8-27B：

| 引擎 | 代码解码 | 散文解码 | prefill 128K | 8 路并发总吞 |
|---|---|---|---|---|
| TensorFold (Vontra 4bit) | 209 | 98 | 2,581 | 322 |
| mlx-serve (iQ-4.7bpw) | 185 | 118 | 5,274 | 257 |

（短上下文 decode，tok/s）

TensorFold 代码解码略快、并发吞吐更高，但 prefill 只有 mlx-serve 的一半。<span class="mention">@今天群内信息量极大</span> 确认在 Mac 上速度确实不如 mlx。<span class="mention">@细心的熊猫</span> 的整体判断是各家引擎都在互相抄、追赶很快，「但是目前还没有一家能把 m5 ultra 的能力完全释放」。

### 本地推理的定位之惑

连测三天数字之后，<span class="mention">@今天群内信息量极大</span> 把讨论拉回一个更根本的问题：本地推理到底拿来干什么？他自己的主要用途是调研、email 管理、文案起草——不需要顶级智能的秘书体力活，图的就是快。5090 跑 Qwen 27B 比云端 GLM-5.3-Flash 都快不少，需要高智能的长程任务照样丢给 GPT。<span class="mention">@优雅的喜鹊</span> 给了一句定位：「本地的快就行了，笨点无所谓。」

<span class="mention">@直率的鸵鸟</span> 追问这些活在线模型也能做，为什么非得本地。<span class="mention">@今天群内信息量极大</span> 坦言「一直在 struggle 本地 host 模型到底有啥用」。更深层的反思来自一天测试后的系统性体验：纸面数字高不等于体验好。

> <span class="mention">@今天群内信息量极大</span>：Local host 它是一个系统性的东西，不是说测出来纸面数字高，体验就会更好。它有相当多的影响因素，比如它到底能不能并发，它的 scheduling algorithm 是什么样的，它对 cache 的管理是不是足够精细人性化。

他同时开源了自己在 M5 Max 上部署 Qwen3.8-Flash-Next 的 [MLX 包装器](https://github.com/grapeot/qwen38-mlx-serving)，直接交给 Claude Code 或 Codex CLI 调用。

### 做出来不等于学会

<span class="mention">@冷静的飞鼠</span> 和 <span class="mention">@今天群内信息量极大</span> 受邀在哥伦比亚大学 COMS W4995（Agentic Engineering）做了 88 分钟的客座讲座，[回放和中英课件已公开](https://www.superlinear.academy/c/recording/columbia-ai-learning-and-judgment-20261002)。

核心主张：AI 能替你把东西做出来，但做出来不等于学会。一项高中数学实验中，练习时能随时用 GPT-4 的学生练习成绩高 48%，但到了无 AI 考试反而比从未用过 AI 的学生低 17%；第三组由老师设定 GPT-4 只给提示不给答案，练习高 127%、考试没有明显下降。结论是 AI 做对时最危险——你以为自己也会了。

<span class="mention">@今天群内信息量极大</span> 在讲座中提出了一个拆解技术名词的框架：每个概念分成「绕开当年技术限制的包装」和「一直都在的底层问题」。四个例子：RAG 的分块流水线是 2023 年上下文窗口小时的产物，真正要学的是信息检索；LangChain 的层层抽象多半是给较弱模型打的补丁，留下的核心问题是编排四问——agent 能看到什么、能做什么、什么时候停、什么时候找人；MCP 默认把一切塞进上下文，CLI 加说明文件往往够用；微调几乎不适合灌知识，只剩固定风格和大规模降本两件正经活。判断方法：如果模型强十倍，这套做法还重要吗？

### Worktree 与 agent 并行

<span class="mention">@80-HD</span> 提到同时开几个 worktree 硬盘快撑满了。<span class="mention">@谨慎的灰熊</span> 问 worktree 到底有什么用——上次让 Claude Code 清硬盘，清出了几十 GB 的 worktree 和 200 多 GB 的 npm 包。<span class="mention">@坦荡的灰熊</span> 解释：worktree 相当于拷一份代码避免修改时和 agent 冲突，「拉出来容易合回去难」。<span class="mention">@热情的狮子</span> 补充关键价值：多个 agent 可以 parallel 工作、不在同一个 branch 上打架。<span class="mention">@搞仁义毛义仁</span> 提醒 worktree 不是免费午餐，本质是多 clone 一次但共享 .git 文件夹，用完要及时删除。<span class="mention">@洒脱的猫头鹰</span> 建议在顶层 agents.md 写上用 pnpm，减少重复安装的体积。
