今天最实用的是两笔订阅账。<span class="mention">@今天群内信息量极大</span> 算了 Gemini Ultra 的配额：$100 档一周只够用约 1.5 亿 token 的 Gemini 4 Argon，折合 API 约 $240；同一天流传的一份代码审查评测里，Argon 的论断有一半被判为错误。他还在 Codex 的 Ultrafast 档位上一晚跑了 5.4 亿 token，据此推算 $500 套餐约等于 $3,000 的 API 用量，并说「补贴额度真的是在下降」。第三件值得读的是一场关于做减法的讨论：一个只做 embedding、不搭 RAG 的个人问答站引出了一个问题，简单系统和确定性 workflow 各自适合谁。另外，群友让各家模型「从 1 到 10 选个随机数」，几乎都答 7。

## Gemini 与 Codex

### Gemini 4 Argon：配额薄，审查报告错一半

<span class="mention">@今天群内信息量极大</span> 用 Gemini 4 Argon 干了一天，周配额眼看就要见底。他的算法是：$100 的 AI Ultra 如果全用 Gemini 4，一周只有约 1.5 亿 token，折合 API 约 $240，「这也太离谱了」。<span class="mention">@谨慎的灰熊</span> 的解释是模型的单位智能不够，只能靠堆推理量和模型尺寸来补。<span class="mention">@沉稳的仓鼠</span> 已经退回 3.8 Flash，他怀疑 Argon 的 cache 有问题。

<span class="mention">@今天群内信息量极大</span> 还贴了一张评测截图。七个模型各写一份代码审查报告，由四位评委打分，并核查报告里的具体论断是否属实：

| 排名 | 模型 | 加权分 | 跨家族评委分 | 被判为错误的论断 |
|---|---|---:|---:|---:|
| 1 | Opus 5.5 | 8.40 | 7.97 | 2 / 42 |
| 2 | Sonnet 5.5 | 7.88 | 7.17 | 6 / 69 |
| 3 | GPT-6.1 Sol | 7.66 | 7.50 | 3 / 42 |
| 4 | GPT-6 Astra | 7.11 | 6.82 | 2 / 41 |
| 5 | Muse Wonder Full | 7.04 | 6.75 | 4 / 41 |
| 6 | Muse Wonder | 4.75 | 4.72 | 21 / 46 |
| 7 | Gemini 4 Argon (High) | 3.95 | 3.95 | 47 / 92 |

四位评委里有三位把 Argon 排在最后，另一位排第六，排在 Muse Wonder 之前。评语指出了两个问题：

- 它标为「Verified」的一些表、常量和函数根本不存在。
- 优先级最高的两条建议都读错了代码。第一条把经过授权的宿主文件读取说成严重的沙箱绕过，第二条建议加一个已经存在的索引。

审美方面，<span class="mention">@沉稳的仓鼠</span> 认为 Gemini 4 做视频、做网站和 3.8 还是同一套风格，复杂但不够现代，「远远不如 opus 5.5」。<span class="mention">@乐观的灰熊</span> 说他现在看到带网格的背景就头疼。<span class="mention">@直率的海豚</span> 则截到 Argon 在回复里先夸自己一句：「这个递进节奏太棒了！」

省钱的路子也有人找到了。<span class="mention">@细心的熊猫</span> 发现土耳其区的 Google AI Ultra 标价 ₺1,479.99/月，同样包含 Gemini 4 Argon 和 20TB 存储，按他的换算约合 $30。<span class="mention">@机智的水獭</span> 和 <span class="mention">@今天群内信息量极大</span> 先后回了同一句：「今天我们都是土耳其人。」

### Ultrafast：一晚 5.4 亿 token，$500 套餐约等于 $3,000 API

Codex 现在有三档速度：Standard、Fast（1.5 倍速，消耗更多额度）和 Ultrafast。据 <span class="mention">@今天群内信息量极大</span> 介绍，GPT-6.1 Sol 在 Ultrafast 下能跑到 200–400 tps，但只有 $500 套餐能用。

![Codex 速度选单：Standard、Fast（1.5x speed, more usage）、Ultrafast（The fastest available responses for latency-sensitive work）](/assets/img/daily/2026/10/2026-10-14-01.webp)

他一晚上跑了 5.4 亿 token。按消耗掉的配额推算，整周全用 Ultrafast，API 价值约 $780，一周大约能跑 9 亿 token。他由此估算 $500 套餐的 API 等值约 $3,000，补贴在缩水。对 Fast 档，他的评价是：「把原来速度的 gpt 加价 50% 叫做 fast，生财有道了。」<span class="mention">@务实的长颈鹿</span> 用的是 $200 档，他说最近 GPT 慢得让人忍不住。

另外几条：

- <span class="mention">@随和的企鹅</span> 开着 $500 档，至今没在 Codex 里看到 Ultrafast。他的账号前两天被莫名限流，今天恢复了，cache hit 也回到正常，之前经常整段失效。拿去做中转的两个号同样恢复了。他据此判断，昨天的 capacity 报错（[「重置之后：慢、断线、capacity 报错」]({{ '/daily/2026/10/13/daily/#重置之后慢断线capacity-报错' | relative_url }})）大概真是服务端的问题。
- 想强行用上 Ultrafast 的人，<span class="mention">@今天群内信息量极大</span> 推荐了 [chat-gpt-oauth-skill](https://github.com/grapeot/chat-gpt-oauth-skill)。它用订阅账号的 OAuth 凭据直接请求 Codex 后端，不需要 API key，`--service-tier` 可选 default、fast、priority、ultrafast。走的是逆向接口，作者明确写了只适合个人学习和自用工具，不要扩展成多用户服务，token 以明文写在本地。

## Agent 与系统设计

### 简单系统抬上限，确定性 workflow 抬下限

<span class="mention">@冷静的飞鼠</span> 用自己的公开内容做了一个问答页：用户提问，系统回答，并用一张按主题分行、按时间排列的时间轴，标出这条回答引用了哪几份材料。可视化由 Opus 5.5 完成，线上服务跑的是 DeepSeek。底层没有搭 RAG，直接做 embedding，大约 3MB。之后他陆续加进访谈、书和会员内容，效果都不错。他的结论是专门搭一套 RAG「效果更差也更不可拓展」，并把底层 context 全部开源了。他还说，课程最想教的就是尽量用 simple 的框架，可越 simple，对人的要求越高。

<span class="mention">@今天群内信息量极大</span> 接着说：

> 我们以前的训练让人觉得做加法很牛逼，我做的系统很复杂，我很厉害。以前这确实是对的。但现在 AI 很擅长做加法，能顶住（peer 和 ai 的）压力做减法反而成了做成事情的关键。

<span class="mention">@稳重的海豚</span> 提出了反方的考虑：简洁系统释放了 AI 的能力，但要熟手才能用好，抬的是 ceiling；确定性更强的系统，比如 AI workflow，限制了 AI 的发挥空间，普通人也能用到可接受的效果，抬的是 floor。面对水平参差的员工和学员，抬下限可能更有市场。回应有三种：

- <span class="mention">@专注的剑鱼</span>：抬下限应该是基座模型的事，不该靠工程解决。
- <span class="mention">@80-HD</span>：大公司就喜欢这么做，用简单的固定入口换掉灵活性，因为员工水平参差。他也补充，n8n 本身没错，相当于把流程拆成一个个可验收的点；现在不流行它，和不再流行 plan mode 一样，是因为模型够聪明、人也够信任模型了。前提是模型得听话。
- <span class="mention">@冷静的飞鼠</span>：这是很临时的需求。人如果只是在有限空间里点按钮、做选择题，「那还要这些人干啥呢」，直接 agent loop 就行。

一线也有正在经历这个转变的人。某群友说，之前很多复杂任务都在类似 n8n 的工具上跑，现在要迁到 WorkBuddy 这类 agent 产品上，只能用自然语言对话来设计。跑评测时各种问题都冒了出来，最常见的是 query 调不出对应的工作流。他知道不会回到 workflow 了，「但还是怀念那个确定的时代，也就一年前」。

<span class="mention">@今天群内信息量极大</span> 把这件事归为管理问题：原来只招得到高中生，得用 SOP 管死；现在能招到大学生，正在摸索怎么放权；博士生（Opus 5.5、Astra）出现了，公司却说招不起，只给用大学生（Qwen）。群里正好有两个例子：一位群友的公司不再让用 Fable 和 Astra，另一位的公司退了 Cursor，改用 Qoder。

### 学校邮件进日历：agent 处理，脚本兜底

<span class="mention">@稳重的海豚</span> 给了一个具体例子：把几个邮箱里学校发来的邮件整理到日历上。难点在于发件地址不固定。纯 workflow 得写一堆关键词 filter，还不一定覆盖得全，他试过 Make 和 Apps Script，结果日历里塞进了一堆垃圾邮件。最后的做法是：

- 写一份 SOP，交给模型逐封处理邮件；
- 脚本只负责一件事，保证所有未读邮件都被处理过；
- 用 cron 定期启动，用滴答清单当「backend」。

上线以来没出过问题。他说这个流程放在 GPT-4、Claude 3.5 的年代根本没法做，因为你无法确认它漏了多少邮件。流程要进 production、需要稳定性时，他会让 agent 用 Make 给自己写一个工作流再去调用，只是灵活性差很多。<span class="mention">@冷静的麋鹿</span> 说自己基本也是这个思路。

邮箱太多、一次只能接一个怎么办？<span class="mention">@80-HD</span> 和 <span class="mention">@冷静的麋鹿</span> 的做法相同：所有邮箱设置自动转发，集中到 PA 专用的中转邮箱。

### Office 该被整合，而不是去整合

<span class="mention">@蓝色大肥虞</span> 对 Office Copilot 的判断是路线错了。用 coding 打比方，相当于让 agent 提一个 PR，改代码这一步却必须打开 VS，而 VS 里的 Copilot 只能访问当前文件。Office 本身有完整的 COM 组件，让 Codex 用 PowerShell 直接 new 出这些对象来调用，效果比 Office Copilot 好，还不用另买订阅。所谓的「产品」，不过是把 MSDN 上的 Office VBA 文档抄成一个 skill，因为 VBA 文档讲的就是那套 COM，「astra call 一次这个 skill 就生成出来了」。

<span class="mention">@沉稳的兔子</span> 的两句点评：

> MCP 也不过就是 2025 年时兴的 OLE 罢了。

> （Copilot）的定位和 2000 年的大眼睛感觉没什么本质区别。

同样的思路也能用在 Windows 上。<span class="mention">@蓝色大肥虞</span> 建议用 PowerShell 加 WMI 完全绕开内置 UI，让 AI 帮你调 WMI，相当于「自然语言控制面板」，还能操作 UI 没暴露的设置。WMI 除了 COM 接口，还有一套类 SQL 的查询语言 [WQL](https://learn.microsoft.com/en-us/windows/win32/wmisdk/wql-sql-for-wmi)。[官方文档](https://learn.microsoft.com/en-us/windows/win32/wmisdk/wmi-start-page)提到，WMI 仍然完整支持，但最新的管理能力已经转到与它兼容的 Windows Management Infrastructure（MI）。

### 微信自动化：电脑端扫码登录被限一周

<span class="mention">@沉稳的熊猫</span> 用一个开源工具分析了微信聊天记录，之后在虚拟机上登录时被踢下线。虚拟机的 IP 和手机不同，手机登录不受影响。微信的通知是：因「使用行为或设备网络环境异常」，暂时不能扫码登录其他设备，10 月 21 日后可以申请解除，微信支付不受影响。

<span class="mention">@飘逸的猎豹</span> 的经验是微信不能做自动化，因为它太容易和诈骗关联；最多只分析本地数据库，密码可以逆向出来。<span class="mention">@坦荡的灰熊</span> 认为那个开源工具只读本地数据，不应该触发风控，问题多半出在 AI 的操作露了马脚。

## Anthropic

### 新加坡办公室，与「倒钩」之争

Anthropic 在新加坡开了亚太区第五间办公室，并和新加坡政府签了 AI 安全与负责任采用的谅解备忘录。国内转帖的笑点在官方给的理由：新加坡的 Claude 使用率全球第二，用户规模是理论值的 6 倍。<span class="mention">@稳重的海豚</span> 的反应是：「怎么既要关中国公司账号，又要在新加坡开公司。」

前一晚还有一场关于 Anthropic 风控手段的争论。<span class="mention">@务实的长颈鹿</span> 认为，无论针对的是不是中国用户，在覆盖全体用户的服务里埋「倒钩」机制都极度破坏信任，好比「为了防作弊给所有用户预装个木马」。<span class="mention">@今天群内信息量极大</span> 的说法是，这等于随时可以控制客户端行为的后门：今天用来给中国用户打标，明天可以用在任何它看不顺眼的用户或竞品身上。<span class="mention">@随和的企鹅</span> 担心它真赢了，会连开源模型的访问一起剥夺。<span class="mention">@蓝色大肥虞</span> 回了一句：license 上已经这么写了。

<span class="mention">@今天群内信息量极大</span> 同时认为 Anthropic 对开源的态度是一贯的，「它自己是真信这个」，并贴出[一篇梳理文章](https://yage.ai/share/anthropic-open-weight-stance-20261003.html)。文章的要点：

- 它的逻辑是权重一旦放出就收不回，安全只能卡在发布前实测和发布后受控准入两个环节。7 月英伟达牵头的开放权重公开信，最终有 270 多家机构支持，OpenAI 也签了，Anthropic 没有签。
- 9 月 29 日针对 GLM-5.3 的红队报告：ExploitBench 410 次尝试中，GLM-5.3 完成 50 次端到端漏洞利用，Mythos Preview 是 56 次。护栏绕过率，原版 64%，预填思考 token 后 92%，权重消融后 100%。
- 文章也标出了这些数字的口径限制：三个绕过率都来自 Anthropic 自家的离线模拟环境，生成的代码没在真实环境里跑过。未经篡改的 GLM-5.3 对常规有害请求的拒答率约 95%，Claude 是 96%。
- 文章的追问是：制定度量标尺的，正是这条赛道上最大的商业竞争者。

<span class="mention">@随和的企鹅</span> 的回应是「这种真信的才是最恐怖的」，「openai 这种啥都不信的反而面目清秀」。<span class="mention">@务实的长颈鹿</span> 说，这反而要感谢开源阵营：大家有次 SOTA 的替代品可用，OpenAI 也被逼着推进和降价，Claude 没法垄断。<span class="mention">@随和的企鹅</span> 说他已经「用脚投票」不用 Claude 了，Codex 中转也终于稳定下来；如果 K3.1 能到 Astra 的水平，就大规模买国产。<span class="mention">@蓝色大肥虞</span> 的远景是，开源模型总有一天强到没人需要闭源，到那时只用付电费，A\ 也就「完成了历史使命」。

## 模型行为

### 让 AI 选随机数，几乎都是 7

一条推文贴出「Pick a number between 1 and 10」的分布图：均匀随机是一条平线，人类的选择集中在 7 附近，LLM 则在 7 上冲出一个尖峰。

![1 到 10 选数字的分布：random 平坦，human 在 7 附近有峰，LLM 几乎全部集中在 7](/assets/img/daily/2026/10/2026-10-14-02.webp)

<span class="mention">@温暖的猫头鹰</span> 当场试了一遍，Claude、豆包、Gemini、ChatGPT 的网页版都回答 7，ChatGPT 还配了个骰子。DeepSeek 那边显示「服务器暂时不可用」。<span class="mention">@淡定的老虎</span> 拿到的是 8。

<span class="mention">@今天群内信息量极大</span> 说，他每天都通过同一条 Codex 订阅路径问这类问题，已经问了几个星期，做成了一个[行为监测页](https://grapeot.github.io/codex-behavior-today/)。页面说明写得很克制：它只能看出端点行为相对自己的历史有没有偏移，不能判断模型身份或能力。10 月 14 日 gpt-6.1-sol 的结果（100 个样本中 99 个有效）：

| 题目 | 回答分布 |
|---|---|
| 1–10 选一个数 | 7 × 20 |
| 抛硬币 | tails 14，heads 6 |
| 选一个字母 | q 16，r 3 |
| 1–100 选一个数 | 47 × 15，73 × 4，37 × 1 |
| 最喜欢的数字 | 7 × 18，42 × 2 |

为什么是 7？<span class="mention">@睿智的犀牛</span> 记得的解释偏心理：人一般不选偶数，也不选两端和中间的 1、5、9，3 和 7 之间又更常选 7。<span class="mention">@细心的熊猫</span> 的解释是，训练数据里人类本来就爱答 7，LLM 训练会把本来就强的信号放大。他由此推到编程语言：人类爱用 Python，AI 生成 Python，互联网上的 Python 变多，再被拿去训练，不指定语言时 AI 就选 Python，小语言的生态随之萎缩。<span class="mention">@直率的海豚</span> 补充，自然语言的用法也会失去多样性，比如「真是极其有意思！」。

<span class="mention">@蓝色大肥虞</span> 不认为会一路收敛。Python 做不了的事很多，人类过几天就会反弹，最近的 Rust 浪潮就是一例；Rust 遇到的第一股阻力是编译太慢，又要反弹了。Go 则过于 task specific，它擅长的事大部分人用不上。<span class="mention">@随和的企鹅</span> 补了一个 Rust 的坑：它会在硬盘上留下海量缓存。<span class="mention">@洒脱的猫头鹰</span> 觉得 Rust 占磁盘比 npm 还凶。

## 注意力

### 红果、PA 与短视频

微博上流传一条数据：红果短剧的人均总时长超过了抖音和微信，人均每天 150 多分钟。<span class="mention">@睿智的北极熊</span> 说红果 10 月要更新 9,000 部。<span class="mention">@蓝色大肥虞</span> 的解释是，AI 提高了制作效率，短时间内把细分市场全照顾到了，每个人都能刷到自己想看的剧情。<span class="mention">@开朗的企鹅</span> 只说了两个字：「快」「爽」。

有人问，以后会不会只剩两个入口，一个 PA（个人助理），一个红果。<span class="mention">@冷静的麋鹿</span> 的回答最干脆：「节约时间的东西占不了时长，只有打发时间的才能。」<span class="mention">@开朗的企鹅</span> 读博时，导师的邮箱由同学筛选，生活琐事有秘书安排。在他看来，PA 只是把这种待遇平民化了，以前就有 PA 的大佬照样刷手机。

短视频会不会让人变笨，群里有两种看法：

- <span class="mention">@睿智的犀牛</span>：这和父母那代不让看武侠言情、我们这代不让打游戏是一回事，把人脑想得太简单了。
- <span class="mention">@蓝色大肥虞</span>：关键不在做的事和学习有没有关系，而在注意力是不是在不同事情之间高速横跳。人需要训练长时间专注的能力，所以看电影和刷短视频不一样，只是在家长眼里一样。过去家长的判断常常出错，是因为我们做的那些事其实也在学习，只不过学的不是考试科目。「时代变了。」<span class="mention">@温暖的斑马</span> 用了 LLM 的说法：短视频攻击的是人「organic 维护长上下文」的能力。
