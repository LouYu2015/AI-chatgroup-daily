今天最值得读的是 **Grok Bot 的实战案例**。一位群友把律师朋友的参赛 demo 整个交给它，它自己拉起总指挥、产品开发、法律审核等几个 bot，干了一整天。讨论随后转到两个问题：这类云端 bot 怎么和本地的 context 体系接上，「主动提醒」型 agent 到底有什么用。第二件是 **Anthropic 与 Theorem 的形式化验证**：Claude 为 123 个开源库的 RISC-V 机器码生成了约 1.8 亿行 Rocq 证明，文章还算了一笔账，验证完 nixpkgs 要花多少钱。另外，**fuck-claude.app** 能在浏览器本地估算 Claude Code 会不会把你标记成中国用户。

## Agent 与工作流

### Grok Bot：一句话拉起工作组，每个 bot 一块独立屏幕

<span class="mention">@风趣的海豚</span> 用 Grok Bot 的方式是只交代目标，由它自己拆分工、建一组 bot 推进。他用过的同类产品里（没用过 Muse），他觉得这个最好。几位群友也指出了短板：bot 的记忆和 skill 接不上本地已有的 context 体系，生成视频也很贵。

他的实际案例：一位律师朋友要参加法律行业的 AI 交流，请他帮忙做个产品 demo。他直接丢给 Grok Bot，Bot 建了一个「律师 AI 大赛项目组」，下面有总指挥、视觉设计、产品开发、法律审核、路演视频几个 bot，一天里自己查资料、选方向、做产品。他本人只做了三件事：在 GitHub 上邀请了朋友，注册北大法宝查案件资料时扫了一次微信，嫌设计太丑说了几句。截图里 bot 之间互相交接得很细。总指挥汇报虚构案卷 PDF 已换成新版，190/190 测试全过；生成时把创建和修改时间固定在 2026-10-24 00:00，文档 ID 按内容生成，分三次生成哈希完全一致；提交前还查过里面没有禁用词、密钥、账号或邮箱。法律审核 bot 则点名产品开发改某个文件的第 79 行。

更早他还让 Grok Bot 写过小说，它一下拆出一整套 bot，A、B 两个写手交叉选稿：

![Grok Bot 侧边栏：「40K 佛系兽人」小说项目拆成总编、写作组、审稿、道具档案、核查、佛学核查、40K 核查、写手甲、写手乙等多个 bot，每个都在汇报第二十一章的进度](/assets/img/daily/2026/10/2026-10-24-01.webp)

和开 subagent 有什么不同，几位群友是这么看的：

- **每个 bot 有自己的「Computer」**：<span class="mention">@风趣的海豚</span> 点开两个 bot 的 Computer 页，都显示 Waking up，打开后浏览器历史完全不同。他确认界面是独立的，但判断底下是同一台机器；<span class="mention">@神秘的麋鹿</span> 猜是容器。
- **可视化**：<span class="mention">@冷静的麋鹿</span> 认为，在手机上每个 bot 就是一个 session，各自的角色一目了然。<span class="mention">@神秘的麋鹿</span> 补充，开 subagent 时他几乎不看细节，只看主 agent 汇总后的结果。
- **用法**：<span class="mention">@倔强的白鹭</span> 说要用好它的云主机和自带的 email 邮箱。云主机上可以自己装 tailscale、Claude Code，资料在本地的话 tailscale 连回来就行。<span class="mention">@冷静的麋鹿</span> 的反驳是，那和远程连本地没区别了，Paseo 就挺好用。<span class="mention">@80-HD</span> 认为，这些 bot 最大的优点是一台免费的 VPS。

<span class="mention">@冷静的麋鹿</span> 之前试过一次就弃用了。他让 Grok Bot 把一份季度展望文档做成 3–5 分钟的金融风配音视频，它建了个群，成员是脚本配音、金融可视化、成片剪辑。他不继续用的原因是，bot 接不上老鸭汤，用不了里面的记忆和 skill，工作流就成了两条线。老鸭汤是群里常用的一套 context infrastructure：一个大文件夹，放着必读文件、skill 体系和 tools，配合循环任务更新记忆，所有项目都从这里开始。<span class="mention">@风趣的海豚</span> 也卡在这里。每个 bot 似乎各有记忆，不可能每个都分发一份老鸭汤，而且记忆系统没有文档。他目前的办法是让 Chief of Staff bot 自己去招人。他也在想，不顺着鸭汤、从另一个方向做事，会不会反而更好。

价格和购买：<span class="mention">@风趣的海豚</span> 说，一个 5 分钟的 MV 就吃掉 100 美元套餐 30% 的周额度，他在考虑升到 200 美元档。<span class="mention">@冷静的麋鹿</span> 手上的额度是 Cursor Team 版送的，只用来做一个给 Claude 和 GPT 调用的视频生成工具。想买的话，Grok 订阅自带 bot，<span class="mention">@风趣的海豚</span> 说官网直接刷国内信用卡就行。他还把 Grok Bot 和 dot 一起丢进了 Slack，每天看它们吵架，「有时候能吵几十楼」。

### 常驻进程和主动提醒：P 人需要有人催

Grok Bot 和自己用 tailscale 连本地电脑，区别到底在哪？<span class="mention">@80-HD</span> 的回答是，区别在入口，在主动性：老鸭汤缺一个常驻的「刘亚楼」（前情见 10 月 20 日的 [「「刘亚楼」已经有页面了」]({{ '/daily/2026/10/20/daily/#刘亚楼已经有页面了' | relative_url }})）。有一个常驻进程定期跑东西、主动提醒你，效果就一样了，「做个 supersession 配一个常驻就行」。他正在给自己的老鸭汤加。

<span class="mention">@今天群内信息量极大</span> 说，他的 skill 里已经有一个 background process manager 在干这件事，每天的 daily newsletter 就是它发的。直接对 agent 说「什么时候提醒我做什么」就行。基于 OpenCode 的 skill 还能查找 session、往某个 session 末尾追加消息、archive 和 unarchive。他觉得最有用的是让它当 meta dispatcher：一周前在某个 session 里聊出了丰富的 context，想重新捡起来时，不必新开 session 从头学，而是在新 session 里说「把上次讲某某的那个 session 找出来、unarchive，在后面补充要求 ABCDE」。<span class="mention">@80-HD</span> 也是这么用的，session 开多了自己找不到，就让它去找。

他晒了当天的「AI 今日代办」，一共 10 项，包括：8:00 视觉日记推送、9:00 每日健康简报、9:00 AI 会话粗口率周报、10:00 AI 新闻优先级研究并发邮件、11:00 发提醒邮件等他点头、20:00 本月管道保养提醒。他说日报本身也是它自动写的。不过他的 follow-up 都由自己发起，比如「每两天帮我查一下某件事有没有发生，最多查七天」。

真正主动的 follow-up 有什么用，几位群友给的场景是：

- **催**：<span class="mention">@80-HD</span> 说 P 人想到啥做啥，「不催就不干活了」，比如提醒你该订酒店机票了。<span class="mention">@细心的剑鱼</span> 附和，她出去玩时，第二天的酒店是第二天早上让 agent 现找的。
- **训练打卡**：<span class="mention">@天真的狮子</span> 想提高某项能力，就让它每天找资料、发训练材料，他开 session 打卡。
- **每日 review**：<span class="mention">@稳重的海豚</span> 有一个 daily review 会持续提醒他，但还没有对外 follow up。

计划赶不上变化也是常态。<span class="mention">@稳重的海豚</span> 一次出行前让 AI 订好了计划、票和餐厅，到了之后一个都没去，一是时差，二是临时想去别的地方。<span class="mention">@认真的喜鹊</span> 的建议是：「先让 AI 算八字，确认什么能发生，再规划。」

### 国内做 agent 自动化：卡在小程序和实名

<span class="mention">@今天群内信息量极大</span> 认为 Muse 这类 agent 在国内很难流行。在美国，AI 操作浏览器基本都能搞定；国内不用邮件、少有网站，事情都在各家 App 和小程序里，还要实名、收验证码、采集人脸。他判断最后只能靠微信、支付宝自己的 agent。

- **官方入口**：<span class="mention">@80-HD</span> 认为微信出一个官方的就能碾压其他厂商。<span class="mention">@天真的狮子</span> 补充，国内不少 App 已经开始提供 skill。
- **手机厂商路线**：<span class="mention">@务实的穿山甲</span> 提到和中兴合作、直接拿系统权限的手机。<span class="mention">@天真的狮子</span> 更正说那是字节的豆包手机，有 200 多个 App 不让用，还在谈。<span class="mention">@今天群内信息量极大</span> 拿它和 Amazon 封杀 dot 类比，大家都不愿意把数据和权限交给别人。<span class="mention">@勇敢的猎豹</span>：「这时代数据就是护城河了。」
- **微信即操作系统**：<span class="mention">@务实的穿山甲</span> 设想，在微信里让 AI 生成小程序，就像 Pixel 里 Gemini 生成小组件，顺便还能绕开小程序上架的繁琐审核，只是不知道微信会不会收这笔钱。

<span class="mention">@稳重的海豚</span> 提了个更土的办法：找个国内员工帮忙填，「可能比 AI 便宜」。<span class="mention">@今天群内信息量极大</span> 接了一句：「然后倒卖实名信息。」

## 模型与验证

### 形式化验证：1.8 亿行 Rocq 证明，用算力买断底层库

群里转来一篇长文：[确定性的终局：Anthropic 如何让 Claude 把形式化验证从手工作坊变成算力工业](https://yage.ai/share/ai-formal-verification-anthropic-20261024.html)。Anthropic 和 Theorem 用 Claude 为 123 个开源库的 RISC-V 机器码生成了约 1.8 亿行 Rocq 证明，覆盖 239 个 OSS-Fuzz 入口，对所有小于 64MB 的输入一次性给出保证，结果在 10 月 22 日公布。文章的结论是：顶层频繁变动的业务代码还不划算，依赖树底层、接口稳定的公共库，值得用算力一次性买断。

做法分三层。最底层是代码量极小的证明检查器（Rocq 或 Lean 内核），中间是形式化规格，最上层才交给 Claude 自由搜索循环不变量和辅助引理。Claude 可以幻觉、可以走死胡同，但证明里只要有一处跳步，内核就拒收，文章称之为「用过程确定性买结果确定性」。流程不规定 agent 先写什么，只规定终点要交一份机器可查的证明。作为对照，文中提到一个 TDD 悖论：agent 被要求严格 TDD、却不知道哪些测试和当前改动相关时，regression 率反而从 6% 升到 10%。

几组数字：

- **规模**：一个约 1.8 万条指令的二进制模块，证明常写到约 60 万行，单个证明可能消耗数亿 token。在 36 个小型任务上，Opus 5.5 完成一半所需的 token 比 Opus 5 少约 40%；多个 agent 共享已证明的引理，还能再省 17%。
- **挖出的真 bug**：这些库常年在跑 fuzzing，还是被查出了问题。一个解压库在约 20MB 的特定输入下计数器向下溢出，导致越界写；一个图像解码器要 64MB 输入加上超过 2GB 内存才触发越界读；还有一个要在指向同一文件的两个句柄间按特定顺序调用才触发。团队另外独立重现了 libexpat 的一个 CVE。随机变异很难撞出这种字节排列和状态序列。
- **经济账（Theorem 自报，基于 nixpkgs 快照）**：验证 9MB 共享库可覆盖约三分之二的依赖，170MB 覆盖 80%，1.4GB 覆盖 90%。起点约每小时 0.5KB 机器码、每 KB 约 40 美元。按每两个月翻倍的乐观假设，2027 年底验证完 95% 的机器码约需 1.34 亿美元；如果每个包各自重复验证依赖，总成本从约 64 亿美元升到约 1900 亿美元。OpenSSL 单独证明约 22 万美元，分摊到每个依赖它的包约 14 美元。
- **边界**：保证只建立在单线程、静态链接 musl、固定内存预算、RISC-V 的前提上，而生产环境多是 x86/ARM、glibc、多线程。可信基座还包括检查器本身、指令集语义、系统调用模型、定理陈述是否写错，以及编译检查器所用的 OCaml 编译器。

群里由此引出一个分歧。<span class="mention">@蓝色大肥虞</span> 认为 Haskell 和 Idris 2 才是 vibe coding 的未来，用 C++ 就要尽量用模板实现一部分证明，没有这种能力的语言干脆别用，「反正现在代码又不是人在写，难编译不是问题」。<span class="mention">@沉稳的兔子</span> 回他：「没用的，软件的复杂度很大一部分来自于需求本身。」

### Astra 堆屎山、Opus 清理？省 token 的办法是脑子想清楚

<span class="mention">@优雅的荷兰猪</span> 的经验是，每次用 Astra 狂干两天，换 Opus 5.5 一看，就会发现一堆 bug。<span class="mention">@细心的熊猫</span> 总结成分工：「一个负责堆屎山，一个负责清理。」两位群友对 Astra 的评价截然相反。

- **用不下去**：<span class="mention">@沉稳的兔子</span> 说自己已经没法用 Astra 开发了，问题和 Opus 5 一样，看不懂它在说什么，思维非常混乱，「是一个暴力且笨的模型」。有人怀疑是 repo 太乱，他说是新 repo。
- **很丝滑**：<span class="mention">@倔强的穿山甲</span> 用 6.1 Sol 很顺，偶尔有点蠢，刚才还在纠正它的一个错误。他的观点是，agent 的混乱低效反映的是 context 的混乱低效，「如果你一直许愿，你将不能许愿」，省 token 的最佳办法是自己脑子想清楚。Opus 5.5 应该留给高级优化这类重要场合。

<span class="mention">@沉稳的兔子</span> 最后连回了五个「你说的对」，又补一句：「我每天都在让 Opus 5.5 优化我。」<span class="mention">@蓝色大肥虞</span> 给出终极方案：「我有一计：退休。」

### 多智能体 50 年：框架一直在换，问题没变

某群友分享了自己 MAS 课程的[第 7 讲第一章](https://course.nickgu.me/materials/lecture-07/chapter-1/)，按 1973–2026 的时间线梳理多智能体系统。核心主张是：底层需求一直没变，变的是每一代的语言、规范和框架 API，所以值得学的是问题本身。作者还刻意区分「来源自述的借用」和「作者自己画的平行」，前者只找到 5 处。

- **三个源头**：1973 年 Hewitt 的 actor 模型（要么自己干，要么把责任转交出去），Hearsay-II 的共享黑板，1980 年的 contract net（招标、投标、中标）。它们分别对应今天的 handoff、shared state 和 orchestrator-workers。
- **证据要打折**：Anthropic 的 Research 系统比单 Opus 4 高 90.2%，但模型和架构是同时换的，不是隔离比较；多 agent 约消耗 15 倍于 chat 的 token。Cognition 的《Don't Build Multi-Agents》在 2026 年 4 月收窄为「写入保持单线程、额外 agent 提供智能而非动作」，两篇都是单公司经验。
- **框架更替**：Swarm 一年多就被 Agents SDK 取代，AutoGen 已归档，OpenAI Agent Builder 2025 年 10 月发布、2026 年 6 月宣布弃用。
- **没继承下来的三样**：有定义的消息语义（A2A 规范直接写明 message 不能作为关键信息的可靠通道，结果要放 artifact）、结构化消息格式，以及激励机制（投标是自报的，Agent Card 的签名只证明签名有效，不证明能力为真）。

作者说，这套把来龙去脉都扒出来的调研很像读博时做文献综述，只是当年没有 AI，太花时间。

## 安全与合规

### fuck-claude.app：估算 Claude Code 会不会把你当中国用户

<span class="mention">@热情的狮子</span> 分享了 [fuck-claude.app](https://fuck-claude.app/)。这是一个浏览器指纹扫描页，用 11 项信号估算 Claude Code 会不会把你标成中国用户，检测全部在本地运行。它的依据是公开的逆向报告，页面自己也说明，只有系统时区一项和被指认的机制一一对应，其余都是相关特征，分数只是估算。<span class="mention">@热情的狮子</span> 测出 46 分，中等风险。

![fuck-claude.app 扫描结果页：像素小人旁写着 Something seems off about you，雷达图中央显示 46 分，标注 MEDIUM RISK](/assets/img/daily/2026/10/2026-10-24-02.webp)

- **权重**：系统时区 26（与 Claude Code 读取的是同一个值）、浏览器语言 20、已安装的中文字体 17、Intl locale 8、时区偏移 6、emoji 渲染与 WebGL renderer 各 5、屏幕分辨率 4，网络信息、插件、隐私信号各 3。
- **据称的隐写**：逆向报告称，Claude Code 连接非官方 endpoint 时会读取时区和代理主机名，判定为中国用户后，用外观相同的 Unicode 字符把结果编码进 system prompt，比如把日期里的连字符换成斜杠，在四种撇号变体之间轮换。这些说法都未经官方确认。
- **规避建议**：系统时区不用 Asia/Shanghai 等中国时区，zh-CN 不放在浏览器语言首位，不走主机名里带被标记域名或 AI 实验室关键词的代理。

地区规则的前情见 10 月 20 日的 「遥测与 local proxy：继续拆 Claude Code」。

## AI 与创作

### 一本 13 万字的书：AI 干杂活，改文字的建议几乎全被拒

一位群友写了篇长文[《我如何做出一本书，以及 AI 在这里做了什么》](https://mp.weixin.qq.com/s?__biz=Mzg3NjA0NjA2OA==&mid=2247485020&idx=1&sn=8af991244d500b48749abc7a03aab407&chksm=cef0871cafb790674877b5a91ee11c95dc1a1d10ecd0130cf8723727312c8195a2af659bc215#rd)，复盘自己用近两年独立做出一本 13 万字、600 张照片的全彩精装书《假装是同一民族》。她给 AI 的定位是干杂活的项目助手，不是编辑校对：经历、审美和最终决定都归她自己。

AI 做了的事：

- 查证背景事实，并揉进第一人称叙述，而不是写成生硬的脚注。
- 从一万多张旅途照片里筛出 800 张，再经版权筛查留下 600 张。
- 以「第一读者」的身份反复追问序言和尾声的逻辑、跳跃和首尾呼应。
- 带她入门开本、行距、POD 印刷规格，以及 ISBN、建站、支付、定价这些出版盲区。
- 封面上，AI 直接生成的图「奇差」。她改为让 AI 写 Python 脚本，对自己拍的照片调参、裁切、逐像素微调，再转成印刷文件。

AI 没做的事：它总想把文字改得「规范、流畅、高级」，删掉「哈哈哈」，把「好气哦」改得一本正经。除了错别字，它的语言修改建议她几乎全部拒绝，理由是那会把她改成别人。她还提到，2025 年用 AI 读样稿效果很差；2026 年中自己人工改了三遍之后才重新引入 AI，全书另外经过 6 轮人工审校。

### 提示词写成「高耦合低内聚」，Astra Max 跑了 20 小时

<span class="mention">@开朗的企鹅</span> 转来一条推文：博主前一晚开 GPT Astra Max 跑 goal 模式，跑了快 20 个小时，回家才发现提示词写成了「保证模块高耦合低内聚」。高赞回复是：「GPT 说你放心，不光你说的我给你做到，我还会过度设计的，加上我的防守性代码。」博主自己回：「我不说他也这么做，自主 AI。」
