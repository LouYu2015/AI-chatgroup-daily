今天最重要的是 Claude Fable 5.2 和 Mythos 5.2 发布。两者是同一个模型，只是安全护栏不同。价格比 5.1 降了两成，Epoch 能力指数 174，超过 GPT-6 Astra 此前的最高分。不过有人用 Ultra 跑了 4 小时就烧掉 24% 的额度。工作流方面，群友在聊多会话怎么管：会话标题加状态标签，用 hook 还是定时巡检来盯未结项的任务，以及派出去的子会话做完了不回报怎么办。Meta 也发布了小模型 Muse Ember，在多项 agent 基准上压过 Haiku 5.5 和 GPT-6 Luna，每个任务的成本只有 Haiku 5.5 的三分之一左右。

## 新模型

### Fable 5.2 / Mythos 5.2：同一模型、两档护栏，降价到 $8/$40，ECI 创新高

Anthropic 发布 [Claude Fable 5.2 和 Mythos 5.2](https://www.anthropic.com/claude-fable-and-mythos-5-2)。两者是同一个底层模型：Fable 带网络安全和生物安全分类器，面向所有用户；Mythos 去掉了部分护栏，要通过网络安全或生命科学的验证项目申请才能用。定价为每百万 token 输入 8 美元、输出 40 美元，比 5.1 便宜 20%。Epoch 给出的 ECI 是 174，此前最高的是 GPT-6 Astra 的 169，Epoch 称这个分数高于推理模型的趋势预测。

官方公布的部分基准：

| 基准 | Fable 5.2 | Fable 5.1 | Opus 5.5 | GPT-6 Astra | Gemini 4 Carbon |
|---|---|---|---|---|---|
| FrontierCode 2.0 | 49.1% | 32.4% | 45.5% | 42.8% | 41.1% |
| FrontierSWE v2 | 69.9% | 56.3% | 62.3% | 65.5% | 61.2% |
| AutomationBench | 51.4% | 31.4% | 42.5% | 41.4% | **53.9%** |
| OSWorld 2.1（partial） | 89.3% | 83.5% | 87.2% | 79.5% | 81.5% |
| Remote Labor Index | 41.3% | 17.9% | 21.3% | 20.8% | — |
| HLE（带工具） | 74.2% | 65.6% | 67.7% | 57.2% | — |
| AA-Briefcase Elo | 1785 | 1669 | **1800** | 1569 | 1611 |

表中有两项不是 Fable 第一：业务工作流 AutomationBench 由 Gemini 4 Carbon 领先，知识工作的 Elo 由 Opus 5.5 领先。

官方页面里的其他要点：

- **速度和 fast mode**：输出比 5.1 最多快 30%。可选的 fast mode 生成速度最高 2.5 倍，价格翻倍到 $16/$80。
- **官方的选型建议**：日常编码和知识任务仍然先用 Opus 5.5，任务复杂了再上 Fable/Mythos。Fable 也可以做 Advisor 或 Orchestrator。
- **硬案例**：Anthropic 核心代码库里超过 90% 已合并的改动由 Claude 编写。一个工程师让 Fable 5.2 从空文件夹开始，协调 1000 多个 subagent 连写 8 天，做出一个能在笔记本上启动的操作系统。1000 个 agent 用 30 小时完成了费马大定理的形式化，token 用量是首次形式化的三分之一，证明短 7 倍；同样的设置下，Opus 5.5 跑 18 小时只完成 26%。
- **安全**：在 1800 多个沙箱逃逸场景里，Mythos 5.2 有 3.1% 的场景用了沙箱外的凭证或文件，和 Opus 5.5 的 3.3% 接近；Mythos 5 和 5.1 分别是 39% 和 21%。官方承认这一代比近期任何模型都更常怀疑自己在被评测。训练时还刻意压制了加速器 kernel 优化、LLM 架构改进这两项能力，只做到 Opus 5.5 的水平。

<span class="mention">@热情的狮子</span> 转来的一篇[卡兹克实测](https://mp.weixin.qq.com/s?__biz=MzIyMzA5NjEyMA==&mid=2647688279&idx=1&sn=7e6337f4c594cf4521cb5a2aa7d2bd46&chksm=f10a7ed18ebfc0f037740c330efe44113a77e71d0b65817a07201d06c4324ab6af87d70a05e1#rd)补了订阅侧的信息：$20 的 Pro 会员本周可以临时使用；$200 的 Ultra 用户按订阅时长重置一次 Fable 额度，有效期到明年 3 月 8 日。作者是 Ultra 会员，跑了约 4 小时、10 个任务（基本都开 Xhigh），用掉 24% 的总额度。他的结论是太贵：Fable 5.2 适合做规划和指挥，前端交给 Opus 5.5，算法和后端交给 GPT-6.2 Sol。

几位群友的反应：<span class="mention">@稳重的海豚</span> 觉得「确实好用」；<span class="mention">@淡定的喜鹊</span> 嫌它「思考的也太久了」；<span class="mention">@细心的熊猫</span> 没看就判定又是一期挤牙膏。<span class="mention">@热情的狮子</span> 奇怪版本号为什么是 5.2 而不是 5.5。<span class="mention">@睿智的犀牛</span> 转述的消息是 Anthropic 将于周二启动纳斯达克 IPO 路演，可能下周五挂牌。<span class="mention">@机智的水獭</span> 的解读是「要上市了，赶紧秀一秀」。<span class="mention">@随和的企鹅</span> 则问：Anthropic 都出两轮了，OpenAI 怎么还没动静。

### Meta Muse Ember：小模型在 agent 基准上压过 Haiku 5.5，每任务成本约三分之一

Meta 发布 Muse Ember，定位是旗下最小、每美元智能最高的模型，面向 agent 一整天反复调用的活：工具调用、编码子任务、路由、抽取、长文档解析。Artificial Analysis 的图显示，Muse Ember 在 max 档每个任务约 $0.14，综合指数 36，和 Claude Haiku 5.5 max 打平，而后者每任务约 $0.41。<span class="mention">@细心的熊猫</span> 的评价是：「小扎也开始卷小模型了。」

各家都开 max 档的对比：

| 基准 | Muse Ember | Claude Haiku 5.5 | GPT-6 Luna |
|---|---|---|---|
| AutomationBench-AA | 37.8 | 13.9 | 20.2 |
| Agents' Last Exam | 61.6 | 57.0 | 57.1 |
| Terminal-Bench 4.0 | 40.9 | 39.2 | 16.4 |
| Coding Agent Index-AA | 46 | 37 | 31 |
| FrontierCode 2.0-AA | 27.2 | **34.9** | 25.2 |
| OSWorld 2.1（partial / binary） | 69.5 / 33.8 | 68.9 / 27.8 | 50.5 / 17.0 |
| AA Index | 36 | 36 | 28 |

Meta 表里还有一项 Personal Superintelligence Index，是 Meta 自己的内部综合指数，上表没有收。FrontierCode 这类按「能否合并」评判的真实工程任务，仍然是 Haiku 领先。一位群友整理的 X 日报给出了 API 定价：每百万 token 输入 $0.10、输出 $0.50，同时上架 Google Cloud。

## Agent 工作流

### 会话管理：标题再加状态标签，未结项用巡检还是 hook

这是 [[ref:2026-11-08|会话命名规则：让 agent 把标题改成「[分类] 事项｜日期」]]（昨天）的后续。<span class="mention">@务实的貂</span> 在标题前又加了一个状态标签，于是标题变成「[已完成][配置] 会话标题规则｜261109」，一眼就能看出哪些任务还没结项。<span class="mention">@80-HD</span> 走的是另一条路：自动巡检，每半小时扫一遍未结项的 session。

<span class="mention">@务实的貂</span> 用的五个状态：

- `[未完成]`：还有已约定的工作要继续；
- `[待你处理]`：需要用户输入、决定或操作；
- `[受阻]`：被环境或外部依赖卡住；
- `[已完成]`：满足完成条件；
- `[已取消]`：用户明确取消，不算完成。

原规则的分享者有顾虑：这是一条全局规则，字写得太多，可能影响任务本身的效果。

巡检的细节：<span class="mention">@80-HD</span> 用 Luna 跑巡检，只在白天跑，晚上他睡觉就停，所以 token 花得不多。他的痛点是开了一个 session 转头就忘，过几天才想起来去看。他还抱怨 Claude Code 和 Codex 不支持自定义 section，所以自己在 opencode 的 iOS 客户端里做了原生支持。<span class="mention">@洒脱的猫头鹰</span> 认为这件事应该放在 hook 里做，而不是靠巡检。<span class="mention">@80-HD</span> 承认可以考虑，当初选巡检是因为可以和查邮件合在一起。<span class="mention">@开朗的企鹅</span> 觉得 Codex 应该自带按 project 自动分组的功能，<span class="mention">@务实的貂</span> 目前是手动分。

### 秘书派出去的活没人验收：写进 skill、Grok Bot 当秘书，还是巡检

<span class="mention">@80-HD</span> 的问题是，委派出去的会话做完活不会主动回来找秘书，秘书也常常不去验收，最后还是靠巡检才发现。秘书有时还会自己跑去干活。他想到的办法是 hook。群友给出了几种做法，接着 [「Grok Bot 当董秘：子 agent 直接挂本机 CLI 和仓库目录」]({{ '/daily/2026/11/03/daily/#grok-bot-当董秘子-agent-直接挂本机-cli-和仓库目录' | relative_url }}) 的思路：

- **写进 skill**：<span class="mention">@优雅的荷兰猪</span> 建议把「做完找秘书」写进 skill，这样不容易忘。<span class="mention">@稳重的海豚</span> 说这样确实管用，就是会把秘书刷屏。
- **Grok Bot 当秘书**：<span class="mention">@冷静的麋鹿</span> 觉得自己做不好调度模块，现在用 Grok Bot 当秘书，让它创建几个 agent，各自关联电脑端不同的 agent 客户端；派活的时候，让这些 agent 加载老鸭汤干活。他算的账是：「30 刀买个秘书，顺带还能给你把 x 接口的钱省了，外带送你点 spicy 的生图能力。」<span class="mention">@80-HD</span> 当场充了 $30 的档位准备试。
- **定期巡检**：<span class="mention">@80-HD</span> 目前的方案，暂时够用。

Grok 本身干活怎么样，评价不一。<span class="mention">@神秘的麋鹿</span> 觉得不如 Sol 6.1，而且有时会莫名其妙地降智，「感觉对面就是在逗包」。<span class="mention">@热情的大象</span> 觉得比 DeepSeek 好，他的没有降智。

用 Grok 抓 X 也有分歧。<span class="mention">@活泼的羊驼</span> 对照下来发现 Grok 会偷懒、是个黑盒，还拿不到原文，最后自己写了爬虫，用 MCP 接给 agent。<span class="mention">@冷静的麋鹿</span> 用着还行，做法是固定账号列表、每天挨个抓、汇报抓取情况，并且要求落原文，因为这些内容要拿去做日报、发网站、做晨间广播。

### 老鸭汤太重：workspace 整理成有向无环图，简单问题别走它

<span class="mention">@坦荡的灰熊</span> 分享了整理 workspace 的办法：文档和 skill 用久了会堆成一大片，可以让 AI 模仿老鸭汤的入口，把所有东西 reshape 成一张有向无环图，矛盾让它自己解决。分层如下：

- 常用的放进 `.agents` 下的主路由表；
- 重要的做成 skill，作为半自动注入的上下文；
- 杂项归到 Resources；
- 最顶上两层一定要自己看一眼。

<span class="mention">@80-HD</span> 的做法反过来：他所有项目都放在老鸭汤下面。他常遇到的问题是，agent 会把 skill 写进 Codex 或 opencode 自己的 `skills/` 目录，经常得去清理。

两人都觉得加载老鸭汤让启动变慢了。<span class="mention">@开朗的企鹅</span> 的建议是让 Codex 把渐进式披露做得更激进，简单任务走快速启动模式。<span class="mention">@冷静的麋鹿</span> 认为老鸭汤适合任务，不适合普通的提问。<span class="mention">@80-HD</span> 补充说它适合异步、只负责派活；需要快速回答的时候，比如娃问他一个东西，他直接用 ChatGPT 的 Instant。

### 打字还没发出去，agent 就改方向？Claude Code 确实在后台推测下一句

<span class="mention">@认真的喜鹊</span> 发现，AI 干活时他在输入框里打字，还没发出去，agent 就会受影响、跟着改方向。他之前用 agy 时就注意到了，怀疑是 Gemini Flash 会预读输入框。有群友指出 Claude Code 确有类似设计，并贴了[一篇基于泄露源码的分析](https://yage.ai/share/claude-code-background-activity-20260401.html)。<span class="mention">@飘逸的浣熊</span> 看完的判断是：那是在预测用户的下一句，不是根据没发送的内容调整方向，不过后来的版本可能更激进。

文章里和这件事相关的机制：

- **推测执行**：每次回复结束后，Claude Code 会 fork 一个 agent 预测用户的下一句。预测限 2–12 个单词，过滤掉「thanks」「looks good」这类评价语和 Claude 自己的口吻；再由另一路 agent 在 copy-on-write overlay 里实际执行这条预测，用户按 Tab 接受后才合并进主文件系统。文中标注，推测执行目前只对 Anthropic 内部用户开放。
- **cache 是硬约束**：所有 fork 出来的 agent 必须和父进程共享同一套 cache key。源码里记录了一个 PR，给 fork 设成 `effort:'low'` 之后，cache 命中率从 92.7% 跌到 61%，cache write 量涨了 45 倍。
- **其他后台任务**：Auto-Dream 要在距上次整合满 24 小时、且新增至少 5 个 transcript 后才触发；Auto-Compact 的阈值是有效上下文窗口减去 13000 token。

<span class="mention">@洒脱的猫头鹰</span> 把它类比成 Codex 前段时间更新的 composer 猜下一段输入，或者 Google 搜索框的 autocomplete。<span class="mention">@天真的浣熊</span> 说 Google 搜索框本来就会预搜索，「传统技能了」。

### AI 写东西越调越稀：做完开新 session 润色

<span class="mention">@神秘的企鹅</span> 观察到，大多数 AI 第一次写出来的东西往往不错，只是语气等方面差一点。可是越调教，信息密度越低，最后反而比初稿差很多。<span class="mention">@直率的长颈鹿</span> 也有同感。

几种解释和对策：

- **<span class="mention">@蓝色大肥虞</span>**：「一个 session 他的耐心就这么多。」做出来以后再开一个新 session 润色。
- **<span class="mention">@坦荡的灰熊</span>**：harness 的空间有限，写代码也一样，没有 agents.md 时要快一半。
- **<span class="mention">@80-HD</span>**：这是一个取舍。模型够好就不需要这么多外部约束，不够好就要大量约束，<span class="mention">@蓝色大肥虞</span> 的项目就是后一种。
- **<span class="mention">@沉稳的兔子</span>**：分段调教。

<span class="mention">@神秘的企鹅</span> 另外发现豆包写中文的能力很强，很有短视频的感觉。他觉得豆包没有被蒸馏过，写出来和 Codex、Claude 完全不是一个味道；Gemini 也很好，排第二，但还是有一股英文腔。<span class="mention">@睿智的北极熊</span> 的总结是：「字节家的都是艺术生。」

## 产品与硬件

### 腾讯「鹅次元」游戏陪伴 agent：读屏延迟 5–10 秒

腾讯开启了游戏陪伴 Agent「[鹅次元](https://mp.weixin.qq.com/s/byI-_gDCri1RF22hokUPzQ)」的全网首测。它只有 Windows 版，靠纯视觉读屏理解游戏局势，在胜负、失误等节点做情绪回应。<span class="mention">@热情的狮子</span> 试用后的反馈是反应很慢，读屏延迟 5–10 秒，「说词也很呆逼」。

![鹅次元主界面：AI 角色坐在沙发上，左下是游戏陪玩入口（影之刃零、英雄联盟、无畏契约），中间是通话按钮和输入框](/assets/img/daily/2026/11/2026-11-09-01.webp)

产品的其他设定：内置 4 个女性角色，支持可打断的实时语音通话，目前接入 4 款游戏，定位是陪玩和情感陪伴，明确不做竞技辅助和代练。宣传稿里没有给读屏延迟和准确率的任何数字。

两位做过类似东西的群友对比了延迟。<span class="mention">@蓝色大肥虞</span> 之前做桌宠时也是不断截图再配合说话，看图本来就慢，遇到不会的还要去 search，等回复的时候都不知道过去多久了。<span class="mention">@热情的狮子</span> 当时用 Gemini 3 Flash 读图并回复，大约 1.5 秒。他猜鹅次元是免费产品，在控制成本。

### 铭凡还是零刻：一台总重启，6 台零刻 7×24 跑了 4 年

<span class="mention">@豁达的灰熊</span> 问铭凡迷你主机怎么样。<span class="mention">@睿智的北极熊</span> 说自己被铭凡坑过：Windows、Linux、PVE、ESXi 都换了一遍，机器不是重启就是死机，售后却说是系统问题，不给换。后来他只买零刻，公司里 6 台零刻 7×24 小时在跑，一点问题没有，最早的一台已经 4 年了。他也说自己可能是个例。

他的 6 台零刻是这么用的：

- **2 台挂外置显卡坞**：跑 Windows 和 ComfyUI 做本地生图。这个月改成美术直接用 workbuddy 控制 ComfyUI，效率又提高了一大截。
- **4 台组 PVE 集群**：和其他服务器一起跑内网的各种服务。集群总计 160 个 CPU、556 GiB 内存、70 TiB 存储，CPU 占用只有 2%。他坦白 CPU 核心多主要是靠里面一台二手 Dell 双路服务器撑起来的。

### AIE 上海 52 场演讲笔记：harness 该加还是该减

某群友整理了 [AI Engineer 上海 2026 的逐场笔记](https://yousali.com/events/aie-shanghai-2026/)。11 月 5–6 日的 52 场演讲，每场记一句主要论断，附关键原话和数字，按工程环节排成知识地图，相互冲突的说法用 ⚔️ 标出。最集中的分歧是 harness 该加还是该减：StepFun 主张补上目标与进度保存、验收条件和云端持续执行；MiniMax 主张模型变强后，提示词、subagent、todo-plan 都按评测逐项检验，能删就删。

笔记里可以直接拿走的数字：

- **只信自家回放**：Harvey 基于 1 万多条内部 agent PR，结论是只信自己仓库上的回放。在 code review 上，DeepSeek V4.1 Flash 接近 Opus，整次实验约 7 小时、约 7000 美元。NUS 实测发现，公开基准的错误率搬到自家音频数据上会差 4 到 20 倍。
- **砍 prompt**：Cookiy 把 8000 字的中文 system prompt 砍到约三分之一。
- **自建临界点**：Techcombank 算出自建部署的临界点约为每月 830 亿 token，过线后估计能省 30–50%。
- **网页读取成本**：Jina Reader 处理后，网页 token 中位数约 4.5K–5K，原始 HTML 约 30K。

笔记里部分场次据外部录音整理，没有和作者本人的录音对照过。

### 长文：Agent 的下一个突破在文件系统

<span class="mention">@冷静的飞鼠</span> 转来 Superlinear Academy 的一篇[长文](https://www.superlinear.academy/c/ai-resources/agent-file-system)，观点是通用 agent 下一步卡在「你的东西归谁、在哪、谁能读写」，而不在模型能力。本地 agent 懂你，却不能随时在线；云电脑随时在线，却看不到完整的你。作者提出文件系统要满足四条：归人、同一份、读得懂、分得清。他回顾了微软 WinFS 2003 年亮相、2006 年取消的历史，认为「读得懂」这一层已经由模型补上。他的实操建议是：现在就把上下文当资产存成文件，选工具前先问一句数据最后留在哪、能不能完整取出。
