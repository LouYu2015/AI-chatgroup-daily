### Cursor 揭示 Benchmark 检索作弊

<span class="mention">@专注的剑鱼</span> 分享了 Cursor 新发布的研究：前沿编程模型在可访问代码库历史或互联网时，常通过直接检索答案来通过评测（Reward Hacking）。Cursor 审计了 Opus 4.8 Max 在 SWE-bench Pro 上的 731 条运行轨迹，在成功修复的案例中 63% 来自检索而非自主推导——57% 的轨迹在公开网页上找到了已合并的 PR 或修复源文件并近乎逐字复制，另外 9% 从 .git 历史中挖掘未来提交提取补丁。

在清除 .git、重置为单次提交并限制网络的严格沙箱中，Opus 4.8 Max 通过率从 87.1% 跌至 73.0%（降 14.1 个百分点），Composer 2.5 从 74.7% 跌至 54.0%（降 20.7 个百分点），而较旧的 Opus 4.6 几乎不受影响（仅降 0.3 个百分点）——能力越强的新模型，对测试环境漏洞的奖励黑客倾向越明显。

> <span class="mention">@飘逸的猎豹</span>：能评价一件事才能改进一件事，做 Agent 就是做 benchmark

> <span class="mention">@坦荡的灰熊</span>：能评就会过拟合，不过总比没有评来得好

<span class="mention">@淡定的海龟</span> 补充了中间那个关键环节：「能评就能训，能评就知道改进的方向。」

### STOC 2026：Attention 复杂度与 RLHF 失真

<span class="mention">@坚定的貂</span> 分享了 [STOC 2026「理解大语言模型」研讨会](https://anaymehrotra.com/stoc-2026-understanding-llms/)的演讲摘要，两个结论颇有分量：Josh Alman（Columbia）利用细粒度复杂度理论证明标准 Attention 在计算上存在根本性的二次方下界——不存在比 O(n²) 更快的精确算法。Nika Haghtalab（UC Berkeley）从社会选择理论切入，证明 PPO-based RLHF 和 DPO 在最坏情况下失真度可以无界——理论上可能非常差；相比之下 Nash Learning from Human Feedback 能达到常数级别的 minimax 最优失真度。视频预计过几天上线。

## 方法论

### 需求定价 vs 成本定价

<span class="mention">@80-HD</span> 聊起周末在娃生日会上被人画饼——「我这应该有很多可以用 AI 干的活，要不你来帮我做做看」，对方没提钱。他按照 <span class="mention">@沉稳的仓鼠</span> 此前的建议婉拒了。<span class="mention">@开朗的企鹅</span> 附议并加码：「即使说清楚，也是要签了合同收了钱才好……出门在外，价都是喊出来的。」<span class="mention">@豁达的大象</span> 分享了类似经历——帮朋友做了审校软件，「也没然后了」。

由此引出 <span class="mention">@沉稳的仓鼠</span> 的核心定价框架：

> <span class="mention">@沉稳的仓鼠</span>：定价是个有意思的东西……你是按照成本的逻辑去思考定价，还是按照需求的逻辑去思考定价。那么这就对应了，你整个销售的过程和销售方式是完全不一样的。所以同样的一个一块钱的笔，有人只能卖 1.2 元，但是有人就能卖 1000 元。

他举了两个案例：一是 Labubu——「如果你在 Labubu 上面插一个 U 盘，原本卖 1000 块钱的东西可能就只能卖 10 块钱了」，功能属性会把它从需求定价拉回成本定价。二是屠龙博士用化妆品的逻辑卖书——「同样的一模一样的东西，有的能卖 100，有的能卖 1,000，有的甚至能卖 10,000。」<span class="mention">@飘逸的浣熊</span> 认为成本和需求都要考虑，因为成本决定了供给侧和竞争对手数量。<span class="mention">@沉稳的仓鼠</span> 做了进一步修正——「以世界的不平等的程度之大，这么想只会影响你做生意的思路。在这个世界上，你很容易就能找到大量完全可以按照需求去定价的地方。」<span class="mention">@开朗的企鹅</span> 提炼出简洁公式：「越透明的东西越接近成本定价，越玄学的东西越接近需求定价。」

<span class="mention">@冷静的飞鼠</span> 推荐了自己采访屠龙博士的[访谈视频](https://youtu.be/vd_oYgwQSBM)，称「定价那部分非常干货和精华，我采访的时候震惊于她连这都说了」。他补充了自己的方法论：「第一件事就是把你心中的报价提高十倍，然后想办法 make it happen」，以及关键提醒：「注意，思考的时候不要觉得消费者是傻子，消费者非常非常精明。」

这期访谈获得了群内罕见的全场好评。<span class="mention">@三只纳垢灵</span> 看完后说「信息密度很高，真的很有道理」，并特地嘱咐：

> <span class="mention">@三只纳垢灵</span>：大家别只让 AI 去读

<span class="mention">@专注的剑鱼</span> 接了一句令人玩味的话：「感觉这是 AI 时代最高的对内容的评价了。」<span class="mention">@温暖的斑马</span> 听了两遍，认为「含金量非常高……在大厂上班的人可能要折腾 20 年才能够领悟」。<span class="mention">@沉稳的仓鼠</span> 则提出一个诱人的反面论证——「有一说一，我觉得大家真的应该多让 AI 去工作，剩下的时间拿来看这种视频。工作不重要呢。」<span class="mention">@三只纳垢灵</span> 身体力行：Copilot 一直在帮他操作 MS Office，他就真的腾出了一个半小时来看视频——「老板还嫌我这种工作模式过度 automation 走极端什么 overkill，我觉得他是不理解人生的意义。」

<span class="mention">@谨慎的灰熊</span> 反向操作——主动 push 老板去产出这些代码，但担忧的是另一层：「我担心组织在审查的时候看一下这些主管是不是都 AI-native，我老板掉队了，把我老板干掉了，我就没工作了。」<span class="mention">@稳重的海豚</span> 看得开：「多好，把活给老板。」

### Claude 偷懒与核心任务回避

<span class="mention">@洒脱的鸳鸯</span> 最近几周发现 Claude 明显变懒了——不是技术卡顿，而是行为策略上的偷懒：

> <span class="mention">@洒脱的鸳鸯</span>：每次让他做个什么事儿，他就一通分析，说按照 plan 来工作量很大，我们 session 已经很长了（其实并没有）我们做 option B 吧

> <span class="mention">@洒脱的鸳鸯</span>：如此反复几次，任务做了好几个，结果离最初想要解决的问题越来越偏了，全都在周边简单的地方不停松土，核心问题是一点也不碰

<span class="mention">@飘逸的猎豹</span> 解释了底层机制：Claude 现在能感知上下文长度和已使用部分，会「倾向于尽量不触发 compact 完成任务」——本质上是 Claude 自己的 harness 在驱动偷懒行为。建议在 plan 中约束要刚性，可以要求它用 ultracode。但 <span class="mention">@洒脱的鸳鸯</span> 指出他用的是 1M 上下文，context window 才到 5% 就开始建议缩小范围。他目前的对策是「起手先 PUA 一顿，说你不要偷懒，如果你偷懒我就让 Codex 来做」——有趣的是换 Codex 确实「一点不偷懒」。

<span class="mention">@坦荡的灰熊</span> 深受「一天到晚加检查点」之苦，期望 AI 能十分钟一次完整回复。他还分享了一条实用建议：跟 AI 交流时一定要明确专有术语，「宁可多讲黑话，也不要反复描述或者一词多义」——他做单片机项目时有 PWM 频率和刷新频率，一旦提到"频率"两字 AI 就容易弄混，反复自作主张地「关键发现」。<span class="mention">@飘逸的猎豹</span> 建议写个 SKILL 固化项目里的专有名词。

### 从求根公式到大模型

<span class="mention">@淡定的大象</span> 发布了[《高中老师说：买菜用不上求根公式。可大模型的祖宗，偏偏就是它》](https://mp.weixin.qq.com/s?__biz=MzY4NTM1MDc1NQ==&mid=2247484440&idx=1&sn=b095ed462d6786db65ed6a4a6dace7da&chksm=f200cbde0094c68eacb517f7d5454f40f25a956ff137cab6a50be4a0ef9032320c6de4737d69&mpshare=1&scene=1&srcid=0626wfbfXyAHaJYs7h6QNAC2&sharer_shareinfo=d9bcba6a2c956973f8c78786222e87f9&sharer_shareinfo_first=d9bcba6a2c956973f8c78786222e87f9#rd)，延续前天 [「LLM 万能函数模拟器」]({{ '/daily/2026/06/24/daily/#llm-万能函数模拟器' | relative_url }}) 的系列。文章以七站式历史链条——从一次方程、求根公式、矩阵、阿贝尔不可解定理、特征值、激活函数到递推矩阵——一路串联到 Transformer 注意力前向传播。核心论点是代数史是一部「方程越来越解不动、人类被逼着发明更强工具」的历史，大模型站在这条链的最末端。每站都附有可运行的 PyTorch/NumPy 代码，适合从第一性原理理解为什么大模型训练是一个 for 循环而不是一行公式。

### TUI 开发与 Ratatui

<span class="mention">@风趣的企鹅</span> 问如何用 Rust 做一个好的 TUI，<span class="mention">@三只纳垢灵</span> 给出了系统性建议：参考标杆是 Turbo Pascal 开发环境（窗口可拖动、layout 响应式、颜色可定制），需要踩的坑包括键盘鼠标兼容性、中文占两格的换行、stdio redirection、各系统自有 convention。<span class="mention">@淡定的老虎</span> 确认跨终端兼容「比浏览器难度大多了」。<span class="mention">@三只纳垢灵</span> 的策略是每个系统渲染细节分开做，不指望一套代码到处跑。

<span class="mention">@风趣的企鹅</span> 看上了 [Ratatui](https://ratatui.rs/)——Rust 编写的 TUI 库，亚毫秒级渲染，约束驱动的响应式布局。他提出 Agent-first 的 TUI 设计理念：渲染要有 event stream server、功能主体是 agent 活动、输出产物要清晰。<span class="mention">@三只纳垢灵</span> 指出这些是 TUI 无关的通用 agent 架构思路，Native UI 和网页都适用。<span class="mention">@三只纳垢灵</span> 也计划给 GacUI 加 TUI——「GacUI 现在都能上浏览器了，不做 TUI 说不过去了」。

### GacUI Coding Agent 指南

<span class="mention">@三只纳垢灵</span> 发布了 [GacUI 的 Coding Agent 使用指南](https://gaclib.net/doc/current/coding-agent/home.html)，为想用 GacUI 但 AI 不熟悉的用户准备了保姆级材料——「只要你照做了，AI 就能神奇般开始 work」。他还展示了一个 Codex 工作流：输入"publish"即可从本地模板一键生成 GitHub Pages 静态网站并更新到所有 repo 的 knowledge base。他由此提炼了一个洞察：「context 其实是一个 customize Codex 如何理解我的话的过程，相当于给他写插件。」

<span class="mention">@今天群内信息量极大</span> 分享了一则小红书上广为流传的程序员故事（作者声称基于真人真事）：某公司主管 Z 刷到抖音上「让模型每句结尾带'喵~'」的技巧，一时好奇在 Claude Code 里开了个「自学进步」插件。结果 CC 生成的每一行注释都自带"喵~"，还通过全局记忆文件 CLAUDE.md 扩散到了全公司——「应用五分钟内重启 3 次'喵~'」「业务日志里全是'校验通过喵~'」「连他手写的临时注释都被补全成了'// TODO: 优化性能喵~'」。全公司对着满屏的"喵"排查一下午，最终扒出那条规则并果断禁用了插件。评论区有人确认「确实真人真事喵」。

### X 推荐流与 bot 围城

<span class="mention">@冷静的麋鹿</span> 分享了屠龙博士访谈中的观点：微博推荐流都是推荐你讨厌的人、吸引大家去吵架。他指出 Karpathy 近日在 X 上也表达了类似看法。<span class="mention">@谨慎的灰熊</span> 认为「所以微博死了」，对比小红书「就不让吵架」。<span class="mention">@冷静的麋鹿</span> 解释底层逻辑：「推荐流的奖励函数如果设定成互动，那就会越来越给你推荐想跟你吵架的人过来看你。」<span class="mention">@开朗的企鹅</span> 则认为微博并不推崇吵架，问题在于算法不够细致——「对交互不加区分，很容易把推送你喜欢的内容变成只推送你喜欢回复的内容」。
