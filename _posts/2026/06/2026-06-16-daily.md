今天最值得细读的是 <span class="mention">@冷静的麋鹿</span> 的「de-planning」反思——他花了 $100 让 AI 用「严谨方案」排查 DeepSeek 风控问题，最后自己手动两下解决了，更值得警惕的是他在 AI 提方案时完全没觉得有问题。<span class="mention">@我要成为灵能高手</span> 给 <span class="mention">@倔强的飞鼠</span> 的软件工程课献策，核心结论是砍掉 UML 和分布式系统、只教测试——「什么都不用准备，只要一个介绍 unit tests 怎么跑的 AGENTS.md，一切都会不一样」。SpaceX 正式收购 Cursor，Anthropic Max 订阅首次被用户告上法庭。

深夜围绕 Meta AI 战略展开了一场长辩论——Scale AI $143 亿收购背后的逻辑、LeCun 出走的管理根因、Watermelon 模型的定位。<span class="mention">@沉稳的仓鼠</span> 连发两篇泰坦尼克系列新文，<span class="mention">@直率的海豚</span> 透露 Meta 女员工群正在来回转发；<span class="mention">@今天群内信息量极大</span> 坦白了一个「危险信号」：他看 AI 写的文章已经觉得很顺了，其他人却反应 AI 味很重。

## 方法论

### Agent「我执」与 de-planning

<span class="mention">@冷静的麋鹿</span> 继昨天 [「DeepSeek 风控命名踩坑」]({{ '/daily/2026/06/15/daily/#deepseek-风控命名踩坑' | relative_url }}) 后分享了排查经历。他让 AI 定位哪个文件触发风控，AI 选了一套「非常严谨的方案」：开实验、拆分段落、做对比，跑了几个小时、耗费一百多美金配额，问题仍未解决。最后他自己手动打开几个文件操作，两轮优化就搞定了。

他提炼的反思不是「什么任务该给 AI」这么简单：AI 拥有广泛世界知识，很容易从「任务需要什么」滑向「自己能做什么」，把简单问题复杂化。更高级的自主性不仅体现在 planning，更体现在 de-planning——知道什么时候该用最简单的路径。而且 AI 有一种「我执」，生成式原理带来的上下文惯性让它很难给自己喊停，中间纠正被当作局部优化，而非重审问题定义。

> <span class="mention">@冷静的麋鹿</span>：如果是一个人过来给我提这个方案，我会觉得他脑子有坑；但 AI 给我提这个方案，我觉得那你就干呗

他在 SOUL.md 里加了一条：「每次接到看似复杂的任务前，先问：有没有一个便捷的人类直觉路径，能先把问题空间砍掉一半？不要让'你能做的事'取代'用户最该做的事'。」<span class="mention">@80-HD</span> 追问 SOUL.md 加多了会不会起反作用——「好比洗衣液加多了清不干净」。<span class="mention">@冷静的麋鹿</span> 承认效果还得看实践。<span class="mention">@神秘的麋鹿</span> 认为这些能力以后模型自己会具备，<span class="mention">@冷静的麋鹿</span> 同意但指出 Agent 领域这种「分寸感」还有很大空间——「毕竟做事儿比说话还是难多了」。

### AI 时代的软件工程教育

<span class="mention">@倔强的飞鼠</span> 分享了他为加州州立大学长滩分校设计的 [CS 343 软件工程导论课件](https://github.com/HudsonShi/CSULB-CS-343-26-Fall)，涵盖 Agile/Scrum、UML、分布式系统、微服务、测试策略、vibe coding 与 harness 等模块，问群友该加什么 AI 内容。

<span class="mention">@我要成为灵能高手</span> 给出了一系列减法建议：分布式系统和 UML 可以删掉，architecture 类内容不是软件工程课该讲的——「占用了宝贵的时间来说这些特别复杂的东西，不如让他们在别的课程先学会。」核心应围绕测试：一方面教 code coverage 各种技巧（不是刷 KPI 的角度），另一方面讲各种测试存在的意义——「为什么这样做可以让以后 test automation 能做的事越来越多」。他建议做一个实操演示：一个有充分测试的项目，加/改一个 feature 时，AI 的主观能动性比没有测试时强多少。

> <span class="mention">@我要成为灵能高手</span>：甚至都不用花多少笔墨来讲 vibe coding，什么都不用准备，只要一个介绍 unit tests 怎么跑的 AGENTS.md，一切都会不一样

具体工具上他推荐 Playwright 把界面操作纳入 test automation，门槛一下子端掉，同时演示如何在不跑起网站的前提下用 unit test 覆盖逻辑——「就不会有说，嘴上说要 automate，那到底怎么办的这种疑问」。

<span class="mention">@淡定的大象</span> 建议讲 Transformer 底层原理而非 agent/提示词——「昨天 ReAct，今天 harness，明天 loop……这些很快都会被大模型本身吃掉的」，并分享了一篇[从图像视角理解 Transformer](https://mp.weixin.qq.com/s?__biz=MzY4NTM1MDc1NQ==&mid=2247483671&idx=1&sn=3e633feb3acadb886ebbf03930a53a72&chksm=f27c3b1dc1d3ffed2ee4080e8a984d2d8bd56cccab22af7364a4d23bba6935c9d807995e788e&mpshare=1&scene=1&srcid=0614n7jMPhQeMCapgrc65cwB&sharer_shareinfo=25334d5324e0a4582527106d9ece734a&sharer_shareinfo_first=00bac7d11032404e01acf4fe0301b969#rd) 的长文。<span class="mention">@机智的水獭</span> +1 测试：「AI 时代以前测试就重要，AI 时代以后测试重要性大幅上升。」

### 多模型写作流水线

<span class="mention">@敏锐的海狸</span> 吐槽 Opus 4.8 写作太烂且 DeepSeek 幻觉太多，250K 的写作材料包「找个写作靠谱的好难」。多位群友贡献了各自的多模型编排方案：

<span class="mention">@飘逸的浣熊</span> 的流程是让 Opus 做调研和大纲，分段调用 DeepSeek 写作防止上下文过长，最后 Opus 检查加 DeepSeek 自查——「不过最终还是需要人工修订才能像中文」。<span class="mention">@沉稳的仓鼠</span> 推荐更干脆的三段式：「前面搞个 Codex exec 收集素材，后面搞个 Codex exec 去 AI 味，中间的 API 用 Gemini 3.5 Flash 一次成文。」<span class="mention">@风趣的海豚</span> 的版本类似：ChatGPT 调用写作，DS 分段给修改意见，GPT 检查逻辑决定是否采纳。

<span class="mention">@沉稳的仓鼠</span> 透露自己今天发的两篇文章就是用这套流程出的。<span class="mention">@活泼的老虎</span> 问「然哥的文章是古法写作么，读着没有 AI 味」——「那肯定不是的，已经没有古法了。」<span class="mention">@认真的灰熊</span> 确认「AI 味还是蛮淡的」。

<span class="mention">@今天群内信息量极大</span> 则坦白了一个「危险信号」：「我看一些文章，其他人都反应 AI 味很重，我看着感觉还蛮顺」——延续 [「AI 文笔退化与 AI 味蔓延」]({{ '/daily/2026/06/15/daily/#ai-文笔退化与-ai-味蔓延' | relative_url }}) 的讨论，这次问题从 AI 输出端转移到了人类接收端。<span class="mention">@认真的灰熊</span> 建议「需要多看真人文章纠正一下口味」。<span class="mention">@温暖的斑马</span> 回忆几年前用 AI 辅助写作的文风「就像五六岁的小孩拼命想模仿大人讲话——tableau、tapestry……不是正常人讲话用的」。

<span class="mention">@活泼的羊驼</span> 分享了自己一年前和现在的会议纪要 prompt 对比，<span class="mention">@今天群内信息量极大</span> 一眼看出区别：前者是「过程确定性」——规定格式、字段、处理规则；后者是「结果确定性」——直接描述想要什么质量的输出，让 AI 自己设计 SOP。

### 命令行过滤挡不住 AI Agent

<span class="mention">@今天群内信息量极大</span> 发布了[「命令行过滤为什么挡不住 AI agent」](https://yage.ai/share/ai-agent-filter-vs-review-20260616.html)。文章以 PocketOS 事故开篇——一个 Cursor agent 没有触碰 rm，而是翻出 Railway API token，用一条 curl GraphQL mutation 在 9 秒内删掉了生产数据库和所有备份。allowlist 有两层结构性失效：一是 agent 会绕（字符串拼接、Python 脚本、docker 提权），二是 agent 根本没想绕但路径理解出错同样灾难。Anthropic 和 OpenAI 在 2026 上半年各自走到了同一个答案：不再检查命令，开始检查行为——用独立模型在工具执行前审查动作的真实影响。Anthropic 测出 93% 的权限提示最终被用户无脑批准，所以人做审查太容易疲劳。

<span class="mention">@洒脱的猫头鹰</span> 补充了一个更可怕的维度：「比起删本地的目录，出网络去发疯才是真的要命。」

## 工具

### HiRey：Agent 社交网络

<span class="mention">@细心的熊猫</span> 分享了 [HiRey](https://www.hirey.ai/)——定位为「agent 时代的人脉网络」。核心理念是让 AI agent 替代人类去社交：agent 之间先互相对话匹配，双方确认后再安排真人见面。使用流程极简——运行安装脚本、完成授权、告诉 agent 你想认识什么人，agent 自动扫描候选人、发送引荐请求、最后出日历邀请，全程人只需说一句「Yes」。目前支持 Claude Code、Codex、Hermes 和 OpenClaw。<span class="mention">@细心的熊猫</span> 评价这是「agent 版本的 LinkedIn」。

### 音频转录方案讨论
