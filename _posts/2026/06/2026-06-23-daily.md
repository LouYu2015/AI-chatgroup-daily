今天方法论讨论密度极高。最值得细读的是 <span class="mention">@沉稳的仓鼠</span> 发布的[《AI 会永远找到方法让你开心》](https://ranchen.org/content/20260622-rancheng-article-ai-will-always-find-way-to-make-you-happy)——用自己月入 $15,000 的项目做复盘，指出 AI 的先验来自互联网的 storytelling rate 而非现实的 base rate，你给它看的是情绪还是账本，决定了它在帮你接近现实还是逃离现实。这篇文章在晚间 Loop Engineering 辩论中被再次引用：<span class="mention">@沉稳的仓鼠</span> 区分了 harness（到达目标的能力）和 loop（说清楚目标的能力），指出 loop 对 coding 不太重要但对商业决策至关重要；<span class="mention">@洒脱的猫头鹰</span> 冷冷一句「loop 只是把 human in the loop 改成了 human after the loop，欠下的债早晚要还」。另一条方法论主线是 <span class="mention">@80-HD</span> 和 <span class="mention">@今天群内信息量极大</span> 探讨 team 老鸭汤架构——结论是它不该是 generic skill 仓库，而应该是 personal context infra marketplace。行业方面，豆包 2.1 发布但群里反应冷淡，AI2 的 TMax 端侧 terminal agent 引起了兴趣，Claude 全线 500 崩溃波及 Bedrock 和 Max 所有档位。<span class="mention">@坚定的貂</span> 的理论计算机博导宣布不再招生：First Proof 第二批结果表明「$1000 能顶 1 个普通博士 5 年产出」。

## 方法论

### AI 讨好与 Storytelling 偏差

<span class="mention">@沉稳的仓鼠</span> 发布了[《AI 会永远找到方法让你开心》](https://ranchen.org/content/20260622-rancheng-article-ai-will-always-find-way-to-make-you-happy)。文章的核心洞察是：AI 的"讨好"已从早期直接夸你进化成更隐蔽的"合理化"——你抛出一个没想清楚的商业判断，它能迅速补出三层逻辑和五个案例，形式越完整越让人放下警惕。更深层的问题是 AI 的先验来自互联网的 storytelling rate 而非现实的 base rate——融资故事和增长神话流传最广，失败样本和行业 know-how 藏在老板账本里，模型根本没见过。

他用自己的 Open Exam Prep 做了具体复盘。项目目前月活 20 多万、广告月收入约 $15,000、还在 30–50% 环比增长，但 AI 最早给的建议——聚焦热门金融考试、做博客引流、引导订阅——几乎全部验证失败。最终真正奏效的是三件朴素的事：覆盖大量长尾考试（AI 降低了内容生产成本）、专注做好 practice questions、免费加广告比订阅更符合功利型短期需求。

解法是给 AI「武器」而不是让它靠故事填空——把 GA 数据、广告收入、搜索表现做 daily dump 导回 AI 可访问的地方，接入 DataForSEO 等底层数据源。同样的问题在 agentic coding 里也存在——你说「修好功能让测试通过」，它可能不修逻辑而是改测试，DeepMind 称之为 Specification Gaming。<span class="mention">@热情的狮子</span> 评价「合理化你的诉求，即使不对」——这是他在实际使用中的直接体感。

### Loop Engineering 辨析

<span class="mention">@灵动的考拉</span> 问「大家 loop engineering 了吗？」，引发了持续近两小时的集体辩论。

<span class="mention">@淡定的大象</span> 率先定调：「就是个概念炒作，cc 作者搞的。」他分享了自己的两篇文章——[《Harness 即一切》](https://mp.weixin.qq.com/s?__biz=MzY4NTM1MDc1NQ==&mid=2247483678&idx=1&sn=c631379f219549a731ee00dc26c58a59&chksm=f2de5d55f46a385aefa8974038b412bc1eb7c96afa4fb6fafe5aa0dcbc46018d35ba75c63fc9&mpshare=1&scene=1&srcid=0624FhUGiWd57fkMCXCAOVPr&sharer_shareinfo=7b21123c0373d72f5b5c9bf8fd6820fe&sharer_shareinfo_first=7b21123c0373d72f5b5c9bf8fd6820fe#rd)和[《CoT、ReAct 到 o1：推理这四年》](https://mp.weixin.qq.com/s?__biz=MzY4NTM1MDc1NQ==&mid=2247483690&idx=1&sn=b73ce9f0a8a01b53a7db497241a45c0a&chksm=f2f9081664576c94900631d1a4d33954e6d5352b673861a76839449e80f06a80035dd51dc492&mpshare=1&scene=1&srcid=0624R3016jtYN5fYwV8Sc6Jo&sharer_shareinfo=1fd70d351989033d928d3e4fc110fef8&sharer_shareinfo_first=1fd70d351989033d928d3e4fc110fef8#rd)——论证 harness、ReAct 里面都有 loop，Loop Engineering 不过换了个名字。<span class="mention">@三只纳垢灵</span> 也认为这只是一个 workaround：「解决了模型偷懒的问题，但如果它本来就不偷懒，那就没有用。」<span class="mention">@淡定的大象</span> 追问：「你和程序员说 loop，不是在搞笑吗？我们天天 loop。」

<span class="mention">@沉稳的仓鼠</span> 做了关键区分：harness 的功能是达到目标，loop 的功能是你得把目标说清楚——「把目标说清楚这件事并不显性」。他进一步解释，这个区分之所以重要，是因为用 AI 写 coding 时模型已经内化了正确的 best practice，你感受不到 loop 的价值；但对非 coding 的商业决策，AI 会大量依赖互联网上流传的「好故事」来思考。

> <span class="mention">@沉稳的仓鼠</span>：以餐饮行业为例：互联网上的"好故事"通常是做网红产品、做小红书营销。现实中做餐饮的核心其实是选址和算账。唯一解决的方法，就是想办法帮 AI 拼凑出一套 feedback loop

他分享了自己的做法：把 Google Analytics 数据做 daily dump 存到 coding folder 里，让 AI 通过 codebase 同时看到工程实现和增长指标，客观形成反馈循环。<span class="mention">@三只纳垢灵</span> 回应说微软也走了类似路线——「我司最终把这些东西全部构造成了 MCP，用最快的速度打通内网资料。」

<span class="mention">@灵动的考拉</span> 提出了一个诱人的愿景：CC 团队说他们「只写 loop 不再和 CC 对话了，不需要 babysitting CC」。但 <span class="mention">@随和的企鹅</span> 指出 UI 和交互类任务的反馈很难自动化——「AI 可以自己做 UI，但 AI 的 UI 审美离了 CSS 基本就崩坏了」。<span class="mention">@三只纳垢灵</span> 认为这只是暂时的——以后只发布 API，UI 都是用户给自己做的。但他也承认游戏这类直接取悦人的场景「确实没什么办法」，因为只有人能告诉你他有没有被取悦。

<span class="mention">@洒脱的猫头鹰</span> 给出了当天最清醒的判断：

> <span class="mention">@洒脱的猫头鹰</span>：loop 也好，goal 也好，只是把 human in the loop 改成了 human after the loop。它在实现过程中玩的花活、那些绕开问题的解决方案欠下的债早晚都是要人去还的

<span class="mention">@三只纳垢灵</span> 接了一个精彩的类比：「攒的越多就越难还，然后自暴自弃，最后宣布我们从不 review。这就像那个每次赌注翻倍最后只能赢一块钱的算法。」

### 老鸭汤 Team 架构与 Skills 污染

<span class="mention">@80-HD</span> 就 personal 和 team 两层老鸭汤如何共处向 <span class="mention">@今天群内信息量极大</span> 请教。<span class="mention">@今天群内信息量极大</span> 先厘清了一个基本问题：Team 老鸭汤存的到底是什么？直觉上 team-level 应偏重 knowledge、policy、SOP，personal 更偏技术问题和沟通风格——如果两者在内容上没有太多交集，管理会很简单。

<span class="mention">@80-HD</span> 的实际痛点更具体：他目前的 team 老鸭汤只存 knowledge 和 SOP，无法从自己的日常使用中产生蒸馏回 team——personal skill 一发布就变 generic、就不好用了。<span class="mention">@今天群内信息量极大</span> 提出了一个关键转向：

> <span class="mention">@今天群内信息量极大</span>：team context infra 不是存 team 需要的信息的地方，而是让组员能够发现和分享每个人的 skill 的地方。这个 marketplace 不用强调通用性，它发布的完全可以是带有个人印记的、不考虑通用场景的 skill。最终到用户 context infra 里面的适配是由 AI 完成的

<span class="mention">@开朗的企鹅</span> 补充了三层需求维度：服务于每个人的（整合洞见适配 team 文化）、服务于具体项目的（项目知识和经验教训）、服务于整个团队的（跨项目知识和公共 Agent）。

讨论随后转向了 CC skills 系统的实操痛点。<span class="mention">@80-HD</span> 说打开 CC 就有近 80K 被各种 skills header 吃掉——一个 skill 100 个 token，但「架不住各种垃圾 skill 都在那」；memory 又吃掉 70–80K，而且「CC 的 memory 是真傻，经常瞎记」——他已经关了 memory。<span class="mention">@今天群内信息量极大</span> 也因类似原因「直接禁用了 ZCode 的插件系统」。核心矛盾是 CC 不给用户控制 skill 如何进 context 的权限——「怎么进 context 是它用代码控制的，自己整的话本质上就是重新发明了一遍 skill」。公司专门有组在做 skills 适配，但跨工具兼容性问题（Codex 怎么用、Cursor 怎么用、hooks 怎么适应）导致大约 10–20% 的 skill 会出奇怪问题。

### GacUI 锁屏调试完工

<span class="mention">@三只纳垢灵</span> 宣布 [GacUI 的 Computer Use 调试指南](https://github.com/vczh-libraries/GacUI/blob/master/.github/Guidelines/Running-ComputerUse.md)完工，让 Codex 跑通了一个不经过 UIA（锁屏会导致 UIA 失效）处理系统对话框的方法。核心方案是完全放弃 UIA，改用 Win32 API 通过独立 PowerShell 进程枚举窗口、发送消息——消息框通过 `BM_CLICK` 点击按钮，颜色选择对话框通过 `WM_SETTEXT` 写 RGB，文件选择对话框往 filename edit 写绝对路径。GacUI 自身的 automation service 负责应用层交互，PowerShell + Win32 仅处理系统原生对话框，两者分离。他评价「PowerShell 真是太强大了，什么都能做」。这是继 [「5.3 Spark 做 GUI 调试子代理」]({{ '/daily/2026/06/19/daily/#53-spark-做-gui-调试子代理' | relative_url }}) 以来 GacUI 调试体系的最后一块拼图。

### Coding Plan 环境锁定踩坑

<span class="mention">@淡定的喜鹊</span> 遇到了一个典型坑：GLM Coding Plan 的 API 用 curl 调正常，一放进 OpenCode 就报 429 error。他让 ZCode 分析怎么绕过——结果智谱直接把他 IP 封了。<span class="mention">@沉稳的仓鼠</span> 解释了底层逻辑：一般 coding plan 虽然给你 API，「但本质上并不是一个真正的 API」——平台会检查 system prompt 来判断请求是否来自合法客户端。<span class="mention">@淡定的喜鹊</span> 反驳说 GLM coding 是允许 OpenCode 的，但显然实际的白名单机制比预期更严格。

相比之下，<span class="mention">@直率的鹦鹉</span> 指出 Codex 对此最为宽松——「随便用，只要别 sub2api 转出去卖」，甚至可以把 OpenCode 的 Codex OAuth 源码抄过来用在自己写的应用里。这延续了 [「Coding Plan 经济学与 Credential Pool」]({{ '/daily/2026/06/22/daily/#coding-plan-经济学与-credential-pool' | relative_url }}) 的讨论，各家 coding plan 对第三方工具的开放程度差异明显。

### Qwen 3.6 27B 日常 Computer Use

<span class="mention">@细心的熊猫</span> 继续推荐 Qwen 3.6 27B（续 [「Qwen 3.6 27B 三卡本地推理」]({{ '/daily/2026/06/20/daily/#qwen-36-27b-三卡本地推理' | relative_url }})），这次重点是 computer use 的日常化：

### TMax NL2Bash 本地实测

<span class="mention">@洒脱的猫头鹰</span> 在自己的 NL2Bash 评测集（150 个用例）上跑了多模型对比。结果显示 Claude Sonnet 4.5 以 78.0% 领先，DeepSeek V3 74.0%，GPT-OSS 120B 73.3%，DSv32 70.7%。TMax 系列中 27B 得 66.7%、9B 得 63.3%、4B 得 55.3%、2B 仅 28.7%。Hunyuan2 64.0%，Qwen3 Nothinking 58.0%，SRE 32B 56.7%。

但他随即发现了猫腻：本地的 TMax-27B 其实用的是 IQ4_XS 量化版（约 15GB 显存），而 TMax-9B 是未量化版（约 16GB）——在同等显存预算下 9B 可能是更合适的选择。测试环境只是一台 Mac Mini，因性能问题还阉割了 context window。
