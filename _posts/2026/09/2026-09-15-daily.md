DS V4.1 Flash 给了搜索工具也照样编——<span class="mention">@今天群内信息量极大</span> 同 prompt 同工具横评三家模型，只有 DS 搜了一大圈仍编造网址，调研类任务选模型有了硬数据参考。<span class="mention">@专注的火烈鸟</span> 与 <span class="mention">@搞仁义毛义仁</span> 联手拆解了 Astra over-engineering 的根因：旧模型时代攒下的 skill 和 memory 在暗中加活，清理后行为立刻正常——每个从 Sol 迁来的项目都该安排一次 context 大扫除。

## 方法论

### 旧指令反噬 Astra

上午 <span class="mention">@专注的火烈鸟</span> 爆发了一轮对 Astra 的不满：只让它本地复查三个明确问题，它却自行启动完整 PR review，又在此基础上补齐一堆 test case——「一个花个几分钟就能完成的任务，他非要给你拓展到半个小时到一个小时以上」。这不是一次意外，而是反复出现的模式。

<span class="mention">@搞仁义毛义仁</span> 给出了系统诊断：根源大概率是项目里积累的 skill、instruction 和 memory 在暗处驱动模型加活。<span class="mention">@热情的狮子</span> 检查后确认了这个判断——旧 memory 和共享 workflow 保留着更宽、更强的要求，与新规则冲突。这与 OpenAI 此前发布的 Skill 瘦身指南（[「OpenAI Skill 瘦身指南」]({{ '/daily/2026/09/12/daily/#openai-skill-瘦身指南' | relative_url }})）指出的问题一脉相承。

> <span class="mention">@搞仁义毛义仁</span>：非常 micro managing 你的 context，就像过去 micro managing coding 一样，以前是不在乎文档，现在反过来了，总有一样你要投入 micro management

对策方面，<span class="mention">@搞仁义毛义仁</span> 建议把 Astra 在项目中会 over-engineer 的东西全部枚举出来，写进 coding guideline——goal、non-goal、rough design、verification 四段式——「用不了一个星期」就能覆盖完。<span class="mention">@天真的浣熊</span> 推荐 GitHub 搜索 `hero anti-overdefense` 加到 system prompt，能明显改善。<span class="mention">@专注的火烈鸟</span> 认为 security 应该作为开关按需加载，而不是每个 task 自动塞进来一堆安全收尾工作。

模型适配的锁定效应也值得注意。<span class="mention">@搞仁义毛义仁</span> 指出为旧模型调过的 context 直接用在 Astra 上会放大 over-engineering——「所以我现在只用 Astra 不去用别的模型了，这锅汤他们用不了」。<span class="mention">@专注的火烈鸟</span> 的体感是常规简活用 DS V4.1 Flash 才合适，Astra 更适合交付件定义严谨的场景。多位群友反映 Sol 是目前最稳定的选择，<span class="mention">@沉稳的兔子</span> 认为 Luna 只适合 straightforward 的活如修 bug、写编译脚本，<span class="mention">@谨慎的松鼠</span> 则觉得 Luna 不如 Kimi K3 开低 effort。

### Astra 降智传闻

除了 over-engineering，<span class="mention">@务实的灰熊</span> 提出了另一个更棘手的问题：Astra 动不动降智，降智后「连 4.1 都不如」。他观察到 DS V4.1 劈叉至少能提醒一下、还能拉回来，Astra 一旦降智就像 Luna 一样。<span class="mention">@睿智的北极熊</span> 已经在老项目上切回 Sol。

传闻还涉及地区歧视。<span class="mention">@搞仁义毛义仁</span> 称有传闻 Astra 针对中国用户降智，<span class="mention">@务实的灰熊</span> 表示差异「大到画鹈鹕就可以直接测出来——只要画出来是个奇行种基本就是降智了」。<span class="mention">@天真的浣熊</span> 也发现 Opus 中英文输入结果有区别。<span class="mention">@热情的狮子</span> 不太信降智说法，猜测可能是使用垃圾中转或用户过于敏感。<span class="mention">@稳重的海豚</span> 分享了一份[降智检测相关调研](https://www.nickgu.me/files/share/share-dd8337ab5c311f086646ac17a66c353a#k=a7SWngbNry-xrCOPf9jvovi78VWaMO6n2QETWGiLRJk)供参考。

### DS V4.1 Flash 搜索幻觉

延续昨晚的吐槽（让 DS 推荐餐厅，八个全是幻觉），<span class="mention">@今天群内信息量极大</span> 今天做了控制变量实验：同一 prompt、同一 harness、同一套工具（含 Tavily 搜索），分别用 DS V4.1 Flash、GPT 和 GLM 5.3 Flash 跑同一个调研任务（Swatch × AP 联名表发售进度调研）。

结果差距惊人。DS 调用了 22 轮工具，绝大部分是搜索，但关键字飘向不相关内容，给出的网址打不开；GPT 只用 4 轮——先精准搜索、前三个搜到结果、第四个复核——给的网站都真实可用；GLM 5.3 Flash 搜索关键字也合理，虽然不如 GPT 快准狠但不犯错。更反直觉的是 GPT 吞吐量最低却完成最快，因为不做无用功。

> <span class="mention">@今天群内信息量极大</span>：我越比较，越 deep dive，越觉得这个模型是烂泥扶不上墙……我这几天花了几百块，是真的很努力想去爱她

<span class="mention">@稳重的海豚</span> 推测 DS 是「很快就跑偏了，前面影响后边，然后就跑不回来了」——幻觉叠加效应。<span class="mention">@今天群内信息量极大</span> 总结 DS V4.1 的 instruction following 有进步，但幻觉仍是硬伤，「差不多从 2023 年到了 2024 年」。他强调不是工具适配问题——其他所有模型都不犯错，DS 是唯一一个搜了还答错的。整个实验使用的是他自己的 OpenCode iOS 客户端。

### AI 写作的信噪比

<span class="mention">@认真的荷兰猪</span> 分享了一个观察：刚接触 AI 写作时觉得观点好、数据多，对顶级用户的 AI 文章津津有味；最近却读不下去了——扫几眼就觉得一段里没有有价值的观点，整篇文章跳着就看完了。他反思差别在于：优秀作者的文章不只提供观点，还提供值得学习的表达方式和措辞思路；AI 写的文章只需提炼一个观点再做有损压缩，过程中学不到表达。

他举了 <span class="mention">@冷静的飞鼠</span> 此前的[一篇对话记录](https://www.superlinear.academy/c/ai-resources/result-certainty-general-intelligence-wei-xiaoliang)为正面案例——「隐隐感觉有一点 AI 味，甚至又分不太清」，但观点展开好、让人想回读。<span class="mention">@冷静的飞鼠</span> 回应：AI 可以调教好好写，但前提是作者言之有物。<span class="mention">@沉稳的仓鼠</span> 从另一个角度回击：「你看不出来的就不会认为是 AI 了。」

### 果蝇大脑接上 ChatGPT

<span class="mention">@稳重的海豚</span> 分享了一篇[报道](https://mp.weixin.qq.com/s?__biz=MzI2NDk5NzA0Mw==&mid=2248903076&idx=3&sn=d38846663cb02f9b118768dcbfc28949&chksm=e87c025319db9989fe5b5e835980d3a1af811a3275e1d3766d6bcd24acc88e314aff580d7c6d#rd)：开发者用 NumPy 在一台 MacBook 上模拟了一颗完整果蝇大脑（13.8 万神经元、1500 万连接），并首次把神经放电翻译成自然语言直接递给 ChatGPT。果蝇自己拼出的第一句 prompt 是「我闻到醋和酵母的味道。我尝到糖。又暖又亮。我该怎么做？」

验证环节做得讲究：喂糖时 MN9 神经元 78 Hz 放电，加苦味后掉到 3 Hz，方向与 2024 年《Nature》论文一致。反向测试中 ChatGPT 说「向左」、果蝇服从了 37 次一次不差，但从来没找到过食物——能驱动行为与产生意识之间还隔着一道鸿沟。<span class="mention">@稳重的海豚</span> 觉得项目有意思，但吐槽报道「AI 味太浓」，<span class="mention">@神秘的企鹅</span> 点出来源是新智元。

### codex-resets.com 重置追踪站

<span class="mention">@热情的狮子</span> 昨晚分享了 [codex-resets.com](https://codex-resets.com/)，一个专门存档 Tibo 在 X 上发布的 Codex 额度重置公告的第三方站点，目前收录 53 次重置，平均间隔 6.9 天，最长等待 67.7 天。站点日 PV 达 30 万，赞助位 $699/月——做 reset 追踪也能做成流量生意。

站内存档的长公告信息量不小：compaction 阶段保留旧图片可能让 context 二次触发 compaction，修复后重度用图用户用量降约 10%；set /goal 完成后越过停止条件或模型反复重试坏工具，有案例吃掉每周额度 15%–70%；小模型会自行挑更强的 helper；旧版 Computer History 反复摘要，个别情况每周吃掉五分之一额度。官方称已做架构改动防止回归，计划在 app 内显示用量去向。

<span class="mention">@认真的荷兰猪</span> 感慨这验证了他此前做的 Tibo Reset 邮件监控服务（[「Tibo Reset 邮件监控」]({{ '/daily/2026/09/12/daily/#tibo-reset-邮件监控' | relative_url }})）的思路——「能说明我的点子还行，也同时证明了点子不值钱」。

### 本地推理硬件与引擎

延续四卡 5060 Ti 讨论（[「四卡 5060 Ti 本地推理」]({{ '/daily/2026/09/11/daily/#四卡-5060-ti-本地推理' | relative_url }})），<span class="mention">@细心的熊猫</span> 又入手四张 MSI 5060 Ti 16GB，并总结了核心算数：解码速度与显存带宽成正比，并联 GPU 带宽叠加——四张 5060 Ti 的总显存带宽约等于一张 5090，价格却不到一半，满载功耗合计不到 300W。目前在跑 Qwen 3.8 27B 和 MiniMax H3，实测 132 tok/s、TTFT 1.3s。

<span class="mention">@优雅的喜鹊</span> 在单张 5090 上部署 Qwen 3.6 35B-A3B（MoE），单并发 380 tok/s、8 并发 1000 tok/s。他还分享了 NInfer 与 vLLM 的 Prefill 吞吐对比，NInfer 在所有输入长度上全面领先，短输入优势最大：

| 输入 Token | NInfer (tok/s) | vLLM (tok/s) | NInfer 领先 |
|---|---|---|---|
| 95 | 1,815 | 634 | +186% |
| 645 | 10,696 | 4,377 | +144% |
| 4,048 | 17,088 | 9,646 | +77% |
| 8,045 | 17,815 | 7,470 | +138% |
| 24,048 | 15,905 | 12,903 | +23% |

NInfer 在 8K 处饱和于约 17,800 tok/s，vLLM 一路爬到 24K 仍未见顶。稳定性差异也悬殊——NInfer TTFT 极差仅 3–15 ms，vLLM 达 76–482 ms。结论是 NInfer 在交互式对话最敏感的短输入段优势碾压，vLLM 在超长输入上还有余量。

### Codex 跨会话协作

<span class="mention">@豁达的灰熊</span> 提了一个实际痛点：长 session 中途需要写一封 email 发出去，内容和语气需要打磨，但不想灌进执行 session 污染上下文。群友给出多条路径——fork、新开 session 后 @ 老 session、让另一个 agent 盯着并用 session export skill、Codex 原生 branch。

最精确的做法来自 <span class="mention">@洒脱的猫头鹰</span>：Codex 会话支持复制深度链接（deeplink），新 session 里直接丢这个链接就能引用旧对话上下文。他还分享了一个跨项目协作模式：A/B 两个独立项目抽出公共模块 C 作为单独项目，A 遇到涉及 C 的事项就把 deeplink 发给 C 的 Codex 会话，C 改完后再通知 A。

> <span class="mention">@洒脱的猫头鹰</span>：两个项目的 Codex 对话像乒乓球一样，玩的有来有回的

### Computer Use 适用边界

<span class="mention">@认真的荷兰猪</span> 问 <span class="mention">@今天群内信息量极大</span> 在 OpenCode 里遇到浏览器操作和 Computer Use 场景怎么处理。<span class="mention">@今天群内信息量极大</span> 的判断是：Computer Use 对浏览器自动化加成不大，主要价值在操控没有 API 的桌面应用——画图、打游戏、结合 iPhone Mirroring 自动化手机 App。浏览器场景他更推荐 Playwright 配合 CDP 协议直接控制主浏览器。

关键区别在于登录态：主浏览器带真实 cookie，Playwright 临时开的浏览器会自带 bot 标记，「一用就被 block」。反爬的核心不是 Computer Use 有什么 magic，而是要用你自己的真实浏览器。Computer Use 还有个实操障碍——运行时接管鼠标，<span class="mention">@直率的鸵鸟</span> 吐槽「影响我刷视频」。<span class="mention">@认真的荷兰猪</span> 分享了一个创意用法：iPhone Mirroring 配 Computer Use 自动点快捷指令同步健康数据到 Mac。
