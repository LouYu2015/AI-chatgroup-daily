Tibo 亲自标定 Astra low 胜过 Sol high，配合 <span class="mention">@优雅的喜鹊</span> 贴出的 Codex CLI vs Claude Code 速度横评，effort 档位该怎么选终于有了数据支撑——还在拿 high 蹬的 Pro 用户可能多花了数倍额度。<span class="mention">@稳重的海豚</span> 发现网页版 6 Pro 能直接读 GitHub 仓库写代码且不吃 Codex 配额，是目前最划算的 Astra 入口。GPT-6 比前代更爱主动启动 Computer Use，多位群友建议提前写 skill 约束它。

## Astra Effort 校准

### Tibo 标定：Astra low 胜过 Sol high

Tibo 今天连发两条推文校准 Astra 的使用姿势（延续近日的额度讨论 [「费用与 Effort 策略」]({{ '/daily/2026/09/05/daily/#费用与-effort-策略' | relative_url }})）。第一条宣布对 power user 的 long tail 场景做了优化，质量不变、额度消耗最高降三到四倍；第二条给出明确标定：Astra low 的表现已经超过 Sol high，建议之前用 Sol high 觉得够用的人把 Astra 降到 low 或 medium。

从额度消耗来看，<span class="mention">@冷静的麋鹿</span> 估算同为 high 档时 Astra 约为 Sol 的三到四倍，$100 丐版 Pro 如果之前刚好够用现在得升 $200 档；不过他宁可选 Astra low 也不想再忍受 Sol 的龟速。<span class="mention">@聪明的灰熊</span> 做 HTML 交互原型和文档时发现 mid 就足够、速度还很快，多位群友也持类似看法。<span class="mention">@稳重的海豚</span> 在 Codex 里用 high 则觉得不够聪明，认为 max 和 xhigh 才行；<span class="mention">@直率的鸵鸟</span> 干脆混搭 Sol、Terra 和 Astra，否则 20x 额度撑不住。

体验层面也有明显提升。<span class="mention">@搞仁义毛义仁</span> 让 Astra 重写了一封之前 Sol 写过的信，评价「充满了人话，Sol 相比起来充满爹味」。多位群友注意到 Astra 不再废话、直接干活，补漏也很精准——<span class="mention">@洒脱的猫头鹰</span> 在脑暴确认第二点时心里想着第三点要提别的，Astra 在第二点结束时就主动补问了。

### Astra vs Fable 速度实测

<span class="mention">@优雅的喜鹊</span> 贴出了一张 Codex CLI 与 Claude Code 的速度横评。所有配置均为 xhigh reasoning effort、相同 prompt，三任务各跑三轮取中位数：

| 配置 | TTFT | TPS | 倍率 | 费用 / 3 任务 |
|---|---|---|---|---|
| Astra Pro · Normal | 3.0 s | 36 | 基线 | 0.09% weekly |
| Astra Pro · Fast | 2.5 s | 71 | 2.0× | 0.24% weekly |
| Astra API · Normal | 2.8 s | 81 | 2.2× | $1.76 |
| Astra API · Fast | 1.2 s | 124 | 3.4× | $3.01 |
| Fable 5.1 Max · Normal | 1.4 s | 94 | 2.6× | 0.67% weekly |
| Fable 5.1 API · Normal | 4.0 s | 94 | 2.6× | $3.51 |

Astra Pro Normal 速度最慢（36 tps）但额度消耗极低，三个任务只花 0.09% weekly，适合不急的后台任务。API Fast 模式吞吐最高（124 tps）、TTFT 仅 1.2 秒，但每三任务 $3.01。Fable 5.1 的 TPS 稳定在 94，速度居中；Max 订阅制下额度消耗是 Astra Pro Normal 的七倍以上，API 则略贵于 Astra 同档。如果再按 Tibo 的建议降到 low/medium，Pro 用户的实际性价比还会进一步拉开。

### 网页版 6 Pro 省额度

<span class="mention">@稳重的海豚</span> 分享了一条省额度的路径：把老鸭汤和项目代码都放在 GitHub mono repo 里，用 ChatGPT 网页版的 6 Pro 模式直接读取仓库并写代码。6 Pro 走单独的对话配额（<span class="mention">@细心的麋鹿</span> 确认约每周 200 条），不消耗 Codex 的 weekly limit。<span class="mention">@冷静的麋鹿</span> 展示了 6 Pro 通过 GitHub connector 读项目的截图，告诉它「看一下我的 git」就能搜索仓库、检查结构、给出优化建议。

安全方面有顾虑：他不敢把老鸭汤放 GitHub，里面私人内容太多，万一 agent 乱改权限设置就出事了。<span class="mention">@稳重的海豚</span> 认为网页版写权限有限，风险可控；也可以通过 Google Drive 等 connector 加载。

不过多人反映 6 Pro 执行力不如预期，写出来的东西「最多 extra high 的感觉」，有假 Pro 之嫌。<span class="mention">@乐观的灰熊</span> 持不同看法：旧版 Pro 虽好但动辄十分钟，现在速度合适得多。实际使用的建议是拿 6 Pro 做 plan 和初稿，写完交给 Codex 迭代闭环，因为网页版无法跑测试和 CI。

## 方法论

### Session Export 反查决策偏差

<span class="mention">@稳重的海豚</span> 今天实践了此前 <span class="mention">@今天群内信息量极大</span> 介绍的 AI Export Skill（[「Context 复利与偏好训练」]({{ '/daily/2026/09/05/daily/#context-复利与偏好训练' | relative_url }})）：导出全部 Codex session 历史后让 Astra 扫描，直接定位到了此前决策失误的地方。

Astra 在帮他备课时还自动写出了一个 utility function：`U = 10(bug fixed) + 5(tests pass) − 8(regressions) − 4(unnecessary changes) − 3(compute cost) − 100(security vulnerability)`。从权重可以窥见训练偏好：安全漏洞的惩罚系数是其他项的十几倍。他由此提出：和 agent 交互时应该把个人的 utility 显式讲清楚，而不是让模型按默认权重决策。

> <span class="mention">@稳重的海豚</span>：直接给我 ping 到了当时犯傻的地方——也不能这么说，因为是对 Sol 而言合理的 utility

### 评测任务设计经验

<span class="mention">@活泼的羊驼</span> 分享了用开源项目做大模型对齐评测的实操经验：选工程化质量好的开源项目、确保能本地端到端运行、通过 PR 历史筛选中型以上需求（不要修 typo 级别的琐碎任务）、代码中 `.git` 历史必须去掉否则 AI 可反解答案、远程链接也要清理以减少开卷机会。<span class="mention">@沉稳的仓鼠</span> 追问这和直接跑 benchmark 有何区别，<span class="mention">@活泼的羊驼</span> 认为差不多，相当于花钱买人工标注。<span class="mention">@搞仁义毛义仁</span> 推荐自己的 GacUI 项目：todo 充足、依赖干净、验证简单，跑起来看画面对不对就行。
