今天最值得读的是模型商品化的集中爆发——Gemini 3.8 Flash 与 Muse Spark 1.3 同日发布，Flash 级模型在多项跑分上逼近甚至超越 SOTA，<span class="mention">@今天群内信息量极大</span> 用两周消耗数据证明九成任务已不需要贵模型。<span class="mention">@活泼的羊驼</span> 领读了 Uncle Bob 关于 AI 时代软件基本功的播客，多 Agent 流水线设计值得一看；GPT-6 确认明天上午发布。

## 模型商品化加速

### Gemini 3.8 Flash 登顶

<span class="mention">@谨慎的灰熊</span> 贴出 Google 官方公告：Gemini 3.8 Flash 发布，同步推出专攻网络安全的 3.8 Flash Cyber。3.8 Flash 输入价 $0.75/M tokens，输出 $3.75/M，生成速度 305 tok/s，在 DeepSWE v1.1 上拿到 71%。

<span class="mention">@天真的浣熊</span> 贴出 benchmark 对照表：3.8 Flash 在 Vals Finance Agent（61.4%）、Harvey's Legal Agent（10.0%）、Terminal-bench 2.1（89.4%）等项上全线领先，HLE-Verified（54.9%）也超过了 Sol（54.5%）和 Opus 5（54.4%）。<span class="mention">@开朗的企鹅</span> 转发[新智元报道](https://mp.weixin.qq.com/s?__biz=MzI3MTA0MTk1MA==&mid=2652722488&idx=1&sn=3b9fd8d47527a7b927ffed3f35eb1a14&chksm=f064987f4b2d41b2f1071045ad17bcb2c9dc1a63e88daf28b4b90ee2c11ffacd188f4e48fcb4#rd)，文中提到 Gemini 3.5 Pro 内部候选模型均被毙掉——因为不比 Flash 强多少。

<span class="mention">@沉稳的仓鼠</span> 实测 3.8 Flash one-shot 做网站：速度飞快但结果太丑，幻觉率依然很高。他的体感是「5.6 还在想的时候它就做完了」。

### Muse Spark 1.3：Meta 回归

<span class="mention">@风趣的企鹅</span> 贴出 Artificial Analysis 数据：Meta 新发的 Muse Spark 1.3（xhigh）在 AA Intelligence Index 上拿到 61–62 分，与 Grok 4.6 和 GPT-5.6 Sol 持平，生成速度 235 tok/s。Alexandr Wang 在 X 上甩了句「gemini who?」，群友围观一番。

<span class="mention">@今天群内信息量极大</span> 做了价格对比：Muse Contributor 输入/输出价仅 $0.10/$0.20 per M tokens，比 DeepSeek V4 Flash API 还便宜，但默认使用用户数据训练，需切换到 Standard tier 退出。<span class="mention">@风趣的企鹅</span> 实测后表示非常可以。

### Flash 就是新 SOTA

<span class="mention">@沉稳的仓鼠</span> 抛出当天最具深度的判断：SOTA 模型不是趋势，Flash 才是主战场，model 最终就是真 commodity——这也意味着模型公司没什么 margin，高估值难以理解。<span class="mention">@谨慎的灰熊</span> 补充：Sam Altman 自己也认为不可避免，所以已经在做芯片。<span class="mention">@细心的熊猫</span> 翻出自己一年前的群聊截图作证。

<span class="mention">@幽默的犀牛</span> 指出，如果模型厂不在 harness 或 context layer 发力就很危险——用户没有粘性。<span class="mention">@沉稳的仓鼠</span> 对此同样不乐观：harness 很快也会被卷平。他点出一个更深层模式——AI native 产品面临用户消失的风险：今天做 AI PPT 工具可能触达一亿用户，但一两年后可能没人再写 PPT 了。<span class="mention">@冷静的飞鼠</span> 补充这个推演他[在 2023 年文章里就讲过](https://www.superlinear.academy/c/ai-resources/chatgpt)：类似 Grammarly 的工具先被 AI 增强，然后整个存在场景被 AI 消灭。<span class="mention">@认真的灰熊</span> 持不同意见——他相信 PPT 会长寿。

与此同时，Fable 5.1 的体感也在印证趋势。<span class="mention">@细心的熊猫</span> 直言蹬起来毫无激情，反倒对 Astra 翘首以盼。<span class="mention">@敏锐的海狸</span> 做 bio research 时发现 Fable 5.1 的请求被 Claude CLI 自动切回了 Opus 5。<span class="mention">@天真的浣熊</span> 透露 Fable 5.1 的反蒸馏已被破解。

> <span class="mention">@沉稳的仓鼠</span>：你做了 AI 的产品，但是产品做完，用户已经消失了

### 便宜模型 90% 够用

<span class="mention">@今天群内信息量极大</span> 晒出近两周的模型消耗表：GLM 5.3（12.82 亿 token）、Qwen 3.8-27B（9.54 亿）、GPT-5.6-Sol（8.04 亿）、Grok-4.6（5.31 亿）、GLM-5.2（1.55 亿）。他已退订 Claude 一段时间且毫无不适，GPT 也很少用——九成以上任务交给便宜模型，harness 混用 DSH 和 OpenCode。

本地 Qwen 3.8-27B 跑在三卡 5090 集群上，并行 decode 达 500–600 TPS，体感比调 API 还快。Mac 端跑 Qwen 3.8 Flash Next（线性注意力，128K prompt prefill 达 1900 TPS，decode 约 92 TPS），不过这主要用于调研和写作而非 coding。GLM 5.3 Flash 他用 Ollama Cloud 订阅制，比智谱 coding plan 快得多。GPT 则留着做运维——利用它 over-engineer 的个性当看门狗，小事就 block。

<span class="mention">@随和的企鹅</span> 试了 GLM 5.3 的中文后直呼震惊——太差了。<span class="mention">@直率的海豚</span> 解释这是 coding 优化后训练的副作用。<span class="mention">@今天群内信息量极大</span> 也承认 27B 模型的中文写作 AI 味仍浓，正式写作要用 External Writing Skill 转交给写作更好的模型润色。

<span class="mention">@80-HD</span> 从近日讨论中观察到一个体感反转：frontier 模型太慢、反馈周期长，体感反而差；Flash 类小模型需要更多人工干预，但反馈快体感好。<span class="mention">@谨慎的松鼠</span> 总结：要么开 xHigh 让大模型啃大活，要么开低档快反馈，中间档最容易打乱节奏。<span class="mention">@搞仁义毛义仁</span> 不同意——他认为保证质量的前提下尽量少干预才是正解，在公司让 Copilot 研究 feature gate 的 CI coverage，直接跑了 50 个小时自主完成。

> <span class="mention">@今天群内信息量极大</span>：我是感觉模型智能已经过剩了。可能部分尖端领域还需要最新的模型，但我 90% 以上的任务都在用便宜模型了

## 方法论

### Uncle Bob：Agent 时代的基本功

<span class="mention">@活泼的羊驼</span> 分享了 [Uncle Bob × Matt Pocock 对谈领读](https://mp.weixin.qq.com/s?__biz=MzU4MTgxOTE2OQ==&mid=2247484775&idx=1&sn=ac5d6b305548786aff37ded9a108fdac&chksm=fcaed5c9ab1a43508a3f6981e86085595ce6dcf39c145e39307ff3615202b9a4199e4eea76af#rd)，贴了大量截图逐段解读。核心观点是 agent 也会被烂代码拖垮——承受阈值可能比人类高，但混乱积累到一定程度后同样会变慢、反复打转甚至放弃。由此他提出一套多 Agent 流水线：specifier 把需求转成 Gherkin 和 QA 流程 → coder 写测试和实现 → cleaner 跑 CRAP 分析和代码清理 → hardener 跑变异测试要求 100% 覆盖率 → QA agent 执行验收脚本。单任务约一小时，仍比人快且质量更高。

Uncle Bob 强调能写成检查器的规则不要只写在 prompt 里——长上下文会稀释规则，而测试、lint、复杂度检查这类确定性工具不会消失。他同时明确不会把人类纪律机械照搬给 agent：严格 TDD 是为人类短期记忆设计的，agent 可以放宽 CRAP 阈值（从人类的 4 推到 6 甚至 8）。对于 agent 怎么对待这些规则，他的比喻很传神——那是《加勒比海盗》里的规则，参考性质而已。他还对「裁掉员工、换一百个 agent」的说法态度明确：全是扯淡。

<span class="mention">@洒脱的猫头鹰</span> 认为 BDD 的 Gherkin 文档在人和 agent 之间是很合适的粒度。<span class="mention">@搞仁义毛义仁</span> 更务实：理想丰满，但模型不够聪明。<span class="mention">@风趣的企鹅</span> 贴出了 Uncle Bob 的 [SwarmForge](https://github.com/unclebob/swarm-forge) 仓库——基于 tmux 的多 Agent 编排平台，每个角色有独立 git worktree 和交接邮件。

### Code review 的哈希表原理

<span class="mention">@搞仁义毛义仁</span> 分享了一次 Sol 连续跑 12 小时完成的任务经历。其中一个 localization 分支——跨系统浏览器快捷键适配——因对象嵌套层次太深把 Sol 搞迷糊了，虽然做出来但用了一种奇怪的 listener pattern 且有潜在性能问题。他在 code review 时看到某个 class 继承了一个毫无理由的 interface，追问后才发现症结。

他由此阐述了持续 review 的方法论（延续前天的讨论 [「万行代码一分钟验收」]({{ '/daily/2026/08/28/daily/#万行代码一分钟验收' | relative_url }})）：哪怕一个 PR +19k/-14k 行，快速滚过去，跳过生成文件，手写 diff 看着不够美就会引起警惕，甚至不需要花时间理解为什么觉得丑。

> <span class="mention">@搞仁义毛义仁</span>：只要你一直做，它的成本实际上会分摊在每一次 review 的过程，每次都只眼粗略扫一眼……这就像哈希表的复杂度算成 O(1) 是同一个原理

### Sol 防御式编程顽疾

<span class="mention">@随和的企鹅</span> 吐槽 Sol 写 C# 代码极度啰嗦——堆满 defensive programming，一顿 trim 才能减到原来三分之一，怀疑 C# 的训练材料本身如此。更根本的是 Sol 似乎训练时就没学到 correctness by construction 优于各种 check。

<span class="mention">@活泼的羊驼</span> 分享了他的分层优化方法：先让 Sol 写出能跑的代码，然后用多个 skill 一层一层优化代码质量。不过他也承认这样做老慢了。<span class="mention">@稳重的海豚</span> 表示加了 descope skill 也无法完全阻止 Sol 越界扩展共享边界——贴出一条 PR 的错误链路图佐证。

## 工具

### Grok Bot 云端 VM 深挖

延续昨天的初印象（[「Grok Bot 上手体验」]({{ '/daily/2026/09/01/daily/#grok-bot-上手体验' | relative_url }})），昨晚 <span class="mention">@今天群内信息量极大</span> 转发了一篇 [Grok Bot 深度体验文](https://mp.weixin.qq.com/s?__biz=MzI1MTUxNzgxMA==&mid=2247502846&idx=1&sn=bd1ab42af9401581d16d4cb44606aabb&chksm=e8c738a523d9c0563533da51d4b511e5e4afe87b4f857e344976d12daf99ffea522ea277f11d#rd)，判断 Grok Bot 才是真正的 Jarvis。最大卖点不是模型本身，而是完整权限的云端电脑——能同时操作本地与云端。作者列举了 YouTube 全字幕抓取和博客生成（Codex、Claude Code 以版权为由拒绝，Grok Bot 直接交付）、X 社交媒体智能筛选、跨国财务秘书等场景。

<span class="mention">@热情的大象</span> 跑了 VM benchmark：8 核 Xeon 2400MHz、15.64 GiB 内存、Debian 13、Docker 虚拟化、Cloudflare ASN，多个 bot 共享同一 IP 但桌面独立。他的实际经验是只敢给只读权限——之前让 Grok Bot 调优笔记本风扇曲线，稀里糊涂改了一堆东西。

<span class="mention">@热情的狮子</span> 贴出薅羊毛截图：有人拿 Grok Bot 的 VM 跑了 5 个 GitHub runner 省掉 GitHub 费用。<span class="mention">@搞仁义毛义仁</span> 对文中无版权顾虑的案例冷淡：看着像想偷东西。<span class="mention">@稳重的海豚</span> 认为这玩意更适合干秘书活，但给客户配机器成本太高。

### 手搓代码的上古时代

<span class="mention">@睿智的犀牛</span> 贴了一张 X 截图：「我们这一辈可以对小孩说——我读高中大学的时候都没有 AI，每天作业都是手搓的。」评论区接龙最佳——「爸爸，你以前写代码为什么要自己手搓？」「因为那时候家里穷，养不起 Agent。」
