连续五天的 Jev 热度在 <span class="mention">@冷静的飞鼠</span> 一篇叙事陷阱拆解长文中收束——比技术结论更值得带走的是那套识别叙事操控、找回真正比较对象的判断框架，下一个被吹上天的技术来了直接套用。Astra 过度工程投诉今天集中爆发，一个简单 SQL benchmark 的 PR 被塞满 gate 校验代码是最典型案例，harness 设计和 context 遗留可能是深层原因。Anthropic IPO 推迟到 11 月，Ramp 企业支出数据显示 Astra 在企业市场已反超 Fable。

## 方法论

### Astra 过度工程困局

<span class="mention">@80-HD</span> 翻了隔壁 org 一个刚 merge 的 PR：五万多行代码，打开一看三分之一是各种 gate 加 hash 校验。PR 本身只是一套 SQL benchmark，「根本不需要这一大堆被 Astra over engineering 的东西」。<span class="mention">@稳重的海豚</span> 感慨清理这些冗余本身又得烧一轮额度。

<span class="mention">@直率的鸵鸟</span> 直言过度设计是 Codex 当前最大的问题——有时改一个功能连续跑几个小时，中断后重新来十几分钟搞定，他甚至怀疑是官方 harness 的设计在推波助澜。<span class="mention">@淡定的雪豹</span> 已经加了一堆 AGENTS.md 来约束行为，「每次都要被急死」。<span class="mention">@直率的鹦鹉</span> 一段模仿 Astra 口吻的独白道出了群友的集体感受：

> <span class="mention">@直率的鹦鹉</span>：你说得对，但是我要开始哈希，基线，冒烟，测试，备份，回滚了。先建立唯一基线，再进行可追溯备份，先进行最小改动，我先进行一轮烟测，检查 89 个门禁是否通过，上线前进行一轮全量 dry-run，上线后校验哈希值，最后进行一轮实测的验收矩阵。

<span class="mention">@80-HD</span> 还碰到另一个症状：AGENTS.md 里明写了不要 browser use、prefer API，Astra 转身打开浏览器开始点点点。<span class="mention">@搞仁义毛义仁</span> 昨晚提供了一条更深层的线索——换了 Astra 之后如果 context 还是当初给 Sonnet 设计的，它就会按自己的理解自由发挥，结果就是一路 over engineering。

<span class="mention">@搞仁义毛义仁</span> 这两天做了一个有意识的实验：为了迅速消耗周额度，他设计了一批带详尽 verification 的任务让 Astra 连轴跑了两天，消耗了 80% 的周配额。结果是 Astra 每次都漏一点，开新 session 让它自比 request 和 commit 能找到问题、但也会无中生有，大部分 gap 靠人工 code review 反而更快。

> <span class="mention">@搞仁义毛义仁</span>：要不是为了烧 token 肯定不会这么干的。现在 KPI 差不多完成了，还是得把它做的事翻一遍。这也是一种更多的 token 做更少的事的一个例子。

他的整体评价是 Astra 放在公司 perf review 框架里大概就是 SDE1，希望下个季度能看到持续进步。额度消耗方面，<span class="mention">@80-HD</span> 反映 $200 plan 跑两个 PR 就干掉 15%，不如以前 $100 plan 经用。而 <span class="mention">@搞仁义毛义仁</span> 恰好有相反的烦恼——OpenAI 给的 banked reset 太多烧不完，干脆把 GacUI 的 feature 计划提前做了。

### 叙事陷阱识别框架

<span class="mention">@冷静的飞鼠</span> 发布了一篇长文 [为什么不必追着 Jev 跑：谁替你决定了什么叫"厉害"？](https://www.superlinear.academy/c/ai-resources/ai-builders-learning-path)，以 Jev 为切入点拆解 AI 技术热点中反复出现的叙事陷阱。核心论点：新技术往往先替你定义什么叫「厉害」，再证明自己厉害——真正该比的 best alternative 被刻意忽略了。Jev 官方拿自回归 LLM 当比较对象，但真正该比的是本地小模型直读 logits 归一化，或上一代 BERT 分类器。

文章提出五层判断：知道怎么用 → 知道边界 → 拿回评价标准 → 找到真正的比较对象 → 判断这个问题值不值得现在投入。其中第三层举了 Jev 保险理赔实验的硬数字：某道承保问题概率在 0.43–0.53 之间波动，「比别人更稳」和「足够让我自动执行」是两道不同的题。同一框架被回溯套到 MCP、RAG、LangChain、OpenClaw 上，指出各自被夸大的机制，也回顾了<span class="mention">@今天群内信息量极大</span> 过去几次对技术的判断为何准确。

<span class="mention">@今天群内信息量极大</span> 评价很高，认为对市场营销如何带歪评价体系的分析讲得透彻，并将其与博士训练中审 paper、指出作者心思的能力类比。<span class="mention">@搞仁义毛义仁</span> 反应更调侃：「都来不及深入理解什么是 RAG/LangChain 就已经开始批判了，AI 时代果然是学的慢就不用学。」<span class="mention">@随和的老虎</span> 预测 Jev 最后会被某个冤大头收购。

这篇文章与群内此前四天的 Jev 讨论（[「Jev：JSON 判断不靠自回归」]({{ '/daily/2026/09/16/daily/#jevjson-判断不靠自回归' | relative_url }}) → [「Jev：LLM 的 LISP」]({{ '/daily/2026/09/17/daily/#jevllm-的-lisp' | relative_url }}) → [「从并行解码到营销共识」]({{ '/daily/2026/09/18/daily/#从并行解码到营销共识' | relative_url }}) → [「Jev 定量拆解收官」]({{ '/daily/2026/09/19/daily/#jev-定量拆解收官' | relative_url }})）形成了完整弧线，群内共识至此基本固化。

### Agent 多线程远程工作流

由过度工程的讨论自然引出了工作流话题。<span class="mention">@敏锐的海狸</span> 分享了自己的做法：保留一个 main thread 基本不做具体的事，data、分析、回测全丢给不同的 worker thread，「这样发现 main thread 的脑子会比较清醒」。worker thread 间的 prompt 质量还不错。<span class="mention">@今天群内信息量极大</span> 指出 Cursor 专门有 multi-threading 模式，是同一思路的产品化。

<span class="mention">@搞仁义毛义仁</span> 补充了实操细节：coding 和 review 必须分到不同 session，否则会有「思维惯性」；Astra 搭配 Ultra 后混合做的表现比过往好，但最好还是分开。他让 Astra review 完之后把 prompt 写进文件 commit，手机装 Codex 开 push notification，在外面也能跟进——「非常 Codex remote friendly」。<span class="mention">@敏锐的海狸</span> 附议，最近天天在外面 hiking 换脑子找思路，只看 main thread 定期汇报。

一个额外的正面发现是 Astra 的审美能力：<span class="mention">@洒脱的猫头鹰</span> 评价审美比 Sol 好一大截，<span class="mention">@搞仁义毛义仁</span> 更进一步——Astra 能直接从 GacUI 皮肤的 XML 定义里感受颜色运用，甚至不用跑起来截图。

### Skill 共享与家庭部署

<span class="mention">@80-HD</span> 折腾了半天怎么把 agent skill 分享给老婆用，各种方案都太复杂。最后做了个简单的 mailbox——Mac Mini 上的共享文件夹，老婆的 agent 直接问他的 agent，不用考虑 skill as a service。他还搓了个简化版的聊天界面给老婆，因为 OpenCode 客户端功能太多。

<span class="mention">@今天群内信息量极大</span> 提供了另一条路线：他给家人用的是自己开源的 [opencode-private-host](https://github.com/grapeot/opencode-private-host/)，在自有 VPS 上通过 SSH 网关多用户部署 OpenCode，每人一个容器、数据完全隔离。<span class="mention">@80-HD</span> 就是在此基础上魔改的。<span class="mention">@今天群内信息量极大</span> 指出这种 email/mailbox 模式其实是他和 <span class="mention">@冷静的飞鼠</span> 之间协作的常用方式——两边各接入 email skill 就很方便。由于双方 agent 都能 access 本地，甚至连 email 环节都可以省掉。<span class="mention">@稳重的海豚</span> 建议做一个中控 plugin 让 agent 统一调用所有 skill。

### Jev RLCD 技术深潜

<span class="mention">@冷静的白鹭</span> 分享了一篇[全网首篇 Jev RLCD 技术拆解](https://mp.weixin.qq.com/s?__biz=MzIyNDgwNDg0MQ==&mid=2247483741&idx=1&sn=5a292828b4e80745f3abef46a984af5d&chksm=e9166324ca70f0384d5fdb6c30d25e44ba40bb1f81c7579b06adc0e60d43a77e6202d0a6b692#rd)。文章区分了 RLCD 与传统分类器的本质差异：分类器建模「给定输入，标签分布是什么」，RLCD 建模「这个概率算错了，下游会亏多少钱」——前者是统计拟合，后者是决策问题。由于下游决策链不可导（argmax 分段常数、阈值阶跃函数、跨 API 梯度断裂），只能用策略梯度做训练。

文章还指出 Jev 的工程边界：单次前向无思维链，复杂否定不可靠，不做符号运算，不处理对抗输入；推理确定性在部署时锁定，同一问题重复 5 次标准差 0.0。作者推断护城河在数据回路而非算法——评测参考答案是 GPT-6 Astra 和 Claude Fable 5.1 在 high thinking 下回答的平均值。
