### 「被带走16人」传闻与辟谣

### 草台班子的数据安全忧虑

凌晨的讨论从「Anthropic 报告可不可信」转向了「就算属实，问题出在哪」。<span class="mention">@今天群内信息量极大</span> 点出要害：用户选 Kimi「主要就是图个国产放心」，结果数据反而经由蒸馏链路泄露到了海外。<span class="mention">@开朗的企鹅</span> 持怀疑态度——他认为 Anthropic「经常把不怎么确定的事情说的斩钉截铁」，判断路径可能只是根据 system prompt 上下文推断；真正的敏感部门「和智算中心签合约就可以了」。

某群友反驳说现实没那么理想：不少机构既没预算签合约，也没技术人员调优本地模型，员工为了出活只能偷偷用商用 API；另一位群友补充自己所在机构虽然有大规模 GPU 集群，管理却很混乱，很多组拿不到资源。<span class="mention">@活泼的羊驼</span> 补了一个侧面佐证：「深圳这边 2025 年最赚钱的行业就是走私 N 卡。」<span class="mention">@淡定的海龟</span> 提出另一种可能——并非 Kimi 官方主动转发，也许中间的中转站捞了一批 Kimi 数据，下游再拿 Claude 合成高质量训练集，复用了用户的 query。

> <span class="mention">@洒脱的猫头鹰</span>：说是说，做是做。要对草台班子抱有足够的信任！

<span class="mention">@飘逸的狮子</span> 从商业角度给了另一个视角：Anthropic IPO 在即，发这些报告「都是有想法的」。<span class="mention">@聪明的灰熊</span> 更直接：「A\ 的可信度一半都不到，朴素的认知战罢了。」

## 工具

### 四卡 5060 Ti 本地推理

<span class="mention">@细心的熊猫</span> 晒出了他的四卡 PNY RTX 5060 Ti 配置，跑 Qwen3.8 27B 达到 prefill 6,856 tok/s、decode 132 tok/s（单 session），8 路并行时每路仍有约 70 tok/s。软件栈是 sglang + dflash2，降压超频后满载功耗仅约 80W 一张卡，四卡加起来可能还不到一张 5090。

![四卡 PNY RTX 5060 Ti 实机照片](/assets/img/daily/2026/09/2026-09-11-01.webp)

卡间通信走 PCIe 5.0×4，瓶颈主要在 prefill——当前约 1,400 tok/s，若用 PCIe 5.0×8 插槽可翻倍到 2,800。decode 相比双卡已翻倍。<span class="mention">@风趣的海豚</span> 追问有没有黑魔法优化，回答是「基本上就是 sglang + dflash2」，开箱即用。<span class="mention">@直率的鸵鸟</span> 感慨多卡优化进步之大，表示如果本地能力超过 Luna 级别就有部署价值。

### 腾讯 TeamAI CLI

<span class="mention">@睿智的北极熊</span> 分享了[腾讯开源的 TeamAI CLI](https://github.com/Tencent/teamai-cli/blob/main/README.zh-CN.md)，核心思路是把 Skills、Rules、Docs、Agents 等资源统一放在共享 Git 仓库管理，兼容 Claude Code、Codex、Cursor 等主流 harness，实现「团队共享鸭汤」。每次 AI 会话开始时自动 pull 同步资源，个人改动走分支和合并请求审批后才分发。还有实验性的 Team Context 功能：根据摩擦信号（用户打断 AI、工具重试失败等）自动判断是否需要沉淀经验到团队知识库。

<span class="mention">@热情的大象</span> 提了一个关键担忧：「这些 skills 可能相互影响吗？」<span class="mention">@80-HD</span> 确认有可能。他接着问「有人往汤里拉屎怎么办？」<span class="mention">@沉稳的兔子</span> 笑答：「把皮炎堵住就好了……主要怕窜稀。」

### DS V4.1 Flash 工程甜点

<span class="mention">@今天群内信息量极大</span> 对 V4.1 Flash 给出了正面评价（延续 [「DeepSeek V4.1 Flash 发布」]({{ '/daily/2026/09/10/daily/#deepseek-v41-flash-发布' | relative_url }})），同时发布了两篇分析文章：[V4.1 KV cache 压缩设计思路](https://yage.ai/share/deepseek-v41-flash-kv-cache-memory-20260911.html)和 [AI Benchmark 为什么注定难设计](https://yage.ai/share/ai-benchmark-leaderboard-industry-20260913.html)。

他的核心判断是 instruction following 终于不再是死穴——以前「天天删库的傻逼玩意不敢用」，V4.1 到目前为止表现很好。智能方面比 Qwen 27B 有可感提升，加上 1M 上下文和远超自建的速度，定位是一个「工程甜点，倒不是说真的有多聪明」。<span class="mention">@务实的灰熊</span> 指出 Artificial Analysis 上的分数依然很低。

### Startup 的 Pro+API 混合策略

<span class="mention">@热情的狮子</span> 分享了创业公司的成本管理方式（延续 [「Pro 20x 暂停新订阅」]({{ '/daily/2026/09/10/daily/#pro-20x-暂停新订阅' | relative_url }})）：日常主力走 Pro 订阅，额度用完就买 $80 reset——新 20x 不让开，只能这么干。API 作为 backup：当订阅账号耗尽时自动切换到 Azure，额度恢复后再切回来。微软创业计划提供的总额度有限，按 API 价格一个月就能烧掉很大一部分，因此 API 只能兜底。他还吐槽 AWS 上 Claude 的默认 token limit 太低，申请更多也不给。

<span class="mention">@搞仁义毛义仁</span> 问为什么公司不买 Enterprise，他坦言 startup 没那么多钱烧 API，「送就送吧，各取所需」。Azure 给的 rate limit 倒还算宽裕，15M tokens/min + 15K requests/min。

## 方法论

### 老鸭汤不是 Skill 集合

<span class="mention">@坦荡的灰熊</span> 问 <span class="mention">@今天群内信息量极大</span> 有没有像 Matt Pocock 那样使用老鸭汤的 skill，并想用 `/deposit` 之类的 slash command 沉淀调研内容。<span class="mention">@80-HD</span> 做了明确区分：Matt 给的是一堆 skill，老鸭汤是一整个体系，可以把 Matt 的 skill 吸收进来。他指出用 slash command 触发的思路「很不老鸭汤」——直接说「把当前 session 沉淀一下」就行。

> <span class="mention">@80-HD</span>：按照<span class="mention">@今天群内信息量极大</span> 的说法，slash command 太 engineering 了，并不是 AI native

他给出了两个入口：自动沉淀用 [ai_heartbeat](https://github.com/grapeot/context-infrastructure/tree/main/periodic_jobs/ai_heartbeat)，手动触发在 [skills 目录](https://github.com/grapeot/context-infrastructure/tree/main/rules/skills) 里加一个即可。portable 是核心考量——不是所有 harness 都支持 slash command，但「直接说一句话」到处都行。他还补了一句：自己的汤还是自己炖比较好，<span class="mention">@今天群内信息量极大</span> 的老鸭汤只是个例子，没必要原封不动照搬。

### Agent 评测不用冻结轨迹

<span class="mention">@活泼的羊驼</span> 提出一个评测难题：在同一评测集上，模型 1 的 Tool Call 轨迹可以记录，但换到模型 2 时调用链路完全不同，如何冻结做对比？<span class="mention">@淡定的海龟</span> 给了简洁的回答：直接对最终产物打分或校验就行，不需要关心轨迹——「一般不关心你怎么调用、做了什么，只看你完成或者通过与否」。冻结快照的目的是保证任务状态确定和可复现，不是冻结轨迹本身。<span class="mention">@稳重的海豚</span> 补充说轨迹分析可以定量地看，但放到 golden set 里未必有太大价值。

### 此处确实有坑

<span class="mention">@睿智的北极熊</span> 贴了一张截图：用户问 AI「你刚刚改了什么？现在界面白屏了」。AI 花了 11 分钟定位后坦白——代码注释中明确写着「此处有坑，勿动---2019/03/08」，但它还是手欠改了。修复之余还贴心地新增了一条注释：「此处确实有坑---2026/08/24」。<span class="mention">@80-HD</span> 说他以前还真遇到过注释即代码的项目——因为不想改语法但需要支持新功能，最后把逻辑加到了注释里，结果「更糟糕的是因为是注释，所以语法高亮什么的都没有，很容易 typo」。
