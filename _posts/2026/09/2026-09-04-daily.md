今天最值得读的是 Astra 全面开放后的首批实测——比 Sol 更快但更贵，Tibo 再发 banked reset 而 Claude 同步重置额度，军备竞赛肉眼可见。<span class="mention">@今天群内信息量极大</span> 对 Cerebras 的实测博文同样值得细读：标称超高速在真实 agentic 场景里大打折扣，本地部署仍是小模型最优解。

## Astra 首日实测

### Astra 全面开放

GPT-6 Astra 今天正式面向 ChatGPT Pro 用户全面开放（延续昨天的发布 [「Astra 跑分与 Harness 之争」]({{ '/daily/2026/09/03/daily/#astra-跑分与-harness-之争' | relative_url }})）。<span class="mention">@热情的狮子</span> 最先在 Codex CLI 中确认 `gpt-6-astra` 可用，随后 <span class="mention">@天真的浣熊</span> 发现 Copilot 也已接入 GPT-6。<span class="mention">@务实的长颈鹿</span> 贴出 ChatGPT App 截图，模型列表中 6 Astra 排在首位。

Codex CLI 中 Astra 显示为默认模型，标注 "Our most capable model for complex, demanding work"。Web 端的「6 Pro」就是 Astra，进度条从蓝色变成了紫色渐变。不过部分用户遇到了灰度差异：<span class="mention">@谨慎的松鼠</span> 发现网页版已有 Astra 但 CLI 和 desktop 迟迟未更新；<span class="mention">@洒脱的猫头鹰</span> 确认 $100 Plan 也能用；<span class="mention">@冷静的麋鹿</span> 确认更新客户端后 CLI 和桌面端均已到位。

### 初步体感

多位群友第一时间跑了任务。<span class="mention">@开朗的企鹅</span> 最直观的感受是快——之前同一个任务 12 分钟，用 6 Pro 只要 6 分钟。<span class="mention">@飘逸的狮子</span> 也直呼快，但 2 分钟 high effort 就烧掉了 1% weekly 额度。Astra 单任务消耗比 Sol 贵约 75%；<span class="mention">@天真的浣熊</span> 用 API 跑了一轮 code review，$100 直接没了。

<span class="mention">@搞仁义毛义仁</span> 让 Astra 审视自己 GacUI 项目中 Opus 4.6 花数天生成的 UIA 规划文档。17 分钟纯 research 后 Astra 给出精准诊断：虚构的 API 方法、与官方文档矛盾的控制契约、概念混淆、不完整验证等多项错误。结论是这份规划有用的研究和组织，但技术验证严重不足——他尚未验证 Astra 自身的修订是否正确，要等实际执行后再下定论。

<span class="mention">@敏锐的海狸</span> 做 agency infra design 时感觉 Astra 比 Sol 更克制、意图对齐更好。<span class="mention">@冷静的麋鹿</span> 对宣传中多指令并行推进的能力特别期待但还没测到。<span class="mention">@天真的浣熊</span> 注意到架构变化——CoT 隐藏在内部，蒸馏难度加大。<span class="mention">@务实的长颈鹿</span> 展示了一个有趣的场景：Astra 做游戏项目时自己搭了一个美术效果检视工具来做质量检验标准。

### 额度军备竞赛

Astra 发布当天引发了一场多方额度大战（延续近日的额度焦虑 [「定价与 Banked Reset」]({{ '/daily/2026/09/03/daily/#定价与-banked-reset' | relative_url }})）。Tibo 在 X 上宣布：因为 Astra 提前上线，所有 Plus、Pro 和 Business 用户均获得一次全额 banked reset，当天 8pm PT 前创建或升级的账号也能拿到。Anthropic 几乎同一时间出手——Lydia Hallie 宣布 Claude Max 用户额度全部重置，理由是 Fable 5.1 刚发布加上长周末。<span class="mention">@天真的浣熊</span> 感叹有竞争就是好。

<span class="mention">@搞仁义毛义仁</span> 发现升级到 $200 会直接触发 reset，加上补偿卡和自然重置，手上已攒了多张。群友们纷纷宣布要猛蹬，<span class="mention">@热情的大象</span> 三张重置券在手直接冲了 Pro x20。

### 使用策略初探

<span class="mention">@开朗的企鹅</span> 提出了一套混合工作流：在网页端用 6 Pro 做高质量 planning（免费且 context 干净），让 Codex Sol 收集信息和跑验证，再回网页 6 Pro 迭代 plan，最后用 Terra 执行编码。<span class="mention">@认真的荷兰猪</span> 有些担心导出 context 时会漏掉代码库信息。

<span class="mention">@搞仁义毛义仁</span> 分享了自己的方法论：人给一个粗粒度方向，把不想怎么做或一定要怎么做框好，丢给 Astra Ultra 扩写，瞟一眼没问题再 xhigh 干。他期待的理想状态是 Astra 能 xhigh 一路到底、一个 session 一直做也顶得住，这样可以一路 queue 下去。

<span class="mention">@冷静的麋鹿</span> 强调拿到新模型第一件事是扫一遍所有必读 md 和 skill。<span class="mention">@认真的荷兰猪</span> 深有同感——agent 效果不好时总觉得是自己的 skill 写得有问题。<span class="mention">@天真的浣熊</span> 推荐 Codex 稳定性方案：tmux + Termius 比 remote 模式稳定得多。

## 工具

### tok/s 是 agentic 场景里最会骗人的数字

<span class="mention">@今天群内信息量极大</span> 写了一篇[详细的实测博文](https://yage.ai/share/toks-deceptive-agentic-20260906.html)，给昨天让群友们兴奋不已的 Cerebras 泼了冷水（[「Cerebras Qwen 3.8 27B 上线」]({{ '/daily/2026/09/03/daily/#cerebras-qwen-38-27b-上线' | relative_url }})）。核心发现：标称 1500 tps 只计 decode 且限于极短 context，在真实 agentic 工作流中有效吞吐 P50 仅约 357 tps（本地 5090 约 102 tps），纸面 15 倍差距缩水到约 3.5 倍。

更致命的是限流。agentic 循环让 context 在 65 秒内从 11K 膨胀到 99K，缓存读取虽然单价低但在速率限制中仍全额计入 TPM，一两分钟内就触发 429 报错。三分钟花了 $1.57，82% 是缓存读取；同样任务本地跑约 11 分钟、电费约 $0.017，成本差约 90 倍。<span class="mention">@乐观的海豚</span> 一句话总结：tps 虚高、上下文短、限流小、还贵。

不过 Cerebras 并非完全没有适用场景。<span class="mention">@细心的熊猫</span> 表示自己蹬了几十分钟没遇到 429，体感上正常模型用起来都像便秘，时不时充点零花钱进去爽一下。<span class="mention">@冷静的白鹭</span> 提到 RunPod 也上线了同款服务。<span class="mention">@敏锐的麋鹿</span> 认为 Cerebras 芯片更适合 context constrained 的场景如机器人和 FSD——延时敏感但上下文不需要滚雪球。

> <span class="mention">@今天群内信息量极大</span>：经常就是讲了一个 prompt，然后他工作了几十秒就要 compact，然后 compact 一两轮以后就触发 429。感觉做 chatbot demo 可以，实际 agentic workflow 还是不太行

### GLM-5.3-Flash 速度与推理卡困境

<span class="mention">@今天群内信息量极大</span> 昨晚贴出一张跨 17 个模型、30 天约 7.3 万真实样本的 P50 有效吞吐对比图。智谱 Coding Plan 的 GLM-5.3-Flash 以 20 tps 光荣垫底，同一套权重走 Ollama Cloud 能跑到 70 tps——serving stack 造成 3.6 倍差异。<span class="mention">@务实的长颈鹿</span> 深有体感：从 GLM 5.0 开始最不能忍的就是慢。<span class="mention">@随和的企鹅</span> 补充 GLM 5.3 大模型大概 60 tps，但 K3 官方也只有约 20 tps。

<span class="mention">@活泼的羊驼</span> 给出了根本性解释：国内推理最好的卡还是 GB200/GB300 系列，在国内是战略资源、翻倍加价，好卡优先拿去训练而非推理，承担推理的基本是国产卡。<span class="mention">@直率的鹦鹉</span> 补充现在国产模型一般在海外东南亚数据中心训练。<span class="mention">@专注的剑鱼</span> 也指出 Flash 在国产卡上跑 tps 肯定不高。

<span class="mention">@今天群内信息量极大</span> 的本地方案是三张 5090 32G，每个模型跑单卡，三实例做 cache-aware load balancing，量化 nvfp4，推理库用 NInfer。<span class="mention">@优雅的喜鹊</span> 也在调自己的 Hermes 日志做用户画像，准备以此为标准测试自部署的多个模型，并确认单纯的 tok/s 意义不大——他的单轮输入上下文大概是输出 token 的 200 倍。

## 方法论

### Codex 过度工程化的代价

<span class="mention">@坦荡的灰熊</span> 贴出了他为防止 Codex 过度工程化而写的一堆否定式约束：不计算或生成 hash、不解压最终 ZIP、不做字节流比较、信任特定命令的成功结果。但 Sol 会绕着走——不让做 hash 就改 byte by byte 比较，防不胜防。更可怕的是子代理静默执行：开一百个子代理，每个都在悄悄 hash、try-catch、copy 备份。

他由此提出一个判断框架：「过」的危害远大于「欠」——欠的话还能自由增加要求、通过 skill 解决；过的话你什么都发现不了，对 agent 自身的 scale up 也极为不利。体感上，30 天的任务 1 天做完让人兴奋，但 30 分钟的任务仍然花一天做完就很痛苦。

<span class="mention">@谨慎的灰熊</span> 直言这个问题已是「明日黄花」——Sol 的多智能体调度能力明显稚嫩，要看 GPT-6 有没有改善。多位群友反映 Codex 整体感觉太重，<span class="mention">@细心的熊猫</span> 打算转试 Codex CLI。<span class="mention">@坦荡的灰熊</span> 回忆 5.5 时期速度非常快、一天能解决好多事，那时用 Claude 反而痛苦。

> <span class="mention">@坦荡的灰熊</span>：30 天的任务 1 天做完，我会很兴奋；30 分钟的任务，特么还是 1 天做完，我人都不举了
