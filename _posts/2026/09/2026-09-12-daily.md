OpenAI 开发者博客今天发了一篇 Astra 专属的 skill 瘦身指南，判断是为旧模型写的约束正在反噬新模型——这篇值得所有还在用 Sol 时代 AGENTS.md 的人立刻读，群里的实战讨论也印证了同一方向：把 planning 与 execution 拆到两个 session、用 Astra 定 plan 让 Terra 跑执行，额度焦虑随之缓解。另一条值得追踪的线：数百位数学家联名反对 AI 生产的 slop mathematics，OpenAI 撤出了 Caltech 数学竞赛赞助，这是 NS 证明风波之后学术界第一次组织化反弹。

## 方法论

### Astra/Terra/Luna 分层策略

延续近日的额度焦虑（[「xHigh 反而比 Medium 省额度」]({{ '/daily/2026/09/09/daily/#xhigh-反而比-medium-省额度' | relative_url }})），凌晨群里围绕「哪些任务该用哪个模型」展开了一轮实操讨论。<span class="mention">@直率的鸵鸟</span> 直言 Astra 消耗太快，不太复杂的任务已经切回 Sol；<span class="mention">@神秘的企鹅</span> 试了一个任务就吃掉 20% 额度，想知道 Luna xHigh 能否扛日常编程。<span class="mention">@直率的鹦鹉</span> 泼冷水：Luna 主动性差，「踢一下动一下」；<span class="mention">@淡定的老虎</span> 补充 Luna 有时会死磕走不通的路。

最终收敛出的甜点方案来自 <span class="mention">@开朗的企鹅</span>：Astra 定 plan，Terra 执行。<span class="mention">@直率的鸵鸟</span> 认可这个分层——Terra 够用且省额度，Luna 在没有高级模型监督的情况下很多任务直接搞不定。<span class="mention">@今天群内信息量极大</span> 则提供了另一种路径：他最近用 Astra Low 也觉得不错，暗示降 effort 有时比换模型更高效。

> <span class="mention">@直率的鸵鸟</span>：我觉得 terra 很甜点。luna 确实不行，没有高级模型监督很多任务直接是搞不定的

### 规划与执行分会话

<span class="mention">@稳重的海豚</span> 下午抱怨 Astra Ultra「经常容易偷懒儿，还没有 max 好使」。<span class="mention">@幽默的犀牛</span> 附议：Ultra 废话多、干活慢，经常做一半就创造无用需求。<span class="mention">@敏锐的海狸</span> 推荐的组合是 xHigh。

<span class="mention">@搞仁义毛义仁</span> 给出了他经过与 Sol 搏斗后沉淀的完整策略。首先，prompt 同时写清 goal、non-goal、rough design 和 verification——其中 non-goal 的典型案例是 error recovery：他专门写了一段告诉 AI 为什么在这个项目里 crash by exception 优于优雅降级，堵住了 OE 的最大重灾区。其次，planning 和 execution 拆到两个新 session：planning session 出 plan 时会顺手把 verification checklist 交代清楚，「反正不是他做的」不会污染到 execution 那边；execution 照着 checklist 走，自己不用思考。他还为 Astra 的偷懒和 scope creep 定了性：

> <span class="mention">@搞仁义毛义仁</span>：不管是偷懒还是创造需求的根源都是 AI 觉得自己既当运动员又当裁判

Subagent 管理方面，Codex 有个令人头疼的毛病：自己开的 subagent 跑太久时主 session 会浪费大量 token 偷窥进度。<span class="mention">@搞仁义毛义仁</span> 的应对是自己估算模型最大 scope、手动拆任务提交。<span class="mention">@敏锐的海狸</span> 的做法不同——用一个 orchestrator 分派给其他 primary agent，主 agent 停着等返回结果，context window 质量更高。<span class="mention">@幽默的犀牛</span> 对比了 Codex 和 OpenCode：后者不会偷窥 subagent，暗示这是 harness 层面的设计选择。

compact context window 是否是 Astra 走偏的罪魁祸首引发了小辩论。<span class="mention">@敏锐的海狸</span> 认为 Codex 的 compact 做得不如 Claude 好，<span class="mention">@搞仁义毛义仁</span> 不同意——他每个任务都要 compact 好几遍，从未因此出问题。<span class="mention">@稳重的海豚</span> 补充默认 context window 为 258K，模型能力在这个范围内已经到位；更长 context 不会让能力变更强，关键是 just-in-time 让模型自己去抓需要的内容。

### OpenAI Skill 瘦身指南

<span class="mention">@热情的狮子</span> 分享了 OpenAI 开发者博客新文 [Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)，核心论点是为旧模型积累的大量 skill 和 AGENTS.md 规则正在拖累 Astra。文章指出：skill 描述太长或数量过多时 Codex 会截短描述，模型更难判断何时调用；给 Sol 或 Luna 写的指导可能过度约束 Astra；要求每次编辑前读完整 repo map 对改个 typo 是浪费；Astra 会主动跑测试和自查，旧的「记得跑测试」指令反而制造多余测试。建议是 skill 描述只说何时使用，多工作流 skill 的根文档做成最小路由器，遵循 progressive disclosure。另一个值得注意的提醒：Astra 比 Sol 更谨慎——Sol 会长时间一路往前推，Astra 可能完成第一版就回来等审查，因此需要在开始前把「完成」的定义说清楚。

这篇文章与 <span class="mention">@搞仁义毛义仁</span> 长期坚持的「不装 skill 和 MCP，所有指令只通过 agents.md 下发」的策略高度一致。但 <span class="mention">@稳重的海豚</span> 对文章持怀疑态度——他体验到的 Astra Ultra 和 6 Pro 网页版都不像文章描述的那么乖，反问「他们到底用的什么 Astra」。

同日更早，<span class="mention">@稳重的海豚</span> 还分享了一篇 [InfoQ 对 Anthropic 工程师 Thariq 的长访谈](https://mp.weixin.qq.com/s?__biz=MjM5MDE0Mjc4MA==&mid=2651292911&idx=1&sn=ba2b48778e441ad6709201d9587e91a8&chksm=bc6ca9a3964ccc486346ee967fb93cb203a64ef3e8f4d50ff856be34217d401b1fee82760ec5#rd)。其中 Tibo 与 Thariq 给出了截然相反的判断——Tibo 认为 harness 随模型进步会越来越轻，Thariq 则认为模型越强、harness 反而越复杂。两人其实不矛盾：「教模型怎么做事」的部分在变轻，「让模型安全、长期、并行地做更多事」的基础设施在变重。

### 团队 AI 协作探索

傍晚一场持续近两小时的讨论试图回答一个问题：几个人各自带着 AI 开发时，已梳理好的项目现状和判断依据如何在不同「人+AI」单元之间接续？

> <span class="mention">@开朗的企鹅</span>：现在每个人都有自己的 AI，实际协作单位已经是"人＋AI"了。但不同协作单位之间，往往只能共享资料、任务和结果，已经梳理清楚的项目现状和判断依据却接不过去

<span class="mention">@稳重的海豚</span> 从组织角度切入：他采用 Pod 结构（3–4 人），拆小项目降低重叠，每个项目下维护 `.dev` 文件夹存放专用 skill、SOP 和架构文档。<span class="mention">@敏锐的海狸</span> 认为最关键的是一整套 design doc 加进度汇报——他的 multi-agent 体系就围绕这样一套文档运转。<span class="mention">@搞仁义毛义仁</span> 更激进：直接在 repo 里共享 skill 目录即可，session 质量良莠不齐，但知识只有对错。

工具侧也有进展。跨设备 session 同步目前 Codex 原生不支持，<span class="mention">@开朗的企鹅</span> 自己做了 session fork 功能；<span class="mention">@谨慎的灰熊</span> 指出 Codex 其实有 remote（控制远端任务）和 hand-off（转移任务到另一台机器）两种机制。<span class="mention">@开朗的企鹅</span> 最终归纳了两个核心需求：一是从工作轨迹中定位真实进度和卡点，二是问题溯源——不仅要知道问题在哪，还要追溯当时是怎么跑偏的、为什么没被测试拦住。<span class="mention">@风趣的犀牛</span> 补充说现有工具大多 designed by coders for coders，非技术用户的工作进度更难界定。<span class="mention">@稳重的海豚</span> 在讨论间隙分享了自己整理的 [Context Engineering 框架笔记](https://www.nickgu.me/files/share/share-19f54bd820b949abb813083dbff26cdf#k=XvHLA00G0Cemb2oSkEm8ZgHeV-xrfNBp5tcI57kfeX8)，把从 Prompt Engineering 到 Context Infrastructure 的演进脉络串成了一条问题链。

### 世界模型长文

昨晚 <span class="mention">@开朗的海龟</span> 发了一篇原创长文 [Coding Is All You Need? Why We Need a World Model!](https://hokindeng.com/coding-is-all-you-need-why-we-need-a-world-model/)，从六亿年生物进化史出发论证：自回归 Transformer 本质上仍是 Sherrington 反射系统的现代版——context 是刺激、深层次层级是整合、下一个 token 是响应——缺的是 Tolman 认知地图那样的世界模型。文章以 Astra 机器人臂实验（粗任务高分、精细任务撞墙）为引子，追溯海蛞蝓突触、Hassabis 的场景构建理论和 Spelke 的核心知识系统，结论是 coding 在闭系统（数学、棋类、代码）里无往不利，但通向开放世界的智能还需要一个独立的器官。群里暂未展开讨论。
